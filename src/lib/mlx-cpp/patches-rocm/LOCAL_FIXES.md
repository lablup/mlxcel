# Local changes relative to NripeshN/mlx@75915908

Every change this overlay carries on top of the fork commit in `UPSTREAM`, with the reason. Fixes that apply to the fork itself should also be proposed there; retarget-only changes follow the fork when it merges newer MLX.

Name the files an entry touches: `scripts/mlxcelverse/rocm_overlay.py drift` fails for a backend file that differs from the fork but no entry names, and every core-file residual in `CORE_RESIDUAL.diff` carries a note pointing at its entry. Entries that apply to the fork are prepared as pull requests to NripeshN/mlx `rocm-support` under `docs/mlxcelverse/upstream/`, submitted by hand; its README maps entries to packages and records each link once a PR is open. The procedure for pin bumps and fork syncs is `docs/mlxcelverse/rocm-overlay.md`.

## Retarget onto the MLX pin (81ba1c6a)

The fork branched from upstream on 2026-06-26 (`39886de4`). Moving its ROCm code onto the pin needed:

1. **Core file merges.** `mlx/backend/common/compiled.cpp` keeps upstream's `negative_strides` tracking and the fork's constant-input skipping. `mlx/fast_primitives.h` keeps both upstream's `compile_options` and the fork's `output_input_aliases` on `fast::CustomKernel`. `mlx/io/safetensors.cpp` keeps upstream's empty-tensor guard and the fork's ROCm `staged_write`.
2. **`isnan` lookup.** Upstream `a124ac09` (ml-explore/mlx#4291) added a host-only `mlx::core::isnan` template in `mlx/types/complex.h`, which hides the device `isnan` overloads inside the ROCm namespace. The 23 unqualified device-side calls use `::isnan` (in `device/binary_ops.hpp`, `quantized/convert_fp8.hip`, `reduce/reduce.hpp`, `reduce/reduce_ops.hpp` and `sort.hip`).
3. **Compiled kernels.** `compiled_collapse_contiguous_dims` returns a 4-tuple with `negative_strides`; `mlx/backend/rocm/compiled.cpp` unpacks it and forces the large-index kernel for negative strides, as the CUDA backend does.
4. **Custom kernels.** `mlx/backend/rocm/custom_kernel.cpp` passes an empty `CompileOptions::Data` before the aliases argument. `output_input_aliases_` stays out of `CustomKernel::state()` because `mlx/export.cpp` serializes that tuple and has no encoding for it (the fork's `state()` did not include it either).
5. **SDPA.** `ScaledDotProductAttention::use_fallback` takes upstream's new `force_fused` argument, with the CUDA semantics: throw if fused is forced and no fused kernel applies.
6. **New upstream primitives.** `GatherQQMM`, `SearchSorted` and `fast::CrossEntropy` (with its VJP, using the graph fallback) get `NO_GPU` stubs in `mlx/backend/rocm/primitives.cpp`.
7. **Event errors.** `Event::error()` (ml-explore/mlx#3742) is populated on ROCm since lablup/mlxcel#1804, on the Metal model: each `CommandEncoder` owns an `Error`, and events signaled on a stream point at that stream's `Error` once the stream fails. Measured on gfx1151 with ROCm 7.15 (a probe kernel writing 2^40 bytes past its buffer): the HIP runtime does not abort the process on a queue fault, with or without `HIP_SKIP_ABORT_ON_GPU_ERROR` (the variable made no observable difference, so mlxcel does not set it); it prints the fault and the kernel name to stderr, then every HIP call on every thread returns `hipErrorIllegalAddress` for the rest of the process, `hipDeviceReset` included, and no queued `hipLaunchHostFunc` callback ever runs. That defeated all three of the backend's waits: `HipEvent::wait()` spun while `hipEventQuery` was not `hipSuccess`, `AtomicEvent::wait()` polled a counter that only a host callback lands, and `CommandEncoder::synchronize()` waited on a promise a host callback resolves. `HipEvent::wait()` now ends on any status other than `hipErrorNotReady`; `AtomicEvent` keeps the stream it was signaled from and polls `hipStreamQuery` on it about once a millisecond while waiting; `Worker::commit()` returns the `hipLaunchHostFunc` status and the encoder records a failure; `synchronize()` checks every status and polls the stream while it waits for the handlers. `Event::wait()` calls `check_error()` before and after the wait as Metal and CUDA do, `Event::is_signaled()` reports a failed event as signaled with the error attached (so `array::is_available()` detaches it and throws instead of pending forever), and `Event::wait(Stream)`/`Event::signal(Stream)` go through `scheduler::wait_event`/`signal_event` on CPU streams so the CPU-stream error path is upstream's. Synchronous launch failures: `launch_module_kernel` checks `hipModuleLaunchKernel`, and `gpu::eval` reads the thread's pending HIP error after each `eval_gpu` (kernels launched with `hipLaunchKernelGGL` or `<<<>>>` report a rejected launch no other way) and throws it as that primitive's error; a pending `hipErrorOutOfMemory` is skipped there, because it is what a recovered allocation failure leaves behind (the allocator's cache-release retry and managed fallback, hipBLASLt's workspace fallback) and an unrecovered one has already thrown. Under `MLX_GRAPH_PREFILL_REPLAY=1`, a launch that throws inside `launch_kernel`'s capture ends the capture and falls back to the eager launch, so a now-checked launch failure cannot leave the stream capturing. Destructor-path `hipGraphDestroy`/`hipGraphExecDestroy` calls discard their status explicitly, and `HipHandle::reset()` reports rather than throws, since on a faulted device every destroy fails and a throwing destructor would terminate the process at exit. `MLX_ROCM_GPU_WATCHDOG_SECS` (default off) bounds a single host wait for a kernel that never finishes; it is parsed with `strtol` and must be a whole non-negative integer, otherwise it warns once on stderr and stays off. Not covered: after a queue fault the device is dead for the process and its shutdown may hang, because HIP's teardown waits on the callbacks that never run (measured: the probe process hung at exit whenever a host callback was pending); the process has to be killed and restarted. Files under `mlx/backend/rocm/`: `device.cpp`, `device.h`, `eval.cpp`, `event.h`, `event.hip`, `fence.cpp`, `jit_module.h`, `utils.h`, `worker.cpp`, `worker.h`. Applies to the fork; to be proposed there.

## Fixes to the fork's kernels

8. **mxfp4/mxfp8 scale type in qmv dispatch.** `mlx/backend/rocm/quantized/qmm.hip` dispatched every mode with the activation dtype as the scale type, but mxfp4 and mxfp8 store one E8M0 byte per group. The kernels read scales at 2 to 4 times the real stride, which gave NaN and out-of-bounds reads (a GPU memory fault in `qmv_warp_shared_kernel` on the unfixed fork). Non-affine modes now dispatch with `uint8_t` scales. Applies to the fork; to be proposed there.
9. **Expert-batched gather qmv: strided index reads, a faster inner loop, f16, on by default.** `gather_qmv_expert_batched_kernel` in `mlx/backend/rocm/quantized/qmm.hip` handles a sorted, transposed, affine, group-size-64, 4- or 8-bit `gather_qmm` with `M == 1`, `B >= 64`, `E <= 64` and `B / E >= 4` (the prefill of an MoE with at most 64 experts) by reading each expert's weights once for all of that expert's rows. It read `lhs_indices[b]` and `rhs_indices[b]` as flat `[B]` arrays, while MLX broadcasts the two index arrays against the activation's batch shape without copying them, so an index array can have stride 0 along a broadcast axis. `x` as `[T, 1, K]` with sorted `rhs_indices` of shape `[T, 1]` gives a `[T, T]` batch with rhs strides `(1, 0)` and implicit lhs strides `(0, 1)`, and the kernel read both arrays past their end: that call is how the defect was found (relative error above 1.0 against the unsorted path for bf16; f16 and f32 looked correct only because the kernel was gated to bf16), and the overlay first made the kernel opt-in. `SwitchGLU`'s own sorted path passes flat `[B]` indices and was never wrong. The kernel now reads both index arrays through the batch shape and strides (`gather_index_loc`, as the launched per-row gather kernels in the file do), and so does the never-launched `gather_qmv_idot_expert_batched_kernel`. While fixing it, the kernel measured 2.3x slower than the per-row wide kernel on granite's prefill, so its inner loop was rewritten: each lane loads one packed 32-bit word with its group's scale and bias and applies them to four rows of the run before the next load, the lanes reduce once per row instead of once per group, all 16 lanes of a column work (only 8 did at 4 bits), and block z is the expert itself, found with two binary searches, instead of the z-th run found by a serial walk over every earlier run. f16 activations take the same kernel, as item 12 did for the warp-shared kernel; that is the only new instantiation (two, for 4 and 8 bits), and `qmm.hip` still compiles in about 38 s (37.5 and 37.7 s, against 38.4 and 38.0 s before, same flags), since the simpler kernel offsets them. On gfx1151, 512-token prefill went from 535.7 to 918.6 tok/s on `granite-4.0-h-tiny-4bit` (bf16, 64 experts) and from 25.95 to 125.6 tok/s on `Mixtral-8x7B-Instruct-v0.1-4bit` (f16, 8 experts), with decode unchanged (`docs/benchmark_results/rocm-moe-prefill-gfx1151-2026-10-05.md`), and every case of `tests/rocm_gather_qmm_expert_batched.rs` (bf16 and f16, 4 and 8 bits, Mixtral-like and 64-expert shapes, flat and broadcast indices) is within 0.1% of the unsorted path's own error against a dequantized f32 reference, so the kernel is on by default again; `MLX_ROCM_GATHER_QMV_EXPERT_BATCHED=0` turns it off. Applies to the fork, which runs the kernel by default with the flat reads; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
10. **mxfp4/mxfp8 in `gather_qmm`.** When a non-affine mode missed the affine-only fast paths in `GatherQMM::eval_gpu`, the generic dispatch instantiated `gather_qmv_kernel` with `AFFINE=true` and a T-typed scale pointer, so fp weights were dequantized with the affine formula (relative error 1.0 to 1e34 for mxfp8). Non-affine modes now launch `gather_qmv_kernel<T, uint8_t, BITS, 32, false>`; other fp group sizes throw. After the fix mxfp8 and mxfp4 `gather_qmm` match a dequantized f32 reference (relative error about 3e-3 for bf16) with sorted and unsorted indices. Applies to the fork; to be proposed there.
11. **`arg_reduce` launch geometry.** For short reduction axes `ArgReduce::eval_gpu` (`mlx/backend/rocm/arg_reduce.hip`) launched one 1024-thread block per output over a 1-D grid. AMD limits each grid dimension to 2^32 - 1 threads, so the launch failed with "invalid configuration argument" past about 4.2M outputs; mxfp4 `quantize` of a 4096x4096 matrix (an argmin over 16.7M elements) hit it. Axes of at most 64 elements now use a 64-thread block, and the grid spills into y. GPU `quantize` in mxfp4 is then bit-identical to the CPU at 4096x4096. Applies to the fork; to be proposed there.
12. **f16 in the fast `gather_qmm` path.** `GatherQMM::eval_gpu` sent only bf16 activations to `gather_qmv_warp_shared_kernel`; f16 fell through to the generic `gather_qmv_kernel`, which took about 205 ms per call on `gfx1151`. f16 checkpoints such as `mlx-community/Mixtral-8x7B-Instruct-v0.1-4bit` decoded at about 0.1 tok/s, with 99.7% of GPU time in that kernel (rocprofv3). f16 now uses the same warp-shared kernel (the kernel was already templated on the element type), which takes 1.44 ms for a decode-shaped call at Mixtral's expert shape and matches a dequantized f32 reference. Applies to the fork; to be proposed there.
13. **f32 activations in the tiled qmv path.** `QuantizedMatmul::eval_gpu` entered the tiled qmv branch for any activation dtype, launched `qmv_tiled_kernel` only for bf16 and f16, and then returned, so f32 activations produced no kernel launch and the output was whatever the fresh allocation held (relative error from 1.0 up to 1e35 at every tested shape). The branch is now entered only for bf16/f16 and group sizes 32/64/128, so f32 takes the generic qmv dispatch, which matches a dequantized f32 reference (relative error about 1e-7). mlxcel-core's split/fused projection tests use f32 inputs and exposed it. Applies to the fork; to be proposed there.
14. **Scatter wrote every update to the first index.** `Scatter::eval_gpu` passed `upd_post_idx_size` as `int32_t` while `scatter_general_kernel` declares it `int64_t`. `CommandEncoder::add_kernel_node` hands HIP the address of each argument, so the kernel read eight bytes from a four-byte value, got a huge divisor, and computed index element 0 for every update: `z[idx] = v`, `.at[idx].add(...)` and everything built on scatter (`eye`, `identity`, `tri`, `diag`) applied only one update. The size is now `int64_t`, and `add_kernel_node` statically asserts that every argument has the size of its kernel parameter, so this class of mismatch fails to compile (checked by reintroducing the `int32_t`). Applies to the fork; to be proposed there.
15. **`SearchSorted` implemented.** The fork leaves `SearchSorted` a `NO_GPU` stub, and the exception crosses the cxx bridge into a `noexcept` extern, so it ends in `std::terminate`. mlxcel has no call site of its own; it is reached from MLX internals, because `residual_resample` in speculative decoding calls `fused_sample`, which falls back to `random::categorical` where no Gumbel-max kernel exists, and `categorical_impl` takes its inverse-CDF branch for 1-D logits, which is mlxcel's single-row sampling case. `mlx/backend/rocm/sort.hip` now carries the kernel, ported from `mlx/backend/cuda/sort.cu` and reusing this backend's `LessThan` so NaN ordering matches the CPU. Unlike the CUDA original it is grid-stride: the ROCm launch geometry caps the grid, so one index per thread would silently leave the tail of a large output unwritten. Verified against the CPU stream on both sides for duplicate runs, strictly increasing sequences, out-of-range queries, NaN, a single element, and 17M queries (past the 65535 x 256 grid extent). Applies to the fork; to be proposed there.
16. **`Hadamard` implemented.** The fork leaves `Hadamard` a `NO_GPU` stub, which aborted every TurboQuant KV cache mode and `tests/wht_op.rs`. `mlx/backend/rocm/hadamard.hip` adds a single-stage radix-2 butterfly in shared memory for `m == 1` and a power-of-two last axis up to 8192, which is the whole of what mlxcel reaches: `wht()` asserts a power-of-two last axis and the KV cache advisor demotes Turbo modes for the models that would not have one, so the sizes seen here are head dims, chiefly 64, 128 and 256. Larger `n` and the `m` in {12, 20, 28} families throw a message naming the limit rather than returning a wrong answer; the CUDA path covers them by generating a radix-m codelet through NVRTC. The scale is the primitive's `scale_`, which MLX defaults to `1/sqrt(n)`, so the transform stays the involution mlxcel relies on; accumulation is in float regardless of element type. Like the CUDA original the grid is clamped at 65535 blocks and the kernel is grid-stride. Measured with `examples/wht_numeric_probe` against the M1 Ultra Metal reference: norm ratio 1.000000 to within 1e-5 at head_dim 64, 128 and 256, fp16 relative RMS about 2.0e-4 against Metal's 3.8e-4 to 5.0e-4, f32 relative RMS about 1e-7 matching Metal. The fp16 figure is lower than Metal's because this kernel keeps the butterfly in float in shared memory and rounds once on the way out, where Metal rounds between stages; more accurate than the reference is still inside the band, but it is worth knowing before someone reads the gap as a measurement error. Applies to the fork; to be proposed there.
17. **Narrow index dtypes in `Gather` and `Scatter`.** Five dispatch sites in `mlx/backend/rocm/indexing.hip` picked the kernel's index type with `int32_t` for int32 and uint32 and `int64_t` for everything else, so int8, uint8, int16, uint16 and bool index arrays reached a kernel that read eight bytes per element from a one or two byte buffer. On ROCm that is an `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION`: the GPU queue aborts and the process spins instead of failing. mlxcel reaches it with uint8, because the TurboQuant 4-bit codebook lookup is a `take` with uint8 indices, which is why every TurboQuant KV cache test faulted once the `Hadamard` stub was gone. Narrow index arrays are now widened to int32 once before the dispatch. The alternative, giving each of the eight integer dtypes its own instantiation, was implemented and measured first: it is also correct but takes this translation unit from 26 s to 348 s to compile, because the index type multiplies an existing product of twelve value dtypes and five to six index-count branches, so widening was kept at the cost of one copy pass on the paths that are broken today. Upstream does instantiate per index dtype, in both Metal (`backend/metal/indexing.cpp` puts the index dtype in the kernel name and builds the source from a template) and CUDA (`backend/cuda/indexing.cpp` passes it as an NVRTC template argument), but both compile the kernel at runtime and cache it, so the combinations cost nothing at build time. This backend compiles `indexing.hip` ahead of time, so the same strategy is paid by every build. The asymmetry is the compile model, not the strategy, and it is the argument for proposing widening rather than instantiation to the fork. Upstream already uses the same move for the offset type, choosing int32 or int64 by size rather than instantiating every combination. Verified against the CPU stream for int8, uint8, int16, uint16, int32, uint32, int64 and uint64 at four index shapes. Applies to the fork; to be proposed there.
18. **`FFT` implemented through hipFFT.** The fork leaves `FFT` a `NO_GPU` stub, which aborted Kokoro text to speech and the Phi-4-multimodal audio front end, the only two mlxcel paths that reach a device FFT (the other audio front ends use the host-side transform in `src/audio/fft.rs`). `mlx/backend/rocm/fft.hip` ports `mlx/backend/cuda/fft.cu`, with two differences. This hipFFT has no `hipfftXtMakePlanMany` or `hipfftXtExec`, so the typed API is used instead: one `hipfftType` per plan and one exec entry point per transform, which is enough because MLX only asks for float32 and complex64. And hipFFT work cannot be a HIP graph kernel node, so execution goes through `CommandEncoder::launch_kernel`, the same path the rocBLAS and hipBLASLt GEMMs take. The plan cache holds 128 entries, as in the CUDA file (`MLX_ROCM_FFT_CACHE_SIZE` overrides it). It was 8 until lablup/mlxcel#1876: at 16 and above the first plan eviction hung inside `hipfftDestroy`, whose `hipFree` never returned. The cause was not rocFFT or the number of live plans but the order of `hipSetDeviceFlags` against the first HIP queue, fixed in entry 20. Verified against the CPU stream for rfft, irfft, round trips and complex fft at lengths 2, 8, 400, 512, 1024, 1200 and 2048 and batches up to 512, all within 1e-5 relative. Applies to the fork; to be proposed there.
19. **`get_launch_args` removed.** The fork's `mlx/backend/rocm/kernel_utils.hpp` defined `get_launch_args` (a sized overload and an `array` overload) that fixed the block at 256 threads, ignored `shape`, `strides` and `large`, and capped the grid at 65535 blocks, returning that grid with nothing in its name or comment saying the kernel had to be grid-stride. A kernel written one index per thread with an early return past the end would leave every element past 65535 x 256 unwritten, with the output keeping whatever the allocation held (the failure shape of item 13). Upstream CUDA's helper of the same name (`mlx/backend/cuda/kernel_utils.cu` at the pin) does not cap x, takes a `max_block_dim`, and honours `large` through `get_2d_grid_dims`, so a kernel ported from the CUDA backend with its call intact would compile here and inherit the truncation. Nothing called it, in this overlay or in the fork at `75915908`; launch sites compute their own geometry. Most sites that clamp at 65535 blocks launch a grid-stride kernel (`binary.hip`, `unary.hip`, `hadamard.hip`, `sort.hip` among them). `SliceUpdate::eval_gpu`'s reduce-op path in `indexing.hip` was the exception when this item landed: it clamped and launched `slice_update_op_kernel`, which then did at most `NWORK` elements per thread and never read `gridDim`, so an update larger than 65535 x 256 x `NWORK` elements left its tail unapplied. That was the same defect at a real call site; it was fixed separately in item 21, because this item changes no kernel's geometry. Of the three options weighed in lablup/mlxcel#1874 (delete it, rename it to state the grid-stride requirement, or spill the overflow into another grid dimension the way upstream's `get_launch_args_general` spills y into z), deletion was taken: it cannot regress, and the other two keep a helper that only looks like upstream's. Spilling into y would not even make a one-index-per-thread kernel correct unless that kernel also reads `blockIdx.y`, and AMD caps each grid dimension at 2^32 - 1 threads (item 11), so a faithful port of upstream's geometry is not a drop-in either. In place of the definitions the header now declares `template <typename... Args> void get_launch_args(Args&&...) = delete;` with a comment giving this reason, so a ported call fails to compile at the explanation rather than as an undeclared name someone might "fix" by restoring the old helper. A fork sync that brings the old definitions back must drop them again. Applies to the fork; to be proposed there.
20. **Blocking-sync flag set before the first HIP queue.** The fork set `hipSetDeviceFlags(hipDeviceScheduleBlockingSync)` in `rocm::device()`, but the allocator runs first: the first unified allocation's host read calls `hipStreamQuery(nullptr)` in `allocator::Buffer::raw_ptr()`, which creates the null stream's queue, and CLR gives that queue non-interrupt completion signals because active wait is still on. After the flag flips, CLR (`HwQueueTracker::ActiveSignal` in `rocvirtual.cpp`) no longer swaps such a signal for an interrupt one when a command needs a completion handler, and ROCr rejects async handlers on non-interrupt signals (`hsa_amd_signal_async_handler() failed to set the handler!` under `AMD_LOG_LEVEL=4`). The marker a device-wide sync enqueues on the null stream then never signals its waiter: `hipFree` hung in `std::condition_variable::wait` below `Device::SyncAllStreams`. rocFFT's plan destroy was the first thing to hit it (entry 18), but any `hipFree` or device-wide sync with pending null-stream work could. `rocm::ensure_device_flags()` in `device.cpp` (declared in `device.h`) now sets the flag once per device index, thread-safe and touching only that device, and runs before every path that can create a queue ahead of `rocm::device()`: `unified_malloc`, both branches of `raw_ptr()` and the async-pool free streams in the `RocmAllocator` constructor (all in `allocator.cpp`), `gpu::init()` (`eval.cpp`) and `staged_write`'s device sync (`host_stage.cpp`); `rocm::device()` uses it too. If `hipSetDevice` fails it returns without recording the device, so a later call retries; if `hipSetDeviceFlags` fails it prints one line to stderr naming the device index and the HIP error and does not retry, so a regression of #1876 is visible. With it, `hipSetDeviceFlags` precedes the first `Created SWq` line in the `AMD_LOG_LEVEL=3` log, the 40-shape plan probe completes at plan-cache capacities 16, 32 and 128, and `tests/rocm_fft_plan_cache.rs` guards it (it times out with the ordering reverted). A standalone HIP reproducer without MLX or hipFFT (null-stream touch, then the flag, then `hipMalloc`, sync `hipMemcpy`, a null-stream kernel and `hipFree` in a loop) hangs at its first `hipFree` and completes without the early touch. Measured on gfx1151 with HIP 7.15.26333 and rocFFT 1.0.39 only. Applies to the fork; to be proposed there, and the reproducer is a candidate for a CLR report.
21. **`slice_update_op_kernel` made grid-stride.** `SliceUpdate::eval_gpu`'s reduce-op path (Sum, Prod, Max, Min, as built by `slice_update_add`, `slice_update_prod`, `slice_update_max`, `slice_update_min` and by `SliceUpdate::vjp` for Prod) in `mlx/backend/rocm/indexing.hip` clamps its grid at 65535 blocks of 256 threads, and `slice_update_op_kernel` handled one `NWORK`-element chunk per thread without reading `gridDim`. `NWORK` is 4, 2 or 1 by what divides the collapsed update's innermost dimension, so every element past 65535 x 256 x `NWORK` (16,776,960, 33,553,920 or 67,107,840) kept the input value, with no error. The kernel now loops over chunks with a stride of `gridDim.x * blockDim.x * NWORK`, recomputing the output and update indices at the top of each chunk (through `elem_to_loc` on the non-contiguous branches, as the old prologue did); a chunk starts at a multiple of `NWORK`, which divides the innermost dimension, so it never crosses an innermost row and the per-element stride increments stay valid. The clamp stays, as in `sort.hip` and `hadamard.hip`: removing it alone would only move the cliff, since `num_blocks` is an `int` and AMD caps each grid dimension at 2^32 - 1 threads (item 11). No template instantiation was added (item 17). mlxcel's own model paths use only the None reduce, which goes through `copy_gpu_inplace`; `tests/rocm_slice_update_reduce.rs` reaches the reduce kernel through a test-only bridge function, `slice_update_reduce`, and compares against the CPU stream exactly on int32 data. Measured on gfx1151 with the old kernel: contiguous Sum updates of 16,777,217 (NWORK=1), 33,554,434 (NWORK=2) and 67,108,868 (NWORK=4) elements left exactly the last 257, 514 and 1028 elements unapplied, a scalar-update Sum over 16,777,217 left 257, and a Max through a `[4099, 4097]` update into columns 1..4098 of a `[4099, 4099]` output (strided output, NWORK=1) left 16,643, and so did a Sum through a transposed update of the same shape (strided output and update), each the element count past the grid's reach; below that size every reduce matched. With the fix every case matches the CPU. The test runs the GPU op first on the same source the CPU reference reads afterwards, which also checks item 24. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
22. **`get_2d_grid_dims` with a divisor sized strided scans too large.** `Scan::eval_gpu` sizes the `strided_scan` grid (a scan along any axis but the last) with `get_2d_grid_dims(shape, strides, axis_size * stride)`. The fork's `mlx/backend/rocm/kernel_utils.hpp` carried its own body for that overload, an older form of upstream's that removed a dimension from the divisor only when the dimension divided it whole and never divided the grid by the remainder; upstream's `get_2d_grid_dims_common(shape, strides, divisor)` in `mlx/backend/common/utils.cpp` takes the gcd of each dimension and divides the grid by what is left, and the CUDA backend delegates to it. For `[1, 48, 24, 24]` scanned along axis 2 the old body returned 576 blocks where 48 cover the array, and each extra block read and wrote `axis_size * stride` elements past the end of it. That is the SSD `segsum` of a 48-head Mamba2 layer over a 24-token chunk, so the lablup/mlxcel#1809 correctness matrix found it as an `HSA_STATUS_ERROR_MEMORY_FAULT` in `strided_scan<float, float, Sum, 4, 32, 32, true, false>`: the width-8 trace of `granite-4.0-h-tiny-4bit` faulted on the chunk whose context pass was 24 tokens, and `NVIDIA-Nemotron-3-Nano-30B-A3B-4bit` (64 heads) faulted in its width-8 trace on the 16-token context pass (`[1, 64, 16, 16]`: 256 blocks for 64) and in its width-256 trace on the first chunk. Whether a shape is hit depends on how the head count and the chunk length share factors: with 48 heads, chunks of 8 and 16 tokens were sized correctly, which is why granite's width-1 trace and short prompts ran. An overshoot that stays inside mapped memory does not fault; it reads and writes whatever lies past the array. The overload now delegates to `get_2d_grid_dims_common`, as the non-divisor overload beside it already did. `tests/rocm_strided_scan.rs` compares `cumsum` on the GPU with the CPU stream, exactly, on small integers stored as f32, for that shape, for `[64, 96, 32, 32]` (6144 blocks needed, 98304 launched by the old body), and for shapes the old body sized correctly. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
23. **`ScaledDotProductAttention::use_fallback` checks the stream device.** The fork's `mlx/backend/rocm/scaled_dot_product_attention.cpp` decided from the shapes alone whether a fused kernel applies, so a call on a CPU stream with a decode-shaped query (the vector kernel's shape) built the fused `ScaledDotProductAttention` primitive, whose `eval_cpu` throws "NYI". Through the cxx bridge that is `std::terminate`: on a ROCm build, `MLXCEL_DEVICE=cpu mlxcel generate` and `examples/logit_trace` aborted at the first token of any attention model (seen on Qwen3-0.6B-4bit and a Qwen3.5 FP8 block checkpoint while building the CPU reference for lablup/mlxcel#1807). `use_fallback` now returns `true` for any non-GPU stream first, and throws for `force_fused` there, which is what upstream CUDA's `has_fused_kernel` does before its shape checks. `tests/cpu_device_sdpa.rs` runs attention on the CPU device against a host softmax reference. Applies to the fork; to be proposed there.
24. **`SliceUpdate` and `DynamicSliceUpdate` no longer donate a source that is still referenced.** Both `SliceUpdate::eval_gpu` (`mlx/backend/rocm/indexing.hip`) and `DynamicSliceUpdate::eval_gpu` (`mlx/backend/gpu/primitives.cpp`) gave the source's buffer to the output whenever the buffer had one owner (`in.data_shared_ptr().use_count() == 1`), without checking whether the source array itself was still referenced. A second handle to the same array, or an unevaluated node that takes it as an input (a `Slice`, a `Copy`), holds the array but not its buffer, so the update was written into an array that could still be read. Upstream's `array::is_donatable()` requires both counts to be one, and Metal and CUDA reach it through `copy_gpu`, whose `set_copy_output_data` donates only when `is_donatable(in, out)` holds. Both primitives now call `copy_gpu` exactly as upstream CUDA's `SliceUpdate::eval_gpu` and upstream's `DynamicSliceUpdate::eval_gpu` do. `DynamicSliceUpdate` also forced donation whenever `rocm::graph_active()` was set, for KV cache accumulation under HIP graph capture; that override is removed, because it donated even a buffer other arrays shared, and it could not fire: `graph_active()` is set only by the `CommandEncoder` constructor when `use_hip_graphs()` is true, `use_hip_graphs()` returns a constant `false` in `mlx/backend/rocm/device.cpp`, and `MLX_GRAPH_PREFILL_REPLAY` is read only behind `use_hip_graphs()`. If HIP graphs are turned back on, accumulation under capture has to be solved in the capture, not by writing into a referenced source. It was a live bug in mlxcel, measured on gfx1151: DeepSeek-V4's `PoolingCache::accumulate_windows` returns windows that lazily read the previous remainder rows while the same call writes the new remainder over those rows, and the model's cache barrier evaluates the buffer first, so a chunked prefill that completes a window across a remainder and leaves a new one read the new tail instead (`tiny_model_chunked_prefill_with_pool_remainder_matches_cpu` moved the first logit by about 9e-3 relative against the CPU; 1e-5 after the fix); and a prompt-cache `ModelStateSnapshot` of a `RotatingKVCache`, a lazy `copy` of the live keys, took the next token's ring overwrite when a one-token suffix wrapped the ring (`rotating_steady_state_snapshot_survives_the_next_wrap_write`; the existing `rotating_inplace_warmup_and_wrap_keep_shared_snapshots_intact` also fails on the old build with `MLXCEL_KV_INPLACE_WRITE=0`). `tests/rocm_slice_update_source.rs` holds a source, runs a GPU update through `slice_update` (None), `slice_update_reduce` (Sum, Max) and the test-only `slice_update_dynamic` bridge, and checks the source is unchanged; every held-source case fails on the old build. A source dropped before evaluation is still donated, which is the KV cache's own update pattern (`self.keys = slice_update(self.keys, ...)`), and the single-token FP16 decode write goes through `inplace_slice_write` rather than `SliceUpdate`. Decode throughput on gfx1151 (`scripts/bench_decode.sh`, pp512/tg128, interleaved runs with no other GPU process or compiler running): Qwen3-0.6B-4bit 279.0 and 279.8 tok/s before, 279.5 and 279.9 after; Meta-Llama-3.1-8B-Instruct-4bit 35.68, 35.67 and 35.82 before, 35.90 and 35.69 after; no change beyond the run-to-run spread (under 1%). Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
25. **`MLX_ROCM_FFT_CACHE_SIZE` validated.** The fork's `LRUBytesKeyCache` constructor in `mlx/backend/rocm/lru_cache.h` read its capacity variable with an unchecked `std::stoul`, and its one env-driven user is the hipFFT plan cache in `fft.hip` (entry 18). Per value, confirmed with a host g++ 14 probe of the header: `0` was accepted, and the first `put()` then ran `while (size() >= capacity_)` on an empty list and called `back()` and `pop_back()` on it, which is undefined behavior (the probe threw `std::bad_alloc`; with `-D_GLIBCXX_ASSERTIONS` it aborts on `!this->empty()`); `abc`, an empty value and an overflowing value such as `99999999999999999999999` threw `std::invalid_argument` or `std::out_of_range` whose message is only `stoul`, out of the static's initializer in `FFT::eval_gpu`, so the static stayed uninitialized and every later FFT threw again; `-1` was taken silently as `SIZE_MAX` (a cache that never evicts), `8abc` silently as 8, and `0x10` as 0, with the same undefined behavior as `0` (on gfx1151 the first GPU rfft failed with `std::bad_alloc` for both). `capacity_from_env()` in the same header now parses it the way `gpu_watchdog_seconds()` in `device.cpp` parses `MLX_ROCM_GPU_WATCHDOG_SECS`: `std::strtol` base 10, the whole string must be the number, and the value must be 1 to `INT_MAX` (the bound CUDA's `int` read implies). Unset gives the default silently; anything else prints one stderr line, `[ROCm] ignoring invalid MLX_ROCM_FFT_CACHE_SIZE="<value>" (expected a positive integer); using the default 128`, and uses the default, once, because the static then initializes. Both `LRUBytesKeyCache` and `LRUCache(size_t)` now throw `std::runtime_error("LRUCache requires capacity > 0.")` for a capacity of 0, as upstream CUDA's `LRUCache` does (`mlx/backend/cuda/lru_cache.h` at the pin). Upstream CUDA reads `MLX_CUDA_FFT_CACHE_SIZE` with `atoi`, so there `0` or junk throws that error at the first FFT and `-1` becomes `SIZE_MAX`; that was not copied. The comment on `fft_plan_cache()` in `fft.hip` states the rule; editing that file was also what made a warm build recompile it, because at the time each HIP object depended only on its own `.hip` source (fixed in item 26). `tests/rocm_fft_cache_env.rs` runs one child process per value (`0`, `-1`, `abc`, empty, `8abc`, `0x10`, an overflow past `long`, `2147483648`, `16`, `1`, `2147483647`, unset) and checks the warning count and an rfft against the CPU stream. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
27. **CPU-stream BLAS runs single-threaded over fine-grained memory.** On an APU the fork's allocator (`mlx/backend/rocm/allocator.cpp`, `unified_malloc`) gives every array fine-grained device memory, CPU-stream arrays included, and `Buffer::raw_ptr()` hands the CPU that same pointer. MLX's CPU backend writes BLAS and LAPACK results straight into it (`cblas_sgemm` in `mlx/backend/cpu/gemms/cblas.cpp`, also `conv.cpp`, `masked_mm.cpp` and the LAPACK primitives), and multithreaded OpenBLAS returned wrong output columns there, differently from call to call. Measured on the gfx1151 host (Ryzen AI MAX+ 395, Debian OpenBLAS 0.3.29 pthread, 32 threads): a standalone C `cblas_sgemm` of `[1, 2880] x [2880, 2880]^T` was wrong in 37 of 50 calls with inputs and output from `hipExtMallocWithFlags(hipDeviceMallocFinegrained)`, in 10 of 300 with only the output there, and exact in every call with malloc or `hipHostMalloc` buffers or with `OPENBLAS_NUM_THREADS` at 1, 2 or 4. Through MLX the wrong columns were each the last column of one OpenBLAS thread's share of the output (shares of 93 columns: 650, 1022, 1859, ...), the column whose 64-byte line the next thread also writes. This was lablup/mlxcel#2072: `tests/rocm_mxfp4_quant.rs` failed `qmm 2880x2880 M=1` in 3 of 8 runs here (7 of 10 in the issue), and the fault was in its CPU reference, not the GPU kernel; with the tensors dumped from a failing run, the GPU result matched an independent dequantize-and-dot of the packed bytes and the CPU `matmul` did not. `unified_malloc` now calls `openblas_set_num_threads(1)` once, on its first fine-grained allocation, which precedes any CPU-stream BLAS call writing such a buffer; the symbol is declared weak, so a build against another BLAS links and changes nothing. The cost is CPU-stream BLAS speed: the CPU reads fine-grained memory slowly, and that gemv went from about 0.2 s to about 1.4 s per call. GPU work and quantized or half-precision CPU matmuls (MLX's own kernels, no BLAS) are unaffected, so model inference under `MLXCEL_DEVICE=cpu` barely touches BLAS. Keeping BLAS multithreaded by giving it a cacheable scratch output would need a change at every BLAS call site in MLX's CPU backend and was not taken. `tests/rocm_cpu_blas_finegrained.rs` repeats that gemv on the CPU stream against an f64 host reference; with this change reverted it failed in 5 of 5 runs, and with it `quantized_matmul_matches_dequantized_reference` passed 50 runs in a row. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
28. **In-flight command batches bounded by what they allocate, and the cache limit enforced.** Measured on the gfx1151 host at pp512/tg128 (lablup/mlxcel#2062), the MLX peak (live buffers, `get_peak_memory`) was 20.60 GB for Meta-Llama-3.1-8B-Instruct-4bit, whose weights take 4.75 GB once loaded, and 23.56 GB for Qwen3-30B-A3B-4bit (17.17 GB), and the device-wide `mem_info_vram_used` rose by 21.19 GB and 24.09 GB. The excess was not buffer cache (0.4 to 1.7 GB at every phase boundary) but live transients inside the measured prefill: every buffer an operation allocates is kept by `CommandEncoder::add_temporary` until its batch's completion handler runs, the eager path (`use_hip_graphs()` is off) committed only every `MLX_MAX_OPS_PER_BUFFER` ops (2000) and never registered those commits with MLX's scheduler, so neither the scheduler's task cap nor `set_memory_limit` ever made the host wait, and the host could encode far ahead of the GPU, holding the transients of many batches at once. For the 8B, an f16 checkpoint, most of it is the f16 weight copy `QuantizedMatmul`'s dequantize-and-GEMM path allocates per matrix (with `MLX_ROCM_QMM_DEQUANT_GEMM=0` the peak was 6.78 GB, at a twentieth of the prefill speed); the MoE model is bf16, whose affine 4-bit matmuls took the fused WMMA kernel at the time and allocated no copy (item 29 moved its prefill projections to the dequantize path) (the variable left its peak at 23.56 GB), so its excess is other operations' outputs held the same way, which the bound below removes too. `MLX_MAX_OPS_PER_BUFFER=50` alone changed nothing, because more commits do not stop the host from running ahead. Now `gpu::eval` (`mlx/backend/rocm/eval.cpp`) adds what each primitive allocated during `eval_gpu` to its encoder's open batch, read from a thread-local byte counter in the allocator (`rocm::thread_allocated_bytes()`, so frees on the worker thread do not disturb it), and `CommandEncoder::maybe_commit` (`mlx/backend/rocm/device.cpp`) commits once the open batch has allocated a quarter of `MLX_ROCM_MAX_INFLIGHT_MB` (default 1024); after that commit and after the commit `gpu::finalize` makes at the end of every eval and `async_eval`, it records a HIP event, and blocks on the oldest such batch while the committed ones still exceed the budget. The wait is `hipEventSynchronize` (the device is in blocking-sync mode, so the thread sleeps), or a polled wait that gives up at `MLX_ROCM_GPU_WATCHDOG_SECS` when that is set; a faulted stream ends either with the fault, which is recorded as the stream's error. Nothing is tracked while a decode-step capture or any stream capture is in progress. The events are raw `hipEvent_t` owned by the encoder, not `HipEvent`: `HipEvent` returns its handle to a function-local static pool when destroyed, an encoder can be destroyed after that pool at process exit, and a first version built on it aborted `tests/rocm_mxfp4_quant.rs` at exit with `malloc_consolidate(): unaligned fastbin chunk detected`. `0` restores the old behavior. `tests/rocm_inflight_bound.rs` runs 40 f16 4-bit 8192x8192 matmuls over 512 rows in one evaluation (5 GiB of dequantized weight copies): the peak rose by 1.75 GiB with the default and by 6.25 GiB with `MLX_ROCM_MAX_INFLIGHT_MB=0`, which fails its 3 GiB bound. With the default the peaks were 6.14 GB and 18.57 to 18.58 GB over three harness runs each, decode throughput was unchanged (median 37.57 against 37.02 tok/s and 61.69 against 61.79 tok/s) and the 8B's prefill lost 1.8% (the MoE model's prefill varies more than that from run to run); budgets from 256 to 4096 MiB traded peak for prefill speed within a few percent (the table is in `docs/benchmark_results/rocm-memory-gfx1151-2026-09-30.md`). Separately, `RocmAllocator::set_cache_limit` stored `max_pool_size_` and nothing read it, so MLX's `set_cache_limit` (mlxcel's `MLXCEL_CACHE_LIMIT`) bounded nothing, while the exact-size cache (`min_utilization` 1.0) keeps every buffer size it has seen until `clear_cache()`. `malloc_async` now trims the cache on a cache miss once it exceeds `max_pool_size_`, the only place the footprint grows, so active plus cache stays within the live set plus the limit plus the one request; it trims to three quarters of the limit, so one round of blocking `hipFree` calls covers several misses of a workload whose shapes keep changing; `free()` and cache hits still never call `hipFree`, which the fork avoids for the training reasons in its comment there. The limit still defaults to the memory limit (76.8 GiB here), so the trim changes nothing until someone sets a limit; mlxcel sets 2 GiB on ROCm builds. `memory::tests::cache_limit_bounds_the_free_buffer_cache` in mlxcel-core frees 64 buffers of distinct sizes under a 1 MiB limit and checks the cache stays under 8 MiB; with the trim removed it held 49.8 MB and failed. The count is of allocations, not only of transients (a batch that grows the KV cache counts too), and a batch's buffers are dropped by the worker thread just after its event completes, so the bound is approximate. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
29. **bf16 GEMMs of 128 rows or more leave the fused WMMA kernel on RDNA 3.5.** `QuantizedMatmul::eval_gpu` (`mlx/backend/rocm/quantized/qmm.hip`) sent every single bf16 affine GEMM with more than one row (4-, 6- or 8-bit, group 64, `N % 16 == 0`, `K % 64 == 0`) to `qmm_wmma_dense_kernel` on a device with native WMMA that is not a low-CU iGPU, however many rows it had. On gfx1151 that kernel lost to the dequantize + hipBLASLt path it bypasses on every bf16 shape measured from 128 rows up (1.0x to 3.1x at 128 rows, 1.6x to 2.4x at 256, 2.4x to 5.1x at 1024 and 2048; it won only on some shapes at 2 to 64 rows), so bf16 prefill ran at a fraction of what the same device did for f16 checkpoints (lablup/mlxcel#2081). It also made `quantized_matmul` and `dequantize` + `matmul` disagree for bf16 (499 of 1,048,576 outputs at `[1024, 2048] x [1024, 2048]`, a reduction-order difference), which is what mlxcel's dense prefill path checks. The dispatch decision is now one function, `select_qmm_route`, used by `eval_gpu`; it keeps the kernel below `MLX_ROCM_WMMA_QMM_MAX_M` rows (default 128 on the RDNA 3.5 tier, no ceiling on the unmeasured tiers) and sends larger GEMMs to the bf16 dequantize + hipBLASLt route, except where that route would be the fp8 path (RDNA 4), which keeps the kernel as before. `MLX_ROCM_WMMA_QMM=1` removes the ceiling, which is the old dispatch on any device that is not a low-CU iGPU (there it forces the kernel on, as it always did). `rocm.h` exports `quantized_matmul_runs_dequant_gemm` (stubbed in `no_rocm.cpp`), which answers from the same function whether a single GEMM of a given shape takes dequantize + hipBLASLt, for mlxcel to decide when its dense prefill path returns the same bytes. Same binary, `MLX_ROCM_WMMA_QMM=1` against the default, prefill tok/s over three ABBA runs: Gemma 3 4B 4-bit 1146 to 2289 at 512 tokens and 961 to 2815 at 2048, Qwen3-0.6B 4-bit 4581 to 7633 and 3059 to 4236, Qwen3-30B-A3B 4-bit (MoE, only the attention projections take this path) 311 to 326 and 283 to 297; decode unchanged, and MLX peak memory within 0.1 GB except Qwen3-0.6B at 512 tokens (1.04 to 1.46 GB), since the route allocates a bf16 weight copy per matrix that item 28 bounds. The route's dequantized-weight LRU (8 matrices or 256 MB, `MLX_ROCM_QMM_DEQUANT_CACHE_SIZE`, `MLX_ROCM_QMM_DEQUANT_CACHE_MAX_BYTES`) gets no hits across a model's projections in prefill but still keeps its last entries alive afterwards, as it already did for f16 checkpoints; `MLX_ROCM_QMM_DEQUANT_CACHE_SIZE=0` turns it off. `docs/benchmark_results/rocm-bf16-qmm-route-gfx1151-2026-09-30.md` has the tables. Applies to the fork; the ceiling was measured on gfx1151 only.
30. **Custom kernels receive `<input>_shape` and `<input>_strides` by value.** `build_kernel` in the fork's `mlx/backend/rocm/custom_kernel.cpp` declared an input's shape and strides as `const int32_t* <name>_shape` and `const int64_t* <name>_strides`, while `CustomKernel::eval_gpu` passes them with `KernelArgs::append_ndim`, which pads the vector to `JIT_MAX_NDIM` (8) entries and hands `hipModuleLaunchKernel` a pointer to that storage, so the kernel received the values themselves and read the first eight bytes of the shape as an address. Any `fast::hip_kernel` source that mentioned `<name>_shape` faulted the queue on its first launch: the HIP Gumbel-max sampler (lablup/mlxcel#2064), which reads `logits_shape[1]` as the CUDA and Metal ports do, died with `HSA_STATUS_ERROR_MEMORY_FAULT` at address `0x80000000000`, the page of `0x80000000800`, which is the shape `{2048, 2048}` read as a 64-bit pointer, on gfx1151. No HIP kernel in mlxcel used either argument before, which is why it went unseen. The generated header now defines `KernelShape` (8 `int32_t`) and `KernelStrides` (8 `int64_t`) with an `operator[]`, the parameters are declared with them by value, which is what upstream CUDA's `const __grid_constant__ Shape` / `Strides` does, and `elem_to_loc` gains an overload for them; a `static_assert` ties the 8 to `JIT_MAX_NDIM`. The launch also appends an input's shape, strides and ndim only when its ndim is above zero, the condition under which `build_kernel` declares them; before, a 0-d input whose name appeared as `<name>_shape` in the source shifted every later argument (no mlxcel kernel has such an input). `sampling_fixed_key_tests` in mlxcel-core reads `logits_shape` through the Gumbel-max port and faults without this change; the `_strides` declaration has no user in mlxcel and was checked only by compiling it. Applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).

## Fixes to the fork's build

26. **HIP objects track the headers they include.** The fork's `mlx/backend/rocm/CMakeLists.txt` compiles each `.hip` file with its own `add_custom_command` whose only dependency was `DEPENDS ${hip_src}`, so CMake never learned which headers an object includes and a warm build recompiled no `hip_objs/*.o` when only a header changed (`kernel_utils.hpp`, `device.h`, `lru_cache.h`, `reduce/reduce.hpp` and so on). Fresh builds were correct; reused build trees could link kernels compiled against an old header, which is what made the first run of the item 25 fix behave like the old code until `fft.hip` itself was edited, what could leave a warm tree running the pre-item-22 grid code in `scan.hip`, and what made a header-only bisect unreliable (lablup/mlxcel#2072). The `.cpp` sources added through `target_sources(mlx ...)` were never affected, because CMake scans those itself. Each command now passes `-MD -MF <object>.d` to `hipcc` and `DEPFILE <object>.d` to `add_custom_command`, under `if(CMAKE_VERSION VERSION_GREATER_EQUAL 3.20)` (the first version with `DEPFILE` for the Makefile generators, which is what `build.rs` gets from `cmake::Config` by default) with policy `CMP0116` set to `NEW` when it exists. Below 3.20 every object instead depends on a `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)` list of every `*.h`, `*.hpp` and `*.cuh` under `mlx/` (the HIP sources also include MLX headers outside the backend, such as `mlx/primitives.h`), which rebuilds every HIP object on any header change; since this overlay's top-level `CMakeLists.txt` requires CMake 3.25, which also already implies `CMP0116` NEW, the branch is not reachable today and only guards a lower minimum. The dependency chain: an overlay edit changes a file under `src/lib/mlx-cpp/patches-rocm/`, which `build.rs` watches with `rerun-if-changed`, so Cargo reruns the build script; CMake reconfigures and `configure_file(... COPYONLY)` in `src/lib/mlx-cpp/CMakeLists.txt` rewrites the copy under `_deps/mlx-src` only when its content differs; `hipcc` reads those copies (each `.hip` file's own directory and `-I${PROJECT_SOURCE_DIR}`, which is `_deps/mlx-src`), so the depfiles name the copies by absolute path and never the overlay originals, and the build tool compares the copy's mtime with the object's. A bare `touch` of an overlay header therefore rebuilds nothing, by design. Measured on gfx1151 with CMake 3.31.6 and Unix Makefiles in a warm `test-fast` tree: before the fix, appending a comment to `kernel_utils.hpp` rewrote the build-tree copy and recompiled 0 of 41 objects; after it, the same edit recompiled the 39 objects whose depfiles name the header (all but `event.o` and `quantized/qmv_tiled_kernel.o`), an edit to `reduce/reduce.hpp` recompiled exactly its 7 includers (both sets agree with a walk of the `#include` graph over the build-tree sources, independent of the depfiles), reverting each recompiled the same set, and a rebuild with no change recompiled none. The first build after picking up this change recompiles all 41 objects once, because the command line changed, so existing warm trees heal themselves. The same mechanism was checked under Ninja 1.13 on a two-file probe project with the same `configure_file` copy layout (edit recompiles only the includer, touch and no-change rebuild nothing, depfile names the build-tree copy); the full mlxcel build was not run under Ninja. The depfile comes from the host compilation only, so it lists ROCm and system headers too (an update to them rebuilds every HIP object) but not headers included only on the device side; `rocwmma/rocwmma.hpp` in `flash_attention_wmma.hip` is the one such include today (`quantized/qmm.hip` includes it on the host side too, so its depfile lists it). `docs/installation.md` (ROCm, Build) describes how to force a clean HIP rebuild. Fork-side build glue; applies to the fork; to be proposed there (upstreaming candidate, lablup/mlxcel#1813).
