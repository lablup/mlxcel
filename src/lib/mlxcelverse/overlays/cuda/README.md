# overlays/cuda: CUDA backend and core overlay

This directory holds mlxcelverse's source overlays for MLX's CUDA backend (`mlx/backend/cuda/**`, 30 files) and CUDA-only MLX core files (`mlx/*.cpp`, 3 files).

## How `CMakeLists.txt` applies this directory

`mlx_apply_source_overlays` in `../../CMakeLists.txt` applies the two subtrees with distinct gating:

1. `mlx/backend/cuda/**` (33 files: the Windows delay-load hook `delayload.cpp` and its runtime directory choice `runtime_dir.h` (one CUDA runtime directory per process, a relocatable runtime bundle, lablup/mlxcel#2640), the PTX cache path rules and Windows trust check `ptx_cache_dir.h`, `ptx_cache_dir_win.h` and `ptx_cache_acl_win.h` (lablup/mlxcel#2797), checkpoint weight upload through pinned staging slots (`load.cpp`, #1564), custom grouped GEMM and CUTLASS arch selection, quantized QMV/QMM/FP-QMV kernels and tile selection, reduce ops, binary/unary ops, compiled JIT module and CUTLASS include resolution, `compiled.cpp` (fused `AsType` uses the eager `cast_to` so complex64 to real casts compile, issue #2739), `conv.cpp` (a cuDNN graph with no execution plan, such as an f32 dilated convolution with `MLX_ENABLE_TF32=0` on sm_121, falls back to the gemm convolution instead of throwing, issue #2739), device/allocator adjustments, `device.cpp` (captured child graphs such as cuBLASLt matmuls are barriers inside a CUDA graph and are chained to each other, so independent GEMMs no longer overlap each other or unrelated kernel nodes; issue #2462, `MLXCEL_CUDA_GRAPH_CAPTURE_BARRIER`), `layer_norm.cu` (a barrier after each block reduction reads its shared partials, so LayerNorm and its VJP no longer race between their two reductions; lablup/mlxcel#2696; the VJP's tail branch indexes its per-thread weight and cotangent vectors by in-vector offset, so rows whose width is not a multiple of the vector width no longer read past them, lablup/mlxcel#2759), and `mlxcel` helper headers `grouped_gemm_arch.h`, `qmm_naive_tile.h` and `load_staging.h`): copied into `${mlx_source_dir}/mlx/backend/cuda/` on every build. MLX only compiles `mlx/backend/cuda/` when `MLX_BUILD_CUDA` is `ON`, so copying them unconditionally is a no-op on Metal, ROCm, and CPU-only builds.
2. `mlx/{dtype,fast,ops}.cpp` (3 MLX core files): copied into `${mlx_source_dir}/mlx/` **only when `MLX_BUILD_CUDA` is `ON`**. These files adjust `bfloat16` + `float32` type promotion and norm precision to avoid `copy_v` kernel overhead on CUDA, which would alter Metal precision on `bfloat16` vision weights (such as SigLIP position embeddings) and conflict with the ROCm core overlay if applied outside CUDA builds.

## Provenance and pin bumps

Every file in this directory is modified from upstream `ml-explore/mlx` (except the seven mlxcel-authored helper headers `grouped_gemm_arch.h`, `qmm_naive_tile.h`, `load_staging.h`, `runtime_dir.h`, `ptx_cache_dir.h`, `ptx_cache_dir_win.h` and `ptx_cache_acl_win.h`, which are marked `// New file for mlxcel (no upstream MLX counterpart)`), retains Apple's copyright header, and declares its upstream base commit on the line `// Modified from upstream MLX <40-char-sha> <upstream/relative/path>`. On an MLX pin bump, 3-way merge each file from its declared base commit to the new pin (`git merge-file`) and update the header SHA as documented in [CONTRIBUTING.md](../../../../../CONTRIBUTING.md). That checklist's drift check walks every file under `overlays/{cpu,metal,cuda}` by its header line, so `device.cpp` (added for issue #2462) and `load_staging.h` (PR #2474) are covered without being listed anywhere else; there is no separate per-file list to maintain.
