# Image generation throughput on GB10 (2026-11-04)

Text-to-image and image-edit latency for the mlxcel server on **NVIDIA GB10 (DGX Spark)** at mlxcel 0.8.1. Twenty-four Diffusers-style checkpoints were discovered under `models/`; 21 answer the text-to-image route, the three `mage-flow-edit*` checkpoints are edit-only and were measured on the edit route instead.

Raw rows: `benchmarks/cuda_gb10_imagegen_2026-11-04.csv` (21 models) and `benchmarks/cuda_gb10_imagegen_edit_2026-11-04.csv` (3 models). Harness: `scripts/bench_imagegen.py`.

## Method

One server process per checkpoint, started fresh; `load_ms` is the time until `GET /v1/models` answers 200, so it is a ceiling with one-second granularity. The timed measurement is end-to-end `POST` latency: HTTP, tokenization, the full denoising loop, VAE decode and base64 PNG encoding. Load time is excluded from `p50_ms` because the warmup request absorbs it.

The same 512x512, 8-step shape is used for every model so the rows compare with each other. That is not each family's default step count: a distilled model may default to 4 and a non-distilled one to 20 or more. `steps` is a CSV column, and a model measured at a non-default step count is a throughput number, not a quality claim.

The edit ladder uses `tests/fixtures/test_image.png` as the reference (a 679-byte PNG), a fixed edit instruction (`make it a night scene with moonlight and falling snow`) and the same 512x512 and 8-step shape, through `POST /v1/images/edits`.

## Observations

- **The 4-bit FLUX.2 Klein renders slower than bf16 at this shape.** `flux.2-klein-4b-bf16` reads 1.83 s/image against 2.04 s/image for `flux2-klein-4b-4bit`, and 3.21 against 3.72 for the 9B pair. At 8 steps the quantized weights save memory, not time, the same pattern the embedding ladder recorded for 8-bit Nemotron. More steps shift the balance toward the quantized kernels; this is one shape, not a general verdict.
- **Turbo variants are 1.5x to 1.7x faster within a family.** `mage-flow-turbo` 2.75 against 4.61 for `mage-flow`, `llada-image-turbo` 4.20 against 7.02, and `mage-flow-edit-turbo` 3.77 against 5.58. `ernie-image-turbo` is the exception at 20.64 against 24.47, only 16% faster; its prompt enhancer and text encoder dominate that pipeline.
- **`z-image` pays its 13.5 to 14.0 s load once and then generates in 7.44 s (turbo) or 14.68 s (bf16).** The load figure is the largest in the roster by an order of magnitude; the first request after readiness also has to warm the text encoder, which the untimed warmup absorbs.
- **`ming-image` scales the expected way with precision**: 4-bit 11.85 s, 8-bit 13.01 s, bf16 18.59 s. This is the one family here where the lowest-bit checkpoint is also the fastest, which points at the same MLX quantized-matmul dispatch that makes 4-bit FLUX.2 lose at 8 steps being acceptable at this pipeline's larger compute per token.
- **Edit and generation sit in the same range for the mage-flow family.** The edit variants land at 3.77 to 5.59 s and the generate variants at 2.75 to 4.61 s. The reference image does not add a separate vision encoder in this family; the denoising loop at this size dominates both routes.

## Caveats

- One box, one run of three timed requests per model after one warmup. `min_ms` in the CSV shows the spread; this is not a throughput-under-load study and the server runs requests one at a time.
- Fixed 8 steps for every model. A family's quality default is different, so these are latency comparisons at one shape, not recommendations for production step counts.
- 512x512 only. Denoising cost scales with pixel count and the text encoder cost does not, so a 1024x1024 sweep would move the ranking toward the larger backbones.
- base64 PNG encoding is inside the timed request. A client that accepts a file path or URL avoids that cost.
- Quality was not evaluated; this document says nothing about which checkpoint produces better images.
- The harness records ROCm hosts through the same `hardware` column (`rocminfo` gfx target, ROCm release, sysfs VRAM), so the same command produces the gfx1151 ladder on that host.
