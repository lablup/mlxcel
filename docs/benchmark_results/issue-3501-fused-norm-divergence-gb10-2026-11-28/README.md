# Issue #3501: graph path against the fused add+RMSNorm on Llama 3.2 1B, GB10

Why `MLXCEL_FUSED_ADD_RMSNORM=1` changes greedy output on `llama-3.2-1b-instruct-bf16` at B=1 on the 128-token synthesized prompt (128 tokens on the graph path, an end-of-generation token after 98 with the fusion, first divergence at generated index 11, 287 against 430). Measured with `examples/fused_norm_divergence_probe.rs` on GB10 (sm_121), kernel 7.0.0-1019-nvidia, driver 580.178.04, `MLXCEL_CUDA_ARCHITECTURES=121`, base `da347a2b`, a build with `MLXCEL_BUILD_CUDA_OXIDE_FUSED_NORM=1` so every probe process printed its route counters. Verdict: a near-tie from the fp32 summation order of the sum of squares, not a defect.

## Results

- **The probe runs the CLI computation.** Free-running, it reproduces both `tokens_sha256_16` values of `cuda-oxide-fused-norm-gb10-2026-11-27/m1-end-to-end.csv`: `153e97b6c47aae0d` (graph, 128 tokens, 0 fused joins) and `ca3dde687d118faf` (fused, 98 tokens, 1584 joins on the existing kernel, 0 on cuda-oxide). The layer walk behind `--dump-layers` gives byte-identical `steps.csv` to the plain forward, at step 0 and at step 11.
- **Margins** (`steps-*-teacher-forced.csv`, both arms forced on the graph arm's tokens). The only argmax flip in 128 steps is step 11, position 138. Graph: 287 and 430 both at 18.5, an exact bf16 tie that argmax breaks to the lower id (margin 0). Fused: 430 at 18.5, 287 at 18.375 (margin 0.125, one bf16 ulp at that magnitude). Step 10's margin is 1.75 on both arms. Seventeen graph-arm steps have a margin of 0.125 or less.
- **Accumulated deviation at step 11.** The logits differ at every step from step 0 on. At step 11: max abs 0.125, RMS 0.0283 (reference RMS 2.76), 108,456 of 128,256 differing. The graph arm's margin (0) is below the accumulated deviation (0.125), the issue's near-tie condition.
- **First divergence** (`--dump-layers 0`, the prefill). Layer 0 and layer 1's `x`, `attn_out` and `h` are byte-identical on both arms; the first differing tensor is layer 1's `normed`: 19 of 262,144 elements, all one bf16 ulp (max abs 1.95e-3, RMS 7.0e-6). `new_residual` (`h`) never differs before `normed` does. At step 11 the first differing tensor is layer 2's `attn_out`, which reads the prefill's KV.
- **Same-input op diff** (`op-diff-*.csv`, graph-arm inputs into both `graph_add_rms_norm` and the fused launcher in one process). `new_residual` is byte-identical on every layer. `normed` differs on two of the 16 prefill joins: layer 1 (19 elements, 1 ulp, all in row 124) and layer 11 (27 elements, at most 2 ulps, all in row 47); the step-11 decode joins are byte-identical on all 16 layers. Against a float64 reference of the graph's formula, the fused kernel is right and the graph off on layer 1 (misses 0 against 19), and the reverse on layer 11 (27 against 0).
- **One normalizer per row explains it** (`normalizer-fit-prefill.csv`, `scripts/fused_norm_normalizer_fit.py`). Each differing row of each side is reproduced exactly by `bf16(w * bf16(x * inv))` with a single fp32 `inv`, and the two sides' ranges do not overlap: on layer 1 the graph row needs `inv` at or above the fp32 rounding of the exact normalizer (0..+24 ulps) and the fused row below it (-24..-1); on layer 11 the graph needs +1..+24 and the fused row -24..0. Under the two fitted normalizers the rounded intermediates `bf16(x * inv)` are at most one bf16 ulp apart (19 and 28 elements). The outputs are one ulp apart on 19 + 25 elements and two ulps apart on 2 (layer 11), where the gain multiply carries a one-ulp change of the intermediate across a binade of the product. The fit ranges `0..+24` and `-24..-1` (and `+1..+24`, `-24..0`) are clipped at the script's search limit of 24 fp32 ulps, so a bound at 24 or -24 means "at least that far", not "exactly that far"; what the fits establish is that each side's row is reproduced by one normalizer and that the two sides' ranges do not overlap.
- **The summation order accounts for the normalizers.** Simulated in fp32 in each kernel's order (below), the sums of squares of the two rows differ by exactly one fp32 ulp: 3.1238654 (MLX order) against 3.1238656 (fused order) on layer 1, 74.0694 against 74.069405 on layer 11. The smaller MLX-order sum gives the larger normalizer, the side the graph's fit is on. Squares of bf16 values are exact in fp32, so FMA contraction does not change these sums.
- **Against the issue's budget.** The criterion was at most one bf16 ulp per element on the same input. The rounded intermediate meets it; two output elements are two ulps apart, which exceeds the literal one-ulp budget. The near-tie verdict still holds because nothing in the formula differs (a single fp32 normalizer per side reproduces each side's row exactly through the graph's formula, and the float64 reference agrees with each side on one row and splits the two), so this is recorded as the near-tie outcome, with the two-ulp output bound stated rather than the one-ulp one.

## Why the sums differ

MLX's CUDA `rms_norm` at bf16 dim 2048 dispatches `rms_norm_small` with `BLOCK_SIZE = 128`, `N_CHUNKS = 2` and `N_READS = 8` (read from `dispatch_num_chunks`: `nvec = 256`, divisible by 128); `cuda-oxide-fused-norm-gb10-2026-11-27/m4-nsys-kernels.csv` shows the kernel name and its 128-thread block. The `ALIGNED` template argument was not observed: it selects only the load function in `rms_norm.cu` (vector loads or bounds-checked ones), not the order in which squares are summed, so the conclusion does not depend on it. Each thread sums elements `[8t, 8t + 8)` then `[1024 + 8t, 1024 + 8t + 8)` in order, `cg::reduce` folds each warp with an xor butterfly from mask 16 down, and a second butterfly folds the four warp partials. The fused kernel (`FUSED_ADD_RMS_NORM_CUDA_SOURCE`) launches 512 threads of 4 elements (`[4t, 4t + 4)`) and folds 16 warp partials with the same butterfly. Same formula, same rounding points, different fp32 partition of the sum of squares.

Making the CUDA fused kernel byte-identical would mean copying that geometry per dim (`dispatch_num_chunks`' block size and chunk count, 16-byte vector loads, the per-thread chunk order, and the looped `rms_norm<T, 1024, N_READS>` for rows past `N_READS * 128 * 8`), as the ROCm port did with its overlay's 256-thread block. The cuda-oxide artifact is a bitwise port of the current kernel and its tests assert bitwise equality with it, so that change also needs the artifact regenerated with the cuda-oxide toolchain.

## Reproduce

```bash
MLXCEL_BUILD_CUDA_OXIDE_FUSED_NORM=1 MLXCEL_CUDA_ARCHITECTURES=121 cargo build --release --features cuda --example fused_norm_divergence_probe
P=target/release/examples/fused_norm_divergence_probe; M=models/llama-3.2-1b-instruct-bf16; O=/tmp/issue-3501
# graph-tokens.txt: the graph arm's first_row_tokens from m1-end-to-end.csv (CLI, B=1, 128)
env -u MLXCEL_FUSED_ADD_RMSNORM gpu-lock run --tag issue-3501 -- $P --model $M --expect-route graph --out $O/free-graph
MLXCEL_FUSED_ADD_RMSNORM=1 gpu-lock run --tag issue-3501 -- $P --model $M --expect-route fused --out $O/free-fused
env -u MLXCEL_FUSED_ADD_RMSNORM gpu-lock run --tag issue-3501 -- $P --model $M --tokens graph-tokens.txt --dump-layers 0 --expect-route graph --out $O/graph
MLXCEL_FUSED_ADD_RMSNORM=1 gpu-lock run --tag issue-3501 -- $P --model $M --tokens graph-tokens.txt --dump-layers 0 --expect-route fused --out $O/fused
$P --compare $O/graph/step0 $O/fused/step0
gpu-lock run --tag issue-3501 -- $P --model $M --op-diff $O/graph/step0 --out $O/opdiff
python3 scripts/fused_norm_normalizer_fit.py $M $O/opdiff/graph $O/opdiff/fused 1
```

`--dump-layers 11` instead of `0` gives the step-11 dumps and logits.
