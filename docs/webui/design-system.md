# WebUI design system contract

The WebUI is a browser application that follows the macOS 27 hierarchy without claiming native AppKit rendering. It uses system fonts, semantic tokens, shared React primitives and deterministic layout assertions so page work can compose the same shell instead of inventing page-local glass, spacing or color rules.

## Reference mapping

| Reference | Applied design decision |
|---|---|
| Apple Human Interface Guidelines, Materials: https://developer.apple.com/design/human-interface-guidelines/materials | Glass is reserved for navigation chrome, toolbar chrome and transient overlays; content cards, tables and forms use stable neutral surfaces for readability. The CSS fallback is opaque when `backdrop-filter` or reduced-transparency support is missing. |
| WWDC26 session 289, AppKit design updates: https://developer.apple.com/videos/play/wwdc2026/289/ | The sidebar reaches the shell edge on desktop, compact view uses an explicit off-canvas navigation sheet instead of a permanent miniature rail, active navigation uses semibold selection emphasis, and rounded cards/buttons use concentric radius tokens rather than unrelated corner sizes. |
| Apple design kits news for macOS 27: https://developer.apple.com/news/?id=e2lxw9l1 | The token set includes light, dark, high-contrast, tinted and opaque variants, plus explicit component states, matching the public design-kit emphasis on expanded component/state coverage. No Apple assets, SF Symbols or proprietary controls are bundled; the SVG icons in `webui/src/design-system/icons.tsx` are project-authored and licensed with this repository. |

## Tokens

Theme-independent tokens (spacing, radius, motion, focus ring) and the accessibility overrides live in `webui/src/design-system/tokens.css`, the glass intensity scale in `glass-intensity.css`, and every color, material and shadow value per theme under `webui/src/design-system/themes/` (see [Themes](#themes)). Pages must use these semantic names instead of hard-coded hex values: `--color-bg`, `--color-bg-elevated`, `--color-bg-neutral`, `--color-text`, `--color-muted`, `--color-separator`, `--color-focus`, `--color-selection`, `--color-warning`, `--color-error`, `--color-success`, `--material-glass-bg`, `--material-content-bg`, `--material-control-bg`, `--shadow-chrome`, `--shadow-card`, `--radius-*`, `--space-*` and `--motion-*`. Every shipped theme defines each of them; `src/design-system/theme-stylesheets.test.ts` fails when a stylesheet reads a custom property some theme leaves undefined.

`data-theme`, `data-theme-family`, `data-color-scheme`, `data-material`, `data-high-contrast`, `data-reduce-transparency`, `data-reduce-motion`, `data-backdrop-filter` and `data-glass-intensity` are the only supported appearance switches. The 0-100 glass intensity preference is represented by discrete CSS rules, not inline styles, so the CSP can continue to reject unsafe inline styles. High contrast is `system` by default, can be explicitly `on` or `off`, and overrides decorative transparency when enabled by either the browser preference or the explicit setting. The overrides are written with more specificity than the theme blocks, and the blur and saturation resets sit after the intensity steps, so an opaque material, reduced transparency, a browser without `backdrop-filter` or raised contrast wins over any intensity and any theme.

## Themes

The WebUI takes its theming from the `@lablup/ui-common` theme mechanism. The package's `base.css` declares the `--token-*` contract on `:root`, and a theme is a block of those tokens keyed on one `data-theme` value. `src/main.tsx` imports exactly one theme stylesheet, `design-system/themes/index.css`, directly after `base.css`, which is the package rule (at most one theme file alongside `base.css`, never imported by a component). No ui-common theme file is loaded: the package ships only its orange family, and its `base.css` leaves a product with its own identity to ship its own `[data-theme]` blocks.

`data-theme` always holds a family-scoped id, `<family>-<scheme>`:

| Family | Settings label | Ids | Notes |
|---|---|---|---|
| `mlxcel` (default) | Standard / 표준 | `mlxcel-light`, `mlxcel-dark` | The approved 4185 baseline. Its values moved from `tokens.css` and `common-tokens.css` into theme blocks unchanged. |
| `glass` | Glass / 글래스 | `glass-light`, `glass-dark` | Frosted glass in the macOS 27 language: translucent chrome with a top light reflection, tinted glass controls and highlighted button fills, near-opaque content surfaces. |

The stored preference is kept apart from the applied id. `mlxcel.webui.appearance` stores `themeFamily` and `colorScheme` (`system`, `light` or `dark`). `src/design-system/theme.ts` resolves `system` against the host scheme, and `applyAppearance` writes the id to `data-theme`, the family to `data-theme-family` and the raw preference to `data-color-scheme`, so `data-theme` never holds `system`, `light` or `dark` on its own. A `system` preference follows host changes live. Appearance saved before the family existed carried the scheme in a flat `theme` field and is still read as the color scheme.

Files: `themes/contract.css` binds the scheme-dependent half of the token contract (colors, shadows, button fills, focus color, tab surfaces) to the semantic tokens above for every shipped id; `themes/mlxcel.css` and `themes/glass.css` set the per-id values and any contract token a family styles differently; `common-tokens.css` keeps the theme-independent half (type scale, spacing, radius, control heights, motion, z-index) on `:root`, as ui-common's own `base.css` does.

The theme is applied before the first paint. `webui/public/theme-bootstrap.js` is a classic, render-blocking script in the `<head>` of `webui/index.html`; it reads the same storage key, resolves the id and writes the three theme attributes before the stylesheet paints or the app module runs, so a cold load never shows the wrong theme. It is an external file because the served CSP is `script-src 'self'`. `scripts/webui/build_bundle.py` refuses a bundle whose `index.html` lacks it, loads it after the app module or carries any inline script, and `src/design-system/theme-bootstrap.test.ts` runs the file against `applyAppearance` over stored-value and host-scheme combinations so the two cannot drift. It is the one script in the bundle without a content hash and revalidates like `index.html`.

The glass family reads only the existing switches. Glass intensity sizes the chrome blur, saturation and translucency. Buttons get a tinted translucent fill but no backdrop blur of their own, because they sit on transcript, table and form surfaces, which stay stable, and a blur layer per button would be repainted on every streamed token. `data-material="opaque"`, reduced transparency (setting or `prefers-reduced-transparency`), `data-backdrop-filter="unsupported"` and raised contrast (setting or `prefers-contrast: more`) turn every glass surface opaque and drop the button highlight, at any intensity. Reduced motion drops the press transform. The glass tokens live in this repository rather than in `@lablup/ui-common`: they are bound to this product's semantic token layer, which the package does not have, and proposing a glass family to the package is a separate decision for that package. The glass values derive from lablup/backend.ai-go's glass theme under Apache-2.0; see [NOTICE](../../NOTICE).

The product's own `.material-glass` chrome writes `-webkit-backdrop-filter` before `backdrop-filter`, because Lightning CSS, which minifies the bundle, keeps only the prefixed form when it follows the standard one, and Chromium and Firefox ignore that form; `theme-stylesheets.test.ts` keeps the order.

`pnpm --dir webui run check:theme-selectors` (`webui/scripts/check-theme-selectors.mjs`, run by the `webui-bundle` CI job and `make verify-webui-frontend`) is the gate that keeps this from rotting. It evaluates every `data-theme` and `data-theme-family` attribute selector in `webui/src`, `webui/public`, `webui/tests` and `index.html` against the ids `theme.ts` exports, whatever the operator, and fails on one that matches none, since such a rule compiles, renders and silently never applies. It also rejects `data-color-scheme` selectors (the raw preference), `@media (prefers-color-scheme)` in stylesheets and `prefers-color-scheme` queries in app code outside the resolver and the bootstrap (the host OS, not the applied theme), literal non-id values compared with or written to `data-theme`, theme stylesheet imports outside the single entry, and a shipped id with no theme block. A genuine host-OS concern keeps its query only with a written `theme-selector-allow: <reason>` on the same or the preceding line.

## Components

The user-requested [ui-common migration](ui-common.md) now centralizes available controls on pinned alpha.19 while retaining product tokens and native modal exceptions. That document defines the mandatory feature-page export seam and the new verification gates; historical4185 acceptance below does not certify rewritten component DOM.

`webui/src/design-system/primitives.tsx` exports the canonical Button, IconButton, Field, Select, StatusBadge, ProgressBar, EmptyState, ErrorBanner, Dialog, Sheet, Tooltip, Tabs, Inspector, DataTable, DenseList, AuthGate, LoginView and SchemaMismatchView. Use native `<select>` as the combobox baseline and native `<dialog>` through these wrappers as the single modal/sheet primitive so focus restoration and Escape behavior are consistent. LoginView is controlled by callbacks, keeps submitted tokens in component memory only and clears the field on submit, logout and unmount. The form and password field request `autocomplete="off"` as a browser hint; this does not guarantee that browsers or password-manager extensions will decline to save a credential. SchemaMismatchView exposes an explicit recovery callback. Do not add page-specific focus traps, alternate dialog implementations or second auth caches.

All controls expose visible focus, disabled and busy states, minimum 24 px targets with 32 px toolbar targets, and non-color-only state text. Long English/CJK labels must use `.truncate` with a `title` or another accessible full label. Progress uses explicit indeterminate semantics when total bytes are unknown rather than fabricated percentages. Lifecycle badges cover `unloaded`, `loading`, `ready`, `draining`, `unloading` and `failed` without implying a model is ready in placeholder screens.

## Shell and localization

`AppShell` defines the sidebar, top toolbar, content area and optional inspector. Primary navigation contains Models, Chat, Activity and Settings; the component gallery remains available as the direct `#gallery` artifact route and is listed in the command palette only while that route is already active. Cmd/Ctrl+K opens the command palette, `?` opens keyboard help, Escape closes the active dialog through the native dialog mechanism, and `[`/`]` move primary navigation only while the sidebar owns focus. Global shortcuts are suppressed inside edit controls, modal dialogs, IME composition and Alt-key chords. Compact widths below 960 px use an off-canvas sheet opened from the toolbar; no permanent mobile rail is rendered.

The production shell consumes the shared `WebUiProvider` snapshot and actions directly: LoginView submits through `actions.login`, logout uses `actions.logout`, and connection, catalog/operation freshness, selected model and schema recovery derive from the shared authority. It maintains no second session cache. Initial browsing makes no local API call before explicit login; authenticated route browsing does not load models or call inference endpoints. Models, Chat and Activity currently expose truthful staged guidance until their feature-page issues implement the workflows.

Every user-facing string has a typed key in `webui/src/i18n/catalog.ts` and a synchronized entry in `tests/fixtures/webui/strings.json` with English, Korean and a primary test ID. Locale-aware formatting helpers live beside the design system for bytes and tokens/s.

## Verification

The component gallery is available at `#gallery`. `pnpm --dir webui run unit` executes the activity-stream and theme-selector node:test specs (35 tests) and 448 Vitest tests across 43 files, covering the shared client/provider, shell and theme behavior. `pnpm --dir webui run browser` executes 62 Playwright tests, 63 with `MLXCEL_WEBUI_FONT_DIAGNOSTICS=1`: 21 layout and accessibility cases (14 gallery and 7 product-shell variants), seven further `browser.spec.ts` cases covering provider/mock-API journeys, keyboard/focus/shortcut behavior, production-selector compact reflow, contrast/reduced-motion/visibility behavior and backdrop-filter fallback, the Activity, Chat, Models and Settings route specs, and 23 `theme.spec.ts` cases covering the pre-mount theme, live host-scheme changes, the Settings theme controls, the unchanged mlxcel baseline and the glass intensity, transparency, contrast and motion rules. The variants in `webui/tests/browser-fixtures.ts` cover 390/1024/1440 widths, all four theme ids, tinted/opaque, high contrast and CJK labels. Each of the 21 cases runs axe with all violations rejected and asserts measured geometry: document and key-panel overflow, toolbar hiding above 960 px, 44 px compact hit targets, data-table column visibility, heading hierarchy across repeated tab remounts and progress/sample row alignment. No pixel baselines are committed. A baseline is specific to one renderer, font set and platform, so keeping one per platform required a hosted capture and a manual visual review on every font, Chromium or UI change, and it bought no assertion that the geometry checks do not already make. A failing case still writes its actual page image and a trace into `webui/test-results/`, which is git-ignored and uploaded as a CI artifact; run with `--headed` to watch a variant render. The CI job still pins `fonts-dejavu-core`, `fonts-dejavu-extra` and `fonts-wqy-zenhei` on Ubuntu 24.04, because the geometry assertions measure text and the CJK drawer variant needs a Korean face to lay out at all. The opt-in `MLXCEL_WEBUI_FONT_DIAGNOSTICS=1` test reports the fonts Chromium actually resolved, rather than trusting `fc-match` alone.

The text-scale case uses a test-only root attribute to enlarge text metrics to 200%; compact wrapping itself is implemented in production CSS, and a separate test checks it without text-scale layout selectors. These assertions cover document/key-panel overflow, full labels, visible compact focus and 44 px compact toolbar targets; they are not native browser zoom tests. Product-shell cases use explicit mock API responses, not a real backend session.

The [maintainer approved the revised 4185 design](https://github.com/lablup/mlxcel/issues/1843#issuecomment-5648012196) on 2026-09-13, superseding the rejected 4183/4184 visual direction.
