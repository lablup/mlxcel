# WebUI design system contract

The WebUI is a browser application that follows the macOS 27 hierarchy without claiming native AppKit rendering. It uses system fonts, semantic tokens, shared React primitives and deterministic layout assertions so page work can compose the same shell instead of inventing page-local glass, spacing or color rules.

## Reference mapping

| Reference | Applied design decision |
|---|---|
| Apple Human Interface Guidelines, Materials: https://developer.apple.com/design/human-interface-guidelines/materials | Glass is reserved for navigation chrome, toolbar chrome and transient overlays; content cards, tables and forms use stable neutral surfaces for readability. The CSS fallback is opaque when `backdrop-filter` or reduced-transparency support is missing. |
| WWDC26 session 289, AppKit design updates: https://developer.apple.com/videos/play/wwdc2026/289/ | The sidebar reaches the shell edge on desktop, compact view uses an explicit off-canvas navigation sheet instead of a permanent miniature rail, active navigation uses semibold selection emphasis, and rounded cards/buttons use concentric radius tokens rather than unrelated corner sizes. |
| Apple design kits news for macOS 27: https://developer.apple.com/news/?id=e2lxw9l1 | The token set includes light, dark, high-contrast, tinted and opaque variants, plus explicit component states, matching the public design-kit emphasis on expanded component/state coverage. No Apple assets, SF Symbols or proprietary controls are bundled; the SVG icons in `webui/src/design-system/icons.tsx` are project-authored and licensed with this repository. |

## Tokens

Colors are Astryx tokens, set per family by the product's Astryx themes (see [Themes](#themes)), so the product stylesheets and the Astryx and ui-common components read the same values. Pages use the Astryx names where a role exists: `--color-background-body` (page canvas), `--color-background-surface` (cards, tables, popovers, fields), `--color-background-muted` (recessed fills), `--color-text-primary`, `--color-text-secondary`, `--color-border`, `--color-text-accent` (links, focus, accent text), `--color-accent` (the solid primary fill), `--color-overlay-hover` (hover and selection tint), and `--color-warning`, `--color-error`, `--color-success` with their `-muted` backgrounds. Everything the product defines itself is named `--mx-*`: the spacing, radius, motion and focus-ring scale in `webui/src/design-system/tokens.css`, the glass intensity inputs in `glass-intensity.css`, and the materials, shadows and button fills per family in `themes/mlxcel.css` and `themes/glass.css` (`--mx-material-glass-bg`, `--mx-material-content-bg`, `--mx-material-control-bg`, `--mx-shadow-chrome`, `--mx-shadow-card`, `--mx-button-*`, `--mx-glass-*`). Hard-coded hex values stay out of page stylesheets. `src/design-system/theme-stylesheets.test.ts` fails when a stylesheet reads a custom property some family leaves undefined, or declares one that is neither `--mx-*` nor an Astryx token it overrides.

`data-theme`, `data-astryx-theme`, `data-theme-family`, `data-color-scheme`, `data-material`, `data-high-contrast`, `data-reduce-transparency`, `data-reduce-motion`, `data-backdrop-filter` and `data-glass-intensity` are the only supported appearance switches. The 0-100 glass intensity preference is represented by discrete CSS rules, not inline styles, so the CSP can continue to reject unsafe inline styles. High contrast is `system` by default, can be explicitly `on` or `off`, and overrides decorative transparency when enabled by either the browser preference or the explicit setting. The overrides are written with more specificity than the family rules, and the blur and saturation resets sit after the intensity steps, so an opaque material, reduced transparency, a browser without `backdrop-filter` or raised contrast wins over any intensity and any theme. High contrast also overrides two Astryx tokens (`--color-border`, `--color-overlay-hover`); the root Astryx `<Theme>` wrapper re-declares the theme's tokens, so it inherits those two from `<html>` instead.

## Themes

Each product family is an Astryx theme over the pre-built neutral theme that ui-common 0.2 wraps, pre-built with `astryx theme build` so nothing injects a `<style>` element at runtime (the served CSP is `style-src 'self'`; see [ui-common](ui-common.md#theme-and-stylesheets)):

| Family | Settings label | Astryx theme (`data-astryx-theme`) | Source | Notes |
|---|---|---|---|---|
| `mlxcel` (default) | Standard / 표준 | `mlxcel` | `themes/mlxcel.theme.ts` | The approved 4185 baseline. Its pre-#1903 values are the theme's tokens unchanged. |
| `glass` | Glass / 글래스 | `mlxcel-glass` | `themes/glass.theme.ts` | Frosted glass in the macOS 27 language: translucent chrome with a top light reflection, tinted glass controls and highlighted button fills, near-opaque content surfaces. |

`themes/palette.ts` maps a family's palette onto Astryx's roles (`--color-background-*`, `--color-text-*`, `--color-icon-*`, `--color-border`, `--color-accent*`, `--focus-outline-color`, `--color-overlay*`, the status colors and their `-muted` and `on-` pairs, and the neutral theme's own status fills), with `[light, dark]` pairs that the build turns into `light-dark()`, and sets the system font stack. The sources are plain configs extending the built `neutralTheme` (the CLI resolves them; its icon resolver only recognizes Astryx core's own `defineTheme` import, which the WebUI does not import). `pnpm --dir webui run build:themes` writes `themes/built/mlxcel.{css,js,d.ts}` and `themes/built/mlxcel-glass.{css,js,d.ts}`; `pnpm --dir webui run check:themes` (the `webui-bundle` CI job and `make verify-webui-frontend`) fails when they differ from a fresh build. Theme names are unique: `ASTRYX_THEME_NAMES` in `src/design-system/theme.ts` names them, and `theme.test.ts` checks the built modules carry those names and `__built`.

`src/main.tsx` imports exactly one theme stylesheet, `design-system/themes/index.css`, directly after the ui-common entry, and no component imports a theme file. It imports both built stylesheets, unlayered (they sit in Astryx's own `reset` and `astryx-theme` layers, scoped by `[data-astryx-theme="<name>"]`), so switching family changes one attribute and loads nothing; then `themes/mlxcel.css` and `themes/glass.css` in `@layer components`, which hold the product-only tokens with no Astryx role. `mlxcel.css` is the base on `:root` and `glass.css` overrides it under `[data-theme-family="glass"]`. Colors there use `light-dark()`; only a value whose geometry differs between schemes (the card shadow) is keyed on `data-theme="dark"`.

The document root carries three theme attributes, and all of them agree with what the root Astryx `<Theme>` writes, so nothing rewrites another's value:

- `data-theme` is the resolved scheme, `light` or `dark`: Astryx's own attribute, from which its theme CSS sets `color-scheme` (which `light-dark()` follows). It never holds `system`.
- `data-astryx-theme` is the family's Astryx theme name, which scopes the built theme CSS.
- `data-theme-family` is the product family, for the product-only rules.

The stored preference is kept apart from the applied values. `mlxcel.webui.appearance` stores `themeFamily` and `colorScheme` (`system`, `light` or `dark`). `src/design-system/theme.ts` resolves `system` against the host scheme, and `applyAppearance` writes `data-theme`, `data-astryx-theme`, `data-theme-family` and the raw preference to `data-color-scheme`. `App` renders `<Theme>` with the family's built theme and the resolved scheme, so its root sync writes the same `data-theme` and `data-astryx-theme`. A `system` preference follows host changes live. Appearance saved before the family existed carried the scheme in a flat `theme` field and is still read as the color scheme.

The theme is applied before the first paint. `webui/public/theme-bootstrap.js` is a classic, render-blocking script in the `<head>` of `webui/index.html`; it reads the same storage key, resolves the scheme and writes the four theme attributes before the stylesheet paints or the app module runs, so a cold load never shows the wrong theme. It is an external file because the served CSP is `script-src 'self'`. `scripts/webui/build_bundle.py` refuses a bundle whose `index.html` lacks it, loads it after the app module or carries any inline script, and `src/design-system/theme-bootstrap.test.ts` runs the file against `applyAppearance` over stored-value and host-scheme combinations so the two cannot drift. It is the one script in the bundle without a content hash and revalidates like `index.html`.

The glass family reads only the existing switches. Glass intensity sizes the chrome blur, saturation and translucency. Buttons get a tinted translucent fill, a translucent edge and a tinted shadow but no backdrop blur of their own, because they sit on transcript, table and form surfaces, which stay stable, and a blur layer per button would be repainted on every streamed token. `data-material="opaque"`, reduced transparency (setting or `prefers-reduced-transparency`), `data-backdrop-filter="unsupported"` and raised contrast (setting or `prefers-contrast: more`) turn every glass surface opaque and drop the button highlight, at any intensity. Reduced motion (setting or `prefers-reduced-motion`) drops the press transform in every family. The glass tokens live in this repository rather than in `@lablup/ui-common`: they are this product's materials, and proposing a glass family to the package is a separate decision for that package. The glass values derive from lablup/backend.ai-go's glass theme under Apache-2.0; see [NOTICE](../../NOTICE).

The product's own `.material-glass` chrome writes `-webkit-backdrop-filter` before `backdrop-filter`, because Lightning CSS, which minifies the bundle, keeps only the prefixed form when it follows the standard one, and Chromium and Firefox ignore that form; `theme-stylesheets.test.ts` keeps the order.

`pnpm --dir webui run check:theme-selectors` (`webui/scripts/check-theme-selectors.mjs`, run by the `webui-bundle` CI job and `make verify-webui-frontend`) is the gate that keeps this from rotting. It evaluates every `data-theme`, `data-astryx-theme` and `data-theme-family` attribute selector in `webui/src`, `webui/public`, `webui/tests` and `index.html` against the values `theme.ts` exports (the schemes, the Astryx theme names, the families), whatever the operator, and fails on one that matches none, since such a rule compiles, renders and silently never applies; the pre-Astryx `<family>-<scheme>` ids are the likeliest slip. It also rejects `data-color-scheme` selectors (the raw preference), `@media (prefers-color-scheme)` in stylesheets and `prefers-color-scheme` queries in app code outside the resolver and the bootstrap (the host OS, not the applied theme), literal values compared with or written to `data-theme` or `data-astryx-theme` that the app cannot write, theme stylesheet imports outside the single entry, and a family whose Astryx theme has no built stylesheet under `themes/`. A genuine host-OS concern keeps its query only with a written `theme-selector-allow: <reason>` on the same or the preceding line.

## Components

Controls are built on the pinned `@lablup/ui-common@0.2.0-alpha.19` (Astryx 0.7.0) through the adapter seam; the product keeps its own tokens, theme families, the native modal Dialog and the components with no package equivalent. [ui-common.md](ui-common.md) is the contract for that dependency: the version pins, the import rules, the component to adapter matrix, the remaining bridges, the CSP boundary and the bundle budget. The historical 4185 acceptance below does not certify the rewritten component DOM.

`webui/src/design-system/primitives.tsx` exports the canonical Button, IconButton, Field, Toggle, Select, StatusBadge, ProgressBar, EmptyState, ErrorBanner, Dialog, ConfirmDialog, Drawer, Tooltip, Tabs, Card, PageLayout, PageHeader, StatCard, LoadingStatus, SmoothHeight, Badge, Inspector, StaticTable, DataTable, DenseList, AuthGate, LoginView and SchemaMismatchView; the shell has its own seam (`common-app-shell.tsx`, see [Shell and localization](#shell-and-localization)). The [ui-common matrix](ui-common.md#component-to-adapter-matrix) names the shared component behind each adapter and the bridges each one needs. Native `<dialog>` through `Dialog` is the single modal-dialog primitive, and the shared `Drawer` (also a native modal dialog) is used below 1100 px for the Models inspector and for Chat's sheets; the compact navigation sheet is AppShell's MobileNav. All of them keep a focus trap, Escape close through Astryx's layer stack and focus restoration to the opener. LoginView is controlled by callbacks, keeps submitted tokens in component memory only and clears the field on submit, logout and unmount. The form and password field request `autocomplete="off"` as a browser hint; this does not guarantee that browsers or password-manager extensions will decline to save a credential. SchemaMismatchView exposes an explicit recovery callback. Do not add page-specific focus traps, alternate dialog implementations or second auth caches.

All controls expose visible focus, disabled and busy states, minimum 24 px targets with 32 px toolbar targets, and non-color-only state text. Long English/CJK labels must use `.truncate` with a `title` or another accessible full label. Progress uses explicit indeterminate semantics when total bytes are unknown rather than fabricated percentages. Lifecycle badges cover `unloaded`, `loading`, `ready`, `draining`, `unloading` and `failed` without implying a model is ready in placeholder screens.

## Shell and localization

`AppShell` (`webui/src/design-system/shell.tsx`) defines the application bar, primary navigation, content column (the shared PageLayout) and optional inspector, composed on ui-common's `AppShell` through the `common-app-shell.tsx` seam: AppShell owns the skip link ("Skip to content" / "본문으로 건너뛰기" from the Astryx catalog, the first focus stop, moving focus to the main landmark), the banner landmark around the bar, the `role="main"` content landmark, the sticky bar and side navigation (`height="auto"`, so the page scrolls) and the compact drawer. The bar sits in AppShell's `topNav` slot as the product's own row (menu toggle, the mx mark, title and subtitle, loaded models, session, command palette and help); it is not a ui-common `TopNav`, which renders a navigation landmark and, below the breakpoint, keeps only its heading and end content on one row. Primary navigation is a ui-common `SideNav` named "Primary navigation" with one `SideNavItem` link per route (`aria-current="page"` on the current one) and the connection footer in its footer slot; the route content sits in an unnamed `<section>`, so the PageHeader's `<header>` is not read as a second banner inside the `role="main"` div. App hands it plain data (`loadedModels` as `ShellLoadedModel` records and a `connection` summary) plus callbacks, so the shell imports neither the provider nor the catalog. Primary navigation contains Models, Chat, Activity and Settings. The component gallery is a direct `#gallery` artifact route only; it is in neither the navigation nor the command palette.

The toolbar names the models the server holds, from `loadedModels(snapshot)` in `webui/src/provider-surfaces.tsx`: entries in `ready`, `loading`, `draining` or `unloading`, ready first, then by display name. It never shows the browser's selection, which stays visible only in the Chat model picker and the Settings target. The region shows a count, up to `TOOLBAR_CHIP_LIMIT` (3) one-line chips with the truncated name and an inline lifecycle status (its dot and label, no pill), and a "+n" chip that opens the command palette; with nothing loaded it says "No model loaded". `AppShell.loadedModels` is `null` when the loaded models are not known, and the region then says "Loaded models unknown" instead: App passes `null` until an authenticated session holds a catalog snapshot, which covers signed out, the window before the first catalog page and the reset after a server restart, so the toolbar never claims that nothing is loaded on a server it has not read. On a desktop toolbar short of room the chips share it equally; each stays on one line, its name truncating down to 2rem while the status keeps its dot and whole label. Below 1024 px the region is a toolbar row of its own that scrolls sideways inside itself instead of wrapping: chips keep their width up to `min(14rem, 80%)` with truncated names, so the sticky toolbar stays two rows high (title, chips) however many models are loaded, and three below 320 px (title, actions, chips). A chip reached with Tab is scrolled fully into view, since Chromium leaves an element that is already partly visible where it is. The full name stays in the chip's `title` and the state in its accessible name. A chip selects the model and opens its inspector on Models, or opens Models with no inspector if the model has left the catalog; it never loads or unloads. Opening the model that is already selected dispatches no selection (`modelSelectionFor` in `provider-surfaces.tsx` computes the target), because a selection change restarts observation and clears the runtime history. Chips take their accessible name from their visible text and carry no `aria-label`. The sidebar footer reads `{mode} · {status} · v{version}`, where `{mode}` is the localized name of the bootstrap server mode from `serverModeLabel` ("Multi-model", "Multi-model, no models", "Single model", or the generic "Server" for a mode the bundle does not know), never the raw `router_pool` identifier; the provider summary (backend, build, phase, catalog and operation counts, snapshot), the server instance id and the event sequence appear only inside a collapsed "Connection details" disclosure under it.

Every route renders exactly one `PageHeader` as the first child of the shell's PageLayout, with the route's actions in its action slot and the route's stale or action error in its error slot. The adapter always makes that h1 the route's dialog focus fallback (`tabIndex=-1` and `data-dialog-focus-fallback`), so each route has exactly one fallback and `restoreModalFocus` lands on a named heading when a dialog closes after its opener is gone. Routes do not hand-roll headings, eyebrow lines or heading button rows.

The command palette (`webui/src/command-palette.tsx`) opens with an empty query. Its Commands section lists the four routes and "New conversation", matched on the localized label or the route id, so Korean input finds them too. Its Models section lists the loaded models while the query is empty, and otherwise the catalog entries whose display name or id contains the query (`paletteModelMatches`: case-insensitive, loaded first, at most 20). Selecting a model does what a chip does; the palette has no way to load a model.

`globalShortcuts` in `shell.tsx` is the single source for the keyboard help dialog, so the list cannot drift from the handlers: Cmd/Ctrl+K, Cmd/Ctrl+N, Cmd/Ctrl+Enter, Esc, `[`/`]` and `?`. The shell handles Cmd/Ctrl+K (palette), `?` (help) and Cmd/Ctrl+N, which opens Chat and, when Chat is available, raises `requestNewConversation()` in `features/chat/session.ts`; Chat consumes that request once on mount or on change and runs its own guarded `create()`. Escape closes the active dialog or the navigation drawer through the native dialog mechanism and Astryx's layer stack, with focus back on the opener, and `[`/`]` move primary navigation only while the side navigation or the drawer owns focus. Global shortcuts are suppressed inside edit controls, modal dialogs, the open navigation drawer, IME composition and Alt-key chords; the chat composer handles Cmd/Ctrl+Enter and Cmd/Ctrl+N itself outside composition. Below 1024 px (AppShell's `lg` breakpoint, switching to the wide layout at equality) the side navigation is not rendered; the same SideNav renders as ui-common's MobileNav drawer from the start edge, opened by AppShell's `MobileNavToggle` in the bar ("Open navigation", 44 px), titled "Primary navigation", with the mx mark above the routes and the connection footer below them. It is a native modal dialog: MobileNav focuses its sheet on open (the close button is the first Tab stop), the page behind it is inert, Escape or a route closes it and focus returns to the toggle. Widening past the breakpoint while it is open unmounts it and moves focus to the current route in the side navigation. No permanent mobile rail is rendered. Below 320 px the layout holds down to 195 CSS px; see the [layout floor](ux-contract.md#visual-and-viewport-contract).

The production shell consumes the shared `WebUiProvider` snapshot and actions directly: LoginView submits through `actions.login`, logout uses `actions.logout`, and connection, catalog/operation freshness, selected model and schema recovery derive from the shared authority. It maintains no second session cache. Initial browsing makes no local API call before explicit login; authenticated route browsing does not load models or call inference endpoints. Models, Chat and Activity currently expose truthful staged guidance until their feature-page issues implement the workflows.

Every user-facing string has a typed key in `webui/src/i18n/catalog.ts` and a synchronized entry in `tests/fixtures/webui/strings.json` with English, Korean and a primary test ID. The strings Astryx and ui-common components render themselves (loading announcements, skip link, navigation, sort, close and tab-strip labels) come from their own catalogs in the same appearance locale, Korean as a lazy chunk; see [ui-common.md](ui-common.md#localization-of-library-strings). Locale-aware formatting helpers live beside the design system for bytes and tokens/s.

## Verification

The component gallery is available at `#gallery`. `pnpm --dir webui run unit` runs the node:test specs for the activity stream, the activity performance diagnostics and the theme-selector gate, then the Vitest suite: the shared client and provider, shell, theme and appearance behavior, the shared-component adapters (`src/design-system/ui-common-*.test.tsx`, `common-adapters.test.tsx`), the library strings in both locales, and the feature screens. `pnpm --dir webui run browser` runs the Chromium Playwright suite: the gallery and product-shell layout and accessibility variants and provider/mock-API journeys in `browser.spec.ts`, the Activity, Chat, Models and Settings route specs, the shell layout floor, loaded-model chips and palette search in `shell.spec.ts`, the shared-component specs `ui-common-components.spec.ts` and `ui-common-shell.spec.ts`, and the theme specs in `theme.spec.ts` (pre-mount theme, live host-scheme changes, the Settings controls, the mlxcel baseline and the glass intensity, transparency, contrast and motion rules); `MLXCEL_WEBUI_FONT_DIAGNOSTICS=1` adds a font report. The runner prints the counts; they are not restated here. The variants in `webui/tests/browser-fixtures.ts` cover 390/1024/1440 widths, both families in both schemes, tinted/opaque, high contrast and CJK labels. Each layout case runs axe with all violations rejected and asserts measured geometry: document and key-panel overflow, the menu toggle hidden at and above 1024 px, 44 px compact hit targets, data-table column visibility, heading hierarchy across repeated tab remounts, progress/sample row alignment and the CSSOM allowlist for `style` attributes. No pixel baselines are committed. A baseline is specific to one renderer, font set and platform, so keeping one per platform required a hosted capture and a manual visual review on every font, Chromium or UI change, and it bought no assertion that the geometry checks do not already make. A failing case still writes its actual page image and a trace into `webui/test-results/`, which is git-ignored and uploaded as a CI artifact; run with `--headed` to watch a variant render. The CI job still pins `fonts-dejavu-core`, `fonts-dejavu-extra` and `fonts-wqy-zenhei` on Ubuntu 24.04, because the geometry assertions measure text and the CJK drawer variant needs a Korean face to lay out at all. The opt-in `MLXCEL_WEBUI_FONT_DIAGNOSTICS=1` test reports the fonts Chromium actually resolved, rather than trusting `fc-match` alone.

The text-scale case uses a test-only root attribute to enlarge text metrics to 200%; compact wrapping itself is implemented in production CSS, and a separate test checks it without text-scale layout selectors. These assertions cover document/key-panel overflow, full labels, visible compact focus and 44 px compact toolbar targets; they are not native browser zoom tests. Product-shell cases use explicit mock API responses, not a real backend session.

The [maintainer approved the revised 4185 design](https://github.com/lablup/mlxcel/issues/1843#issuecomment-5648012196) on 2026-09-13, superseding the rejected 4183/4184 visual direction. The approved source digest is `c4df0326df35998f03e315ab1382867150bb20b3ad516aebe184e722cbf20748`; the deterministic embedded asset-tree digest is `abb41bf0eb305acbc21291249afd7ac558b2d341382686dd705a1d1f5cf3fde0`. Shared design approval is confirmed, and the [targeted manual recheck is recorded as user-reported PASS](https://github.com/lablup/mlxcel/issues/1843#issuecomment-5653425099); it remains separate from automated evidence.

## Manual Safari and VoiceOver checklist

The maintainer explicitly accepted the revised immutable 4185 candidate in direct replies to the design question and the targeted Safari/VoiceOver/native-200%-zoom question. The [acceptance ledger](https://github.com/lablup/mlxcel/issues/1843#issuecomment-5653425099) records USER-REPORTED PASS for the changed toolbar, compact menu, Cmd+K Tab/Escape focus handling and native browser zoom. This supplements the older cb489/4184 report; it is not an independent browser observation or acceptance of future revisions. Central integration gates remain open in order #1838 → #1841 → #1843, so the issue and PR remain in review. The checklist below is retained for future regressions, not as an unanswered request.

Use `pnpm --dir webui run build && pnpm --dir webui exec vite preview --host 127.0.0.1 --port 4173`, open `http://127.0.0.1:4173/#gallery` in Safari on macOS 27, then verify: VoiceOver announces the primary navigation, selected route, command dialog title, mobile navigation sheet title, shared select combobox and its list, dialog close button, status badges and schema/authentication views; Tab and Shift-Tab traverse visible controls in order; Escape closes the command, sheet and confirmation dialogs with focus restored to the opener; browser zoom at 200% has no horizontal page scroll at 390 px; high-contrast and reduced-transparency preferences keep content readable over the worst-case tinted background.
