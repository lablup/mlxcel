# ADR 0009: The engine step API and the batch-of-one rule

**Status:** Accepted (2026-10-07). Epic #2166 Phase 4b (issue #2172). Amends [ADR 0007](0007-unified-batch-native-engine.md): it settles the signatures the "Engine" row of the component table left to this phase and records how "a single sequence is a `StepBatch` of one" is implemented. ADR 0007's decision table stands unchanged. Amended by #2176 (Phase 6): the raw-completion client and the token-only speculative entries, recorded in the "Raw completion" section below. Amended by #2229: the split forward and per-row draw (`submit_forward`, `draw_row`) behind the raw-completion client's per-row pipeline.

## Context

ADR 0007 fixed the names `Engine`, `SequenceSpec`, `SequenceId`, `open`, `prefill`, `step` and `close` and deferred their signatures to the phase that introduces them. `BatchScheduler` ran model forwards, sampler draws and the finish step itself at nine sites, with the single-sequence path (`LanguageModel::forward`) and the batched path (then `forward_batched_with_context_and_ids`, now `forward_batched_with_ids`) reached from different scheduler functions. The issue body also proposed making `LanguageModel::forward` a provided method that delegates to the batched entry with one row.

## Decision

### Signatures

`mlxcel_core::engine::Engine<M: LanguageModel>` owns the model and the `CachePool`. The scheduler holds one and reaches the model and the pool only through `model()`, `pool()`, `pool_mut()` and `parts_mut()` for capability queries, snapshot and restore hooks, admission accounting, prompt-cache detach and handoff; every forward and every sampler draw goes through the entries below. The model is only ever handed out shared (`&M`), but `LanguageModel::forward` takes `&self`, so the type does not stop a raw forward: the acceptance grep and the `prefill_span_coverage_tests` source guard do. `parts_mut()` stays for the disaggregated handoff restore, which lives in the root crate (`distributed::disaggregated::handoff_impl`) and so cannot become an engine method in the core.

| Entry | Signature | Notes |
|---|---|---|
| open | `open(SequenceSpec { layout_override: Option<SequenceStateLayout> }) -> Result<SequenceId, EngineError>` | Pool allocation plus `prepare_sequence_state`. `adopt(DetachedCacheSet)` / `adopt_paged(DetachedPagedCacheSet)` open a sequence over a prompt-cache entry. |
| prefill | `prefill(&PrefillStep { seq_id, input, embeddings, mask, last_pos, trim_excess, eval }) -> Result<PrefillOutcome { logits, eval, trim }, EngineError>` | One `PrefillPlan` piece per call, so chunked prefill interleaves with decode. The forced eval and the pad trim are reported separately so the caller records the eval against its backend health counter before acting on the trim. `prefill_cohort(&[SequenceId], input, mask)` is the padded batched window and `trim_padding(SequenceId, excess)` drops a cohort row's pad positions afterwards (`EngineError::Trim` on failure); `complete_prefill(&logits, &mut StepRow<H>) -> RowOutcome` samples and finishes the first token. `piece_input` builds a piece's input and padded mask, shared by the scheduler and `DirectEngine`. |
| step | `step(&StepBatch { seq_ids, input }, &mut [StepRow<'_, H>]) -> Result<StepOutput { rows: Vec<RowOutcome> }, EngineError>` | The one decode entry for every row count. `StepRow` carries the row's `RowSampler`, `SamplingConfig`, token history, generated stream, EOS set, `max_tokens`, `LogprobsConfig` and an `H: StepRowHooks` (logit mask, token override, matcher, first-token stamp, logprob payload hand-off, plus the `FinishHooks` half). A batch of one always runs the per-row chain: mask, draw, `try_eval`, override, logprobs, matcher, first-token stamp, `finish_step`. A larger batch takes the fused `[B, vocab] -> [B]` draw when every row is fused-eligible and shares its parameters (`shared_fused_params`, the one rule the scheduler's lookahead gate also calls), evaluates the `[B]` tokens through `try_eval`, and fails every row with one shared `RowError::BatchEval` when that throws or when the readback does not hold one token per row; otherwise it runs the per-row chain for each row, where a throw fails only that row with `RowError::Eval`. A `rows` slice whose length differs from `seq_ids` is refused with `EngineError::Batch` before the forward. Rows that continue advance their pool offset. |
| submit / submit_forward / draw_row / finish_rows | `submit(&StepBatch, &FusedSampleParams, &[&TokenBiasMap]) -> Result<UniquePtr<MlxArray>, EngineError>`; `finish_rows(&[i32], &mut [StepRow<'_, H>]) -> Vec<RowOutcome>` | The split form the lookahead pipeline needs: the speculative forward runs inside `DecodeLookaheadAppendScope`, the fused draw is scheduled with `async_eval` and returned as lazy device tokens; the collect half finishes each row once the tokens are on the host, and a token count that differs from the row count fails every row with `RowError::BatchEval` and advances none. `submit_forward(&StepBatch)` is the same speculative forward without a draw, returning the lazy logits, and `draw_row(&MlxArray, &mut StepRow<'_, H>)` builds one row's per-row-chain draw from them once its previous token is committed, scheduled and returned as the lazy `[1]` token; it refuses a row with a mask, override or logprobs payload (`EngineError::Batch`). `unwind_appends(SequenceId, n)` undoes up to `DECODE_LOOKAHEAD_MAX_SPECULATIVE_APPENDS` positions through the pool trim or `rewind_decode_appends`. |
| close | `close(SequenceId) -> ClosedSequence { id, was_open }` | Releases the model's per-sequence state and the pool entry. |

Errors are per row. `EngineError` (`MissingSequence`, `Batch`, `Open`, `Trim`, `Rewind`, `Eval`) names the sequence it concerns; `RowOutcome.error` (`RowError::Structured`, `RowError::Eval`, `RowError::BatchEval`) marks a failure inside a batch, and the scheduler finishes each failed row with `FinishReason::Error` and no neighbour (#822). An eval failure reaches the client with the wording every eval site uses (`inference backend error: {mlx}`). A per-row `RowError::Eval` is one eval and bumps the backend health counter once per failed row. The rows of one fused draw share a single `RowError::BatchEval`: it is one eval over many rows, so `apply_row_outcomes` records it once for the slice and aborts every row carrying it with that one message, which keeps one transient throw on a wide batch from exhausting `MAX_CONSECUTIVE_EVAL_FAILURES` and stopping the scheduler. `RowOutcome::eval_ok` is false for both eval variants. `EngineError::Eval` is the pipelined `submit`'s schedule failure, which the lookahead records and unwinds before it falls back to the synchronous step. A failed `unwind_appends` is the row-only error that overrides a `Length` or `Stop` recorded on the same tick so the desynchronized state is not donated (#2182).

### A single row equals a batch of one, at the engine

`Engine::step` is the only decode entry for every `B`; the scheduler's synchronous single and batched paths both call it (`run_engine_step`). Inside, `B = 1` runs the family's single-row forward (`forward_with_sequence_id`), which is what the provided `forward_batched` does at `b == 1` and what the measured B=1 throughput rests on, and samples through the per-row chain the single-sequence decode always used; `B > 1` runs `forward_batched_with_ids`.

The trait shape is unchanged: `LanguageModel::forward` stays the required method and the batched entries stay provided methods with per-family overrides. Inverting the required method (a provided `forward` delegating to a required batched entry) is a mechanical change across more than 200 `LanguageModel` implementations, about 40 of which override a batched entry, and buys nothing the engine-level single entry does not already give: no caller other than the engine chooses between the two forwards. Instead, the equivalence the issue's criterion wants is pinned where it can be violated: `src/models/single_row_batch_parity_tests.rs` runs, on a real checkpoint under `MLXCEL_SDPA_DETERMINISTIC=1`, the single-row forward and the one-row batched forward of every locally available family that overrides the batched entry (Qwen3, Llama 3) and requires byte-identical logits at each of four decode steps, both without sequence ids and with a distinct `SequenceId` per cache set, the form `Engine::step` passes. A family whose one-row batched path ever differs makes its `b == 1` delegate to the single-row forward.

## Raw completion (Phase 6, #2176)

ADR 0007's "Raw completion" row is implemented by `mlxcel_core::engine::DirectEngine<M>`, promoted from the parity harness's `d:engine` probe: one sequence through `open`, the prefill plan's pieces through `prefill`, `complete_prefill`, `step` until the finish step, `close`. It carries the request's KV mode and its token bias. The order on every `open` is fixed: the resolved per-layer table (with the Boundary-V upgrade) is injected into a model-owned family first, since `prepare_sequence_state` builds the sequence's caches from the modes the model holds at that moment (the scheduler injects once at configuration time); then `Engine::open`; then the same table is applied to the pool's own caches, which the pool allocates in `Fp16`. The `[TTFT]` line (`MLXCEL_PROFILE_TTFT`) is opt-in per client (`DirectEngine::with_ttft_report`): `mlxcel generate --profile` and `mlxcel-bench-decode`'s measured pass set it, their warmups do not, so a warmup run never prints a cold line of its own. The client borrows the model: `LanguageModel` is implemented for `&M`, so `Engine<&M>` runs over a model the caller keeps. `mlxcel generate` (text and VLM embeddings, `--profile`), `MlxInferenceSession`, `mlxcel-bench-decode`, `mlxcel-bench-engine`'s CLI arm, `speculative_bench`'s baseline and the harness's `a:cli` and `d:engine` arms all call it; `CxxGenerator` and its four loops are gone, and `evaluate_loglikelihoods` is `Engine::score`, a prefill-only pass that returns the whole window's logits.

Two further engine entries serve a token-only drafter: `Engine::verify` forwards the current token and a proposed block as speculative appends (inside `DecodeLookaheadAppendScope`) and returns every position's logits, and `Engine::commit_appends` keeps the accepted prefix after `unwind_appends` drops the rest. `DirectEngine::generate_with_drafter` is the round loop over them; prompt lookup is such a drafter (`speculative::prompt_lookup_drafter::PromptLookupDrafter`, `Drafter::drafts_from_tokens_only`), so `--prompt-lookup` decodes on the engine and the scheduler can offer the same drafter through the same entries. The classic draft-model `SpeculativeGenerator` is deprecated for removal in the next minor release.

After its first token the client decodes on the lookahead pipeline whenever the scheduler's rules admit the sequence, overlapping step n+1's forward with step n's host read as the retired loop did: each iteration submits the next forward fed by the still-unread device tokens (`submit`, `lookahead_feedback_input`), reads the current token and commits it (`finish_rows`). A finishing token (EOS or stop id, length, repetition loop) or a callback stop leaves exactly one speculative append, which `unwind_appends` drops, so the stream, the pool offset and the KV state equal the synchronous loop's; no forward is submitted after the token that spends the budget, and a zero budget runs no forward at all. The two eligibility rules are the scheduler's own, shared through the engine: `shared_fused_params` (fused-eligible sampling: no repetition, frequency or presence penalty, no DRY, no mask, override or per-token logprobs, and no mirostat or adaptive-p feedback state, so the host token is never needed before the next forward; a request with any of those takes the per-row pipeline described below) and `Engine::can_unwind_lookahead` (a dense or pool-backed paged tail, or a model-owned family that rewinds its own state, keyed on the natural backend). The pipeline's teardown is `Teardown::Unwind` under that exact rule. The client also pipelines a model-owned family that cannot rewind its own state (`Teardown::Discard`), as the retired loop pipelined every family: every caller closes the sequence right after the decode, so the one append past the finishing token is released with it rather than unwound (the stream is the synchronous loop's), and a failed submit that left an append in place ends that run with the submit's error instead of falling back; the scheduler and the drafter loop keep the exact rule, since their sequences outlive the append. A request the fused rule turns away (history penalties, DRY, mirostat, adaptive-p, the extended chain) decodes on the per-row pipeline instead (#2229), as the retired loop's `sample_next_step` did: each iteration submits the forward fed by the still-unread per-row draw (`submit_forward`, the same speculative forward without a draw), reads that draw and commits it (`finish_rows`, which pushes it to the penalty history), and only then builds the next draw from the submitted logits (`draw_row`, `RowSampler::draw_and_accept` with the token bias in its chain position). The draw for t+1 sees the same logits, history and sampler state as the synchronous step's and forwards consume no randomness, so greedy and seeded streams equal the synchronous loop's token for token. Its admission and teardown are the fused pipeline's (`Teardown::Unwind` or `Teardown::Discard`); `draw_row` refuses a row with a logit mask, token override or logprobs payload, which the client never carries, and the B9 pre-bias counters (`lang_bias_counters`), which read the pre-bias argmax on the host at every draw, keep a request synchronous. The scheduler's lookahead stays fused-only. `MLXCEL_FORCE_SYNC` (`engine::force_sync_requested`, probed once per client) and `DirectEngine::with_force_sync` keep every step synchronous, and every other request takes the synchronous `step`. The raised command-buffer input budget (`DecodeCommandBufferBudget`, Apple Silicon only) is held around the pipelined steps alone, never around prefill, the synchronous chain or a verify block, because a synchronous step encodes and then waits and loses the encode / execute overlap under the larger budget; the scheduler applies the same rule in `run_decode_tick`. Loop detection stays on the pipeline here, because the finish step runs on every committed token; the scheduler excludes it only because its steady tick skips that scan. The state machines are not shared: the scheduler's tears the pipeline down on admission, preemption and membership changes and re-runs a finishing tick through its synchronous path so completion and prompt-cache donation see clean caches, none of which an in-call single sequence has. With a stochastic sampler the pipelined fused draw and the synchronous per-row draw consume the RNG differently (the per-row pipeline's draw is the synchronous one, so it does not), so a seeded run's tokens depend on the path, as they do between the server's B=1 sync and lookahead ticks. The drafter loop pipelines its plain rounds the same way once the drafter asks for it (`Drafter::pipelines_plain_rounds`; prompt lookup after more than two rounds without a proposal, or at once while a gated governor is paused); a proposal found while a step is in flight is retracted (`Drafter::retract_draft`) and looked up again from the in-flight token, which the next round verifies synchronously. The drafter loop holds the raised command-buffer budget only while such a plain round is in flight. It refuses a sampler with feedback state (mirostat, adaptive-p), which a verify block cannot replay, and a sequence whose caches cannot trim a rejected block. A greedy request with no history penalty, DRY or token bias decides every verify position from one batched argmax and one host read; a request with a penalty, DRY or bias samples each position in order through the per-row chain. A verify block that ends on an EOS commits only the positions before it, as the synchronous step does not advance the pool offset for the EOS token, and a model whose verify or scoring forward returns logits of another rank or too few positions fails the run with an error instead of indexing past them.

## Consequences

- The scheduler keeps admission, tick policy (ADR 0005), preemption, prompt-cache lookup, donate and adopt, disaggregated handoff and the speculative burst generators. The MTP and DFlash burst adapters (`server::batch::speculative_burst`, `dflash_target`) still run their target and draft forwards themselves, outside the engine, as the issue scoped them; moving them behind an engine entry is later work; `rg '\.forward[a-z_]*\(|sample_token_[a-z_]*\(' src/server/batch/scheduler --glob '!*_tests.rs'` returns only `PrefillPlan::forwarded_len()` accessors, and no `RowSampler::draw` or `fused_sample` call. The `prefill_span_coverage_tests` source guard classifies the engine entries instead of raw forwards.
- `mlxcel-engine-parity` gains arm (d), a direct `Engine` B=1 run through `engine_probe::engine_direct::DirectEngine`, compared against the server's dense B=1 arm; a divergence there is scheduler policy, not engine execution.
- Phase 5 (#2173) was planned here to give the CLI a `StepRowHooks` of its own and drive `Engine` the way `DirectEngine` does. It followed ADR 0007's "CLI front end" row instead: `mlxcel run` starts the server worker in-process (`server::in_process::InProcessServer`) and submits requests through `ModelProvider`, so the CLI reaches `Engine` through the scheduler at one slot and shares the request path (template render, option build, `StreamFilter`, prompt cache) as well as the engine. `DirectEngine` stays the probe that separates scheduler policy from engine execution.
- The ADR 0008 deferral is closed. The model-owned families attend through their own caches: `KvAttention` (`src/lib/mlxcel-core/src/cache/attend.rs`) is the per-storage entry, implemented by `KVCache`, the new `RotatingKVCache::attend` and `ChunkedKVCache::attend`, and by Gemma 3's `Cache` and Llama 4's `Llama4Cache` by matching to the inner cache; `cache::attend_batched_rows` is the per-row batched loop every non-pooled batch takes, and `attend_batched` hands its declined and dense batches to it. `RotatingKVCache::attend` writes through `update_and_fetch`, so a single-token write inside `DecodeLookaheadAppendScope` is logged with the rows it overwrote and a multi-token append clears the log exactly as before (`cache::attend::attend_tests` pins both; `cache::decode_undo` and `scheduler_model_owned_lookahead_tests` are unchanged and green). `rg 'is_paged_backed\(\)|is_paged_decode\(\)' src/models` returns nothing; `gemma4_verify_rows` asks `KVCache::is_dense_fp16()` instead, a layout question, not a kernel choice.
- `DecodeBatchContext` and the core `DecodeStorageBackend` are gone, not kept for non-model code: the engine's `StepBatch` carried it only to hand it to the model, the scheduler built it only for that, and no counter read it. The trait entry is `forward_batched_with_ids(input_ids, seq_ids, batch_caches, mask)`; `forward_batched_with_context` is folded into `forward_batched`, which the VLM wrappers already delegated. Storage is decided once, where `CachePool` wires the sequence's caches (ADR 0008), and the model-owned families' state is never pool-backed, so they take the dense rows of the ADR 0008 table on either backend.
- Routes that changed op order, listed as #2210 listed its own: (1) Gemma 3 and Llama 4 on the paged backend no longer run the dense-pointer `paged_decode_attention_dense_compat` / `_rotating_compat` kernels, which were per-row C++ loops of block slices, a concat and one SDPA per row; the per-row `attend` loop is the same attention without the block concat, not bit-identical to it. (2) A Gemma 3 global layer in any Turbo mode with a dequant-first or compressed decode variant (Turbo4Asym; Turbo4Delegated, whose compressed route is on by default; sparse-V behind its environment gates, for example a Turbo4Asym layer under `MLXCEL_TURBO4_ASYM_DEQUANT_SDPA=0` with a sparse-V threshold, which is the lossy route), and a Turbo-mode Llama 4 dense layer, decode through the variant `KVCache::attend` selects (ADR 0002) instead of `update_and_fetch` followed by SDPA; the dequant-first variants are the same exact math in a different op order. FP16 and Int8 global layers and every sliding layer run the exact ops they ran (`models::gemma3::cache_attend_entry`, `models::llama4::cache_attend_entry` pin FP16, Int8 and sliding Turbo4Asym bit for bit, prefill and wrapped or front-trimmed decode, and pin the Gemma 3 Turbo4Delegated decode to `update_and_turbo4_delegated_attention`). (3) Llama 4's RoPE layers (3 of every 4) run the whole block batched on the dense backend too: Q/K/V and output projections, the residuals, the post-attention norm and the MoE feed-forward run once for the batch (`forward_batched_decode_llama4`; before #2172 the dense backend ran every row through the single-row block). The per-row attention is unchanged. On a real checkpoint, `scheduler_real_batch_parity_tests` (ignored; gemma-3-1b-it-4bit, `MLXCEL_SDPA_DETERMINISTIC=1`) runs two concurrent greedy requests through the server scheduler, 47 of 47 decode ticks at B=2, and gets the token streams each request produces alone, on the paged and the dense backend. No Llama 4 checkpoint is local, so its batched route is pinned only by the synthetic `models::llama4::batched_decode_entry` test (1e-3). The dense-compat kernels and their metadata builders remain in the core as the reference pair `ffi_tests` pins and can be removed in a follow-up; `examples/profile_paged_decode_kernel.rs` and `scripts/benchmark_paged_decode_rollout.sh`, which compared the two through the removed context, are gone.
- Open follow-up: Gemma 3 and Llama 4 still report `supports_paged_decode_backend() == true`, so `--decode-storage-backend auto` resolves to paged for them and they pay the pool allocation and the per-step `sync_sequence_storage` shadow accounting, although no attention path reads the pool any more. Whether they should resolve to dense is a throughput decision left to the epic's end-of-run measurement, not changed here.
