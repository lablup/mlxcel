# PR #2955: Per-bucket `QMV4_MAX_B` compilation for the ragged native GEMV

**Date**: 2026-11-11
**Status**: Completed (draft PR; closes #2955)

## Executive Summary

The `B=4` ragged decode loss in #2933 came from the compile bound, not from predication or the dispatch shape. Every multi-row export in `csrc/qmv4.hip` unrolls `QMV4_MAX_B` accumulators, and the ragged loader compiled the one artifact with `QMV4_MAX_B=8` and reused it for both bundled buckets. A `B=4` step therefore carried the instruction stream, register allocation and 1 KiB shared-memory reduction buffer of `B=8` while half of its accumulator lanes were dead.

The loader now compiles one HSACO per bucket with `-DQMV4_MAX_B=<bucket>` and reuses the default artifact for the widest bucket. At the #2933 acceptance shape (`llama-3.2-1b-instruct-4bit`, `gfx1151`, `n=256`, `--batch 4 --requests 8 --maxcap 24`) a controlled interleaved A/B on one binary, swapping only the embedded HSACO, measures a median `42.29` to `43.56 tok/s` (about 3 percent) with the narrow arm ahead in 5 of 5 paired rounds. At `--requests 16` the medians are `50.74` to `52.13 tok/s` (about 2.7 percent), positive in 2 of 3 rounds. Every run prints `REFERENCE-EXACT PASS`. The `B=8` bucket takes the same compile as before, so it is unchanged.

The measured gain is smaller than the artifact change suggests. Predication already suppresses the dead lanes' weight reads and arithmetic, so the remaining cost of the wide bound is issue bandwidth, register allocation and shared memory; removing those recovers a few percent, not the whole gap.

## 1. Problem Statement

`qmv4.hip` declares `float acc[QMV4_MAX_B]` with `QMV4_MAX_B` fixed at 8, keeps `warp_sums[QMV4_MAX_B * 32]` in shared memory in the block-per-row forms, and predicates the unrolled loop with `if (bb < B)`. One HSACO served the `B=4` and `B=8` ragged graphs. At `B=8` the multi-row form won; at `B=4` the #2933 measurement was `60.0` and `62.2 tok/s` against `65.6` for the f16 path, about 5 percent.

The issue named four candidate causes: register pressure and occupancy, fixed-width predication, shared-memory sizing, or dispatch shape. This work measures each before changing anything.

## 2. Measurement and Root Cause

### 2.2 Per-dispatch trace

A `rocprofv3 --kernel-trace --output-format csv` run of the same pre-fix binary at `B=4` (`--requests 8 --maxcap 24`) and `B=8` (`--requests 16 --maxcap 48`), native arm, produced the multi-row rows below. Both buckets embedded the same `QMV4_MAX_B=8` artifact, so the runtime metadata is the same at both `B`.

| Export | B=4 calls | B=4 mean | B=8 calls | B=8 mean |
|--------|-----------|----------|-----------|----------|
| `qmv4_multi_kernel` | 736 | 0.0547 ms | 1104 | 0.0874 ms |
| `qmv4_multi_row_kernel` | 736 | 0.1932 ms | 1104 | 0.3127 ms |
| `qmv4_qkv_multi_kernel` | 736 | 0.0755 ms | 1104 | 0.1276 ms |
| `qmv4_gateup_multi_kernel` | 736 | 0.2770 ms | 1104 | 0.5406 ms |

The `B=4` run served 8 requests over 46 pump steps and the `B=8` run 16 requests over 69 steps, so each export is called once per layer per step (16 layers) in both. The trace confirms that the multi-row exports are what the ragged graph dispatches and that a `B=4` launch runs the `B=8` instruction stream; the per-call time only falls because predication suppresses the dead lanes' memory and arithmetic, not because the code is narrower. That is the signature of accumulated issue-slot and resource cost, not of a dispatch-shape error.

### 2.3 One-off build

A `-DQMV4_MAX_B=4` artifact was substituted into the existing binary's `B=4` run with a warm vmfb cache and the same prompts. In an interleaved A/B (5 pairs at `--requests 8 --maxcap 24`, 3 pairs at `--requests 16`), the narrow artifact is ahead in 5 of 5 and 2 of 3 paired rounds, with medians `42.29` to `43.56` and `50.74` to `52.13 tok/s`. `REFERENCE-EXACT PASS` on every round. This selected accumulator width as the cause; predication and dispatch shape were left alone.

## 3. Implementation

- `csrc/qmv4.hip`: the bound is a default, `#ifndef QMV4_MAX_B` / `#define QMV4_MAX_B 8` / `#endif`, so `-D` can override it. No kernel body changed.
- `native_qmv.rs`: `hsaco()` and `hsaco_multi(arch, b_max)` share one `compile()`; `bucket_bound` rejects values outside `1..=MAX_BATCH` and maps the widest bucket to the default artifact; `genco_args` adds `-DQMV4_MAX_B=<b>` only for narrower buckets; `cache_stem` appends `-b<b>` only for narrow buckets. The default stem keeps its pre-fix form.
- `iree.rs`: `IreeRaggedLlama::load_inner` calls `hsaco_multi(&arch, b_max)` instead of `hsaco(&arch)`. The single-sequence engine still calls `hsaco()`. The emitter, the six export names, the `B` push constant and the dispatch shape are untouched. Six `report_load_timing` checkpoints were added to the ragged load for the measurement and stay as diagnostics behind `MLXCEL_XLA_LOAD_TIMING`.
- `max_b` enters the cache key through the file stem rather than the content hash (the issue suggested both). This keeps the default stem format while guaranteeing that a narrow bucket never reads or overwrites the default artifact.

A bucket set that loads both `B` values compiles two HSACOs. The narrow artifact is 83,816 bytes and its `hipcc --genco` takes 1,032 ms on this host against 2,082 ms for the default bound, while the `B=8` bucket runs the same compile as before and hits the existing cache. One extra one-second compile per distinct narrow bucket, cached by content, is acceptable.

## 4. Measurements

All runs are on `gfx1151` under `scripts/rocm_gpu_guard.sh --hold`, llama-3.2-1b-instruct-4bit, same checkpoint and prompts as #2933, native arm unless stated.

### 4.1 Controlled A/B (one binary, HSACO swap)

| Shape | Default `QMV4_MAX_B=8` | Narrow `QMV4_MAX_B=4` | Paired rounds | Result |
|-------|------------------------|-----------------------|---------------|--------|
| B=4, requests 8, maxcap 24 | 44.21, 43.81, 35.36, 42.29, 35.23 | 44.31, 44.47, 43.24, 43.56, 42.45 | 5 of 5 narrow | REFERENCE-EXACT PASS |
| B=4, requests 16, maxcap 48 | 53.33, 50.61, 50.74 | 52.05, 52.85, 52.13 | 2 of 3 narrow | REFERENCE-EXACT PASS |
| B=8, requests 16, maxcap 48 | 55.95, 59.24 (pre-fix baseline) | same artifact | n/a | REFERENCE-EXACT PASS |

Medians: `42.29` to `43.56 tok/s` (about 3 percent) at the acceptance shape and `50.74` to `52.13` (about 2.7 percent) at double the requests. Two default rounds fell to about `35 tok/s` while the narrow arm stayed between `42.45` and `44.47`; the median and the paired sign test are the robust figures, not the mean.

### 4.2 Fixed binary

With a fresh artifact cache the fixed binary compiles exactly two `QMV4` artifacts, which proves the loader selects by bucket: `qmv4-gfx1151-802a2ac3535eaa05-b4.hsaco` (83,816 bytes) for `B=4` and the unsuffixed `qmv4-gfx1151-802a2ac3535eaa05.hsaco` (120,168 bytes) for `B=8`. All runs below are on that binary, native and f16 interleaved.

| Shape | Native 4-bit | f16 | Result |
|-------|--------------|-----|--------|
| B=4, requests 8, maxcap 24 | 42.99, 43.65, 43.53 (median 43.53) | 22.07, 22.50, 22.45 (median 22.45) | REFERENCE-EXACT PASS |
| B=8, requests 16, maxcap 48 | 60.15, 62.16 | 29.51, 34.43 | REFERENCE-EXACT PASS |

The fixed `B=4` median (`43.53`) reproduces the narrow arm of the controlled A/B (`43.56`), which confirms that `load_inner` runs the specialized artifact. A `rocprofv3` trace of that run reports `LDS_Block_Size=512` and `VGPR_Count=16` for `qmv4_multi_row_kernel`, against `1024` and `24` for the same export in the pre-fix trace, and 46 pump steps with `REFERENCE-EXACT PASS`. The load breakdown for the same shape is `ragged-total` 1159 ms, of which `ragged-context-and-upload` is 1142 ms; the compile phase is a cache hit (`ragged-compile` 0 ms). The `B=8` rates (`60.15`, `62.16`) are above the pre-fix numbers measured earlier in the window (`55.95`, `59.24`) because the later runs had a less loaded host; the bucket runs the same default compile, so there is no code change to attribute.

### 4.3 Why the absolute #2933 thresholds are not reproduced here

The `65.6` and `74.5 tok/s` targets could not be used as same-binary comparators in this measurement window, for two reasons outside this change:

1. The f16 arm of the same binary measures `20.6` to `22.5 tok/s` at `B=4`, not `65.6`. `MLXCEL_XLA_LOAD_TIMING` puts `ragged-context-and-upload` at about 4.8 s for the f16 graph against about 1.1 s for the native graph; the pre-#2933 control binary loads the same checkpoint through the same harness in about 0.7 s. The regression is pre-existing at HEAD, present in the f16 path, and not caused by this change.
2. The host ran below the #2933 rates during this window (sequential baselines `34` to `59 tok/s`), so the absolute decode rates are not comparable even for the native arm.

The honest statement is therefore: the controlled comparison shows the specialization recovers about 3 percent at `B=4`, the `B=8` path is unchanged, both are reference-exact, and the issue's absolute `65.6` baseline cannot be reproduced on HEAD because of the separate f16 ragged-upload cost.

## 5. Verification and Limits

- `cargo fmt --all -- --check`: clean.
- `cargo clippy -p mlxcel-xla --features iree --lib --tests -- -D warnings`: clean.
- `cargo test -p mlxcel-xla --lib native_qmv::`: pass, including the new `kernel_bound_is_overridable_at_compile_time` and `ragged_buckets_compile_with_their_own_bound`.
- `cargo test -p mlxcel-xla --lib native_ragged_decode_emits_multi_row_dispatches`: pass, unchanged.
- Fallback with `HIPCC=/nonexistent/hipcc` and a fresh artifact cache: one warning, f16 graph, `REFERENCE-EXACT PASS`.
- `hipcc --genco` for both bounds compiles; the fixed loader loads the `-b4` artifact for the `B=4` bucket and the default artifact for `B=8`.
- Emission is untouched, so the native-absent MLIR goldens are byte-identical.

Limits:

- The measured gain is a few percent, at the edge of run-to-run noise on this host. It is not the full ~5 percent gap #2933 recorded.
- The OpenXLA serve worker end to end at `B>1` was not exercised.
- Greedy identity between the f16 and native arms is the property established in #2890 and #2933; the bench compares each arm against its own single-sequence reference, and this change only removes dead accumulator lanes while keeping the per-row accumulation order identical, so it cannot change the tokens.
- The f16 ragged-upload cost described in 4.3 is out of scope here.
