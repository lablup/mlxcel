# 기술 보고서: PR #2220 - 스칼라 풀의 모든 슬롯에 자기만의 캐시 라인 부여

**날짜**: 2026-10-07

**상태**: gfx1151 호스트(ROCm/HIP)에서 구현 및 검증 완료. 코드 head `a7c85a73`, main `8ac65bd8` 기준, PR 열림, 머지 대기. #2213 종료.

**언어**: C++(ROCm 오버레이 `allocator.cpp`, `allocator.h`), Rust(신규 `tests/rocm_scalar_pool_concurrency.rs`, 수정 `tests/rocm_device_map_concurrency.rs`), Markdown(`patches-rocm/LOCAL_FIXES.md`)

**위험도**: 낮음. 8192개 스칼라 슬롯의 간격을 8바이트에서 128바이트로 늘리고 풀을 64 KB에서 1 MB로 키울 뿐이다. 커널, 인자, 할당기 락은 바뀌지 않는다. Metal과 CUDA 코드 경로는 건드리지 않는다.

## 요약

이슈 #2213은 #2197(PR #2214)의 테스트 작업에서 나왔다. 그 테스트는 스레드 8개가 각자 스트림에서 `multiply_scalar`와 `full_like`로 `arange * 2 + 1`을 평가한다. 자체 수정을 적용하고도 10회 중 9회 실패했고, 틀린 출력은 디바이스 맵 때문이 아니었다. 원소별 커널이 앞서 다른 스칼라가 들고 있던 값을 상수로 읽었다. #2214는 전체 길이 상수 배열로 우회하고 #2213을 등록했다.

호스트가 쓰고 커널이 읽는 8바이트 이하 값은 모두 `SmallSizePool`에서 나온다. `array(2.0f)`, `full(shape, value)`, `multiply_scalar`, `full_like`, softcap과 스케일링 헬퍼, 디코드 스텝의 한 토큰 인덱스가 그 예다. 서버는 각자 스트림을 가진 여러 스레드(배치 스케줄러, embedding, rerank, audio 워커)에서 평가하므로, 여기서 스칼라가 틀리면 크래시가 아니라 조용히 틀린 결과가 된다.

원인은 모든 스칼라를 프로세스 전역의 증가하는 카운터에서 뽑는 프로브로 분리했다. 틀린 값은 그것을 쓴 스레드와, 커널이 읽었어야 할 값보다 먼저 쓰였는지 나중에 쓰였는지를 알려 준다. main에서는 10회 모두 틀렸고, 틀린 스칼라 75개는 전부 더 이른 쓰기였다. 할당기의 live 비트 검사는 한 번도 발동하지 않았고, 커널을 직렬화하거나 캐시를 쓰지 않는 메모리를 쓰면 실패가 사라졌으며, 펜스는 효과가 없거나 오히려 나빴다. 결론은 다른 큐의 커널이 이웃 슬롯을 읽으며 설치한, GPU 캐시에 남은 오래된 128바이트 라인이다. 할당기 경합도 CPU 저장 순서 문제도 아니다. 오래된 라인이 어느 캐시 수준에 있는지는 확인하지 못했다.

수정은 슬롯을 128바이트 간격(`small_block_stride`)으로 배치해 살아 있는 스칼라 둘이 한 라인을 공유하지 않게 한다. 적용하면 프로브는 20회 중 0회 실패하고, 간격을 8로 되돌리면 20회 중 18회 실패한다. Llama-3.1-8B-4bit의 디코드 처리량은 편차 안에서 변하지 않았다. head의 `make verify-rocm`은 통과했다(161개 스위트, 12,131개 통과, 0개 실패). Metal과 CUDA는 검증하지 못했고, upstream CUDA의 managed 메모리 풀에 같은 위험이 있는지는 알 수 없다.

## 1. 문제 정의

### 1.1 발견 경위

#2197 작업은 `tests/rocm_device_map_concurrency.rs`의 피연산자를 `multiply_scalar`와 `full_like`로 썼다. 디바이스 맵 수정을 적용해도 10회 중 9회, `device.cpp`를 main으로 되돌리면 10회 중 10회 실패했으므로 수정이 원인이 아니었다. #2214 보고서에 좁혀 간 과정이 있다. 스레드당 스트림 하나로 해도 실패했고, 같은 상수를 전체 길이 호스트 배열로 쓰면 10회 모두 통과했으며, 호스트 데이터가 없는 연산도 10회 모두 통과했다. `SmallSizePool`에서 나오는 피연산자는 8바이트 이하 스칼라뿐이므로 풀이 용의자였다. 후보 설명은 두 가지였다. 슬롯 하나가 살아 있는 배열 둘에 할당되는 할당기 경합, 또는 재사용된 슬롯에서 GPU가 오래된 값을 읽는 일관성 문제다.

### 1.2 중요한 이유

`SmallSizePool`은 모든 원소별 연산의 스칼라, 스케일링과 softcap 헬퍼, 디코드 스텝마다의 토큰 인덱스를 담당한다. 워커가 각자 스트림에서 동시에 도는 서버에서는 이 풀 하나를 모두가 공유한다. 이 실패는 오류 없이 그럴듯하지만 틀린 숫자를 만들고, 동시 평가에서만 나타난다. 단일 스트림 벤치마크와 기존 스위트가 이를 보지 못한 이유다.

### 1.3 변경 전의 풀

upstream CUDA와 같이 `SmallSizePool`은 64 KB `unified_malloc` 하나를 8바이트 간격의 8192개 슬롯으로 나눴다(`small_pool_size = 4 * page_size`, `small_block_size = 8`). 할당기 뮤텍스 아래의 프리리스트로 내준다. 따라서 슬롯 16개가 128바이트 라인 하나를 공유한다.

## 3. 진단

### 3.1 프로브

`tests/rocm_scalar_pool_concurrency.rs`의 자식 본문이다. 스레드 8개가 각자 스트림에서 배리어로 동시에 출발하고, 16라운드에 라운드당 4번 평가한다(스레드당 64번). 매번 `arange_f32(0, 256, 1) * k + c`를 계산하며 `k`는 `multiply_scalar`, `c`는 `full_like`에서 오고 모든 원소를 정확히 검사한다.

이슈의 원래 프로브와 다른 점 하나: 모든 `k`와 `c`를 프로세스 전역 `AtomicU32` 카운터 하나에서 뽑고, 각 값을 뽑은 스레드, 라운드, eval, 역할(`k` 또는 `c`)을 표에 기록한다. 커널 출력이 읽은 스칼라를 드러내므로(`c`는 원소 0, `k`는 원소 1 빼기 원소 0), 틀린 값을 쓴 주체를 찾고 카운터 순서로 기대값과 비교할 수 있다. 오래된 값을 읽었다면 더 이른 값이 보이고, 슬롯이 살아 있는 배열 둘에 할당됐거나 커널이 재활용된 슬롯을 아직 읽고 있었다면 더 늦은 값이 보인다.

### 3.2 측정

gfx1151(ROCm 7.15)에서 실행했다. "틀린 값"은 커널이 읽은 스칼라 중 기대와 다른 것의 수이며 각 프로브 로그의 출처 집계에서 가져왔다.

| 구성 | 틀린 실행 | 틀린 값 | 방향 |
|---|---:|---:|---|
| main(8바이트 슬롯) | 10회 중 10회 | 75 | 전부 이른 쓰기, 늦은 쓰기 0 |
| 수정 브랜치, 간격을 8로 되돌림 | 20회 중 18회 | 93 | 전부 이른 쓰기, 늦은 쓰기 0 |
| 8바이트 슬롯에 풀 슬롯별 live 비트 | 5회 중 5회 | 28 | 전부 이른 쓰기, live 비트 abort는 발동 안 함 |
| `AMD_SERIALIZE_KERNEL=3` | 5회 중 0회 | 0 | |
| `HSA_DISABLE_CACHE=1` | 5회 중 0회 | 0 | |
| 슬롯 간격 128바이트 | 5회 중 0회 | 0 | |
| `hipDeviceMallocUncached`로 만든 풀 | 5회 중 0회 | 0 | |
| `GPU_FLUSH_ON_EXECUTION=1` | 5회 중 5회 | 238 | 전부 이른 쓰기(더 나쁨: 어긋난 평가 221건) |

처음 두 행에 덧붙인다. 75개와 93개에서 틀린 스칼라 대부분은 슬롯의 직전 사용자이며, 같은 스레드의 직전 평가인 경우가 많다(예: 스레드 2 라운드 10 eval 0은 `k = 612`를 기대했는데 커널은 596, 곧 스레드 2 라운드 9 eval 3의 `k`를 읽었다).

### 3.3 표 읽기

- **방향.** 실패하는 모든 구성에서 틀린 값은 전부 이른 쓰기이고 늦은 쓰기는 없다. 슬롯의 옛 내용을 오래된 채로 읽은 것이다.
- **할당기 경합이 아니다.** live 비트 실험은 풀 슬롯이 `malloc_async`를 떠날 때 할당기 뮤텍스 아래에서 비트를 세우고 `free`에서 지우며, 두 번째 live 소유자나 죽은 슬롯의 해제에서 abort하게 했다. 틀린 실행 5회 모두에서 발동하지 않았다. 어떤 슬롯도 둘에게 동시에 할당되지 않았고, 해제된 슬롯을 계속 읽는 일도 없었다. 풀의 락 방식은 upstream CUDA `allocator.cpp`의 핀 81ba1c6a와도 같다. 해당 파일로 확인했다. `malloc_async`는 `scalar_pool_.malloc()` 전에 `std::unique_lock lock(mutex_)`를 잡고, `free_cuda_buffer`는 `mutex_`를 잡은 채 호출한다고 주석에 적혀 있으며 `scalar_pool_.free`를 호출한다.
- **CPU 저장 순서가 아니다.** 실행 직전마다 전체 펜스를 넣어도 달라지지 않는다.
- **동시 커널이 관여한다.** `AMD_SERIALIZE_KERNEL=3`이 실패를 없앤다.
- **GPU 캐시가 관여한다.** `HSA_DISABLE_CACHE=1`과 캐시 없는 풀이 실패를 없앤다.
- **라인 공유가 방아쇠다.** 슬롯마다 128바이트 라인을 따로 주면 실패가 사라지므로, 오래된 것은 이웃 슬롯과 공유하던 라인이다.
- **L2 펜스는 듣지 않는다.** `GPU_FLUSH_ON_EXECUTION=1`은 디스패치마다 시스템 범위로 L2를 writeback하고 invalidate하는데 더 자주 실패하고, coarse-grained 풀도 실패한다. L2를 비워도 오래된 사본은 사라지지 않는다.

### 3.4 원인

슬롯의 옛 값을 담은 GPU 캐시의 128바이트 라인이다. 이 라인은 같은 라인의 이웃 슬롯을 읽던 다른 큐의 커널이 설치했고, 그 사이에 이 스레드가 자기 슬롯을 다시 쓰고 실행했다. 그러면 실행은 그 라인의 옛 내용을 읽는다. 오래된 라인이 어느 캐시 수준에 있는지는 확인하지 못했다. L2 펜스로 해결되지 않으므로 호스트 쓰기 아래의 다른 곳이며, 남은 수준을 가르는 실험은 여기서 하지 않았다. 수정은 그 답에 의존하지 않는다. 128바이트 간격은 LOCAL_FIXES 항목 40에 따른 gfx11의 라인 크기와 같으며, 이 수치는 이번 작업에서 측정하지 않았다.

## 4. 설계

### 4.1 수정

`SmallSizePool`은 8192개 슬롯과 프리리스트를 유지한다. 각 슬롯의 데이터는 이전 슬롯보다 `small_block_stride = 128`바이트 뒤에 놓이므로, 풀은 `unified_malloc`으로 64 KB 대신 8192 * 128 = 1 MB를 할당한다. 각 `RocmBuffer`는 여전히 `size = small_block_size`(8)를 보고한다. 다른 살아 있는 스칼라와 공유하지 않는 라인은 소유자의 호스트 쓰기가 반영되는 순간 실행 중인 커널이 붙잡고 있을 수 없다.

### 4.2 기각된 대안

- **캐시 없는 풀**(`hipDeviceMallocUncached`)은 5회 모두 통과했지만, 그러면 모든 웨이브의 스칼라 로드가 메모리로 간다.
- **커널 직렬화나 캐시 비활성화**(`AMD_SERIALIZE_KERNEL=3`, `HSA_DISABLE_CACHE=1`)는 진단용이지 서버에 쓸 선택지가 아니다.
- **펜스**(CPU, L2)는 해결하지 못한다.
- **락 변경**은 할당기가 원인이 아니므로 의미가 없다.

## 5. 검증

### 5.1 테스트

`tests/rocm_scalar_pool_concurrency.rs`(`#![cfg(feature = "rocm")]`)의 부모 테스트는 `#[ignore]` 자식을 새 프로세스에서 10번 띄운다. 자식은 3.1절의 프로브다. 각 자식은 0으로 종료하고 완료 마커를 출력해야 하므로, 검사 전에 건너뛰거나 죽은 자식이 성공으로 통과할 수 없다. 실패 메시지는 원소, 기대값, 그리고 틀린 스칼라마다 그것을 쓴 주체와 기대값보다 먼저인지 나중인지를 알려 준다. 모듈 문서에 측정값을 적었다.

`tests/rocm_device_map_concurrency.rs`는 주석을 갱신하여 `multiply_scalar`와 `full_like`로 복귀했다.

### 5.2 결과

gfx1151(GPU 1개, ROCm 7.15)에서:

| 빌드 | 틀린 자식 실행 |
|---|---:|
| main | 10회 중 10회 |
| 수정 브랜치, 간격 8 | 20회 중 18회 |
| 이 PR(간격 128) | 20회 중 0회 |

부모 테스트(자식 10개)와 `tests/rocm_device_map_concurrency.rs`는 통과한다.

### 5.3 성능

`rocm_gpu_guard.sh` 아래 Meta-Llama-3.1-8B-Instruct-4bit 디코드, 3회 중앙값: 변경 전 37.71 tok/s(범위 37.45~38.09), 변경 후 37.95 tok/s(범위 37.43~37.96). 차이는 실행 간 편차 안이므로 변화를 주장하지 않는다. 추가된 1 MB 풀은 한 번만 할당된다.

### 5.4 게이트

- 두 테스트의 `cargo clippy`: 경고 없음. `make verify-versions verify-kernel-dtype-keys verify-kernel-port-dispatch verify-llama-compat verify-fmt verify-rocm-overlay`: 통과.
- 오케스트레이터의 `a7c85a73`(main `8ac65bd8` 기준) `make verify-rocm`: 스위트 161개, 12,131개 통과, 0개 실패, 395개 무시, 스모크 OK.

검증하지 않은 것: Metal과 CUDA(이 호스트에 없음. 변경은 ROCm 오버레이 할당기와 ROCm 전용 테스트 두 개만 건드린다).

## 6. LOCAL_FIXES 항목 40

"Every scalar-pool slot on its own cache line" 항목은 풀과 사용처, 측정과 각 측정이 배제한 것, 새 간격과 풀 크기, 캐시 없는 풀을 택하지 않은 이유, 테스트 결과, upstream 메모를 기록한다. upstream CUDA의 핀 81ba1c6a는 managed 메모리에서 8바이트 패킹을 유지하고 풀을 같은 방식으로 잠그며, 거기서 이 위험에 도달할 수 있는지는 알 수 없다. 끝에 포크 정책 문구가 있다: "Applies to the fork; kept in mlxcelverse under the 2026-10-06 fork policy, not proposed there (lablup/mlxcel#2213)."

## 7. 기술적 선택과 그 이유

- **다른 메모리 종류가 아니라 간격.** 로드당 비용 없이 공유를 없애고, 풀을 이전과 같은 호스트 가시 메모리에 둔다.
- **슬롯 8192개 유지.** 개수는 CUDA의 값이고 한계라는 증거는 없었다. 바뀐 것은 간격뿐이다.
- **카운터 순서를 쓴 프로브.** 쓴 주체와 시점으로 출처를 따지니 "틀린 값"이 방향이 되었고, 그 방향이 할당기를 배제했다.
- **원인의 캐시 수준은 열어 둠.** 수정은 라인 단위로 동작하며, 수준을 밝히는 실험으로 수정이 바뀌지는 않는다.

## 8. 남은 위험

- **캐시 수준을 모른다.** 오래된 사본이 128바이트보다 큰 단위로 유지된다면 간격이 모자란다. 20회 중 0회라는 결과는 이 호스트에서 그렇지 않음을 말한다.
- **호스트 하나.** 모든 실행은 gfx1151 한 대와 ROCm 7.15에서 했다. 라인 크기가 다른 ROCm 아키텍처는 시험하지 않았다.
- **다른 작은 호스트 쓰기 버퍼.** 스칼라 풀만 살폈다. 호스트가 다시 쓰는 동안 같은 라인의 이웃이 읽히는 다른 할당도 같게 동작할 수 있다.
- **CUDA는 미검토.** upstream 풀은 managed 메모리에 8바이트 슬롯을 촘촘히 둔다. 거기서 GPU 캐시가 오래된 라인을 쥘 수 있는지는 알 수 없고, CUDA 호스트도 없었다.
- **성능은 잡음 범위 안에서만 변화 없음.**

## 9. 학습 포인트

- **통과/실패 횟수보다 출처가 낫다.** 모든 값을 카운터 하나에서 뽑으니 실패가 "오래된 값"이라고 말해 주었다. 실패 횟수만으로는 알 수 없었다.
- **싼 단언으로 가설을 배제할 수 있다.** live 비트는 몇 줄이었고 할당기를 후보에서 지웠다.
- **효과 없는 결과 둘과 더 나빠진 결과도 증거다.** 아무 효과가 없거나 더 나빠진 펜스가 원인을 좁힌 정도는 고친 간격 못지않았다.
- **현실적인 피연산자로 쓴 테스트가 찾았다.** #2197 테스트는 스칼라 연산을 썼고, 주제와 무관한 버그에 닿았다.

## 10. 시리즈 전체

이 PR은 ROCm 실행 경로의 공유 상태를 고치는 한 갈래 작업을 닫는다. 스레드 전반에서 모든 원소를 정확히 검사하는 동시성 테스트가 매번 아무도 들여다보지 않은 다음 공유 전역 상태에 닿았다.

| 단계 | 이슈 / PR | 고친 것 |
|---|---|---|
| 1 | #2196 | JIT 모듈 캐시와 HIP 이벤트 풀 |
| 2 | #2202 | `Device`의 rocBLAS 핸들을 락 아래에서 한 번만 생성 |
| 3 | #2208 | hipBLASLt 핸들, 스트림별 워크스페이스, 스레드 로컬 파이프 캐시 |
| 4 | #2214 | 디바이스 맵, 그리고 이벤트 풀 누수 처리 |
| 5 | #2220(이 PR, #2213) | `SmallSizePool`에서 캐시 라인을 공유하던 호스트 쓰기 8바이트 스칼라 |

시리즈가 열어 둔 것:

- **오래된 라인이 어느 캐시 수준에 있는가.** 수준을 가르는 실험(예: 슬롯 간 거리를 바꾸거나 캐시 제어 비트를 달리해 읽기)으로 밝힐 수 있다. 수정에는 필요하지 않다.
- **upstream CUDA의 managed 메모리 풀에 같은 위험이 있는가.** CUDA 호스트와 같은 프로브가 필요하다. 있다면 upstream의 문제이며, 2026-10-06 포크 정책에 따라 이번 작업에서 그쪽에 제안하는 것은 없다.
