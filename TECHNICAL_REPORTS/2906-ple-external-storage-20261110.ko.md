# 기술 보고서: PR #2906 - feat(models): read the qwen4_exp n-gram table from disk (ple_storage)

**날짜**: 2026-11-10
**상태**: 리뷰 중 (열린 PR, #2881 종료 예정)
**언어**: Rust
**위험도**: 중간

---

## 요약

PR #2906은 `text_config.ple_storage`를 선언한 qwen4_exp 체크포인트가 약 30 GiB의 레이어별 임베딩(PLE) n-gram 테이블을 MLX 파라미터로 보유하지 않고 디스크에서 행 단위로 읽도록 한다. `ple_storage`가 없는 체크포인트는 기존 상주(resident) 경로를 그대로 사용한다. OptiQ 2-bit 체크포인트의 로드 시점 상주 메모리는 45.39 GB(`ranges` 뷰)이다. 새 `PleRowStore`는 `Resident`와 `External` 두 변형을 가진다. `External`은 요청의 토큰 id를 중복 제거하고, 바이트 상한이 있는 LRU 행 캐시(기본 0.5 GB, `MLXCEL_PLE_CACHE_BYTES`)에서 적중분을 제공하며, 미스는 디스크에서 읽어 행마다 한 번만 역양자화한 뒤 호출자의 순서로 복원한다. mlx-vlm v2 매니페스트를 그대로 받아들이고, `mlxcel prepare-external-ple`이 Python 없이 뷰를 만든다. 컨텍스트 4,608 토큰 이후 전체 모델 트레이스에서 상주 대비 외부 방식의 top-1 불일치는 128개 중 0개, logit 차이는 0.0000이었다. 기본 I/O 모드(`mmap`)는 측정이 아니라 단순함을 기준으로 골랐고, 모드별 벤치마크, 피크 메모리 비교, 64/96 GB 하드웨어 실행은 아직 하지 않았다.

---

## 1. 문제 정의

### 1.1 배경

qwen4_exp는 매우 큰 n-gram 임베딩 테이블(PLE 테이블)을 가지며, 각 디코드 또는 프리필 단계는 그중 몇 개 행만 읽는다. 이를 파라미터로 올리면 한 단계가 수천 행만 쓰는데도 약 30 GiB가 상주한다. mlx-vlm은 외부 저장 매니페스트(`ple_storage`)로 이를 이미 해결했고, 그 방식으로 준비된 체크포인트가 존재한다. 이슈 #2881은 mlxcel이 이런 체크포인트를 읽고 더 작은 메모리로 동작해 64 GB, 96 GB Mac에 올라가게 하는 것을 요구한다.

### 1.2 기존 문제

- **테이블이 파라미터이다.** 상주 경로는 모든 행을 MLX 배열에 두므로 메모리가 작업 집합이 아니라 테이블 크기에 비례한다.
- **체크포인트 디렉터리는 신뢰할 수 없는 입력이다.** 매니페스트는 파일, 오프셋, 형상을 지정한다. 이를 그대로 따르면 모델 디렉터리 밖이나 텐서 끝을 넘어 읽도록 조작될 수 있다.
- **메모리 계산이 상주를 가정했다.** `mlxcel inspect`와 `--estimate-memory`가 테이블 전체를 상주로 셌으므로, 이제 들어가는 기기에서도 모델을 거부하게 된다.
- **프리필 루프에 I/O 중첩 지점이 없었다.** 행을 필요할 때 읽으면, GPU가 현재 조각을 실행하는 동안 다음 조각의 행을 미리 읽지 않는 한 단계마다 지연이 늘어난다.

### 1.3 위험 평가

| 위험 | 영향 | 가능성 |
|---|---|---|
| 조작된 매니페스트가 체크포인트 밖 파일을 읽거나 링크함 | 높음 (정보 노출, 파일 덮어쓰기) | 외부 체크포인트에서 중간, 이 PR에서 완화 |
| 외부 행이 상주 행과 수치적으로 다름 | 높음 (잘못된 logit) | 낮음, 픽스처 비트 단위 비교와 실모델 트레이스로 확인 |
| `mmap` 모드가 메모리 압박에서 정체 또는 오류 | 중간 (지연, 파일 절단 시 SIGBUS) | 중간, 기본값 미측정 |
| 디스크 읽기 오류가 forward를 panic시킴 | 중간 (프로세스 중단) | 낮음, forward에 오류 채널이 없음 |

## 2. 변경 요약

### 2.1 행 저장소와 캐시

- `qwen4_exp_ple_storage.rs`가 `PleRowStore`(`Resident` 또는 `External`)를 정의한다. `External::gather`는 id를 중복 제거하고 캐시를 조회하며, 미스를 읽고, 고유 행마다 한 번 역양자화한 뒤 호출자 순서로 되돌린다. 요청된 행이 아니라 고유 행 기준으로 역양자화하므로 반복되는 n-gram id가 저렴하다.
- `qwen4_exp_ple_cache.rs`는 슬랩 기반 LRU이다. 레코드는 64 MiB 슬랩에 저장되어(단계당 한 번 할당, 제거 시 슬롯을 제자리 재사용) 있고, 레코드당 부가 비용 56바이트를 예산에 포함해 슬랩과 부가 비용의 합이 예산을 넘지 않는다.
- 증가는 `RowCacheGrowth::can_grow` 트레이트를 거치며 현재는 항상 허용한다. #2883이 여기에 가용 메모리 검사를 연결할 예정이며, 그러면 메모리가 부족할 때 캐시는 증가를 멈추고 제거한다.

### 2.2 I/O 모드

- `qwen4_exp_ple_io.rs`와 `qwen4_exp_ple_direct.rs`가 `MLXCEL_PLE_IO=direct|mmap|ram`을 구현한다. 기본값 `mmap`, 페이지 캐시를 우회하고 절단 시 SIGBUS를 피하는 `direct`, 테이블을 메모리에 올리는 `ram`이 있다.
- 기본값은 mlx-vlm이 쓰는 방식이며 가장 단순하다. 측정 근거는 없다.

### 2.3 매니페스트, 뷰 생성기, 신뢰 경계

- `qwen4_exp_ple_manifest.rs`는 mlx-vlm v2 매니페스트(`safetensors_ranges`, `interleaved_q4`, affine 4/32, nvfp4 4/16)를 받아들인다. 검증 실패는 모두 해당 필드를 이름으로 알려 준다. PLE 레이어가 둘 이상인 `ple_storage`는 매니페스트 하나가 테이블 하나만 기술하므로 거부한다.
- `qwen4_exp_ple_prepare.rs`와 `commands/prepare_external_ple.rs`가 Python 없이 뷰 디렉터리를 만드는 `mlxcel prepare-external-ple`을 추가한다.
- `qwen4_exp_ple_trust.rs`가 경로 제한 규칙을 담는다(3.3절).

### 2.4 선행 수집(gather-ahead)

- `prefill_lookahead.rs`와 `planned_prefill.rs`, `engine/direct.rs`의 연결부가 GPU가 현재 프리필 조각을 실행하는 동안 다음 조각의 행을 읽게 한다. 힌트는 캐시 내용만 바꿀 수 있고 계산 값은 바꾸지 못하므로, 틀리거나 늦은 힌트는 속도만 해치고 정확성은 해치지 않는다.

### 2.5 계산과 관측성

- `qwen4_exp_ple_footprint.rs`가 `inspect`와 `--estimate-memory`에서 디스크의 테이블이 아니라 행 캐시(`ram`에서는 테이블)를 세도록 한다.
- `qwen4_exp_ple_stats.rs`가 생성 후 적중, 미스, 바이트, 시간을 통계 줄로 출력한다.

## 3. 기술적 선택과 그 이유

### 3.1 중복 제거 후 캐시, 한 번만 역양자화

대안은 요청된 모든 행을 매 단계 역양자화하거나 역양자화된 행을 캐시하는 것이었다. 채택한 설계는 저장 형태(패킹된) 레코드를 캐시하고 gather마다 고유 행을 한 번 역양자화한다. 바이트당 캐시 용량이 커지는 대신 단계를 넘어 적중해도 다시 역양자화한다. 역양자화된 행을 캐시하는 방식과의 비용 비교는 측정하지 않았다.

### 3.2 mmap 기본값, 세 모드 유지

최적 기본값은 이 호스트에서 분리할 수 없었던 디스크와 메모리 압박에 달려 있으므로 세 모드를 모두 유지한다. `mmap`은 가장 단순하고 upstream과 같다는 이유만으로 골랐다. 5절의 벤치마크가 나오기 전까지는 임시 값으로 취급해야 한다.

### 3.3 매니페스트를 믿지 않고 경로를 제한

- 매니페스트와 행 파일은 모델 디렉터리 안으로 해석되어야 하므로 절대 경로 `ple_storage.manifest`는 거부한다.
- `source_root`는 upstream이 뷰 바깥에 대한 상대 경로로 쓰므로 제한할 수 없다. 보완책으로 각 `safetensors_ranges` 텐서가 해당 파일 자체의 safetensors 헤더(오프셋과 형상)와 일치해야 하며, 매니페스트가 파일이 선언하지 않은 바이트를 가리킬 수 없다.
- `prepare-external-ple`은 소스를 벗어나는 인덱스 경로, 심볼릭 링크, 예약 이름을 거부하고 `.safetensors` 파일만 하드링크한다. 이후 커밋에서 OptiQ 사이드카를 두 번 하드링크하지 않도록 고쳤다.
- 따라서 경로만 보고 upstream 뷰를 받아들이는 방식은 배제된다. upstream과의 호환은 위치가 아니라 내용을 검증해서 유지한다.

### 3.4 예산에 부가 비용 포함

첫 캐시 버전은 해시 맵과 리스트 부가 비용 때문에 바이트 예산을 넘을 수 있었다. 레코드당 56바이트(키와 링크 16, 최악의 맵 항목 39)를 부과해 예산을 엄격한 상한으로 만들었다. 맵 수치는 현재 표준 HashMap의 적재율을 가정하므로, 표준 라이브러리 구현이 바뀌면 이 상수를 다시 확인해야 한다.

## 4. 검증

- `models::qwen4_exp` lib 테스트 128개 통과. lib과 테스트의 clippy, `fmt --check` 통과. 매니페스트 규칙마다 테스트가 하나씩 있고, 두 레이아웃, 두 양자화, 세 I/O 모드 모두에서 External이 Resident와 비트 단위로 같다.
- OptiQ 2-bit, 컨텍스트 4,608 토큰 이후 상주 대비 외부 전체 모델 트레이스: top-1 불일치 128개 중 0개, logit 차이 0.0000. `safetensors_ranges` 뷰를 썼으며 행 디코딩을 건드리지 않은 리뷰 수정 이전의 결과이다.
- 리뷰 수정 이후 새 `ranges` 뷰로 `mmap`과 `direct` 모두에서 24 토큰을 생성했다.
- 작은 체크포인트에서 mlx-vlm 0.7.11 `ple_storage.py`와 매니페스트 및 행 수준에서 양방향 호환을 확인했다.

## 5. 미검증 항목과 알려진 한계

- `interleaved_q4`는 작은 픽스처로만 검증했다. 30 GiB 행 파일은 이 공유 호스트의 다른 작업을 방해한다.
- 실모델 호환은 실행하지 않았다: mlx-vlm이 준비한 뷰를 mlxcel에서 생성, 그리고 헬퍼 출력물을 mlx-vlm에서 생성.
- 모드별 쌍체 5회 벤치마크와 피크 메모리 비교는 조용한 머신으로 미뤘다. 측정에 근거한 기본값 주장은 없으며 0.5 GB 캐시 크기도 미측정이다.
- 96 GB, 64 GB Mac 실행: 하드웨어 없음. 대표 수치 45.39 GB는 이 호스트의 로드 시점 상주 값이며 부하 중 피크가 아니다.
- `mmap` 모드에서 매핑된 파일을 절단하면 SIGBUS가 난다(`direct`는 피함).
- 디스크 읽기 오류는 forward를 panic시키며 forward에 오류 채널이 없다. 고치려면 오류를 반환하는 forward가 필요하다.
- `can_grow`가 항상 참이므로 #2883이 들어오기 전까지 캐시는 설정된 예산으로만 제한된다.

## 6. 학습 포인트

- 다른 프로젝트와 호환해야 하지만 신뢰할 수 없는 디렉터리에서 읽는 형식이라면, 경로를 제한할 수 없을 때 파일 자체가 가진 기준(여기서는 safetensors 헤더)에 대해 내용을 검증한다.
- 선행 읽기 힌트는 캐시만 건드리도록 구조적으로 결과를 바꿀 수 없게 만들어, 틀린 힌트가 성능 문제에 그치게 한다.
- 부가 비용은 처음부터 바이트 예산에 포함하지 않으면 예산이 상한 구실을 하지 못한다.
- 단순함을 기준으로 정한 기본값은 튜닝된 값으로 오해되지 않도록 PR에 그렇게 표시한다.
