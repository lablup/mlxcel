# 기술 보고서: Mage-VL 4B 이미지 입력 포팅 (#1365)

**날짜**: 2026-09-29

**상태**: 구현 및 로컬 검증 완료, 머지 대기.

**언어**: Rust

**위험도**: 낮음 (새 모델 계열 추가. 공유 코드는 match arm 추가와 processor 테스트 하나만 변경)

## 요약

Mage-VL(`microsoft/Mage-VL`, `model_type: "mage_vl"`)을 이제 `mlxcel generate --image`와 서버에서 이미지 요청으로 사용할 수 있습니다. 이번 포팅은 Mage-VL 고유의 interleaved 4:6:6 3D RoPE를 쓰는 Mage-ViT 타워와 2x2 LayerNorm/MLP merger를 추가하고, 중첩된 `rope_parameters`에서 RoPE base를 끌어올린 일반 Qwen3 디코더에 연결합니다. `mlx-community/Mage-VL-8bit`에서 greedy 출력이 mlx-vlm과 토큰 단위로 일치하며, 2775 토큰 프롬프트에서도 일치합니다.

## 1. 문제

mlxcel에는 `mage_vl` 분기가 없었습니다. 가장 가까운 타워(`qwen2_vl`, `qwen3_vl`)는 split-half 회전, 레인 쌍마다 같은 주파수, `2i/d` 지수를 쓰기 때문에 재사용할 수 없었습니다. 또한 공개 config는 디코더 RoPE base를 `text_config.rope_parameters.rope_theta = 5e6`에만 저장합니다. 그대로 `qwen3::ModelArgs`로 파싱하면 serde 기본값 10000이 적용되어, 짧은 입력에서는 멀쩡하지만 긴 입력에서 품질이 떨어집니다.

## 2. 변경 사항

- `vision/encoders/mage_vl_rope.rs`: 블록 순서 위치(`positions_from_grid`), `base^(-i/size)` 4:6:6 역주파수, `concat(freqs, freqs)` 각도 테이블, reshape/slice/concat으로 만든 interleaved `rotate_half`(`fast_rope` 미사용), f32 rotary 적용, `frame_windows_size` attention window.
- `vision/encoders/mage_vl.rs`: 타워 본체. patch kernel은 torch `[O, C, P, P]`와 channels-last `[O, P, P, C]`(8-bit 변환본이 후자) 모두 받아 processor 행 위의 Linear로 적용합니다. MLP와 merger에는 정확한 GELU를 쓰고, 마지막 hidden state를 post-norm 없이 사용합니다. attention window(이미지당 하나)마다 타워를 따로 실행하는데, 나머지 연산이 모두 행 단위이므로 upstream의 block-diagonal `cu_seqlens` attention과 동일합니다.
- `vision/mage_vl_config.rs`: 공개값을 기본값으로 둔 vision config와 이름을 밝힌 거부(`use_patch_position_encoding`, `use_head`, `rms_norm`, 정확하지 않은 GELU, 4:6:6으로 나뉘지 않는 head 폭), `lift_rope_parameters`, 토큰 id, EOS, `preprocessor_config.json`의 픽셀 범위와 정규화 값.
- `vision/mage_vl.rs` + `loading/vlm_mage_vl.rs`: `MageVlModel`은 모든 `LanguageModel` 경로(`forward_last_logits*`, batching, paged decode 포함)를 `Qwen3Model`에 위임합니다. 로더는 hub와 MLX 두 키 레이아웃을 모두 매핑하고, 최상위 `quantization`을 상속하며, `vlm_has_vision`이 vision이 제거된 체크포인트라고 판단하면 타워를 로드하지 않습니다.
- 통합: `ModelType::MageVLM`, detection, registry, metadata, memory estimate, TP placeholder, `LoadedModel`, `VlmRuntimeRef::MageVl`, `has_vision_tower`, `vlm_runtime` 분기(Qwen2-VL 전처리와 `<|image_pad|>` 확장, feature 개수 검증, image/video pad id에 대한 LLaVA scatter), CLI 요약 출력, 문서.

## 3. 기술적 결정

- 런타임은 `QwenVlRuntime`을 거치지 않습니다. 이 trait은 MRoPE 상태를 만들지만 Mage-VL 디코더는 일반 1-D 위치를 씁니다.
- vision이 제거된 `mage_vl` 체크포인트도 `qwen3`로 보내지 않고 `ModelType::MageVLM`을 유지합니다. flat Qwen3 텍스트 로더는 중첩된 `text_config`나 `language_model.*` 키를 읽지 못하므로, #1367의 Qwen2-VL 계열 방식(로더에서 `vlm_has_vision`, `vision: None`, 이미지 요청에 공통 거부 메시지)을 따릅니다.
- mlx-vlm 레퍼런스와 맞추기 위해 vision 타워는 체크포인트 dtype(8-bit 변환본은 bf16)을 유지합니다.

## 4. 검증

- 단위 테스트(신규 26개, 전부 통과): 블록 순서 위치, merge cell 묶음, grid 커버리지, interleaved 회전, 8/12/12 크기와 `i/size` 지수, 연결된 각도 테이블, rotary 공식, attention window, processor 행 순서 대비 channels-last kernel, 랜덤 가중치 forward(행 수, 유한값, grid 오류), 이미지 간 격리, RoPE lift(10000 fallback을 기록하는 테스트 포함), quantization 상속, 키 매핑, 텍스트 전용 로더 3가지, detection, `temporal_patch_size = 1` processor 행 수.
- 실제 체크포인트 `mlx-community/Mage-VL-8bit`를 같은 가중치의 mlx-vlm 0.7.4와 비교(greedy):
  - 224x224 단색 빨강, "What color is this image? Answer with one word.": `Red`, grid `(1, 14, 14)`, 이미지 토큰 49개.
  - 448x896으로 미리 리사이즈한 `examples/dog.jpg`: 토큰 id 48/48 일치, 양쪽 모두 프롬프트 417 토큰.
  - 원본 1024x2048 `dog.jpg`(mlxcel은 Lanczos3, 레퍼런스는 bicubic으로 리사이즈): 처음 32 토큰 일치.
  - 2775 토큰 프롬프트(레코드 120개와 이미지)로 5번 레코드와 이미지 설명 요청: 출력 동일, 기억도 정확. 같은 실행에서 `rope_theta`를 10000으로 강제하면 "None of the choices provided."로 답합니다.
  - `mlxcel serve`에 dog 이미지로 OpenAI chat 요청: 같은 48 토큰 출력, 프롬프트 417 토큰.
- `cargo fmt --check`, `cargo clippy --release -p mlxcel --lib --tests -D warnings`, 계약 테스트 `cli_help_consistency`, `dead_doc_pointers`, `llama_compat_manifest` 통과.

## 5. 하지 않은 것

- 이슈는 체크포인트 자체의 `transformers` 구현(CPU bf16)과의 parity를 요구했습니다. 여기서 쓴 레퍼런스는 같은 int8 가중치의 mlx-vlm입니다. 모델 카드가 같은 dog 이미지에서 int8 대 PyTorch 48/48 일치를 보고하므로 간접적으로는 연결되지만, 여기서 다시 실행하지는 않았습니다.
- 코덱 네이티브 비디오와 프레임 샘플링 비디오는 범위 밖입니다. 이후 비디오 경로를 위한 attention window 헬퍼는 들어가 있습니다. 이 계열에는 vision feature cache를 연결하지 않았습니다.
