## 요약

이 변경은 mlxcel에 네이티브 PP-DocLayoutV3 탐지기를 추가하고 모델이 예측한 페이지 읽기 순서를 기존 Falcon-OCR 레이아웃 처리 흐름에 연결합니다. 두 공개 체크포인트 레이아웃을 모두 받아들이고, 원본 이미지 픽셀 좌표의 박스와 연속적인 1부터 시작하는 `reading_order`를 출력하며, 순서 헤드가 없는 RT-DETRv2의 기존 출력 계약을 유지합니다.

ROCm/gfx1151에서 탐지기 수치 게이트를 완료했습니다. 두 레이아웃 모두 고정한 Hugging Face 프로세서 tensor를 정확히 재현하고, source-bound F32 바이너리는 `logits`, `pred_boxes`, `order_logits`의 최대 절대 오차와 RMS 오차가 모두 0입니다. 두 실제 탐지기 CLI 실행도 통과해 `1..16` 순서의 16개 항목 JSON을 byte 단위로 동일하게 출력하며, 실제 28개 탐지 RT-DETRv2 회귀도 통과했습니다.

첫 실제 Falcon child process는 종료 0이었지만 잘못된 텍스트를 만들었고, Introduction anchor가 없어 integration assertion이 정확히 실패했습니다. 이 음성 실행은 기능에 필요한 기존 Falcon loader/runtime 결함을 드러냈습니다. Source-bound 수정은 실제 크기 1-token projection 회귀, 정확한 Pillow 전처리, 레퍼런스와 같은 direct/engine title token `[526, 969]`을 통과했습니다.

수정된 전체 페이지 수락도 ROCm/gfx1151에서 통과했습니다. 두 detector layout은 같은 16개 JSON을 출력하고 Falcon은 OCR 영역 13개를 유지해 1,109 token을 생성하며 `Introduction`, `Language model pre-training`, `There are two existing strategies`를 요구한 순서로 포함합니다. 역사적 결과는 source `2de95857...`와 manifest `b3314f9a...`에 계속 묶여 있습니다. 수정 네이티브 통합은 source `90dc24a7...`에서 Paddle/HashNuke 원시 출력, RT, CLI union, 전체 Falcon 게이트를 다시 실행했고 모든 child/wrapper 상태는 0입니다. 저장소 계약과 clippy도 통과했습니다. 최종 보고서 commit/head, CI, merge만 대기 중입니다.

## 문제

Falcon-OCR의 레이아웃 인식 모드는 PP-DocLayoutV3 박스와 학습된 읽기 순서가 필요합니다. 변경 전 mlxcel은 외부 레이아웃 JSON을 받을 수 있었지만 PP-DocLayoutV3 자체를 실행할 수 없었습니다. RT-DETRv2에는 학습된 페이지 순서 헤드가 없어 기하학적 폴백은 다단 문서를 행 단위로 읽습니다.

## 구현

### 공통 탐지기 경계

`src/vision/detection/mod.rs`가 공통 `Detection`, `DetectionResult`, `Detector` 계약을 소유합니다. `load_detector`는 `config.json`의 정확한 `model_type`을 읽어 `rt_detr_v2` 또는 `pp_doclayout_v3`로 디스패치합니다. PP 결과는 `reading_order: Some(n)`을 갖고 RT 결과는 `None`을 유지합니다.

`detect` 명령은 모든 결과에 모델 순서가 있을 때 직렬화 전에 그 순서대로 정렬합니다. 순서가 없거나 일부만 있으면 기존 기하학적 폴백을 사용합니다. JSON은 값이 있을 때만 `reading_order`를 추가하므로 RT-DETRv2 스키마는 유지됩니다.

### 네이티브 PP-DocLayoutV3 그래프

새 모델군은 다음을 구현합니다.

- 비대칭 stem 패딩, group/light block, 4개 feature stage를 갖는 HGNetV2-L
- AIFI/FPN/PAN 하이브리드 인코더와 stride-4 mask feature 분기
- mask 기반 top-k query 초기화
- half 입력에서 f32 grid sampling을 사용하는 deformable decoder 6개 층
- mask-to-box 경로와 GlobalPointer 순서 헤드
- `logits [1,300,25]`, `pred_boxes [1,300,4]`, `order_logits [1,300,300]`의 엄격한 출력 계약

설정과 체크포인트 로더는 추론 전에 topology, checked allocation 경계, 키 집합, shape, 부동소수 dtype, 유한값을 검증합니다.

### 두 체크포인트 레이아웃

로더는 이름 변경 전에 출처를 구분합니다.

- `e4f489dc536556fc1be02b973ba06756e0d4a2ac`의 `PaddlePaddle/PP-DocLayoutV3_safetensors`: `model.*` 키와 NCHW convolution tensor
- `cd50996ad0c7e35a7e20c27480f99cec1822cf7b`의 `HashNuke/pp-doclayout-v3-mlx`: 변환된 이름과 NHWC tensor

원본 Paddle namespace에서 왔음이 증명된 tensor만 transpose합니다. 혼합 레이아웃과 정규화된 이름 충돌은 모호한 shape나 map 순서에 의존하지 않고 실패합니다.

### 프로세서와 후처리

프로세서는 입력을 RGB로 변환하고, 고정한 Torchvision 방식 uint8 bicubic 경로로 800 x 800에 맞춘 뒤 업스트림의 나눗셈/정규화 연산 순서를 적용합니다. 역방향 박스 변환을 위해 원본 크기를 보존하고 입력과 할당량을 제한합니다.

후처리는 정확한 shape와 유한값을 검증하고 sigmoid를 적용한 다음 query/class 전체에서 top-300을 선택합니다. 임곗값 이상을 유지하며 필터링 전에 300개 전체 query의 순서를 복원합니다. 클래스 이름이 중복돼도 숫자 label id를 유지하고, 한 query의 여러 label을 결정론적으로 유지한 뒤 모델 순서로 정렬하고 최종 출력 순서를 `1..N`으로 다시 번호 매깁니다.

### 산술 동등성

프로세서 차이는 연산 순서에서 발생했습니다. 고정한 경로는 평균 0/표준편차 1 변환을 pixel/255로 계산하지만 첫 Rust 구현은 반올림된 역수를 곱했습니다. 수정 후 두 레이아웃 모두 최대 절대 오차 0입니다.

host positional encoding, fast SDPA, deformable grid sampling의 제한된 수정도 독립적으로 검토했습니다. 최종 stage 진단의 캡처 91개 중 90개는 byte 단위로 동일합니다. 유일한 차이는 실행 경로에서 우회되는 `decoder.encoder_coordinates` 진단으로 최대 절대 오차는 `4.76837158203125e-7`입니다. 실행된 AIFI, decoder, top-query, GlobalPointer, 공개 원시 출력 stage는 모두 byte 단위로 같습니다. Stage 비교는 원인 국소화를 위한 보조 근거이며, 수락 근거는 별도 source-bound 원시 출력 테스트입니다. 이 테스트는 두 레이아웃의 모든 공개 tensor에서 최대/RMS 오차 0으로 통과했습니다.

### 기존 Falcon 통합 결함 수정

엔드투엔드 실행에서 #2412가 함께 수정해야 하는 기존 Falcon-OCR 통합 결함 두 가지가 드러났습니다.

첫째, Falcon의 fused `w13` tensor는 gate/up 행을 교차 저장합니다. 분리하면 값은 맞지만 행 stride가 있는 두 view가 생겼습니다. ROCm의 M >= 2 matrix 경로는 이를 처리하지만 1-token M = 1 GEMV 경로는 dense layout으로 읽어 잘못된 projection을 반환했습니다. 실제 공개 weight와 실제 Rust decode 입력을 재생하면 strided view가 나쁜 Rust byte를 그대로 재현했고 gate/up 최대 오차는 각각 `2.90893816947937`, `4.000600755214691`이었습니다. 같은 값을 contiguous로 materialize하면 f64 dot 레퍼런스 대비 두 실제 크기 projection의 최대 오차가 `9.5367431640625e-7`로 줄었습니다. 수정은 load 시 Falcon의 분리된 plane 두 개만 한 번 contiguous로 만듭니다. 모델 값, vendor EPSILON 상수, KV-cache 의미, 공통 backend matmul/GEMV 구현은 바꾸지 않습니다.

둘째, Falcon 전처리는 레퍼런스의 Pillow RGB8 bicubic 두 단계를 `image` crate Catmull-Rom으로 대응하고 있었습니다. 수정된 경로는 두 resize 전에 RGB로 변환하고 공유 fixed-point Pillow bicubic 구현을 사용합니다. 이는 PP 탐지기의 pixel 나눗셈 수정과 별개입니다. 인증된 Falcon title probe의 processor 최대 오차, RMS 오차, 다른 값 개수는 모두 0입니다.

집중 수정 바이너리는 실제 크기 M = 1 회귀와 direct-model/`DirectEngine` title probe를 모두 통과했습니다. 두 경로 모두 인증된 Python 레퍼런스와 같은 token `[526, 969]`을 냅니다. 이는 국소화된 원인과 engine 경계를 닫고, 아래에 별도 보존한 전체 페이지 수락이 캡처한 소스의 페이지 단위 계약을 닫습니다.

### Falcon-OCR 연결

사용자 흐름은 명시적인 두 명령으로 유지됩니다.

```bash
mlxcel detect -m models/PP-DocLayoutV3 -i page.png --format json > regions.json
mlxcel generate -m models/falcon-ocr \
  --image page.png \
  --layout-detections regions.json
```

Falcon 단계는 파일 순서를 유지하며 label을 OCR prompt에 매핑하고, 텍스트가 없는 class를 건너뛰고, category 매핑 후 중복 박스를 합치며, 사용할 수 없는 crop을 거부합니다. 남는 영역이 없으면 전체 페이지의 plain 영역으로 폴백합니다. `generate` 내부에서 탐지기를 자동 실행하는 기능은 #2412 범위 밖입니다.

두 실제 탐지기 명령은 종료 0이며 byte 단위로 같은 JSON을 생성합니다. 탐지 16개와 연속 순서 `1..16`입니다. 이전 Falcon child도 종료 0이었지만 텍스트가 잘못됐고, 필수 Introduction anchor가 없어 전체 integration은 101로 종료했습니다. 이 실패는 그대로 보존했고 anchor 계약도 완화하지 않았습니다.

제한된 Falcon 수정 후 전체 실행은 중첩 box 3개를 제거하고 순서가 있는 영역 13개를 OCR에 전달합니다. 1,109 token을 생성하고 `Introduction`, `Language model pre-training`, `There are two existing strategies` anchor를 순서대로 모두 포함합니다. Transcript SHA-256은 `d202733dbaa3157741f1953a1178f685d411073372d4e8f9318bcf30adf8472d`이고, 두 layout의 detector JSON SHA-256은 모두 `877e6a5a7562d89b031414968bc83b6589062110ba9fbae750550cad7241ec69`입니다.

## 실제 레퍼런스 패키지

추적되는 픽스처는 수정하지 않은 mlx-vlm `4319ef2c837b7226b758c3dd69edda51b7079785`와 네이티브 MLX `bff10220c742907f0c68e55ff174aaea56f74e3d`를 고정합니다. 로드된 라이브러리/바인딩 해시, F32 파라미터 857개, 체크포인트 manifest, 정확한 프로세서 tensor, 원시 출력, 명령과 child/wrapper 종료 상태를 기록합니다. 최종 CLI/Falcon 근거와 source binding을 추가한 뒤 fail-closed `python -O` verifier는 인증된 항목 55개의 inventory를 통과합니다. Inventory 파일의 SHA-256은 `8ed3fd8ea485a26b9fd4989ca95470544932fd842f9714f417d401a6dd91b6ca`입니다.

두 업스트림 체크포인트 레이아웃은 byte 단위로 동일한 F32 레퍼런스 tensor를 생성했습니다. 최종 Rust 바이너리도 각각과 정확히 일치합니다.

| Tensor | Shape | Paddle 최대/RMS | HashNuke 최대/RMS |
|---|---:|---:|---:|
| `logits` | `[1,300,25]` | `0 / 0` | `0 / 0` |
| `pred_boxes` | `[1,300,4]` | `0 / 0` | `0 / 0` |
| `order_logits` | `[1,300,300]` | `0 / 0` | `0 / 0` |

손실 없는 2단 입력은 BERT 논문 1쪽이며 CC BY 4.0에 따라 재배포됩니다. 원본 PDF, renderer, pixel hash가 기록돼 있습니다. 실제 후처리는 탐지 16개를 유지하며 학습된 순서가 기하학적 순서와 다름을 보여 줍니다. Source-bound Falcon 실행은 위에서 설명한 순서가 있는 semantic-anchor 계약을 통과합니다.

## 호환성과 제한

- 사용자 흐름은 두 명령입니다. Falcon 생성 과정에서 PP 탐지를 자동 실행하지 않습니다.
- 공개 탐지기 표면은 이미지/파일 기반이며 token generation/server runtime 밖에 있습니다.
- 탐지기는 위에서 고정한 두 공개 레이아웃을 대상으로 하며 더 넓은 체크포인트 호환성을 주장하지 않습니다.
- PR은 필수 통합 게이트에서 드러난 Falcon 전용 contiguous W13 materialization과 exact Pillow 전처리 수정도 포함합니다. 공통 backend matmul/GEMV, vendor EPSILON 상수, cache 의미는 바꾸지 않습니다.
- 이 작업에서 Metal과 CUDA는 검증하지 않았습니다.
- 처리량, 지연 시간, 메모리 벤치마크, 비교 성능 결과가 없습니다.
- 역사적 수치/Falcon 검증은 원래 binary와 manifest에 계속 묶여 있습니다. 수정 네이티브 재실행은 `90dc24a7...`과 항목 75개 통합 패킷에 별도로 묶입니다. 최종 보고서는 보고서 포함 head, CI 결과, merge 신원을 추가해야 합니다.
