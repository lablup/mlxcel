# 기술 보고서: PR #3106 - 디코드 KV 캐시를 수축 정밀도로 저장

**작성일**: 2026-11-16
**상태**: 완료
**언어**: Rust (MLIR emitter), Bash (측정)
**위험도**: 중간

---

## 요약

단일 시퀀스 IREE 디코드 스텝은 KV 캐시를 f32 모듈 전역에 두면서 모든 소비 수축 연산은 f16으로 실행했다. 그래서 매 스텝마다 모든 레이어가 캐시 슬래브 전체를 변환했고, 스텝당 32개의 레이아웃 전치 디스패치와 10.5 MB의 캐시 트래픽(5.3 MB로 충분한 양)이 발생했다. 이제 전역은 수축 정밀도(hip과 cuda에서 f16, `MLXCEL_XLA_PRECISION=bf16`에서 bf16, CPU에서 f32)를 가지며, 새로 쓰는 행은 갱신 지점에서 한 번만 좁아지고, `decode_step.kv_import`는 f32 시그니처를 유지한 채 요청당 한 번 변환한다. 절감량은 KV 슬래브에 비례한다. 용량 512에서는 짝지은 프로토콜의 노이즈 안에 있고(4회 실행, 50라운드, 새 arm이 27라운드 우세), 용량 2048에서는 +2.85%(12라운드 중 9라운드)로 측정되며 greedy 출력은 동일하다.

---

## 1. 문제 정의

### 1.1 배경

이슈 #2886은 OpenXLA/IREE 백엔드의 디코드 격차 중 남은 부분을 다뤘다. #3048이 KV 캐시를 모듈 전역으로 옮기고 PR #3065가 스텝당 호스트 스테이징 읽기를 제거한 뒤, `gfx1151`의 native 양자화 디코드 스텝은 약 5.0 ms, MLX ROCm은 약 4.2 ms로 측정됐다. native 경로의 커널 트레이스(281 디스패치, 커널 시간 3.976 ms, 런치 갭 1.077 ms)는 가중치 스트리밍 커널이 이미 실용 로우프라인에 있음을 보였다. gate/up과 LM head는 230~240 GB/s였고, 스텝 전체는 압축된 가중치 695 MB를 199 GB/s로 스트리밍했다.

### 1.2 기존 문제점

- **문제 1**: 디코드 KV 전역이 `f32`인데 score와 context 수축은 `f16`으로 실행되어, IREE가 수축 전마다 슬래브 전체 `convert`를 삽입했고 이것이 스텝당 32개의 레이아웃 전치 디스패치로 융합됐다.
- **문제 2**: 그 변환이 스텝당 10.5 MB의 캐시를 이동시켰고, 좁힌 형태는 5.3 MB로 충분했다.
- **문제 3**: 변환 비용이 KV 슬래브에 비례하므로, 디코드가 실제로 도는 컨텍스트 용량이 커질수록 함께 커진다.

### 1.3 위험성

| 위험 | 영향 | 발생 가능성 |
|------|------|-------------|
| 어떤 그래프가 좁아진 전역에 f32 행을 씀 (StableHLO 원소 타입 불일치) | 높음 (그래프 컴파일 불가) | 실제 발생: MLA 단일 디코드 경로, 리뷰에서 발견되어 수정됨 |
| greedy 출력이 드러낼 수 있는 수치 변화 | 높음 | 낮음 (측정: 모든 짝지은 실행에서 `text EQUAL`, 배치 `REFERENCE-EXACT`) |
| 출력된 정밀도와 런타임이 컴파일한 정밀도의 불일치 | 중간 | 낮음 (`resolve_precision`이 생성된 MLIR로 vmfb 캐시를 키잉) |

## 2. 기술적 검토 사항

### 2.1 보안 관점

새로운 입력, 네트워크, 파일 표면은 없다. 디바이스 상주 버퍼를 좁히고 C shim ABI는 그대로다. `xla_validate_kv_pair`는 여전히 받는 f32 프리필 캐시를 검증한다.

**체크리스트:**
- [x] 입력 검증 (변경 없음, 프리필 캐시는 f32 rank-4로 계속 검증)
- [x] 인증/인가 (해당 없음)
- [x] 데이터 암호화 (해당 없음)
- [x] 로깅 (모델 데이터 없음)

**발견 사항:** MLA dtype 불일치(`044eded6`에서 수정). 보안 리뷰에서 CRITICAL, HIGH, MEDIUM은 없었다.

### 2.2 성능 관점

| 항목 | 변경 전 | 변경 후 |
|------|---------|---------|
| 트레이스된 디코드 스텝 | 5.054 ms | 4.895 ms |
| 스텝당 디스패치 | 281 | 263 |
| 스텝당 런치 갭 | 1.077 ms | 0.982 ms |
| 스텝당 캐시 트래픽 | 10.5 MB | 5.3 MB |
| 짝지은 A/B, 용량 512 | 197.01 / 199.43 / 200.07 / 201.01 tok/s | 200.14 / 200.20 / 201.87 / 199.78 tok/s |
| 짝지은 A/B, 용량 2048 | 178.02 tok/s | 183.09 tok/s (+2.85%) |

### 2.3 호환성/의존성 관점

- **호환성 파괴**: 없음. 컴파일된 디코드 그래프의 전역 원소 타입은 바뀌지만 번들에 버전이 없고 C shim은 전역을 직접 건드리지 않는다. `decode_step.kv_import`는 f32 시그니처를 유지한다.
- **새 의존성**: 없음.
- **호환성**: 프리필, ragged, 균일 배치 캐시는 f32 버퍼 인자로 남는다. MLA는 `effective_precision`을 통해 자체 기본값(f32)을 유지하고, 명시적 f16/bf16에서는 일반 K/V 경로처럼 latent와 PE 행을 좁힌다.

### 2.4 코드 품질 관점

- **테스트 커버리지**: 전역 원소 타입을 f32, f16, bf16에 대해 고정하고 슬래브 전체 변환이 없음을 단언하는 emitter 테스트, MLA 디코드를 f16으로 생성해 행 변환을 단언하는 리뷰 테스트, 그리고 문서화된 정밀도 오버라이드에 흔들리지 않도록 f32로 고정한 `single_decode_threads_kv_through_module_globals`.
- **코드 복잡도**: 두 쓰기 지점이 공유하는 `narrow_cache_row` 헬퍼 하나, crate 공개가 된 `Precision::dot_elt`.
- **기술 부채**: 감소. MLA 경로가 이탈하게 만든 중복 좁힘 클로저가 사라졌다.

## 3. 기술적 선택과 그 이유

### 3.1 읽기마다 변환하는 대신 캐시를 수축 정밀도로 저장

**컨텍스트:** 캐시는 f32였고 모든 수축이 그것을 좁혔다. 읽기와 저장 중 하나를 바꿔야 했다.

**고려한 대안:**

| 대안 | 장점 | 단점 |
|------|------|------|
| f32로 두고 읽기마다 변환 | ABI와 dtype 변경 없음 | 스텝당 슬래브 전체 변환, 용량에 비례 |
| f16으로 저장하고 읽을 때 넓힘 | 저장도 좁아짐 | 스텝당 슬래브 전체 확장, 비용은 그대로 이동 |
| **선택: 수축 정밀도로 저장하고 새 행만 좁힘** | 슬래브마다가 아니라 행마다 한 번 변환 | 전역 원소 타입이 바뀌므로 모든 쓰기 지점이 좁혀야 함 |

**선택 이유:** 매 스텝 쓰는 행은 `capacity` 행 중 1행이므로, 쓰기 지점에서 좁히는 형태만 비용이 용량에 비례하지 않는다.

**트레이드오프:** 정밀도 적용이 읽기마다가 아니라 쓰기 시점 한 번으로 옮겨졌다. 보안 리뷰는 모든 소비자에 대해 이전 동작과 비트 단위로 동일함을 확인했다. `dot_general`이 f32 피연산자를 강등하고 이미 좁은 피연산자는 건드리지 않기 때문이다.

### 3.2 `kv_import`는 f32를 유지하고 요청당 한 번 변환

**컨텍스트:** 호스트는 컨텍스트 전환이나 캐시 초기화 때 KV 캐시를 가져온다.

**고려한 대안:**

| 대안 | 장점 | 단점 |
|------|------|------|
| `kv_import`를 캐시 원소 타입으로 좁힘 | 그래프 내 변환 없음 | C shim의 f32 버퍼 ABI가 모든 호출자에 대해 깨짐 |
| **선택: f32 가져오기를 유지하고 한 번 변환** | shim 변경 없음, 요청당 한 번 변환 | 가져오기마다 슬래브 전체 변환 1회 |

**선택 이유:** 요청은 한 번 가져오고 여러 스텝을 디코드하므로, 가져오기 시점 변환은 스텝 경로에 없고 shim은 하나의 ABI를 유지한다.

### 3.3 두 쓰기 지점이 하나의 `narrow_cache_row` 헬퍼를 사용

**컨텍스트:** 일반 K/V 경로와 MLA latent/PE 경로가 같은 단일 디코드 전역에 쓴다.

**선택 이유:** 리뷰에서 MLA 경로가 빠져 있음을 발견했고, 중복된 클로저가 두 경로를 이탈시킨 원인이었다. 헬퍼 하나로 묶으면 향후 쓰기 지점은 컴파일되지 않는 그래프를 만들지 않고 즉시 드러난다.

## 4. 구현 상세

### 4.1 주요 코드 변경

**파일: `src/lib/mlxcel-xla/src/emitter/model.rs`**
```rust
let cache_elt = b.precision().dot_elt().unwrap_or("f32");
let cache_ty = Ty::new(vec![c.n_layers, c.context_capacity, c.cache_heads(), c.cache_dim()], cache_elt);
// 새 행은 갱신 지점에서 한 번만 좁힌다.
let k_upd = narrow_cache_row(b, b.reshape(kk, vec![1, 1, nkv, d]));
```
**변경 이유:** 전역의 원소 타입이 IREE가 읽기마다 슬래브를 변환할지를 결정한다. 행을 좁히면 변환이 스텝 경로에서 벗어난다.

**파일: `src/lib/mlxcel-xla/src/emitter/model.rs`, MLA 경로 (`044eded6`)**
```rust
let latent_update = narrow_cache_row(b, latent_update);
let pe_update = narrow_cache_row(b, pe_update);
```
**변경 이유:** 이것이 없으면 `stablehlo.dynamic_update_slice`가 f16 피연산자와 f32 갱신을 섞어 MLA 디코드 그래프가 컴파일되지 않는다.

### 4.2 데이터 모델 변경

디코드 KV 전역이 `tensor<n_layers x capacity x heads x dim x f32>`에서 같은 모양의 f16 또는 bf16으로 바뀐다. 실행 간에 유지되는 상태는 없고, vmfb 캐시는 생성된 MLIR로 키잉된다.

## 5. 학습 포인트

### 5.1 저장 정밀도도 로어링 결정이다

**개념:** 버퍼와 모든 리더 사이에 원소별 변환이 있으면 변환 비용은 버퍼 크기 × 읽기 횟수에 비례한다. 정밀도를 버퍼로 옮기면 쓰기당 한 번의 변환이 된다.

**이 PR에서의 적용:** 스텝당 32개의 디스패치와 5.2 MB의 트래픽이 사라졌고, 절감은 KV 용량에 비례해 커졌다. 그래서 용량 512에서는 보이지 않고 2048에서 측정된다.

### 5.2 짝지은 프로토콜은 작은 효과를 위아래로 한정한다

**개념:** 인터리브 짝지은 라운드는 드리프트를 상쇄하지만 노이즈는 상쇄하지 않는다. 분해능은 라운드 수만이 아니라 호스트의 라운드 간 편차가 결정한다.

**이 PR에서의 적용:** 이 변경의 첫 주장은 트레이스된 스텝 시간 하나였다. 용량 512에서 50개의 짝지은 라운드로도 1퍼센트 효과를 0과 구분할 수 없었고, 그 사실을 정직하게 보고했기에 메커니즘이 드러날 만큼 큰 용량에서 다시 측정하게 됐다.
