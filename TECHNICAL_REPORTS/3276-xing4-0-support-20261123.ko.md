# PR #3276: Xing4.0 (xing4_0) 지원 추가

**날짜**: 2026-11-23
**상태**: Draft PR (#2356을 닫음). 단위 테스트 통과. M3 Ultra에서 `xing4.0-29b-a4b-mlx-8bit`(패리티 게이트)와 `xing4.0-29b-a4b-optiq-4bit` 실체크포인트를 검증했고, 공유 DeepSeek-V3 코드에 대해 `moonlight-16b-a3b-instruct-4bit` 변경 전후 trace를 비교했다

## 요약

Xing4.0은 총 29B, 활성 4B인 MoE다. 디코더는 DeepSeek-V3(MLA attention, 64개 expert에서 top-4를 고르는 `noaux_tc` sigmoid 라우팅과 shared expert 1개, YaRN RoPE)이고, 이를 폭 `hc_mult = 4`인 manifold hyper-connection residual stream이 감싼다. mlx-vlm은 구현하고 있고(`mlx_vlm/models/xing4_0`), mlx-lm은 구현하지 않는다. 이 PR은 기존 `deepseek_v3`의 attention, MoE, sanitize를 조합해 `src/models/xing4_0.rs`로 포팅하고, hyper connection, stream 관리, head만 새로 추가한다.

작업 중 공유 코드의 공백 세 가지가 드러났고, 모두 이 PR에서 막는다.
- `DeepSeekV3Attention`이 YaRN을 전혀 반영하지 않았다. 그래서 Xing만 쓰는 opt-in 주파수 테이블을 넣었고, 다른 family의 경로는 바이트 단위로 그대로다.
- OptiQ 4-bit 내보내기는 4-bit 기본값 아래 MLA projection과 일부 expert plane을 8-bit로 저장한다. 이 때문에 `quantized_matmul` 안에서 프로세스가 abort했다. 두 로더가 이제 각 plane의 폭을 shape에서 구한다.
- 체크포인트 tokenizer 설정에 `add_bos_token`이 없고 `Xing4_0Tokenizer` 생성자의 기본값 true에 기댄다. mlxcel이 이제 이 기본값을 따른다.

그 결과 8-bit trace에서 mlx-vlm 대비 decided top-1 불일치는 1190개 중 0개이고, perplexity 차이는 0.08% 이내다.

## 1. 문제

### 1.1 Hyper connection

블록 사이의 상태는 `[B, L, D]`가 아니라 `[B, L, hc, D]`다. 각 sublayer(attention, 그다음 MLP)는 같은 connection을 거친다.

1. 펼친 `[hc * D]` 상태를 f32로 RMS 정규화하고, activation dtype으로 `hc_fn`(`[(2 + hc) * hc, hc * D]`)과 섞은 뒤 결과를 f32로 올린다.
2. 섞은 값을 `pre`(`hc`), `post`(`hc`), `comb`(`hc x hc`)로 나눈다. `pre = sigmoid(pre * s0 + b)`이고 eps는 없다. `post = 2 * sigmoid(post * s1 + b)`, `comb = comb * s2 + b`.
3. `comb`에 Sinkhorn을 적용한다. [-30, 30]으로 clip하고 `exp(x - rowmax)`를 취한 뒤, 정확히 `iters`번 동안 행 정규화와 열 정규화를 차례로 한다. 각 정규화는 `x / (sum + eps)`다.
4. `sum(pre * x, axis=2)`로 stream을 접어 `[B, L, D]`에서 sublayer를 돌리고, `post * out + comb @ x`로 다시 편다.

임베딩은 `hc`번 반복되어 들어간다. head는 stream 평균을 낸 뒤 final norm을 적용한다.

DeepSeek-V4에도 비슷하게 생긴 hyper connection이 있다. V4는 softmax 행, `pre`에 eps 추가, 열 우선 시작, `comb.T @ x` 확장을 쓴다. 이 차이 하나하나가 그럴듯한 포팅 실수이면서 텍스트를 눈에 띄게 망가뜨리지는 않는다. 그래서 검증에 이 변형들의 negative arm을 넣었다(4절).

### 1.2 공유 코드의 공백

| 공백 | Xing4.0에 미친 영향 | 다른 family에 미치는 영향 |
|---|---|---|
| `DeepSeekV3Attention`이 항상 `rope_theta`로 `fast_rope` 호출 | 위치 주파수가 틀림(체크포인트에 YaRN 블록이 있음) | 실제 DeepSeek-V3, Kimi K2 YaRN 체크포인트도 같음. 이 PR에서는 고치지 않음 |
| `QuantizedMultiLinear::from_weights`가 선언된 bits를 그대로 저장 | OptiQ 4-bit의 8-bit `embed_q`가 `quantized_matmul`에서 abort | MLA family의 모든 per-path override |
| `deepseek_v3::SwitchGLU`가 expert plane 셋에 한 폭만 사용 | OptiQ 4-bit의 8-bit expert plane이 `gather_qmm`에서 abort | DeepSeek-V3 per-path 내보내기도 같음 |
| SentencePiece 경로가 `add_bos_token` 기본값을 false로 둠 | `<_start>` anchor가 빠져 position 0부터 reference와 어긋남 | 없음(class 한정 규칙) |

리뷰 후속 수정(같은 PR):
- Xing에 RoPE 테이블이 없을 때도 `--rope-freq-base`가 attention에 반영된다(pr-reviewer, HIGH).
- 1-bit routed-expert plane은 `gather_qmm` abort 대신 로드 오류가 된다(pr-security-checker, HIGH).

## 3. 설계 결정

**복사가 아닌 조합.** Xing은 `deepseek_v3::DecoderLayer::from_weights`를 그대로 쓰고 분해한다. 그래서 MLA attention, router, expert가 DeepSeek-V3와 같은 코드다. 그 대가로 `deepseek_v3.rs`의 테스트 helper 몇 개를 `pub(crate)`로 열었고, attention에 builder 메서드 하나를 추가했다.

**일반 YaRN 수정 대신 opt-in RoPE 테이블.** 모든 DeepSeek-V3 family의 YaRN을 고치면, 출시된 체크포인트(DeepSeek-V3, Kimi K2)의 출력이 그 체크포인트에 대한 trace 없이 바뀐다. 테이블은 Xing만 설치한다. Moonlight의 변경 전후 trace는 바이트 단위로 같다.

**선언된 폭으로 돌 수 없을 때만 shape에서 폭을 구한다.** 두 로더 모두 shape가 선언과 맞으면 선언된 폭을 그대로 돌려준다. 동작이 바뀌는 레이아웃은 전에 프로세스를 abort시키던 것뿐이다. 이제 그런 레이아웃은 구한 폭으로 로드되거나, plane 이름을 단 로드 오류로 끝난다.

**MLA latent는 fp16만.** `xing4_0`은 `MLA_LATENT_CACHE_FAMILIES`에는 들어가지만 quantized-latent 목록에는 들어가지 않는다. 이 family에서 quantized latent를 측정하지 않았기 때문이다.

## 4. 검증

`docs/architecture.md`에 대한 teacher-forced logit trace다. plan은 `64 40 8 1536`(2560 position, BOS anchor)이고, `scripts/compare_logit_traces.py --decided 2`로 채점했다.

| 비교 | decided top-1 불일치 | Perplexity |
|---|---|---|
| mlxcel 8-bit 대 mlx-vlm 8-bit | 0 / 1190 | 7.9571 대 7.9506 (+0.08%) |
| `comb.T` 확장을 쓴 mlx-vlm 대비 | 180 / 760 | 해당 arm 45.10 |
| V4 Sinkhorn을 쓴 mlx-vlm 대비 | 6 / 1156 | 해당 arm 8.49 |
| YaRN을 뺀 mlx-vlm 대비 | 6 / 1159 | 해당 arm 8.31 |
| mlxcel OptiQ 4-bit 대 mlx-vlm 8-bit | 0 / 1190 | 8.0360 (+1.07%) |
| mlxcel 8-bit 대 mlx-vlm, 단일 토큰 decode step(48 position) | 0 / 11 | +0.69% |

negative arm 결과는 이 trace가 중요한 세부를 실제로 구분한다는 것을 보여준다. reference 자신도 negative arm과 각각 494, 15, 5개 decided position에서 어긋난다. 따라서 mlxcel이 reference에 대해 0인 것은 허용 오차가 차이를 가린 결과가 아니라 실제로 구분된 결과다.

공유 코드: `moonlight-16b-a3b-instruct-4bit` trace(plan `64 20 8 512`)를 `c0bcf575`와 이 브랜치에서 각각 빌드해 비교했고, 바이트 단위로 같았다. 로더를 바꿀 때마다 다시 확인했다.

종단 간 확인:
- `mlxcel generate --temp 0`은 8-bit(약 19 tok/s, 상주 29.2 GB)와 OptiQ 4-bit(약 22 tok/s, 19.2 GB) 모두에서 일관된 텍스트를 낸다. 둘 다 `17 * 23`에 391로 답한다.
- 8-bit 체크포인트로 띄운 `mlxcel-server`는 non-streaming과 streaming chat completion 모두 일관된 답을 돌려준다.

단위 테스트: `models::xing4_0`(16), `models::deepseek_v3`, `models::deepseek_v32`, `models::glm4_moe_lite`, `models::longcat`, `models::detection`, `models::registry`, `tokenizer::tests`, `coverage_tests`, 그리고 mlxcel-core의 `mla::`, `one_bit`, `layers::`. 전역 MLA stats counter를 확인하는 GLM4 MoE Lite와 LongCat의 latent 경로 테스트는 두 모듈을 병렬로 돌리면 실패하고, `--test-threads=1`에서는 통과한다. 이 변경이 있든 없든 마찬가지다. `-D warnings` clippy와 모든 contract check가 통과한다.

## 5. 알려진 한계와 후속 과제

- 실제 DeepSeek-V3와 Kimi K2 YaRN 체크포인트는 여전히 plain RoPE로 돈다. 이들을 opt-in하려면 별도의 긴 컨텍스트 trace가 필요하다.
- OptiQ 내보내기는 로드 시 per-path layer마다 reconciliation 경고를 하나씩 남긴다(약 360줄). 기존 `UnifiedLinear` 경로와 같은 동작이다.
- 범위 밖: MTP drafting, fused Sinkhorn kernel(루프가 sublayer마다 반복당 작은 연산 약 6개를 추가함), hyper connection의 tensor-parallel sharding, 이 family의 quantized latent cache.
