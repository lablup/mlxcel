# Where the Laguna DFlash verify round's fixed cost goes on GB10, and the fix

Issue #1799. Host GB10 (sm_121), MLX pin `81ba1c6a`, CUDA release build, toolchain 1.97.1, source tree `2deae307` (the squash of PR #1771; byte-identical to the PR head `dab18fdf` that the earlier sweep measured). Full measurement record: `docs/benchmark_results/laguna-dflash-verify-cost-gb10-2026-09-11.md`.

## Background

PR #1771 shipped the Laguna DFlash drafter behind a fail-closed exactness gate and measured that no block width beats classic decode on this host: the verify round's device time fit a fixed 77 ms plus about 3 ms per row, 2.5x a single-token step even at 2 rows, and the PR attributed that to the multi-row forward running "eagerly and launch-bound". The issue was filed with that phrase demoted to a hypothesis: nothing in the pinned MLX capture path branches on row count, #1782 had just disproved the same intuition on Qwen 3.5, and neither of #1782's fixes applied here (this drafter was already bf16; Laguna has no gated-delta layers). Its sweep had also run with another session's build on the CPU. So the task was attribution first, on an idle host, with `nsys --cuda-graph-trace=node`, and a measured negative counted as a valid close.

## What the measurement said

Idle host (start gated on load1 under 0.6, load1 recorded per run, `ps` showing only the process under test), same binary on every arm, `mlxcel generate` with the 152-token raw code prompt of #1782, widths 2 to 16 interleaved, n = 3 with min and max. The idle host did not rescue the pairing: classic 29.28 tok/s (34.2 ms per step); block 2 at 0.52x, block 6 at 0.72x (the best), block 16 at 0.52x; device sync per round 71.6 ms plus 3.79 ms per row by least squares; and the round's three serial links (31 ms drafter host build, 4 ms verify host build, 80 ms device sync at block 2) add up to its 115 ms wall to within 0.1 ms.

The graph-side candidates all came back negative with bounds. `MLX_MAX_MB_PER_BUFFER=400`, `MLX_MAX_OPS_PER_BUFFER=100`, both raised, and `MLX_USE_CUDA_GRAPHS=0` each move the 2-row device sync by at most 3% and the round by at most 4%; capture off leaves block 8 faster than capture on, as on Qwen 3.5. Graph replay is healthy (under one `cudaGraphInstantiate` per 1000 `cudaGraphExecUpdate` at every width), so re-instantiation is ruled out. The byte budget is worth 8% on the classic arm (every 256-expert nvfp4 stack exceeds GB10's 25 "MB" cap on its own, since the counter sums element counts) but does not separate the arms.

The profile put the two terms in different places. Differencing a 400-token and a 200-token profile of the same configuration (so load, prefill and the exactness probe cancel) gives per round at block 8: 86.7 ms of GPU kernel time inside a 142.6 ms round, a 61% busy fraction, against 96% on the classic step. The per-row term is GPU work in the routed experts: `qmm_sm80` through `gather_qmm` grows from 39.4 ms at 8 rows to 59.4 at 16, 2.5 ms per row, close to the floor of reading each selected expert once per (row, expert) pair. Two premises of the issue fell here: this checkpoint's attention projections, gate, router and lm_head are plain bf16 (`gemv_single` at one row, a cutlass bf16 GEMM at two or more), only the experts are NVFP4, so there is no `fp_qmv` to `qmm_sm80` switch on the projections; and `SwitchGLU` expands its input so `gather_qmm` sees `M = 1, B = 8n`, which puts the experts on `qmm_sm80` at every width, classic included.

The fixed term is host time in one primitive. MLX's NVTX ranges, differenced the same way, show `ScaledDotProductAttention::eval_gpu` at 67.1 ms per round at block 8 and 75.8 at block 16, against 2.8 ms per classic token, over the same 45 calls (40 target layers plus 5 drafter layers). A one-row decode call takes the `sdpa_vector` kernel. A multi-row masked call with head_dim 128 and bf16 is cuDNN-eligible, and MLX caches the cuDNN execution plan in an LRU keyed on the exact query, key, value and mask shapes and strides. A verify round appends rows to the KV cache, so the key length and mask shape are new every round for each of three shape classes (target full layers, target sliding layers with sinks, drafter layers): three misses per round, each a cuDNN frontend graph build of about 22 ms. That is row-independent, it is invisible to every graph knob, and it also explains the drafter's flat 30 ms host build (its five layers pay one of the three builds).

The same LRU keeps a lifetime miss counter and throws MLX's fatal `Cache thrashing` error past twice its capacity (512). At three misses per round that is about 170 rounds per process: every block 2 profile past 200 tokens aborted on exactly that throw (400 tokens twice, 300 tokens once), while the 200-token runs and the block 8 and 16 runs at 400 tokens (163 and 161 rounds) completed. So before this issue a Laguna DFlash generation longer than about 170 rounds ended the process.

The zero-code control confirmed the mechanism end to end: `MLX_CUDA_USE_CUDNN_SDPA=0` takes 39 ms off the device sync and 21 ms off the drafter host build at every width, leaves the classic arm untouched, and puts block 4 at 1.34x and block 8 at 1.15x over classic. It is not the fix, because it also takes prefill off cuDNN's flash kernels.

## The change

Two pieces, both with an environment kill switch, nothing in the round loop or the Laguna sources.

1. A patched `mlx/backend/cuda/scaled_dot_product_attention.cpp` (the pinned file with one added gate, the same overlay mechanism as the existing `.cu` patch): `supports_sdpa_cudnn` refuses a masked call with 2 to `MLXCEL_SDPA_FALLBACK_MAX_QUERIES` (default 32) query rows over a longer key sequence. Such a call then takes MLX's own ops fallback (the same arithmetic the CPU backend and the Qwen 3.5 head_dim-256 verify already use, sinks included), which has no per-shape build. The one-row decode step is untouched (vector kernel), and so is prefill (its key length equals its query length, or it has more rows than the bound; only the last short chunk of a chunked prefill changes path). `MLXCEL_SDPA_FALLBACK_MAX_QUERIES=0` restores upstream dispatch without a rebuild and is the kill switch for the A/B.
2. `MLX_CUDA_SDPA_CACHE_SIZE` defaults to 2000 on CUDA builds through `hardware::apply_cuda_sdpa_cache_default`, the sibling of the #818 graph-cache default, applied from the same four entry points with the same env-wins contract. With the gate in place the verify no longer misses the plan cache, but prefill prompt-length diversity alone crosses the 512-miss abort on a long-lived server, and the abort is a process death rather than a request error.

Same binary, same method, quiet host, n = 3 per arm; `ks-*` sets `MLXCEL_SDPA_FALLBACK_MAX_QUERIES=0`.

The kill switch reproduces the baseline within 2% at every width. The device sync is now `36.0 + 3.6 ms per row` (was `71.6 + 3.79`): the floor fell from 2.1x to 1.05x a classic step and the per-row slope is the expert reads, unchanged. ## Blast radius: measured against sharing the path

Measured: the Laguna pairing (0.52x to 1.13x at block 2, 0.70x to 1.33x at block 4, kill-switch A/B on the same binary) and Qwen 3.5 as the cross-family control (1.26x and 1.35x, text byte-identical to classic on the new binary). Qwen 3.5's head_dim of 256 never qualified for cuDNN, so the gate cannot reach it; its number shows the rebuild changed nothing else.

Sharing the path without a number: every other CUDA model whose masked SDPA calls with 2 to 32 query rows and prior context reach `scaled_dot_product_attention.cpp` on Ampere or later. That is the speculative verify of any pairing whose target has head_dim 128 or less (in tree: Muse Glimmer DFlash, LFM2 and LFM2.5 DSpark, Inkling MTP; none re-probed here, and a flipped exactness probe declines speculation rather than corrupting output), a short incremental prefill over a reused prefix-cache prefix (2 to 32 new rows over a long key length, a common server shape that no arm here exercised; every arm used a 152-token prompt), and the trailing short chunk of a chunked prefill. Those calls now run MLX's fallback arithmetic instead of cuDNN's. The generic `DFlashAttention::forward` passes no mask, so a non-Laguna DFlash drafter with head_dim 128 or less would still rebuild one plan per round; no such pairing is on main. Metal and CPU are unaffected. The Laguna exactness gate is not touched; its decline on this host (`qmm_sm80` against `fp_qmv` rounding at logit ties) is a separate issue. The cache-size default reaches every CUDA process; the cache is `thread_local`, so 2000 is per MLX eval thread, and a 2000-entry cache of built cuDNN graphs has no measured memory figure.

## What is not fixed

The fallback's cost grows with the key length: it replaces about 66 ms of constant host time per round with GPU work over a `[B, heads, q_len, k_len]` score matrix, about 10 ms more per round at block 2 with 350 keys, and the point where cuDNN's constant plan cost would be cheaper is in the tens of thousands of key tokens at block 16; the gate bounds `q_len` only, and no arm ran past 350 keys. The chunk budget now covers the diverted calls through `layers::attention` and `causal_attention`, while the four sinks paths that call the fast SDPA directly bypass it as before (bounded for Laguna by its 512-key window, unbounded on gpt_oss's full-attention sinks layers).

The general fix is deliberately not attempted here. MLX keys its cuDNN plan cache on the exact key length and mask shape, so a verify round structurally never hits it; padding or bucketing the key length, as MLX's own `use_cudnn_for_decoding` already does for one-row calls against a fixed-size cache, would let the cache hit and keep cuDNN's faster flash kernel, recovering the 10 ms the fallback costs. That cache-key design is the defect underneath this issue and the maintainer is filing it as its own issue; the LRU's lifetime miss counter, which aborted every block 2 profile past about 170 rounds, is the evidence that its miss path is terminal rather than merely slow, and the `MLX_CUDA_SDPA_CACHE_SIZE=2000` default only buys a larger lifetime budget.

What also remains is the per-row expert term (2.5 ms per row, inherent to a MoE verify unless rows that route to the same expert share its read) and the bf16 GEMM's fixed 12 ms over the one-row gemv; the width curve after the fix peaks at block 4 and the checkpoint default of 16 is still the worst width, which is the #1797 policy question. The classic-arm finding that GB10's default graph budgets make capture a net loss on this MoE model (graphs off +12%, both budgets raised +16%, opposite sign to Qwen 3.5) is recorded for #1798 and not changed here.

## Verification

The patched file is the pinned upstream file plus one gate. `git show 81ba1c6a:mlx/backend/cuda/scaled_dot_product_attention.cpp` differs from `src/lib/mlx-cpp/patches/mlx/backend/cuda/scaled_dot_product_attention.cpp` in exactly two hunks, the header comment and the gate in `supports_sdpa_cudnn`. No build wiring was added, because `src/lib/mlx-cpp/CMakeLists.txt` already globs `patches/mlx/backend/cuda/*` onto the fetched MLX tree.

Every call the gate refuses still has a path, and those paths agree with cuDNN's semantics. With an array mask, or with 4 to 32 rows, `supports_sdpa_vector` refuses as well (it takes no array mask and no `q_len` of 4 or more), so `ScaledDotProductAttention::use_fallback` returns true and `mlx/fast.cpp` runs the ops fallback, which honors the array mask, bool masks, GQA repeats, sinks, and a causal offset of `k_len - q_len`. With 2 or 3 rows and no array mask the call takes `sdpa_vector`, whose causal predicate `i <= kL - qL + q_seq_idx` is the same bottom-right alignment as cuDNN's `set_causal_mask_bottom_right`. The one-row decode step never reaches the gate, which requires `q_len > 1`. The frontend's `force_fused=True` path would now raise where cuDNN used to serve it, and nothing in mlxcel sets that flag. The backward primitive never consults `supports_sdpa_cudnn`, and its own `use_fallback` requires `q_len % 128 == 0`, so training shapes cannot intersect the gate.

Measurement: every arm is n = 3 on an idle host (start gated on load1 under 0.6, load1 recorded per run, `ps` checked for a second consumer), baseline and fix on the same binary, with `MLXCEL_SDPA_FALLBACK_MAX_QUERIES=0` as the in-binary kill switch. The kill-switch arm reproduces the pre-fix baseline within 2% at every width, which is what makes the A/B measure the gate and not the rebuild. The classic arm was re-measured in the same session on both settings. Full tables, the nsys attribution and the zero-code controls are in the record.

Gates: `cargo fmt --all -- --check` clean. The Rust side adds `cuda_sdpa_cache_default_matches_build_feature` beside the #818 test in `hardware.rs` and is gated by `cargo test --profile test-fast --features cuda -p mlxcel-core hardware::` and `cargo clippy --profile test-fast --features cuda --lib --bins --tests -- -D warnings`; an unscoped `cargo test --lib` aborts on this host with a `cudaStreamEndCapture` C++ abort unrelated to this change, so the selector is narrow by necessity. The `metal,accelerate` gate is not runnable on this Linux/CUDA host and is unrun, and the change cannot reach it: the patched file is compiled only into the CUDA backend, and `cuda_sdpa_cache_default` returns `None` without the `cuda` feature.
