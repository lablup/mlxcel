# 기술 보고서: PR #3109 - A/B 빌드 워크트리를 모든 종료 경로에서 제거

**작성일**: 2026-11-16
**상태**: 완료
**언어**: Bash
**위험도**: 낮음

---

## 요약

짝지은 A/B 하네스 `scripts/xla/ab_decode_pair.sh`는 git ref로 지정한 각 arm을 약 2.2 GB짜리 임시 워크트리에서 빌드하고도 그 워크트리를 제거하지 않았다. 워크트리 등록이 커맨드 치환 안에서 이루어져 EXIT 트랩이 빈 배열을 보았기 때문이다. 새어 나온 워크트리 6개가 측정 호스트의 16 GiB `/tmp` tmpfs를 가득 채워 측정 실행 하나를 죽였다. 같은 하네스는 측정값을 고정 경로 `/tmp` 파일에서 읽어 들이며 파싱할 수 없는 라운드를 조용히 버렸고, 그래서 10라운드 실행이 오류 없이 `n=3`을 보고했다. 이제 워크트리 경로는 실행별 파일에 기록되고, 정리는 EXIT, INT, TERM, HUP에서 실행되며, 요약은 도달한 라운드 수가 요청한 수와 다르면 결과를 보고하지 않는다.

---

## 1. 문제 정의

### 1.1 배경

OpenXLA/IREE 백엔드의 디코드 성능은 짝지은 인터리브 A/B로 측정한다. 두 arm을 번갈아 실행하고 중앙값을 보고하며 greedy 텍스트가 일치해야 한다. git ref로 지정한 arm은 별도 워크트리에서 빌드해 한 명령으로 두 리비전을 측정한다.

### 1.2 기존 문제점

- **문제 1**: 워크트리 등록 `WORKTREES+=("$wt")`가 `build_arm` 안에서 실행되고, `build_arm`은 `resolve_arm`을 통해서만 호출되며 두 호출부 모두 커맨드 치환(`NEW_BIN=$(resolve_arm ...)`)을 썼다. 서브셸의 배열 추가는 부모에 도달하지 않으므로 EXIT 트랩은 매 실행에서 빈 목록을 순회했다. 인터럽트 때만의 문제가 아니었다.
- **문제 2**: 제거 실패를 `|| true`로 버려서 실패한 제거가 성공처럼 보였다.
- **문제 3**: 등록 전에 실패한 `git worktree add`는 아무도 추적하지 않는 디렉터리를 남겼고, INT/TERM/HUP 트랩이 없었다.
- **문제 4**: 측정값을 `/tmp/ab_decode_pair_old.txt`와 `/tmp/ab_decode_pair_new.txt`에 두고, 요약은 파싱할 수 없는 줄을 건너뛰었다. `/tmp`가 가득 차 잃어버린 라운드는 오류 없이 표본만 줄였다.

### 1.3 위험성

| 위험 | 영향 | 발생 가능성 |
|------|------|-------------|
| 긴 측정 캠페인 중 `/tmp` 고갈 | 높음 (실행 중단, 출력 유실) | 변경 전 높음 |
| 보고된 중앙값이 표기한 라운드 수보다 적은 표본을 덮음 | 높음 (잘못된 성능 결론) | 변경 전 중간 |
| 동시 실행이 소유한 워크트리를 정리가 제거 | 높음 | 낮음 (자기가 기록한 것만 제거하고, 남은 것은 보고만 함) |

## 3. 기술적 선택과 그 이유

### 3.1 호출부를 고치는 대신 기록 파일

**컨텍스트:** 배열은 서브셸 경계를 넘지 못하고, arm은 `$(...)` 안에서 해석된다.

**고려한 대안:**

| 대안 | 장점 | 단점 |
|------|------|------|
| out-parameter (`resolve_arm`이 전역 `RESOLVED_BIN` 설정) | 새 파일 없음 | 두 호출부와 함수 계약을 고쳐야 하고, 다음 리팩터가 같은 패턴을 다시 만들 수 있음 |
| 호출 후 부모에서 등록 | 단순 | 빌드가 끝나야 경로를 알 수 있어 실패한 빌드가 새어 나감 |
| **선택: 실행별 `mktemp` 파일에 추가** | 서브셸을 넘어 살아남고, 워크트리가 생기기 전에도 등록 가능 | 실행마다 임시 파일 하나 |

**선택 이유:** 실패 모드는 정확히 "부모가 서브셸이 한 일을 볼 수 없다"였고, 파일은 양쪽이 볼 수 있는 가장 싼 수단이다. `git worktree add` 전에 경로를 기록하므로 add 실패나 빌드 실패도 덮인다.

**트레이드오프:** 임시 파일이 하나 늘고, 같은 트랩이 그것을 지운다.

### 3.2 남은 워크트리는 삭제하지 않고 보고

**컨텍스트:** SIGKILL로 죽은 실행은 정리할 수 없고, 기록이 없는 과거 실행의 워크트리가 남아 있다.

**선택 이유:** 시작할 때 `${TMPDIR}/mlxcel-ab-` 아래를 지우면 다른 장치에서 도는 실행의 빌드를 파괴한다. 경로와 회수 명령을 출력해 결정을 운영자에게 남긴다.

## 4. 구현 상세

### 4.1 주요 코드 변경

**파일: `scripts/xla/ab_decode_pair.sh`**
```bash
# 변경 전: 추가가 서브셸 안에 있었다
WORKTREES+=("$wt")
# 변경 후: 서브셸과 부모가 함께 쓰고 읽는 파일
printf '%s\n' "$wt" >> "$WORKTREE_LOG"
```
```bash
# 변경 전
old = load('/tmp/ab_decode_pair_old.txt')
# 변경 후: 실행별 파일, 그리고 라운드 수 검사
if len(old) != rounds or len(new) != rounds:
    print(f"... {len(old)} old and {len(new)} new rounds reached the summary, "
          f"expected {rounds}; the run is not reportable", file=sys.stderr)
    sys.exit(1)
```

**변경 이유:** 첫 번째는 모든 종료 경로에서 누수를 없애고, 두 번째는 잃은 라운드를 더 작은 표본이 아니라 실패로 만든다.

## 5. 학습 포인트

### 5.1 서브셸은 셸 상태를 조용히 버린다

**개념:** `$(...)`와 `( ... )`는 자식 셸에서 실행된다. 그 안에서 바꾼 변수, 배열, 트랩, `umask`는 부모에 도달하지 않고, 파일, 종료 코드, stdout은 도달한다.

**이 PR에서의 적용:** 호출자가 stdout이 필요한 함수의 부작용으로 등록이 이루어져 누수가 생겼다. 수정은 부작용을 서브셸이 공유하는 유일한 채널로 옮겼다.

**흔한 사용 사례:**
- 호출자 상태도 바꿔야 하는데 커맨드 치환으로 호출되는 함수 (배열이 아니라 out-parameter나 파일을 쓴다)
- 서브셸에서의 진행 상황 보고

### 5.2 측정 하네스도 테스트가 필요한 코드다

**개념:** 성능 수치는 그것을 만든 하네스만큼만 신뢰할 수 있고, 하네스 결함은 상태가 아니라 숫자를 바꾸므로 조용하다.

**이 PR에서의 적용:** 두 결함 모두 그럴듯한 출력을 냈다. 새 CI 잡이 스텁 툴체인으로 세 종료 경로를 검사하므로, 이제 하네스도 측정 대상 코드와 같은 수준으로 덮인다.
