# PR #2767: CUDA QuantizedMatmul의 배치 디코드 행 폴드

**작성일**: 2026-10-31 (머지 전 작성)
**상태**: 리뷰 중
**언어**: C++, Rust
**위험도**: 중간 (모든 CUDA 장치에 폴드가 적용되고, compute capability 12.1에서는 5~8행의 커널도 바뀐다. 측정은 RTX Spark N1X에서만 했다)

## 요약

배치 디코드는 투영마다 `x = [B, 1, K]`를 공유 2D 가중치 하나와 곱하는데, CUDA는 이를 B개의 독립 문제로 실행해 배치 항목마다 가중치 전체를 다시 읽었다. Metal과 ROCm은 이 형태를 이미 행으로 접고 있었다. 이 PR은 CUDA에 같은 폴드를 넣었고, RTX Spark N1X에서 8클라이언트 합산 디코드가 네 모델 기준 1.2~3.2배로 올랐다. compute capability 12.1에서는 요소 수 2^24 이상인 가중치가 5행부터 GEMM 커널로 넘어간다. 대신 Gemma 4 26B는 5~7클라이언트에서 약 2~5% 느려지는데 원인은 밝히지 못했다. 이 모델의 합산 처리량이 4~8클라이언트에서 평평한 것은 MoE gather를 건드리지 않았기 때문이다.

## 1. 문제 정의

### 1.1 CUDA의 기존 동작

디스패치는 `M = out.shape(-2)`, `B = out.size() / M / N`으로 계산하므로 `[8, 1, K]`는 `M == 1`인 문제 8개가 되고, 커널은 배치 항목마다 가중치를 읽는다. N1X에서 `[8, 1, 5120]`과 `[17408, 5120]`의 4비트 곱은 8.7 ms가 걸렸고, 같은 행을 `[8, 5120]`으로 주면 0.9 ms였다. 둘 다 약 430~520 MHz에서 잰 값이다.

서빙에서도 그대로 드러났다. Qwen 3.8 27B는 4클라이언트의 26 tok/s에서 8클라이언트의 14 tok/s로 떨어졌는데, 그 구간의 클럭은 1570~1830 MHz여서 클럭으로는 설명되지 않았다.

### 1.2 다른 백엔드

Metal의 `eval_gpu`는 2D 가중치와 row-contiguous `x`를 non-batched로 보고 `M = x.size() / K`로 계산한다. ROCm의 `qmm.hip`도 같은 조건에서 `M`에 배치 수를 곱한다. 두 백엔드에는 이 문제가 없으므로 폴드의 효과도 옮겨 가지 않는다.

## 2. 기술적 선택과 그 이유

### 2.1 오버레이 디스패치에서 접기

`QuantizedMatmul::eval_gpu`는 가중치가 2D이고 `B > 1`이며 `x.size() == B * M * K`일 때 접는다. `x`는 이미 row-contiguous이므로 `[B * M, K]` 뷰가 같은 메모리를 가리키고, `run_row_chunked`가 이 뷰를 넘긴다. 3D 배치 가중치는 접지 않는다. `GatherQMM`은 그대로 두었다. (토큰, 전문가) 쌍마다 다른 전문가 가중치를 읽어서 행들이 2D 가중치 하나를 공유하지 않기 때문이다.

### 2.2 기준은 행 수와 가중치 크기로 정한다

폴드만으로는 2~7행이 multirow qmv에 남는다. 행 수별 비교에서는 `[B, 1, K]`를 2행부터 GEMM으로 보낸 경우와 qmv로 둔 경우 두 가지만 돌려도 전환 지점을 모두 볼 수 있었다.

2클라이언트는 네 모델 모두 qmv가 빠르고, 3클라이언트는 Gemma 4에서 qmv가 빠르며 나머지는 비슷하다. 4클라이언트에서 GEMM은 Qwen 18%, Llama 7%, gpt-oss 3%의 이득을 내지만 Gemma 4에서 10~19% 느려져서 4는 기각했다. 5~7클라이언트에서 GEMM은 Qwen과 Llama에서 22~104%, gpt-oss에서 6~10%의 이득을 내고 Gemma 4에서는 5~7% 느리다.

Gemma 4와 gpt-oss의 가중치는 대부분 작고(Gemma 4의 `gate`는 2112 x 2816), Qwen과 Llama의 MLP 가중치는 14336 x 4096 이상이다. `N * K >= 2^24` 조건을 넣으면 Qwen과 Llama의 이득은 유지되고 Gemma 4의 손해는 2~5%로 줄며, gpt-oss의 이득은 2~4%p 줄어든다. 이 값은 네 모델에서 측정으로 고른 경계이고, 하드웨어에서 유도한 값이 아니다.

작은 가중치는 multirow 창의 한계인 8행까지 qmv에 둔다. 8클라이언트 합산이 0.5~3% 올랐고 손해를 본 모델이 없었다. 다른 compute capability는 측정하지 않았으므로 기준 8을 유지한다.

### 2.3 접힌 `M == 1` 배치만 옮긴다

추측 실행 검증은 multirow qmv가 행별 디코드와 비트까지 같다는 데 의존하고, 프리필 계획은 기존의 분할 동작에 의존한다(`docs/CONTINUOUS_BATCHING.md`). 검증 블록과 프리필 조각은 `M > 1`이므로 기준 8을 그대로 쓴다. 기준을 전역으로 낮추는 안은 이 때문에 기각했다.

## 4. 결과

RTX Spark N1X(sm_121), 3라운드, 단일 바이너리, 클럭 게이트 적용, 합산 tok/s 중앙값이다. 전체 표는 `docs/benchmark_results/cuda-qmm-fold-batch-n1x-2026-10-31.md`에 있다.

| 모델 | 5클라이언트, 적용 / 폴드 끔 | 8클라이언트, 적용 / 폴드 끔 |
|---|---:|---:|
| qwen3.8-27b | 34.9 / 23.3 | 45.0 / 14.0 |
| llama-3.1-8b | 59.9 / 47.0 | 75.6 / 33.7 |
| gpt-oss-20b | 89.6 / 86.0 | 87.9 / 72.1 |
| gemma-4-26b | 35.7 / 37.0 | 34.1 / 16.9 |

모든 가중치를 GEMM으로 보낸 6행 `logit_trace`(256 위치)에서 top-1 불일치는 Llama 0개, Qwen 5개(차이 0.125 이하)이고 결정 위치의 불일치는 없다. Gemma 4 26B는 29개인데, qmv나 폴드 끔에서도 27개이므로 이 PR 이전부터 있던 차이다.

## 5. 트레이드오프와 남은 문제

- **비트 일치:** GEMM을 쓰는 배치 행은 같은 행을 혼자 디코드한 결과와 비트까지 같지 않다. 8행에서는 원래도 그랬고, 이번에 큰 가중치의 5~7행까지 범위가 넓어졌다.
- **trace 미실행:** trace는 크기 조건을 넣기 전에 돌렸다. 최종 규칙은 trace한 경우보다 GEMM을 쓰는 가중치가 적다.
- **미측정:** GB10, H100, 그 밖의 compute capability. 폴드는 이들 모두에 적용된다. `docs/CONTINUOUS_BATCHING.md`의 GB10 `--parallel` 안내는 폴드 이전 내용이라고 고쳐 적었다.
- **Gemma 4 손해:** 프로브에서는 5행 이상에서 라우터를 빼면 GEMM이 같거나 빠른데, 라우터만으로는 서빙 손해를 설명하지 못한다. 원인은 아직 모른다. 같은 커널을 쓰는 4클라이언트에서도 두 경우가 약 6% 벌어졌으니 이 모델의 작은 차이는 측정 오차에 가깝다.
- **MoE:** B=8 프로파일(강제 평가)에서 gate, up, down gather는 층당 10.2 ms 중 약 5.8 ms다. 각 연산이 `top_k * B`개의 전문가 행렬을 읽는다. 전문가별로 행을 묶으려면 새 커널이 필요하고, 행들이 전문가를 얼마나 겹쳐 고르는지부터 재야 한다.
- **테스트 한계:** 폴드 테스트는 폴드를 꺼도 통과한다. sm_121에서는 접지 않은 디스패치의 결과도 비트까지 같기 때문이다. 이 테스트는 정확성만 확인하고, 속도를 지키는 검사는 CI에 없다.

## 6. 학습 포인트

- 같은 인덱스를 반복하는 호출 단위 프로브는 대역폭에 묶인 작업을 적게 잡을 수 있다. 64쌍 gather가 프로브에서는 약 0.5 ms, 실제 경로에서는 약 2.2 ms였고, 이 차이 때문에 8클라이언트의 주된 비용이 MoE가 아니라고 처음에 잘못 판단했다.
- Gemma 4에서는 호출 단위 시간으로 서빙 결과를 예측하지 못했다. 프로브는 GEMM이 앞선다고 나왔지만 서빙은 손해였으므로, 기준을 정할 때는 서빙 측정이 필요하다.
- 결정이 행 수에 단조로우면 기준 비교에는 양쪽으로 고정한 두 경우만 있으면 된다.
- 이 노트북에서 클럭 합격선을 1000 MHz로 두었더니 1352 MHz 측정이 정상의 약 4분의 1 처리량으로 통과했다. 활성 전원 구성표의 화면 끄기도 앞서 '안 함'으로 바꿨는데 300초로 남아 있었다. 이를 다시 설정한 뒤 75분 측정에서는 클럭 재시도가 없었지만, 유휴 제한의 원인을 따로 분리해 확인하지는 못했다.
