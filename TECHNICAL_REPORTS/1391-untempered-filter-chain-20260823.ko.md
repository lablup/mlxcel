# 기술 보고서: PR #1391 - 온도 미적용 분포에서 필터링하고 온도를 마지막에 적용

**날짜**: 2026-08-23
**작성자**: 신정규
**상태**: 완료
**언어/기술**: Rust, C++ (cxx 브리지), Metal, CUDA (미러, 미컴파일)
**위험도**: 높음 (절단 필터를 쓰는 모든 요청의 샘플링 분포가 바뀐다. 서버 기본값이 그렇다)

---

## 요약

mlxcel은 top-k·top-p·min-p가 돌기 전에 로짓을 온도로 나눴고, XTC는 그보다도 먼저 원시 분포에 적용했다. mlxcel의 플래그와 요청 스키마가 호환을 목표로 하는 llama-server 체인은 정반대다. **모든 절단 필터를 온도 미적용 분포에서 평가하고, 온도는 마지막에 추첨에만 적용한다.** 서버 기본값(`--temp 0.8 --top-k 40 --top-p 0.9 --min-p 0.1`)에서는 모든 기본 요청이 영향을 받았고, 클라이언트가 다른 곳에서 튜닝한 nucleus가 그대로 옮겨오지 않았다.

이 변경에서 순서 재정렬 자체보다 값진 것이 둘 있다.

**두 번째, 더 큰 결함을 드러냈다.** 스톡 체인의 compiled min-p 필터가 Metal에서 조용한 무동작이었다. 결합 top-k + top-p 라우팅이 vocab 32768을 넘으면 거절되므로, **대형 vocab 모델은 서버 기본값에서 min-p 없이** 돌고 있었다. Qwen3와 Llama 3.1이 여기 든다. rejection 커널은 min-p를 제대로 적용해서 이 결함을 가리고 있었다.

**그리고 그럴듯한 최적화가 실제로는 회귀였다.** 리뷰가 중복된 토큰당 cast를 "공짜로 제거 가능"이라며 hoist를 제안했다. 측정하니 반대였고, 그 이유가 일반화된다. **공통부분식 제거는 커널 fusion을 대가로 치를 때 공짜가 아니다.**

## 1. 문제 정의

### 1.1 배경

Rust 사전 단계가 XTC를 원시·온도 미적용·미필터 로짓에 먼저 적용했다. C++ 스톡 체인은 어떤 필터보다 먼저 온도로 나눴다. rejection 커널은 **이미 온도가 적용된** 확률 벡터 하나를 받아 top-k 개수 판정, top-p 질량 판정, min-p 임계를 거기에 대고 평가했다. 실효 순서:

```
XTC(raw) -> 온도 -> top_k -> top_p (재정규화) -> min_p -> 추첨
```

같은 knob에 대한 레퍼런스 순서:

```
top_k -> top_p -> min_p -> XTC -> 온도 -> 추첨
```

`min_p`의 판정 `p_i >= min_p * p_max`는 재정규화 불변이지만 **온도 가변**이라, 위치가 결과를 바꿨다.

### 1.2 기존 문제

`T = 0.8`에서 온도 적용된 분포는 더 뾰족하므로, top-p 0.9와 min-p 0.1이 llama-server에서 같은 요청이 남기는 것보다 **적은 토큰을 남겼다.** 에러는 없고 출력은 유창했다. 호환 표면이 존재하는 이유인 바로 그 knob들에서 조용한 호환성 간극이 있었다.

### 1.3 위험 평가

높음. 불변식 둘이 성립하지 않으면 대다수 사용자에게 회귀가 된다. **greedy는 바이트 동일**해야 하고 **`T = 1.0`은 동일한 추첨**을 내야 한다. 둘 다 논증이 아니라 변경 전 바이너리 대조로 검증했다.

## 3. 기술적 선택과 그 이유

### 3.1 rejection 분할, 그리고 단조성 논거가 실은 지지대가 아니라는 것

커널은 이제 행 둘을 받는다. `probs_filter = softmax(x)`와 `probs_draw = softmax(x / T)`. `T = 1.0`에서는 두 번째가 **같은 배열 객체**라 두 번째 softmax가 없다.

이슈는 이를 단조성으로 정당화했다. `p_draw = p_filter^(1/T) / Z`가 순증가이므로 필터 공간의 임계 집합이 추첨 공간에서도 같은 인덱스 집합이라는 것이다. 그 논거는 참이지만, **구현을 옳게 만드는 것은 그게 아니었다.** 리뷰가 버퍼 read를 전수 추적한 결과 **어떤 필터 판정도 추첨 행을 읽지 않는다**: row-max sweep, `total`, `tau_min = min_p * p_max`, `pmass_target = top_p * total`, pivot 값, `(count, mass)` reduction 둘이 전부 필터 공간을 읽고, 제안 스캔·CDF 오프셋·`target = u * mass_prop`만 추첨 공간을 읽되 각각 필터 공간의 `probs > low`로 게이트된다.

그래서 이것은 교과서적 rejection sampling이다. 제안은 목표 support의 **상위집합**으로 제한된 온도 적용 행이고, 수용 판정은 필터 공간에서 이뤄지며, 수용된 토큰은 온도 미적용 support로 잘린 온도 적용 행을 따른다. 단조성은 정합성 진술이지 의존성이 아니다. **기록해 둘 값어치가 있다.** 앞으로 어떤 변경이 필터 판정으로 추첨 행을 읽게 만들면, 단조성 논거는 여전히 "성립"하는 채로 샘플러가 조용히 깨진다.

### 3.2 기존의 조용한 무동작, 새 테스트가 그것 없이는 통과할 수 없어서 발견됨

스톡 체인의 min-p 필터가 `mlx::core::compile(fn, shapeless=true)`로 만들어졌고 Metal에서 아무것도 하지 않았다. 변경 전 트리에서 편집 전에 포착한 증거: 고정 행에서 `min_p`를 0.05부터 0.9까지 바꿔도 보고된 분포가 움직이지 않았고, 프로덕션 스톡 체인과 레퍼런스 arm 양쪽으로 2000회 추첨하니 `min_p * p_max` 아래 토큰이 나왔다(`min_p = 0.5`에서 2000 중 317과 95). 같은 op를 컴파일하지 않으면 정상 필터링됐다.

서버를 통해 종단 간으로도 독립 확인했다. 변경 전 바이너리에서 `min_p = 0.3`과 `min_p = 0.7`이 **바이트 동일한 출력**을 냈다. min-p가 자기 크기에 반응하지 않았다. 변경 후에는 정상 분화한다.

이 수정을 PR에 넣은 것은 범위 선택이라기보다 **전제조건**이었다. 이슈가 요구한 테스트 중 하나인 `min_p_support_is_temperature_invariant`가 스톡 체인으로 라우팅되므로, min-p가 무동작인 채로는 통과할 수 없다.

MLX 내부 메커니즘은 범위를 좁혔으나 한 줄까지 진단하지 못했고, 그 정직함에는 대가가 있어 명시해 둔다. 같은 파일이 동일 방식으로 만드는 형제 `compile(fn, shapeless=true)` 자리가 약 15곳이다. min-p와 형태를 공유하는 셋(`compiled_softcap`, `compiled_softcap_sdpa_gqa`, `compiled_clip_residual`)은 PR 본문에 이름을 적었고, 나머지는 활성화 함수와 MLP forward라 무동작이면 조용하지 않고 수치적으로 시끄럽다. 그것은 **논증이지 검사가 아니므로** 감사를 #1392로 발행했다.

### 3.3 측정해 보니 더 느렸던 최적화

리뷰가 두 확률 헬퍼가 공유하는 중복 `astype(logits, float32)`의 hoist를 제안했다. MLX가 따로 만든 노드를 CSE하지 않으므로 bf16 로짓에서 토큰당 전체 행 cast가 두 번이라는 논거였다. 그럴듯하고, 보고된 회귀의 일부이기도 했다.

구현한 뒤 vocab 151936에서 순서를 교대하며 9쌍 교차 측정했다.

| arm | 중앙값 | 범위 |
|---|---|---|
| 미hoist (출하) | **108.15 tok/s** | 107.89 ~ 108.20 |
| hoist | 107.46 tok/s | 107.32 ~ 107.53 |

hoist한 쪽이 **9쌍 전부 패배, 범위 중첩 없음**. 메커니즘: cast를 하나로 공유하면 f32 행이 materialize되어 두 번 읽히고, 따로 만든 둘은 각각 소비자에 fuse되어 600KB 중간 배열이 생기지 않는다. **CSE는 fusion을 대가로 치를 때 공짜가 아니다.**

되돌리고 측정값을 두 헬퍼 위 주석에 남겨 재제안을 막았다. rejection arm의 최종 회귀 수치는 **2.63%**이고, drift가 상쇄되도록 pre/post 4쌍 교차로 재측정했다. 원래 2.6% 추정이 맞았고 더 나은 방법이 값을 좁혔을 뿐이다.

### 3.4 Qwen3-Omni talker는 레퍼런스 순서를 유지

talker의 `sample_logits`가 공유 샘플러를 부르므로 재정렬이 거기까지 **조용히** 닿았는데, 그 doc 주석은 "the reference `top_p_sampling`"을 구현한다고 하고 모듈 헤더도 "Sampling mirrors the reference"라고 적는다. 그 주장이 거짓이 될 참이었다.

talker는 mlx-vlm의 온도-우선 순서를 유지한다. 근거: #1379의 계약은 **요청 기반** 샘플러의 llama-server 호환성인데, talker의 knob은 요청 파라미터가 아니다(`talker_temperature`와 `talker_top_p`는 체크포인트 generation config에서 오고, code predictor의 `top_p`는 0.8 고정). 즉 호환성 논거가 그 경로에 닿지 않는다. mlx-vlm이 유일한 정확성 오라클인데 음성 검증을 돌리지 않았다. mlx-vlm의 `top_p_sampling`을 직접 읽어, 그 오름차순 cumsum 규칙이 mlxcel의 내림차순 배타 cumsum과 대수적으로 동치임을 확인했으므로 **온도 순서만이 유일한 차이**였고, 그래서 보존이 값쌌다.

## 4. 검증

### 4.1 저장한 변경 전 바이너리 대조, 불변식 둘

변경 전 바이너리를 머지 베이스에서 재빌드해 편집 전에 저장했다. `models/qwen3-4b-4bit`, 원시 고엔트로피 프롬프트:

- **greedy(`--temp 0`): 토큰 동일.**
- **`T = 1.0`, min-p 무관 조합 전부, dispatch arm 3종(rejection 커널·스톡 체인·Gumbel) 모두**: 토큰 동일.
- `T = 1.0` 스톡 체인 min-p 조합: min-p 수정이 요구하는 대로 분화.

기억해 둘 방법 메모: **채팅 템플릿이 붙은 프롬프트는 프로브로서 무력했다.** 필터를 다 끄고 `T = 1.5`로 돌려도 greedy와 같았다. 앞 토큰들이 사실상 결정적이기 때문이다. `--no-chat-template`으로 원시 프롬프트를 넣어야 샘플링 차이가 **관측 가능**해졌다. 오케스트레이션 도중 이 때문에 잘못된 결론(CLI 샘플링 플래그가 무효라는)을 한 번 냈다가, 코드가 아니라 프롬프트가 문제였음이 드러났다.

### 4.2 rejection 샘플러 통계 검증

`rejection_kernel_filter_on_untempered_draw_on_tempered`: `T = 0.5`, top-p 0.9에서 **10만 회 추첨**. support 안 모든 경험 빈도가 온도 적용·절단 레퍼런스의 **3σ 이내**, **온도 미적용 nucleus 밖 추첨 0건**, 스톡 arm도 동일 support로 해소.

투기 디코딩 수용률, `qwen3-0.6b` 드래프터 `T = 0.8`: 위치당 0.5167 → 0.5739. 저하 없음이고, 방향이 넓어진 온도 미적용 목표 support와 정합적이다.

### 4.3 리뷰가 찾아낸 커버리지 공백

PR은 원래 C++ XTC 포팅이 "기존 XTC 단위 테스트 **여덟** 개에 element 단위로 붙들려 있다"고 적었다. 일곱 개였고, **전부 Rust 함수만 호출**했다. 실질 공백은 개수가 아니었다. **C++ allowlist 분기가 어떤 테스트에서도 실행되지 않았고**, 프로덕션은 거기에 개행과 병합된 EOS 집합을 채운다. 그 분기에 결함이 있으면 XTC가 EOS를 억제해 **생성이 폭주**한다.

테스트 셋을 추가했다. allowlist 행을 포함한 레퍼런스 4행 전부에 대한 `softmax(apply_xtc_filter(...))` element 단위 대조, compare가 실제로 결정하는 `xtc_probability = 0.5`에서의 gate 테스트, 그리고 **`fused_sample_xtc`를 호출하는 유일한 테스트**로 `T = 0`의 argmax-of-filtered 경로를 덮는다.

### 4.4 게이트

`cargo test --workspace --profile test-fast --features metal,accelerate`: 8379 통과, 0 실패. 로컬 CI(`ci.yml` 잡 10개 중 8개, 이번 세션 GitHub Actions 불가): 7 pass, 0 fail, 2 skip. 실모델 게이트 둘 다 통과. `check_kernel_dtype_keys.py` OK, 커널이 새 입력용 `DrawType` 키를 얻었다.

게이트 두 번이 알려진 플레이키로 실패했고, 둘 다 상시 절차로 판정한 뒤 각 이슈에 새 발생 데이터를 남겼다. `text_only_forward_produces_finite_logits`(#997)와 `e2e_crossover_larger_models_benefit_more`(#1184). 두 번째는 특기할 만하다. **호출부만 보면 순수 해석적 계산**이라, 그 실패가 "결정적 계산이 비결정적으로 실패한다"처럼 보인다. wall-clock 의존은 한 단계 아래, 하네스가 `std::thread::sleep`을 `Instant::now()`로 재는 곳에 있다.

## 5. 검증하지 못한 것

**CUDA 미러.** 이 변경 이전에 이미 트리에서 UNVALIDATED로 표시돼 있었다(파리티를 위해 작성, 컴파일·실행된 적 없음, CUDA 하드웨어도 nvcc도 없음). 주석을 이번 변경의 편집을 명시하도록 확장했다. 검증했다고 주장하지 않는다.

**OpenXLA CI 잡 2개.** CUDA 툴체인이 필요하다.

**Qwen3-Omni talker 변경.** 컴파일·린트만 확인했고 음성 체크포인트를 돌리지 않았다. 이 브랜치 베이스가 이미 갖고 있던 순서로 **되돌리는** 것이라 새 영역에 들어가는 것은 아니지만, 어느 방향으로도 검증되지 않았다.

## 6. 학습 포인트

- **정확성 논거가 참이면서도 코드를 옳게 만드는 그것이 아닐 수 있다.** 단조성은 성립하지만 rejection 샘플러를 옳게 만드는 것은 "어떤 필터 판정도 추첨 행을 읽지 않는다"는 사실이다. 이슈가 제시한 성질이 아니라 **코드가 실제로 의존하는 성질**을 검증한다.
- **"공짜로 제거 가능"은 가설이다.** 중복 계산을 없애는 CSE가, 그 중복이 소비자에 fuse되고 있었고 공유판은 materialize해야 한다면, 아끼는 것보다 더 비쌀 수 있다.
- **프로브가 틀리지 않으면서 무력할 수 있다.** 채팅 템플릿 프롬프트가 필터 없는 `T = 1.5` 샘플링을 greedy와 구별 불가로 만들었고, 그것이 잠시 샘플링 플래그의 버그처럼 보였다. **부재로부터 결론을 내기 전에 프로브가 그 차이를 표현할 수 있는지부터 확인한다.**
- 테스트 개수는 커버리지가 아니고, 커버리지에 대한 주장은 그 테스트가 **무엇을 호출하는지**에 대고 확인해야 한다. Rust만 호출하는 테스트 일곱 개가 호출하지도 않는 C++ 포팅을 붙든다고 기술돼 있었다.
- 수정이 이슈 자신의 수용 테스트의 전제조건일 때 함께 넣는 것은 옳지만, **더 큰 관측 가능 변화는 이름을 붙여 줘야 한다.** 여기서는 vocab 32768을 넘는 모든 모델에서 min-p가 처음으로 실제 적용된다는 것이다.
