# 기술 보고서: PR #1547 - thinking_mode 센티널을 챗 템플릿에서 도출

**작성일**: 2026-08-31
**작성자**: mlxcel maintainers
**상태**: 완료. 실제 체크포인트 템플릿으로 수정 전후를 재현했고, 재현 테스트 두 개는 단언을 뒤집기 전에 수정본에 대해 실패하는 것까지 확인했다
**언어**: Rust
**위험도**: Low

## 요약

사고를 켠 DeepSeek-V4 요청이 비사고 분기를 렌더링하고 평범한 응답을 돌려줬다. 오류는 나지 않는다. 추론을 요청한 쪽은 보통 답변을 받고, 무언가 빠졌다는 신호는 어디에도 없다.

원인은 하드코딩된 센티널 값이다. PR #811은 사고가 켜져 있고 템플릿이 `thinking_mode` 식별자를 언급하면 컨텍스트에 `thinking_mode: "enabled"`를 주입한다. DeepSeek-V4 템플릿은 그 식별자를 언급하지만 게이트는 `'thinking'`이라, 주입된 값이 else 분기로 그대로 빠진다.

흥미로운 지점은 값이 어긋났다는 사실이 아니다. #811이 바로 이 메커니즘을 덮는 테스트와 함께 머지됐는데도 그 테스트가 이 버그를 볼 수 없었다는 점이다. 테스트 픽스처와 구현이 "템플릿이 이 값을 어떻게 표기하는가"에 대해 같은 가정을 담고 있었다.

## 1. 문제 정의

### 1.1 두 가지 관례

#811(이슈 #775)이 상정한 템플릿은 이런 모양이다.

```jinja
{% if thinking_mode is defined and thinking_mode == "enabled" %}<think>{% else %}<no_think>{% endif %}
```

변수를 리터럴과 직접 비교한다. `"enabled"`를 주입하면 사고 분기가 열린다.

DeepSeek-V4-flash는 다른 관용구를 쓴다.

```jinja
{%- set mode = thinking_mode|default('chat') -%}
{%- if loop.last and mode == 'thinking' -%}<think>{%- else -%}</think>{%- endif -%}
```

변수를 `default()`로 감싸 별칭을 만들고, 그 별칭을 `'thinking'`과 비교한다. `"enabled"`는 `'thinking'`이 아니므로 주입은 무의미해지는데, 겉보기에는 동작한 것처럼 보인다. kwarg는 컨텍스트에 들어 있고, 템플릿은 그걸 읽고, 게이트가 아니라고 답할 뿐이다.

### 1.2 감지가 도움이 되지 않은 이유

`wants_thinking_mode_alias()`는 식별자에 대한 substring 스캔이다.

```rust
fn wants_thinking_mode_alias(&self) -> bool {
    self.template.contains("thinking_mode")
}
```

두 관례 모두에서 `true`가 나온다. 그래서 별칭은 DeepSeek-V4에서 정확히 발동했고, 템플릿이 쓸 데 없는 값을 전달했다. 감지와 주입이 그 변수의 의미에 대해 서로 다른 전제를 갖고 있었고, 파이프라인 어디에서도 이를 알아챌 수단이 없었다.

### 1.3 등록 시점에는 잠재, 수정 시점에는 실사용

이슈 #819는 2026-07-19에 등록되면서 자기 영향 범위를 명시했다.

> None at runtime yet: `model_type: deepseek_v4` is not loadable ... The gap becomes user-visible the moment #523 lands.

#523은 2026-08-27에 PR #1455로 머지됐다. 이슈가 스스로 명시한 전제 조건이 충족됐는데 본문은 여전히 영향이 없다고 말하고 있었다. 낡은 이슈 본문이 만드는 전형적인 실패다. 그 문장이 사실이 아니게 된 바로 그 순간부터 안심시키는 문장으로 읽힌다.

## 2. 기술적 선택과 그 이유

### 2.1 표가 아니라 도출

이슈는 두 가지를 제시했다. 템플릿에서 게이트 리터럴을 스캔하거나, 계열별 표(`deepseek_v4`는 `"thinking"`)를 `"enabled"` 기본값 앞에 두거나.

도출을 택했다. 표는 같은 취약성을 한 단계 위로 옮길 뿐이다. 누군가 열거할 생각을 한 계열에는 답하고, 세 번째 표기를 들고 오는 다음 템플릿에는 조용히 잘못된 기본값으로 돌아간다. 이 버그가 도착한 경로가 정확히 그것이다. 게이트를 템플릿에서 읽어내면 비교문으로 표현되는 모든 관례에 답할 수 있다.

### 2.2 추측하지 말고 폴백

도출은 후보 리터럴이 정확히 하나일 때만 값을 돌려준다. 없거나 여럿이면 `"enabled"`로 폴백한다.

이게 핵심 결정이고, 실패 양상에서 따라 나온다. 잘못된 센티널은 조용하다. 템플릿은 else 분기를 타고 그럴듯한 출력을 낸다. 모호할 때 추측하는 도출은 결국 "알려진 잘못된 기본값"을 "예측 불가능하게 잘못된 값"으로 바꾸면서 보이지 않는 성질은 그대로 유지한다. 폴백은 지금 동작하는 모든 템플릿의 동작을 보존하고, 변경 범위를 게이트를 실제로 읽어낼 수 있는 템플릿으로 한정한다.

### 2.3 `default()` 인자 배제

`thinking_mode|default('chat')`는 후보를 내놓지 않는다. 내놓아서도 안 된다. `'chat'`은 이 템플릿의 OFF 값이고, 추론을 요청한 호출자에게 그걸 주입하는 것은 아무것도 주입하지 않느니만 못하다.

배제는 특수 처리가 아니라 구조에서 나온다. `==` 비교에 등장하는 리터럴만 수집하고, `default()` 인자는 비교가 아니므로 어떤 템플릿에서도 후보가 되지 않는다.

### 2.4 #811의 우선순위 유지

호출자가 명시한 `thinking_mode` kwarg는 여전히 도출값을 이긴다. 사고가 꺼져 있으면 아무것도 주입하지 않는다. 둘 다 원래 맞게 동작하고 있었고, 이번에 테스트로 고정했다. 도출을 추가하면서 이 둘을 깨뜨릴 새로운 경로가 생겼기 때문이다.

## 3. 구현

`src/server/chat_template.rs`, +350/-10.

`thinking_mode_sentinel()`이 프로덕션 호출 지점 두 곳에서 기존 불리언을 대체하고, `build_template_context`는 `thinking_mode_alias: bool` 대신 `Option<&str>`을 받는다. 도출은 세 단계다.

1. **값을 나르는 식별자 수집.** `thinking_mode` 자신과, `{% set <name> = thinking_mode ... %}`로 만들어진 별칭. `set ` 기준으로 나눈 뒤 좌변이 순수 식별자이고 우변이 `thinking_mode`로 시작하는 경우를 받는다.
2. **게이트 리터럴 수집.** 템플릿의 모든 `==`를 훑는다. 1단계 식별자가 좌변을 온전한 단어로 끝맺으면 우변에서 문자열 리터럴을 읽고, 비교 순서가 뒤집힌 경우도 대칭으로 처리한다. 온전한 단어 매칭이 필요한 이유는 `my_thinking_mode`가 변수로 오인되지 않게 하기 위해서다.
3. **판정.** 서로 다른 리터럴이 정확히 하나면 반환, 아니면 `None`을 돌려 호출자가 폴백하게 둔다.

`==`의 양방향을 모두 처리한 것은 실제 Jinja 템플릿이 둘 다 쓰기 때문이다. 두 번째 방향을 덮는 비용은 몇 줄이고, 덮지 않았을 때의 대가는 조용한 실패다.

## 4. 테스트 전략

이 버그는 테스트 스위트를 통과해 살아남았다. 그래서 이번 테스트는 통과하는 것이 아니라 판별하는 것을 목표로 짰다.

**재현 테스트 두 개는 먼저 깨진 동작을 단언하도록 작성했다.** 수정 전 코드에서 통과하는 것을 확인하고, 수정본에서 실패하는 것을 확인한 다음에야 올바른 동작을 단언하도록 뒤집었다. 한 번도 실패해 본 적 없는 테스트는 실패할 수 있는 테스트인지 알 수 없다.

- `issue_819_deepseek_v4_gate_opens_from_a_derived_sentinel`: 별칭 형태에서 `<think>`가 열리고, 렌더 결과만 보는 대신 도출된 센티널이 `"thinking"`인지도 단언한다. 엉뚱한 이유로 올바른 렌더가 나오는 변경도 실패하게 만들기 위해서다.
- `issue_819_real_checkpoint_template_opens_the_thinking_branch`: 같은 검사를 `models/deepseek-v4-flash-4bit/chat_template.jinja` 파일 자체로 구동한다. 인라인 픽스처가 대변하는 파일로부터 조용히 벌어지는 것을 막는다. 체크포인트가 없으면 건너뛴다. 도출 렌더가 명시적 우회 렌더와 바이트 단위로 같은지 단언한다.
- `thinking_mode_sentinel_falls_back_when_the_gate_is_not_readable`: 미언급, 언급하되 비교 없음, 게이트 리터럴 둘, #811 관례 불변, 같은 리터럴 반복(실제 V4 형태), 역순 비교, 변수명으로 끝나는 더 긴 식별자, `default()` OFF 값 비선택까지 여덟 경우.
- `derived_sentinel_keeps_811_precedence`: 템플릿이 인식하지 못하는 값이어도 명시적 kwarg가 도출값을 이긴다. 사고가 꺼져 있으면 주입하지 않는다.

## 6. 학습 포인트

**테스트와 그 테스트가 덮는 구현이 같은 가정을 공유하면, 그 테스트는 검증하지 않는다.** `THINKING_MODE_LIKE_TEMPLATE`은 `thinking_mode`를 `"enabled"`와 직접 비교하고, 구현은 `"enabled"`를 주입했다. 둘 다 "템플릿이 이 값을 어떻게 표기하는가"에 대한 같은 심상에서 나왔으므로, 스위트는 동작이 아니라 그 심상을 확인했다. 테스트가 없었던 게 아니라, 코드에 수직이 아니라 평행했다. 픽스처가 그것이 검증할 기능과 나란히 작성될 때는, 구현을 본 적 없는 사람이 쓴 픽스처는 어떤 모양일지 한 번 물어볼 값이 있다.

**조용히 틀린 답에는 보수적인 수정이 어울린다.** 이 버그가 비쌌던 이유는 아무것도 오류를 내지 않았다는 점이다. 그 성질은 수정에도 전파되어야 한다. 모호할 때 추측하는 도출은 보이지 않는 성질을 유지한 채 결과만 덜 예측 가능하게 만든다. 이전 동작으로 폴백하면 변경 반경이 의도가 명확한 템플릿으로 한정된다.

**낡은 이슈 본문은 이슈가 없는 것보다 나쁘다.** #819는 자기 영향을 정확히 "없음"이라고 적었고, 그 문장은 그것이 의존하던 전제가 충족된 뒤에도 페이지에 남아 있었다. 이게 중요한 문제인지 확인하러 온 사람은 문서로 "아니다"라는 답을 받았을 것이다. 현재 상태를 단언하는 이슈 본문에는 유통기한이 있고, 특히 특정 해제 조건을 명시한 본문은 그 조건이 충족될 때 다시 볼 값이 있다.

## 7. 검증되지 않은 부분

- **실제 픽스처로 덮은 템플릿 관례는 두 가지뿐이다.** `== "enabled"` 형태와 별칭 `== 'thinking'` 형태는 실제 또는 현실적인 템플릿에 대한 테스트가 있다. 세 번째 관례는 `"enabled"`로 폴백하는데, 안전하긴 하지만 그 템플릿에 대해 옳지는 않다. 공개된 챗 템플릿을 조사해 세 번째 관례를 찾아보지는 않았다.
- **다단계 별칭은 처리하지 않는다.** `{% set a = thinking_mode %}{% set b = a %}{% if b == 'x' %}`는 아무것도 도출하지 못하고 폴백한다. 알려진 사례는 1단계로 충분해서 더 깊은 체인은 구현하지 않았다.
- **`==` 외의 비교 연산자**(`in`, `!=`, `is`)는 스캔하지 않는다. `thinking_mode in ['thinking', 'deep']`로 게이트하는 템플릿은 폴백한다.
- **종단 간 서버 테스트는 없다.** 수정은 `ChatTemplateProcessor` 수준에서 검증했고, 적재된 DeepSeek-V4에 대한 실제 `/v1/chat/completions` 요청으로는 확인하지 않았다. `tests/chat_template_kwargs.rs`의 기존 서버 통합 테스트는 작은 모델로 서버를 띄우므로, 이 경로를 덮으려면 V4 형태의 템플릿 픽스처가 필요하다.
