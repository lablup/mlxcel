# PR #3448: OpenXLA/IREE Jamba 하이브리드 (Mamba1 + attention + softmax MoE)

**날짜**: 2026-11-26

**상태**: CPU/CUDA 수락 검증 통과, ROCm 재검증은 외부 진행 대기

## 요약

Jamba가 원본 Hugging Face 가중치로 OpenXLA/IREE에서 실행된다. Mamba1 블록과 attention 블록은 `attn_layer_period` / `attn_layer_offset`에 따라 교차하고, dense FFN과 MoE FFN은 `expert_layer_period` / `expert_layer_offset`에 따라 번갈아 나온다. #3348의 Mamba1 mixer에 학습된 dt/B/C RMSNorm 가중치를 추가했고, dense 계열의 MoE 블록은 그대로 재사용한다. 수락 검증 중 softmax 라우팅 MoE의 ragged decode 전체에 공통인 IREE 컴파일 실패가 드러났고, 해당 decode를 aggressive dispatch fusion 없이 컴파일하도록 고쳤다.

## 문제

`from_json_str`가 `jamba`를 거부했다. 기존 Mamba1 `bcdt_norm`은 Falcon-Mamba의 가중치 없는 정규화만 표현했지만, Jamba는 정규화한 dt, B, C 각각에 학습된 벡터를 곱한다. 순수 SSM 모델과 달리 Jamba의 모든 블록은 mixer 뒤에 FFN이 있어서, Mamba1 블록도 잔차가 두 번 있는 전체 레이어 경로를 써야 한다. 공개 체크포인트 `ai21labs/AI21-Jamba-Reasoning-3B`는 `num_experts = 1`이라 실제 모델로는 MoE를 전혀 검증할 수 없다.

## 변경 내용과 기술적 결정

`SsmKind::Mamba1`은 `BcdtNorm::{None, Weightless, Weighted}`를 가진다. Falcon-Mamba는 `Weightless`를 유지하며 golden은 바이트 단위로 같다. Jamba 설정은 period와 offset에서 `layer_mixers`와 레이어별 FFN 종류를 만든다. FFN이 있는 Mamba1 블록은 일반 레이어 경로(`input_layernorm`, mixer, `pre_ff_layernorm`, FFN)를 쓰고, 다른 계열의 FFN 없는 SSM 레이어는 기존 짧은 구조를 유지한다. attention은 RoPE를 쓰지 않는다. KV 캐시는 attention 블록만, recurrent 상태는 Mamba1 블록만 담는다. 체크포인트 교차 검사는 모든 `mamba.*` 텐서, 정규화 벡터, expert 가중치를 확인한다.

라우팅은 Hugging Face를 따른다(전체 expert softmax, top-k, 재정규화 없음). MLX eager 경로는 top-k 안에서 다시 정규화하며 이번 변경에서 건드리지 않았다. expert 가중치는 쌓인 `switch_mlp` 레이아웃만 로드하고, expert별로 나뉜 원본 HF MoE 체크포인트는 로드 단계에서 거부한다.

`--iree-dispatch-creation-enable-aggressive-fusion`을 켜면 IREE가 라우터 softmax를 top-k argmax와 하나의 dispatch로 합치고, llvm-cpu와 CUDA 모두 이를 lowering하지 못한다. 기존 Qwen2-MoE와 OLMoE의 ragged decode golden도 현재 main에서 같은 방식으로 실패하고 플래그 없이는 컴파일된다. 즉 Jamba가 만든 회귀가 아니라 softmax 라우팅 MoE 계열 전체에 잠재해 있던 실패다. `decode_compile_flags`는 `Config::has_softmax_moe()`가 참이면 이 플래그를 빼고, sigmoid 라우팅은 플래그를 유지한다. 생성되는 그래프는 바뀌지 않는다.

## 검증과 증거 범위

통합 런타임 소스는 Falcon-H1 plain RoPE(#3452)와 Plamo2(#3449)가 들어간 main `01e6516b` 위로 rebase한 `b9b5545a`다. 이후 커밋은 증거와 문서만 추가한다. rebase는 Plamo2 동작을 그대로 유지한다. Plamo2 블록은 여전히 `layer_has_post_mixer_norm`과 `MixerKind::is_recurrent()`를 통해 post-mixer 정규화와 SSM mixer 가중치를 받고, `plamo2::offset_layer_norms`가 모든 레이어 가중치를 감싼다. 이 소스에서 PLAMO2, FALCON_H1, JAMBA를 포함한 모든 등록 golden이 바이트 단위로 같았고(lib 테스트 584개), `clippy -p mlxcel-xla --all-targets -D warnings`도 깨끗했다. GB10 CUDA에서 Jamba 3B `validate_arch.sh`, 40토큰 엔진 테스트, CLI 40/40 오라클, 동시 서버 8/8 검사를 다시 통과했고, 합성 MoE 정합성도 두 장치에서 통과했다. Plamo2(합성, window probe, 40토큰 오라클), Falcon-H1(합성, 3584까지의 긴 위치, 40토큰 오라클), Mamba1/Mamba2 SSM 단일 시퀀스와 상태 전달, Nemotron-H 테스트도 CUDA에서 통과했다. 이 실행 기록은 `spike/openxla/jamba_reference/`의 `integrated-*` 파일에 있다.

첫 수락 검증의 런타임 소스는 `c5afefbd` 기반의 `76a3dc4c`였다. GB10 CUDA에서 네이티브 HF fp32 오라클로 `validate_arch.sh --batch 4 --requests 8 --maxcap 24`가 exit 0으로 끝났다. 등록 golden, 40/40 토큰 일치, 배치 170 토큰 reference-exact를 모두 통과했다. CLI는 40토큰 오라클과 일치했고, 동시 non-streaming 4건과 SSE 4건의 서버 응답이 CLI 표시 문자열 및 토큰 수와 일치했다.

시드 고정 4블록, 4 expert, top-2 합성 Jamba가 유일한 MoE 증거다. 라우터와 dt/B/C 정규화 가중치를 무작위로 두었고, 생성기는 모든 expert 쌍이 선택되는지, 정규화 가중치를 빼거나 top-k를 재정규화하면 로짓이 허용 오차 3e-4를 크게 넘게 움직이는지 확인한다. local-task(최대 절대 오차 2.0e-6)와 CUDA(3.6e-6)에서 단일 시퀀스, ragged, slot 재사용 정합성을 통과했고, 두 장치 모두에서 CLI, `xla_oracle_check`, `xla_batch_bench` B=4 N=8을 통과했다.

`mlxcel-xla` lib 테스트는 기존 golden이 모두 바이트 단위로 같은 상태로 통과했다. fmt, clippy, 프롬프트 캐시/APC 가드(Jamba는 둘 다 쓰지 않음), 환경변수 문서 검사, Used by 검사도 통과했다. 증거와 명령은 `spike/openxla/jamba_reference/`에 있다.

검증하지 않은 것: ROCm `hip`, 실제 MoE Jamba 체크포인트, expert별 원본 HF MoE 레이아웃, 양자화 Jamba, decode 플래그 변경 이후의 실제 Qwen2-MoE / OLMoE 체크포인트.

## 배운 점과 후속 작업

실제 체크포인트가 기능을 꺼 두면(`num_experts = 1`) 그 기능의 증거가 되지 않는다. 합성 fixture는 빠진 연산이 있으면 측정 가능하게 실패하도록 만들어야 한다. 그래프 계열 전체에 거는 컴파일 플래그는, 새 아키텍처가 해당 경로에 닿기 전까지 잠재된 lowering 실패를 숨길 수 있다. 다음 IREE 업그레이드 때 softmax-MoE 예외를 다시 확인한다. #3349를 닫기 전에 최종 head에서 외부 ROCm 재검증을 요청한다.
