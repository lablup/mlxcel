# Technical Report: PR #2315 - Gemma 4 12B long-context MTP parity

**Date**: 2026-10-15
**Status**: Completed; final source `1eda64ef` was release-built and smoke-validated, while CI remains pending
**Languages**: Rust, Markdown, JSON
**Risk Level**: Medium

## Executive Summary

PR #2315 reproduces Gemma 4 12B long-buffered MTP divergence on current Metal and extends the existing exact row-wise verification path to the measured 12B geometry. Matching the physical rotating-cache reduction order, maskless single-query full attention, and classic prefill chunking removes all measured teacher-forced and free-generation disagreements on an M1 Ultra.

The release measurement does not support broader default use: forced MTP delivered only 0.837, 0.903, and 0.815 times classic throughput across the three prompts, and the strengthened startup probe added 5.80 seconds to the median scheduler-setup-to-probe interval. The PR therefore corrects the measured exactness path without broadening the default. Performance evidence belongs to commit `bd6d33f2`; the review-driven backend restriction landed in `1eda64ef` and received a separate final release build and smoke.

## 1. Problem Statement

The previous three short startup draws passed before a rotating cache wrapped, but realistic 1,056-token buffered verification diverged from classic decode. The current-main diagnostic baseline first differed in sliding attention for a mixed `8,8,8,1056` sequence and in full attention for an isolated `1056` draw. The actual cache snapshots showed that speculative verification and classic decode exposed the same visible keys in different physical reduction orders; a batched verify block also failed to reproduce classic's maskless single-query full-attention dispatch.

Attention correction alone was insufficient in serving. Candidate MTP prefilling the whole prompt produced outputs that matched a classic whole-prompt control but not classic's normal 512-token chunking. The target adapter therefore also has to follow classic prefill chunking before verification begins.

## 2. Technical Decisions

### Exact row-wise verification for the measured geometry

The change reuses the existing exact-geometry predicate and 31B row-wise implementation for Gemma 4 12B's `16/8/1` query/sliding-KV/full-KV geometry with 256/512 head dimensions. Verification stays linear and singleton, replays the physical sliding-ring order, uses maskless single-query full attention, declines unsupported batched or nonlinear layouts, and prevents the chronological speculative cache from being donated into classic automatic prompt reuse. CUDA's row-wise RoPE correction remains CUDA-only.

The review found that commit `bd6d33f2` enabled this geometry without a backend boundary, expanding unmeasured ROCm and CPU behavior. Commit `1eda64ef` keeps 31B's existing backend-independent policy and the exact original CUDA condition, adds 12B only when Metal is available and selected as the default GPU device, and leaves CPU-selected Metal plus ROCm and other GPU backends on their prior policy. The six-policy by seven-geometry helper matrix and live 12B predicate/long-probe assertion pass. Earlier repeated performance measurements remain attributed to `bd6d33f2`; the final source has separate build and correctness-smoke evidence.

### Stronger startup guard, with measured cost

The startup exactness probe adds a draw at `sliding_window + 32` tokens, bounded to 1,536, for the measured row-wise geometry. This catches the first cache-wrap regime that the three eight-token draws cannot reach. In three release runs, the median setup-to-probe interval increased from 1.245 seconds to 7.041 seconds, a 5.795-second startup cost; median health time increased from 4.796 to 10.408 seconds.

### Correctness does not imply default enablement

Release measurements forced MTP on and disabled adaptive sizing and slice grants to isolate the corrected path. Paired MTP/classic throughput ratios were 0.837 for science, 0.903 for software, and 0.815 for history, corresponding to regressions of 16.3%, 9.7%, and 18.5%. These results keep the existing default policy unchanged.

## 3. Evidence and Validation

### Diagnostic and exactness evidence

- Baseline: main `a2698835`, MLX `243bdf09`, test-fast diagnostic server SHA-256 `b60e1cba62156c6dfa04c9875ce3f3601502370c60c8524bb6fe42af8bc9edc9`.
- Failure localization: the mixed long draw first differed at layer 8 sliding attention, position 2; the isolated long draw first differed at layer 5 full attention, position 0 and reproduced identically.
- Teacher forcing: ordinary block verification disagreed at 18/256 top-1 positions and 2/155 decided positions; corrected verification disagreed at 0/256 and 0/155, with zero reference-choice logit delta.
- Serving parity: three prompts with 1,238-1,638 input tokens produced byte-identical 256-token outputs between corrected MTP and two stable classic references, with nonzero MTP proposal, acceptance, and round counters.
- Regression targets: 31B plus bf16 assistant and Qwen3.8 27B plus 4-bit MTP retained identical before/after output bytes and draft counters for all three prompts.
- Narrow validation at `bd6d33f2`: 82 `gemma4::` tests passed with one unrelated ffmpeg test ignored; 12 ordinary and 13 explicitly selected serial `gemma4_tests::` tests passed.
- Backend restriction at `1eda64ef`: the focused six-policy by seven-geometry helper matrix plus live predicate and long-probe assertion passed; formatting passed.
- Evidence record at `16063a00`: an independent security review recomputed the throughput, startup, all 27 output-hash guards, and draft-counter attribution without finding a discrepancy.
- Final evidence at `e637f970`: the `1eda64ef` release executable has SHA-256 `98fb89c5d81daa8d47e0c575ccf68ad93f1439087cd241994de6c3426902237d`. Across six completions, each of the three final-head classic/MTP 256-token pairs matches one another and the previously recorded hash; MTP proposed/accepted/round counters are 317/150/106, 295/157/99, and 322/148/108.
- True-default startup control: with all `MLXCEL_*` and `LLAMA_ARG_*` variables unset and explicit CLI model arguments, final-head exactness and health passed in 10.375 seconds. This is a single correctness control, not a startup-performance distribution.

### Release performance evidence

The immutable baseline server was built from `c0ae26b2` and has SHA-256 `4fdb66333c5862fbf7d6b14129c11fde6f017d4a27aae8090035a0346e7c27ba`. Four unrelated model-prefill fixes separate it from the earlier diagnostic baseline; the benchmark record does not claim source identity. The candidate release server was built from `bd6d33f2` and has SHA-256 `de772cee794bd5680fdbd0e354e25800d3c000e5af2c5ba8d195a7889bcceada`.

Each baseline, candidate classic, and candidate forced-MTP arm ran three times in fresh processes on an Apple M1 Ultra with 128 GiB, for 27 outputs across three scenarios. All outputs within each scenario had the same hash. One-minute host load ranged from 4.51 to 5.94. Candidate MTP decode medians were 29.748 versus 35.615 classic tokens/s, 32.160 versus 35.615 tokens/s, and 29.066 versus 35.649 tokens/s. Dispersion is retained in the benchmark JSON as min/max and median absolute deviation.

## 4. Change Summary

- Extend the long exactness probe to the measured Gemma 4 12B geometry.
- Reuse row-wise singleton attention and classic-compatible prefill behavior for long buffered MTP verification.
- Strengthen the realistic-window test from 32 to 1,024 tokens and retain fail-closed layout restrictions.
- Archive commands, cache layout, localization, output hashes, counters, startup measurements, throughput repetitions, dispersion, and host load in the benchmark Markdown and JSON.
- Keep default MTP policy unchanged because the measured forced path is slower on this host.

## 5. Remaining Limits

- M5 Max, CUDA, ROCm, and CPU are unmeasured in this investigation. The M1 Ultra result does not establish behavior or profitability on those backends.
- Untouched-default throughput was not measured. The single true-default startup control establishes exactness and health, not a performance distribution; repeated release comparisons deliberately pinned the validation switches and forced M1 B=1 eligibility.
- The 31B and Qwen checks are test-fast correctness regressions, not repeated release performance measurements. The 31B QAT and Qwen bf16-drafter variants were not measured.
- Repository CI, including queued GB10 jobs, is not claimed green by this report.
