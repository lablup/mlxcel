# Technical Report: PR #3282 - LiquidAI d1-3B decisions (`lfm2_vl` D1Model)

**Date**: 2026-11-23
**Status**: Open (draft PR, written before merge)
**Risk Level**: Low (a new decision scorer; the only shared-code edits are new functions on the LFM2 backbone and a loader re-export)

## Executive Summary

LiquidAI d1-3B answers typed questions about a text or image state by reading next-token log-probabilities at the answer slot. Its checkpoint declares `model_type: lfm2_vl`, so mlxcel loaded it as an ordinary chat model and had no way to get decisions out of it (#2367). The PR adds the first family behind the #2343 decision API: a `DecisionKind::D1` loader arm, detected by `auto_map.AutoModel` ending in `D1Model`, and a scorer ported from mlx-vlm's `models/d1` at d998a620. On `LiquidAI/d1-3B-MLX-8bit` the text answers equal mlx-vlm's to all four rounded places and the image answers differ by at most 1e-4.

## 1. Problem Statement

The decision API (`mlxcel decide`, `POST /v1/decisions`, `--decision-model`) existed with only a test stub behind it, so every checkpoint was refused. d1-3B is an LFM2.5-VL-3B finetune: the weights, processor and chat template are LFM2-VL's, and only the readout differs. Generation detection had to keep reading the checkpoint as LFM2-VL (upstream behaves the same), so the routing could live only in the decision loader.

The port also had to follow upstream changes made after the issue was written: `d1.py` now prefills long trunks in 2048-token chunks and batches question rows with a half-length rule, and `prompt.py` refuses bool criteria keys other than `true` and `false`.

## 2. What Changed

- `src/decision/d1_prompt.rs` (new): the System One prompt (state block, `QUESTION:`, choice, bool and score question text, one `<image>` per image), `as_question` with upstream's messages, option codes with the 1028-entry single-token fallback pool, readout ids, the softmax readout, the bicubic 1024 x 1024 area cap, and upstream's `_chunks` as `branch_chunks`.
- `src/decision/d1.rs` (new): `D1DecisionModel` over `Lfm2VlModel`. One question is a single pass. Several share the state and images as a trunk read once into an `Lfm2LayerCache`; each question continues it as a right-padded row in budgeted batches against the cache tiled to the batch. Logits are f32 log-softmax over the tied embedding head; answers are rounded to four places as upstream's `_answer` does.
- `src/decision/loader.rs`: the `D1` variant, detection arm and constructor arm; the worker, route and CLI are unchanged.
- `src/models/lfm2.rs`: `Lfm2LayerCache::tile`, `forward_hidden_with_caches` and `project_logits`, all new. No generation path was edited, so no logit trace was needed.
- `tests/fixtures/d1/`: `generate_reference.py` runs mlx-vlm's `D1Model` on the checkpoint and `reference.json` records its answers, usage, and trunk, branch and readout ids for nine cases.
- Docs: `docs/decisions.md` (supported-models table, d1-3B section, source map), `docs/supported-models.md`, `README.md`, `CHANGELOG.md`.

## 3. Technical Decisions

**Route in the decision loader only.** `detect_decision_kind` matches `lfm2_vl` / `lfm2-vl` plus the `D1Model` `auto_map`; `get_model_type` is untouched, so `mlxcel generate -m d1-3B` still chats and a plain LFM2-VL checkpoint is still "not a decision checkpoint".

**Reuse the LFM2-VL stack, add explicit-cache entry points.** The scorer loads through `load_lfm2_vl` and calls `get_input_embeddings`, so the processor's checkpoint-configured resize filter (#2388/#2459) applies after d1's own pre-downscale. Generation keeps its model-owned sequence state; the scorer builds its own caches, which is why the LFM2 backbone gained `forward_hidden_with_caches` instead of a change to an existing forward. The per-image vision feature cache (#2453) is not used: decisions read each image once.

**Tile, not recompute, the trunk.** `Lfm2LayerCache::tile` broadcasts the visible FP16 KV window (`visible_state` plus `restore_fp16_live_window`) and the conv tail along the batch axis, matching upstream's `_tile`.

**Where the 1e-4 equivalence is gated.** The issue asks that joint and single-question reads agree within 1e-4 in f32. The checkpoint path runs f16 activations, where upstream itself moves the urgency score by 3.2e-3 between the two. The 1e-4 gate therefore runs in float32 on the synthetic LFM2 backbone the embedding tests already use, with forced batch boundaries and chunked prefill, and the checkpoint path is gated against mlx-vlm's own joint and single outputs at 2e-3.

**Exact image inputs for parity.** The COCO image is `tests/fixtures/sam3/cats.png` (pixel-identical to the JPEG under PIL), so the parity does not depend on JPEG decoders. The over-cap case is a 2x pixel-replicated copy that both arms rebuild exactly.

## 4. Review Outcome

- Implementation review: no CRITICAL or HIGH findings. A MEDIUM coverage gap (images with several questions) was closed with the `cats_multi` fixture case.
- Security and performance review, three HIGH findings fixed: the alias fallback rescanned the pool for every option (the scan now resumes, so each pool entry is encoded at most once per alias pass); the prompt had no length cap (now refused as 400 when the trunk plus every question exceeds `text_config.max_position_embeddings`, 32768 on d1-3B); a single wide row ran in one forward (rows wider than 2048 tokens are now read in pieces). One MEDIUM fixed: a literal `<image>` in an image request's state was a 500 and is now a 400.
- Left open (LOW): `serde_json` writes exponents as `1e20` where Python writes `1e+20`, so such a JSON state tokenizes differently from upstream; special tokens written in a state parse as control tokens, as upstream also does.

## 6. Follow-ups

- d1-3B reads no audio, so the 300 s decision-audio cap from #2343 (checked after full decode) is left for the first audio-capable decision port.
- The `--set-size`, `--score-readout` and `system_one` additions in upstream `decide.py` belong to its LFM3 d1 models, not to d1-3B.
