# Technical Report: Port Mage-VL 4B for image input (#1365)

**Date**: 2026-09-29

**Status**: Implemented and validated locally; pending merge.

**Languages**: Rust

**Risk Level**: Low (new model family; shared code touched only by additive match arms and one processor test)

## Executive Summary

Mage-VL (`microsoft/Mage-VL`, `model_type: "mage_vl"`) now loads and serves image requests through `mlxcel generate --image` and the server. The port adds a Mage-ViT tower with Mage-VL's interleaved 4:6:6 3D RoPE, a 2x2 LayerNorm/MLP merger, and wires both into a plain Qwen3 decoder whose RoPE base is lifted out of the nested `rope_parameters`. On `mlx-community/Mage-VL-8bit` greedy output matches mlx-vlm token for token, including at a 2775-token prompt.

## 1. Problem Statement

mlxcel had no `mage_vl` arm. The closest towers (`qwen2_vl`, `qwen3_vl`) use split-half rotation with equal frequencies per lane pair and `2i/d` exponents, so none could be reused. The released config also stores the decoder RoPE base only as `text_config.rope_parameters.rope_theta = 5e6`; parsed as-is into `qwen3::ModelArgs`, serde falls back to 10000 and the model stays fluent at short lengths while degrading at long ones.

## 2. Change Summary

- `vision/encoders/mage_vl_rope.rs`: block-order positions (`positions_from_grid`), the `base^(-i/size)` 4:6:6 inverse frequencies, the `concat(freqs, freqs)` angle table, an interleaved `rotate_half` built from reshape/slice/concat (not `fast_rope`), f32 rotary application, and the `frame_windows_size` attention windows.
- `vision/encoders/mage_vl.rs`: the tower. The patch kernel is accepted as torch `[O, C, P, P]` or channels-last `[O, P, P, C]` (the 8-bit conversion ships the latter) and applied as a Linear over processor rows. Exact GELU in the MLP and merger, last hidden state, no post-norm. Each attention window (one per image) runs through the tower separately, which equals upstream's block-diagonal `cu_seqlens` attention because every other op is row-wise.
- `vision/mage_vl_config.rs`: vision config with released defaults and named rejections (`use_patch_position_encoding`, `use_head`, `rms_norm`, non-exact GELU, a head width that does not split 4:6:6), `lift_rope_parameters`, token ids, EOS, pixel bounds and normalization from `preprocessor_config.json`.
- `vision/mage_vl.rs` + `loading/vlm_mage_vl.rs`: `MageVlModel` delegates every `LanguageModel` path (including `forward_last_logits*`, batching and paged decode) to `Qwen3Model`. The loader remaps both hub and MLX key layouts, inherits top-level `quantization`, and drops the tower when `vlm_has_vision` says the checkpoint is stripped.
- Integration: `ModelType::MageVLM`, detection, registry, metadata, memory estimate, TP placeholder, `LoadedModel`, `VlmRuntimeRef::MageVl`, `has_vision_tower`, a `vlm_runtime` arm (Qwen2-VL preprocessing and `<|image_pad|>` expansion, a feature-count guard, LLaVA scatter over image and video pad ids), CLI summary line, docs.

## 3. Technical Decisions

- The runtime does not go through `QwenVlRuntime`: that trait builds MRoPE state, and Mage-VL's decoder uses ordinary 1-D positions.
- A vision-stripped `mage_vl` checkpoint keeps `ModelType::MageVLM` rather than routing to `qwen3`. The flat Qwen3 text loader cannot read a nested `text_config` or `language_model.*` keys, so this follows the Qwen2-VL-family pattern of #1367: `vlm_has_vision` in the loader, `vision: None`, and the shared refusal message for image requests.
- The vision tower stays in the checkpoint dtype (bf16 for the 8-bit conversion) to match the mlx-vlm reference.

## 4. Validation

- Unit (26 new, all passing): block-order positions, merge-cell grouping, grid coverage, interleaved rotation, 8/12/12 sizes and `i/size` exponents, the concatenated angle table, the rotary formula, attention windows, the channels-last kernel against processor row order, a random-weight forward (row count, finite values, grid errors), cross-image isolation, the RoPE lift (and a test documenting the 10000 fallback), quantization inheritance, key remap, three text-only loader cases, detection, and the `temporal_patch_size = 1` processor row count.
- Real checkpoint `mlx-community/Mage-VL-8bit`, compared against mlx-vlm 0.7.4 on the same weights (greedy):
  - 224x224 solid red, "What color is this image? Answer with one word.": `Red`, grid `(1, 14, 14)`, 49 image tokens.
  - `examples/dog.jpg` pre-resized to 448x896: 48/48 token ids identical, 417 prompt tokens on both sides.
  - original 1024x2048 `dog.jpg` (mlxcel resizes with Lanczos3, the reference with bicubic): first 32 tokens identical.
  - 2775-token prompt (120 records plus the image), asking for record 5 and an image description: identical output, correct recall. The same run with `rope_theta` forced to 10000 answers "None of the choices provided."
  - `mlxcel serve`, OpenAI chat request with the dog image: same 48-token output, 417 prompt tokens.
- `cargo fmt --check`, `cargo clippy --release -p mlxcel --lib --tests -D warnings`, and the `cli_help_consistency`, `dead_doc_pointers`, `llama_compat_manifest` contract tests pass.

## 5. Not done

- The issue asked for parity against the checkpoint's own `transformers` implementation on CPU bf16. The oracle used here is mlx-vlm on the same int8 weights; the model card reports 48/48 int8-vs-PyTorch parity on the same dog image, so the chain is covered indirectly but not rerun here.
- Codec-native video and plain frame-sampled video are out of scope; the attention-window helper is in place for a later video path. The opportunistic vision feature cache is not wired for this family.
