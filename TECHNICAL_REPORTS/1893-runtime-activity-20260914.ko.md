# 기술 보고서: PR #1893 — 런타임 관측과 활동 화면

**날짜**: 2026-09-14

**상태**: 구현과 범위가 명시된 운영 검증 완료 — native hidden 호스트 성능 및 최종 통합 수동 검증은 남아 있습니다.

**언어**: Rust, TypeScript/React, JavaScript, OpenAPI/JSON Schema

**위험도**: 중간

## 요약

에픽 #1834의 하위 이슈 #1847은 npm에 배포된 `@lablup/ui-common@0.1.0-alpha.19` 어댑터로 활동 화면을 구현합니다. 기존 provider, 수명주기, 슬롯과 지표 모듈이 유일한 상태 원천입니다. 알 수 없는 값과 실제 0을 구분하며 MLX 초기화, 자동 모델 로드 또는 GPU 샘플링을 추가하지 않습니다.

## 구조와 동작

정규 런타임 프로젝션을 `webui/api.rs`에서 `webui/runtime.rs`로 분리하고 필수 타입 `slots` 및 전체 응답 계약 픽스처를 추가했습니다. 준비된 provider 상태는 표시 가능한 카탈로그 ID와 revision이 일치할 때만 복제합니다. 새 조회는 CPU 카운터와 제한된 비식별 슬롯 스냅샷뿐이며 `--metrics`, `--slots` 활성화 조건을 유지합니다. 요청 및 provider 수명 내 누적 완료 카운터와 캐시 지표는 단위·범위·시각·출처·집계 범위를 제공합니다. 저비용의 확실한 원천이 없는 실제 일반 병렬도, 프로세스·할당자·장치 메모리, 정확한 KV 바이트, TTFT, 구간 디코드 속도는 N/A입니다.

머지된 #1800의 컨텍스트 카운터에는 수락된 디코드 토큰이 이미 포함됩니다. 활동 화면은 이를 다시 더하지 않으며, 알 수 없거나 0인 컨텍스트 한도로 점유율을 계산하지 않습니다. 공유 풀 크기는 별도의 nullable 값입니다. #1815의 실제 작업자가 공개한 단일 병렬도·컨텍스트 원천을 사용하고 설정값에서 재계산하지 않습니다.

활동 화면은 진행·완료 작업, 명시적인 취소 확인, 타입 오류, 선택 모델 런타임, 일부 슬롯 경고, 안전한 진단 내보내기와 지연 로드 이력 그래프를 제공합니다. 공유 synchronizer 하나가 보이는 탭의 2초 관측, 10초 스냅샷 제한, 숨겨진 탭의 요청·스트림·타이머 종료와 재연결을 관리합니다. 실제 provider 모델 선택은 관측 전용 `selectionChanged()`를 호출하여 진행 중 추론을 유지하며 로그아웃은 전체 세션을 중단합니다. 완전하고 필터 없는 카탈로그에 모델이 없을 때만 선택을 해제하고 세대 및 페이지 일관성을 확인합니다.

선택 모델 이력은 메모리에서만 5분·2초 간격 최대 150개를 유지합니다. 완료 작업은 같은 sequence의 반복 스냅샷에서도 1시간·최대 200개로 제한하고 진행 중 작업은 조용히 삭제하지 않습니다. 진단은 임의 문자열 치환이 아니라 허용 목록만 내보내므로 키, 개인 경로, 프롬프트, 출력, 모델 ID, 작업 오류가 포함되지 않습니다.

## 독립 리뷰 수정

- 정확성 리뷰가 실제 provider에 연결되지 않은 관측 전용 취소 경로를 발견했습니다. 후속 채팅 이슈에서 소유권을 명시적으로 넘겨받아 실제 provider 연결과 선택 시 스트림 유지·로그아웃 시 중단 회귀 테스트를 추가했습니다.
- 보안·성능 리뷰가 스냅샷 완료 작업 TTL 누락, 다른 모델 응답에 의한 선택 이력 오염, 일부 슬롯 경고 누락을 발견했습니다. 모두 회귀 테스트와 함께 수정했고 재리뷰에서 남은 지적이 없습니다.
- 기존 abort-reader 거부 경쟁 수정은 채팅 이슈 소유입니다. 활동 이슈는 이를 중복 수정하거나 transport promise 해결을 추론 성공으로 해석하지 않습니다.

## 남은 검증과 통합

`activity-performance.mjs`는 실제 headed 브라우저에서 보이는 클라이언트 1개·2개·실제로 숨겨진 탭을 각각 UI-off와 5회씩 순서를 바꿔 비교하도록 준비되었습니다. 서버 `timings.predicted_per_second`만 사용하며 쌍별 성능 저하 중앙값과 변동성을 기록하고, 2% 초과 저하 또는 5% 초과 기준 CV는 조사 대상으로 표시합니다. `activity-slots.mjs`는 실제 긴 채팅 스트림 중 native 전·runtime·native 후 슬롯을 기록하고 모든 텍스트를 제외하며 시간 제한과 명시적인 비교 대기 상태를 유지합니다. 하네스는 구문·lint 검증만 했으며 실측 결과가 아닙니다.

중앙 통합 순서는 #1846 → #1847 → #1844 → #1845입니다. 루트는 리베이스 시 설정의 실제 활성 구성·CLI 우선순위와 작업 세션 차단을 보존하고, 스키마 변경을 합쳐 번들을 재생성한 후 전체·실모델·실제 CSP·성능 검증을 수행해야 합니다. Safari·VoiceOver·실제 200% 확대는 최종 통합 수동 검증으로 연기되었으며 통과가 아닙니다. 기존 사용자 체크포인트를 수정하거나 삭제하지 않았습니다.

## 실제 호스트 검증 후속 및 간결한 기본 화면

루트가 이전 `93c825b8` 런타임으로 수행한 운영 브라우저 2건과 CSP 검증, 실제 native/runtime 슬롯 비교가 통과했습니다. 컨텍스트 8192에서 4개 표본을 수집했고 그중 안정적인 비교 구간 3개를 확인했으며 서버는 정상 종료했습니다. 이후 headed 성능 측정은 첫 visible 처리군 이전에 실패했습니다. warmup과 UI-off 요청 각 1건만 존재하므로 UI 오버헤드 결론은 내리지 않습니다. 최초 실패 기록을 보존합니다.

CPU 전용 진단에서도 창 크기 변경 뒤 빈 headed 페이지의 layout/visual viewport가 0이었고 스크린샷이 멈췄습니다. 전체 Chromium의 headless 모드는 정상 크기였지만 창 최소화와 탭 전환으로 `document.hidden`이 바뀌지 않았습니다. 하네스는 이제 warmup 전에 실제 화면 크기·가시성을 검사합니다. 선택적인 visible-only headless 모드는 항상 incomplete이며 native hidden은 not-run입니다. hidden 오버헤드는 통합 #1848의 정상 대화형 호스트 검증으로 남기며 통과·면제 처리하지 않습니다.

루트의 실제 화면 검토에서 기본 N/A 목록이 지나치게 길다는 문제가 확인되어 주요 가용 요청 카운터와 슬롯만 기본으로 표시하고, 사용할 수 없는 측정값 수를 명시했습니다. 측정된 0은 유지하며 모든 측정값·개별 사유·범위·출처는 키보드로 펼칠 수 있는 기본 disclosure에 남겼습니다. EN/KO 사람이 읽을 수 있는 이름과 누적 카운터 구분을 적용했고 백엔드·공통 디자인 토큰은 바꾸지 않았습니다. 독립 재검토에서 차단 지적은 없으며 프런트엔드 139개·오프라인 SSE/검증 정책 17개·TypeScript·ESLint를 통과했습니다. 수정 화면의 실제 브라우저 및 visible-only 성능 측정은 루트 담당 미완료 항목입니다.

## Headless 진단 실행 환경 교정

루트의 `34fffa69` 검증에서 운영 빌드·브라우저 23개·실제 CSP/axe/레이아웃 2개·실제 슬롯 비교를 다시 통과했습니다. 루트가 간결해진 실제 화면도 확인했으며 UI 회귀는 발견하지 않았습니다. 별도 full-Chromium headless 성능 시도는 표본을 남기기 전에 context 교체 중 SIGBUS로 종료했고 display-link/notification-center 오류를 기록했습니다. 이 실패는 정상 UI 검증과 구분하여 보존하며 처리량 증거로 사용하지 않습니다.

진단 하네스만 기본 Chromium headless shell로 바꾸고 headless 경로의 native-window/CDP 호출을 모두 제거했습니다. 실제 가시성 검증, visible-only의 incomplete 상태와 #1848 native hidden 필수 검증은 유지합니다. 런타임·프런트엔드 소스와 UI 자산 바이트는 변경하지 않았습니다.

## 최종 visible-only 실측 증거

최종 하네스 `e83508b083696657cdce36568c8ba3cd94bbfaf3`에서 `34fffa69adafccb7eb085cb1ce4d35b7fb50ee9c` 빌드의 운영 바이너리(SHA-256 `bfdaf8f5d3e5ae020bf00de726a30d9e3b94eb9f01784506782f171746400010`)로 visible-only headless 측정을 완료했습니다. 두 커밋 사이 UI·백엔드·번들 바이트는 동일합니다. 기존 Llama 3.1 8B Instruct 4-bit 체크포인트를 격리된 소유 캐시에 복사하고 같은 모델·요청·하드웨어에서 조건별 off/treatment 순서를 교대하며 5쌍씩 측정했습니다. warmup 1건을 포함한 총 21요청 모두 실제 256토큰을 기록했습니다.

| Headless visible 조건 | 쌍 수 | 중앙 디코드 성능 저하 | 기준선 변동계수 |
|---|---:|---:|---:|
| 클라이언트 1개 | 5 | -0.069808% | 0.271240% |
