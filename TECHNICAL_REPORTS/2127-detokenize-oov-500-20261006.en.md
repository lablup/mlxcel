# Technical Report: Issue #2127 - Answer 500 for out-of-vocabulary ids in POST /detokenize

**Date**: 2026-10-06

**Status**: Implemented and validated on GB10, awaiting merge.

**Language**: Rust (tokenizer, detokenize route, route tests), Markdown

**Risk**: Low (client-visible: ids that were silently dropped, or answered 400 on SentencePiece, now answer 500 `server_error`; valid ids are unchanged)

## Summary

`POST /detokenize` dropped ids that are not in the vocabulary and answered 200 on HuggingFace and tiktoken tokenizers, answered 400 on SentencePiece, and turned `-1` into `4294967295` through an `as u32` cast. llama.cpp answers 500 `server_error` for all of these. A caller could not tell a truncated answer from a real one.

## 1. Change

- `MlxcelTokenizer::contains_id` is a membership test per backend: HuggingFace `id_to_token(id).is_some()` (the lookup `decode` uses, so added and special tokens count), SentencePiece special or added contents or `id < processor.len()`, tiktoken `special_decoder` or `decoder`. It is deliberately not `id < vocab_size()`: the HuggingFace `vocab_size()` counts entries, not max id plus one.
- `DetokenizeRequest.tokens` is now `Option<Vec<i64>>`, so ids above `i32::MAX` reach the check instead of axum's plain-text 422.
- The handler checks every id before decoding. A negative id, one that does not fit `u32`, or one that fails `contains_id` returns `ErrorResponse::internal_server_error("token id {id} is out of vocabulary range (vocab_size {n})")` for the first bad id in request order, with the id as sent. No partial text is returned. `decode` is unchanged.

## 2. Validation

- `cargo test --lib --features cuda server::routes::tokenize tokenizer:: -- --test-threads=1` under gpu-lock: all pass, including six new route tests and `tokenizer::contains_id_tests`.
- The gap-vocabulary test (entries at ids 0..=2 and an added token at id 10, so `vocab_size()` is 4) refuses id 3 and accepts id 10, so it fails if `contains_id` becomes `< vocab_size()`.
- `cargo clippy --lib --tests --features cuda -- -D warnings` and `cargo fmt --check` are clean.
- Live check with a release `mlxcel-server` on `qwen3-0.6b`: `[999999999]`, `[9707,999999999,1879]`, `[-1]`, `[3000000000]` answer 500 `server_error` naming the id and `vocab_size 151669`; `[9707,1879]` answers 200 `Hello world`; `[]` answers 200 `""`.

## 3. Notes

The existing `tower_http` trace layer logs a line for every 500; no handler-level log was added. Continuum Router's pinned 200 fixtures need a re-capture after this lands.
