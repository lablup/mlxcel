# PR #2770: MLX CUDA layer_norm VJP 꼬리 구간을 벡터 내 오프셋으로 인덱싱

**날짜**: 2026-10-31 (머지 전에 작성한 보고서이며, 작성 시점에 PR은 열린 초안 상태)
**상태**: 열린 PR. CUDA(GB10, sm_121)에서만 검증했고 다른 CUDA 아키텍처는 실행하지 않음. Metal과 ROCm은 이 파일을 컴파일하지 않음
**언어**: CUDA C++, Rust, Markdown
**위험도**: 낮음 (마지막 벡터가 일부만 채워지는 행만 타는 분기의 인덱스 식 두 개를 바꿈. 전체 벡터 경로는 소스 수준에서 변경 없음)

## 요약

PR #2770(#2759 해결)은 `fast::layer_norm`의 입력 기울기를 계산하는 CUDA 커널 `layer_norm_vjp`의 꼬리(tail) 분기에서 발생하던 범위 밖 읽기를 고친다. 두 번째 리덕션의 꼬리 루프가 스레드별 벡터 `wn`, `gn`(각각 `N_READS`개 원소)을 벡터 안의 오프셋이 아니라 절대 열 번호 `i`로 인덱싱했다. 그래서 폭이 `N_READS`의 배수가 아닌 모든 행이 이 배열 밖을 읽었다. GB10에서 결과는 dtype에 따라 달랐다. 폭 390의 bf16 VJP는 illegal memory access로 프로세스를 중단시켰고, f32 VJP는 모든 행에서 틀린 `dx`를 반환했다(2048행 중 2047행 또는 2048행이 허용 범위 밖, 최대 절대 오차 약 2.9e-2).

수정은 CUDA 오버레이 `src/lib/mlxcelverse/overlays/cuda/mlx/backend/cuda/layer_norm.cu`에서 `wn[i]`, `gn[i]`를 `wn[i - index * N_READS]`, `gn[i - index * N_READS]`로 바꾸고 `[mlxcel #2759]` 표식을 단 것이다. 새 테스트는 폭 390에서 bf16과 f32, weight 있음과 없음 조합의 `dx`를 f64 호스트 기준값과 비교하고, 폭 384 대조군도 함께 돌린다. main에서는 실패하고(bf16은 중단, f32는 77만 개 이상의 원소가 범위 밖) 수정 후에는 6/6 통과한다.

## 1. 문제 정의

### 1.1 배경

이 버그는 PR #2749(#2696 해결) 리뷰 중에 발견되었다. #2749는 이 오버레이를 추가해 `BlockBroadcastReduce::Reduce`에 두 번째 배리어를 넣었다. 그 PR은 오버레이를 MLX 핀과 한 줄만 다르게 유지하려고 이 두 번째 버그를 의도적으로 고치지 않았고, `TECHNICAL_REPORTS/2749-cuda-layer-norm-reduction-barrier-20261030.ko.md` 6절에 기록해 두었다. #2749가 추가한 VJP 테스트(`bf16_vjp_input_gradient_is_deterministic`, 폭 384)는 꼬리 분기를 타지 않는다. 384는 8(bf16)과 4(f32)의 배수이기 때문이다. 또한 그 테스트는 결정성만 보고 정확도는 보지 않는다.

업스트림 `ml-explore/mlx` main `1ba7f969`(2026-10-30)에도 같은 코드가 그대로 있다. 이 파일은 업스트림에서 `6ec01922`(2026-02-26) 이후 바뀌지 않았고, 이를 다루는 업스트림 이슈나 PR은 없다. 핀을 올려도 고쳐지지 않는다.

### 1.2 원인

`layer_norm_vjp`는 한 행을 세 번 훑는다. 평균을 위한 합, 원소마다 세 가지 인자(`t = x - mean`, `wg = w * g`일 때 `wg`, `wg * t`, `t * t`)를 누적하는 두 번째 리덕션, 그리고 `gx`와 `gw`를 쓰는 출력 단계다. 각 스레드는 연속된 `N_READS = 16 / sizeof(T)`개 원소를 맡는다(bf16과 f16은 8, f32는 4). 두 번째 단계는 다음과 같다.

```cpp
auto gn = load_vector<N_READS>(g, index, axis_size, T(0));
auto wn = load_vector<N_READS>(w, index, axis_size, w_stride, T(0));
if ((index + 1) * N_READS <= axis_size) {
  // 전체 벡터: wn[i], gn[i]에서 i는 [0, N_READS) 범위, 올바름
} else {
  for (int i = index * N_READS; i < axis_size; ++i) {
    float t = static_cast<float>(x[i]) - mean;   // x는 전역 메모리에서 읽음: 올바름
    float wi = wn[i];                             // i는 열 번호인데 wn은 N_READS칸뿐
    float gi = gn[i];
```

폭 390에서 꼬리 스레드는 bf16이면 `index` 48(열 384~389), f32이면 `index` 97(열 388~389)이다. 이 스레드는 8칸 또는 4칸짜리 배열에서 `wn[384..389]` 또는 `wn[388..389]`를 읽는다. 인덱스가 런타임 값이라 컴파일러는 `wn`, `gn`을 스레드별 로컬 메모리에 두므로, 이 읽기는 스레드 프레임 너머의 어딘가에 떨어진다.

손상되는 것은 세 인자 중 앞의 두 개뿐이다. `t * t`는 `x[i]`를 전역 메모리에서 읽으므로 분산과 `normalizer`는 올바르다. 손상된 합은 `meanwg`와 `meanwgxc`로 들어가고, 이 두 값이 출력 단계에서 그 행의 `dx` 모든 원소에 곱해진다. 꼬리 스레드 하나가 행 전체를 망가뜨리는 이유가 이것이다. 첫 번째 단계와 출력 단계는 범위 검사와 0 채우기를 하는 `load_vector`를 쓰므로 올바르고, 따라서 `gw`와 bias 기울기는 영향을 받지 않는다.

### 1.3 dtype마다 증상이 다른 이유

main에서 폭 390의 bf16은 `cudaGetLastError() failed: an illegal memory access was encountered`로 중단되었고(exit 134), f32는 끝까지 실행되면서 조용히 틀린 값을 냈다. PR은 이 차이를 설명하지 않으며, 이 보고서도 설명하지 못한다. 범위 밖 오프셋은 f32 쪽(4바이트 타입의 388번째 열)이 bf16 쪽(2바이트 타입의 384번째 열)보다 크므로 "더 멀리 벗어나면 폴트가 난다"는 설명은 맞지 않는다. 결과는 인스턴스마다 로컬 메모리가 어떻게 배치되는지, 그 너머에 무엇이 있는지에 달려 있다. 정의되지 않은 동작이며, 같은 버그가 어떤 빌드에서는 크래시로, 다른 빌드에서는 틀린 숫자로 나타날 수 있다는 점이 교훈이다.

### 1.4 영향과 수정하지 않았을 때의 위험

mlxcel은 추론 전용이고, CUDA `LayerNormVJP` 프리미티브에는 테스트 브리지 `mlxcel_core::fast_layer_norm_vjp_for_test`(`src/lib/mlxcel-core/cpp/mlx_cxx_bridge.cpp`)로만 도달한다. 현재 프로덕션 코드 경로에는 영향이 없다.

| 위험 | 영향 | 가능성 |
|---|---|---|
| 앞으로 학습, 파인튜닝, 기울기 기반 경로가 생기면 폭이 4나 8의 배수가 아닌 LayerNorm에서 틀린 입력 기울기를 받음 | 높음 (조용히, 모든 행) | 그런 경로가 생기면 해당 폭에서 확실 |
| bf16에서 범위 밖 읽기로 프로세스 중단 | 높음 | GB10 폭 390에서 관측 |
| 프로젝트가 오버레이로 배포하는 커널의 정의되지 않은 동작 | 중간 | 모든 빌드에 존재 |

## 3. 기술적 선택과 그 이유

### 3.1 벡터 로드는 유지하고 인덱스만 고침

| 선택지 | 장점 | 단점 |
|---|---|---|
| 꼬리에서 `w[i * w_stride]`, `g[i]`를 전역 메모리에서 직접 읽기 (이슈에서 기각) | 명백히 올바름. ROCm 오버레이의 인덱싱 방식과 같음 | 업스트림과 더 멀어지고, 핀을 올릴 때 오버레이를 다시 diff하기 어려워짐 |
| 꼬리 분기를 없애고 `axis_size`를 넘는 열을 마스킹한 전체 벡터 루프로 통일 | 코드 경로가 하나 | 0으로 채운 칸은 `t = 0 - mean`이라 `t * t`가 0이 아니므로 모든 인자에 마스크가 필요함. 프로젝트가 소유하지 않은 커널의 구조 변경 |
| **선택: `wn[i - index * N_READS]`, `gn[i - index * N_READS]`** | 식 두 개. 오버레이가 핀과 작고 검토 가능한 차이로 유지됨. 값은 전체 벡터 경로와 같은 `load_vector` 읽기에서 옴 | 꼬리 분기는 여전히 스레드별 배열을 런타임 인덱스로 접근하므로, 그 분기에서 `wn`, `gn`은 이전처럼 로컬 메모리에 남음 |

`index`에 이미 라운드가 반영되어 있으므로(`index = r * BLOCK_DIM + thread_rank`), 오프셋 식은 여러 라운드에 걸친 긴 행(`axis_size > BLOCK_DIM * N_READS`)에서도 올바르다.

### 3.2 전체 벡터 경로는 건드리지 않음

이슈는 폭이 `N_READS`의 배수일 때 출력이 바이트 단위로 같을 것을 요구했다. 전체 벡터 분기의 소스는 바뀌지 않았다. PR은 두 가지 보조 근거를 더했다. cuobjdump로 `layer_norm_vjp` 인스턴스 48개 전부의 SASS를 비교했을 때 main과 수정 빌드의 FADD, FMUL, FFMA, MUFU, BAR, SHFL, LDS, STS 개수가 같았고, 384 대조군은 수정 전후 기준값 대비 최대 오차가 같았다. 둘 다 바이트 수준 증명은 아니며(명령어 개수가 같아도 순서나 레지스터는 다를 수 있음), PR도 그렇게 밝히고 있다.

### 3.3 테스트 설계

- **반올림된 입력으로 f64에서 계산한 기준값.** `vjp_dx_reference`는 커널이 실제로 받은 bf16 또는 f32 입력을 다시 읽어 행마다 `xhat = (x - mu) * rstd`, `wg = w * g`, `dx = rstd * (wg - mean(wg) - xhat * mean(wg * xhat))`를 계산한다. 이슈는 f32 기준값을 제안했지만, f64를 쓰면 기준값 자체의 반올림 오차가 비교에서 빠진다.
- **허용 범위.** f32는 `1e-4 + 1e-4 * |ref|`. bf16은 기존 순방향용 `tolerance(BFLOAT16, ref)`이며, 기준값의 bf16 ulp 하나에 1e-2를 더한 값이다. f32 범위는 양쪽 모두 여유가 크다. 384 대조군의 최대 절대 오차는 4.8e-7이고, 고장 난 390 커널은 2.9e-2다. bf16은 여유가 좁다. 대조군의 최대 절대 오차 7.8e-3에 비해 범위는 최소 1e-2다. 실패 쪽 여유는 bf16에서 필요 없었다. main이 출력을 내기 전에 중단되었기 때문이다.
- **두 가지 weight 모드.** weight 없는 호출은 `w_stride == 0`인 스칼라 weight를 넘기며, 이것도 `load_vector`와 꼬리 분기를 거친다. 두 dtype 모두에서 affine과 no-weight를 다룬다.
- **결정성도 함께 확인.** 각 케이스는 기존 `repeat` 검사(32번 호출, 바이트 단위 정확 비교)도 거치므로, 390 케이스도 #2696 케이스와 같은 기준을 적용받는다.
- **대조군 먼저.** 테스트는 `dim in [384, 390]` 순서로 돌기 때문에, main에서 390 케이스가 프로세스를 중단시키기 전에 384 대조군 네 개의 결과가 먼저 출력된다. 유한하지 않은 출력은 오차를 무한대로 보므로 NaN이 범위를 통과할 수 없다.
- **테스트 하나, 실패 모아서 보고.** 케이스 여덟 개를 모두 돌리고 실패 문자열을 하나의 assertion으로 합치므로, 첫 실패만이 아니라 실패한 모든 케이스가 보고된다(main에서는 첫 bf16 390 케이스의 중단이 실행을 끝내기는 함).

## 4. 검증

모두 GB10(sm_121), `--test-threads=1`, `gpu-lock` 아래에서 실행.

**먼저 실패 확인.** 커밋된 테스트를 main의 `layer_norm.cu`로 빌드했다(로컬에서 오버레이를 되돌리고 MLX를 다시 빌드한 뒤, 빌드된 소스에 표식이 없음을 확인). 384 대조군 네 개가 통과한 다음, 첫 bf16 390 케이스가 illegal memory access로 중단되었다(exit 134). main 커널에서 390 케이스를 하나씩 따로 돌린 결과는 다음과 같다(같은 통과 조건을 가진 이전 버전 테스트와 임시 케이스 필터를 썼고, 둘 다 커밋하지 않음).

| 케이스 (폭 390, 2048행) | main | 수정 후 |
|---|---|---|
| bf16 affine | illegal memory access, exit 134 | 범위 밖 0개, 최대 절대 오차 7.812e-3 |
| bf16 no-weight | illegal memory access, exit 134 | 범위 밖 0개, 최대 절대 오차 6.521e-3 |
| f32 affine | 2047행에서 770741개 범위 밖, 최대 절대 오차 2.943e-2 | 범위 밖 0개, 최대 절대 오차 4.768e-7 |
| f32 no-weight | 2048행에서 771244개 범위 밖, 최대 절대 오차 2.965e-2 | 범위 밖 0개, 최대 절대 오차 3.576e-7 |

고장 난 f32 커널은 결정적이었다(32번 호출에 출력 한 가지). 결정성만 보는 테스트로는 잡을 수 없었다.

**수정 후.** `cuda_layer_norm_determinism` 타깃 전체가 6.59초에 6/6 통과한다. 새 테스트, `bf16_vjp_input_gradient_is_deterministic`, 그리고 #2749의 순방향 케이스 네 개다. 384와 390의 모든 케이스가 32번 호출에 출력 한 가지를 낸다. `cargo fmt --all -- --check`와 `cargo clippy --profile test-fast --features cuda -p mlxcel --tests -- -D warnings`도 통과한다.

## 5. 학습 포인트

- **벡터화된 커널에는 인덱스 공간이 두 개 있다.** 스레드마다 `N_READS`개 원소를 로컬 배열로 읽는 코드에서, 전체 벡터 루프는 칸 번호를 쓰고 꼬리 루프는 보통 열 번호를 쓴다. 꼬리 안의 배열 접근은 모두 칸 번호로 되돌려야 한다(`열 - index * N_READS`). 꼬리 분기를 리뷰할 때는 모든 첨자가 어느 공간에 속하는지 확인해야 한다.
- **벡터 폭의 배수가 아닌 폭을 테스트하라.** 384, 4096, 3840은 모두 8의 배수라서 이전 테스트의 모든 형상이 꼬리 분기를 건너뛰었다. 390처럼 4의 배수도 8의 배수도 아닌 폭은 bf16과 f32의 꼬리를 한 번에 시험한다.
- **결정성이 정확성을 뜻하지는 않는다.** f32 커널은 매번 같은 틀린 바이트를 냈다. 수치 커널 테스트에는 반복 검사만이 아니라 기준값이 필요하다.
- **정의되지 않은 동작은 서로 다른 두 버그처럼 보일 수 있다.** 같은 범위 밖 읽기가 한 인스턴스에서는 크래시를, 다른 인스턴스에서는 조용한 손상을 일으켰다. 실패 양상이 dtype마다 다르면 원인이 둘이라고 가정하기 전에 UB부터 의심하라.
- **크래시가 나도 증거가 남도록 케이스 순서를 정하라.** 프로세스를 중단시킬 수 있는 케이스보다 대조군을 먼저 돌리면, main에서 실패를 확인하는 실행에서도 기준값과 허용 범위가 타당함을 보여 주는 대조군 수치가 출력된다.

## 6. 한계와 후속 작업

- **sm_121에서만 테스트함.** 범위 밖 읽기와 수정은 아키텍처와 무관하지만, main이 크래시를 낼지 틀린 값을 낼지는 다른 GPU에서 다를 수 있다.
- **`gw`와 bias 기울기는 기준값과 비교하지 않음.** 이슈와 커널 구조상 영향이 없지만(출력 단계는 범위 검사를 하는 로드를 씀), 새 테스트는 `dx`만 확인한다.
- **전체 벡터 경로의 바이트 동일성은 뒷받침될 뿐 증명되지 않음.** 3.2 참고.
- **bf16 허용 범위가 틀린 꼬리를 거부하는 장면은 관측되지 않음.** main에서 bf16 390 케이스는 출력 전에 크래시했으므로, 기준값 검사가 이 버그를 잡는 것은 f32 케이스로만 확인되었다. bf16 범위는 #2749가 순방향 커널에서 이미 검증한 것을 그대로 쓴다.
- **bf16은 폴트가 나고 f32는 나지 않는 이유는 설명되지 않음** (1.3 참고).
- **업스트림은 여전히 영향을 받음.** `ml-explore/mlx`에 버그를 보고하는 일은 이슈에서 범위 밖으로 두었다. 업스트림이 고치기 전까지는 MLX 핀을 올리며 오버레이를 다시 diff할 때마다 #2696 배리어와 함께 이 변경도 다시 적용해야 한다.
- **이슈에서 범위 밖으로 둔 항목:** ROCm 커널(`overlays/rocm/mlx/backend/rocm/layer_norm.hip`은 `w[idx * w_stride]`, `g[idx]`를 열 번호로 인덱싱하므로 영향 없음), Metal 커널, `rms_norm_vjp_small`.
