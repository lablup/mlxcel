# 기술 보고서: PR #3017 - fix(python): keep live sockets and non-socket entries at the managed path

**날짜**: 2026-11-14
**상태**: 완료
**언어**: Python
**위험도**: 중간 (시작 시 동작 변경)

---

## 요약

`ManagedServer.start()`는 `mlxcel serve`를 띄우기 전에 Unix 소켓 경로에 있는 것을 무엇이든 삭제했습니다. 일반 파일, 디렉터리 항목, 심볼릭 링크, 다른 서버의 살아 있는 소켓까지 조용히 지워졌고, 실행 중인 서버는 디스크립터는 유지하지만 경로로는 접근할 수 없게 되었습니다. 이제 시작 전에 항목을 먼저 확인하고 아무도 listen하지 않는 소켓만 삭제합니다. 그 밖의 경우에는 자식을 띄우기 전에 `MlxcelServerError`를 발생시키고 항목은 그대로 둡니다. 이 규칙은 #3021의 Rust 서버 `bind_unix` 수정과 같으므로, 두 계층이 stale 소켓을 판단하는 기준이 일치합니다.

---

## 1. 문제 정의

### 1.1 배경

POSIX의 관리형 모드는 띄운 서버와 Unix 도메인 소켓으로 통신합니다. 소켓 파일은 바인드한 프로세스보다 오래 남으므로, 비정상 종료한 서버가 남긴 파일 때문에 다음 `bind()`가 `EADDRINUSE`로 실패합니다. 그래서 클라이언트는 매번 시작 전에 경로를 비웠습니다.

### 1.2 기존 문제

- 삭제가 무조건적이었습니다: `os.path.exists(path)` 다음 `os.unlink(path)`.
- `socket=`로 다른 서버가 사용 중인 경로를 넘기면 그 서버의 경로를 빼앗았습니다.
- `socket=` 오타가 일반 파일을 가리키면 그 파일이 삭제되었습니다.
- 바로 앞에 머지된 #3005는 자식을 띄우지 않았을 때 `close()`가 경로를 삭제하지 않게 했습니다. 이것이 없으면 이 PR이 발생시키는 오류 뒤에 생성자의 정리 코드가 경로를 다시 삭제했을 것입니다.

### 1.3 위험 평가

| 위험 | 영향 | 가능성 |
|------|------|--------|
| 항목을 지우며 성공하던 시작이 이제 실패 | 호출자가 `MlxcelServerError`를 받음 | 낮음, 이전 동작은 파괴적이었음 |
| 살아 있는 listener를 stale로 오판 | 이전처럼 경로 삭제 | accept 큐가 완전히 찬 macOS에서만 |
| 탐침과 삭제 사이의 경쟁 | 같은 stale 경로에 대한 동시 시작 두 개 | 낮음, 락이 아니라고 문서화 |

## 2. 기술 검토

### 2.1 보안

파괴적인 동작의 범위를 좁힙니다. `lstat`을 사용하므로 경로의 심볼릭 링크는 "소켓 아님"으로 보고되고 링크 대상은 건드리지 않습니다. 판단할 수 없는 탐침 결과(`EACCES`, `EPROTOTYPE`)는 stale이 아니라 "사용 중"으로 취급하므로 추측으로 삭제하지 않습니다.

### 2.2 성능

시작 시 기존 소켓에 대해 non-blocking `connect()` 한 번. 무시할 수준입니다.

### 2.3 호환성 및 의존성

- **호환성 깨짐**: 파일, 디렉터리, 심볼릭 링크, 살아 있는 소켓, 다른 종류의 소켓이 있는 경로에서의 시작은 이제 삭제 대신 오류를 냅니다. 비정상 종료한 서버가 남긴 소켓은 이전처럼 교체됩니다.
- **새 의존성**: 없음.
- **호환 범위**: POSIX 전용. Windows는 TCP를 쓰며 새 테스트는 건너뜁니다.

### 2.4 코드 품질

`python/tests/test_startup_path.py`는 각 케이스를 `ManagedServer.start()`, `LLM(...)`, `AsyncLLM(...)`로 실행합니다. 대역 자식은 마커 파일만 쓰므로 프로세스가 시작되지 않았고 항목의 device, inode, mode가 바뀌지 않았음을 확인할 수 있습니다. 살아 있는 listener는 이후에도 새 연결을 받아야 합니다. stale 소켓 케이스는 경로를 직접 바인드하는 자식을 사용해, 남은 소켓이 그대로 있으면 `EADDRINUSE`로 실패하게 합니다.

## 3. 기술적 선택과 그 이유

### 3.1 non-blocking connect 한 번으로 분류

**맥락:** 소켓 파일에는 소유자가 살아 있는지에 대한 기록이 없습니다.

| 탐침 결과 | 해석 |
|---|---|
| `ECONNREFUSED`, 경로 사라짐 | stale, 삭제 |
| 연결됨, 또는 `EAGAIN` (Linux에서 큐가 가득 참) | 살아 있는 listener, 거부 |
| 그 밖 (`EACCES`, `EPROTOTYPE`) | 알 수 없음, 거부 |

non-blocking이 중요합니다. 가득 찬 accept 큐에 대한 blocking connect는 listener가 accept할 때까지 기다립니다. #3021의 Rust `probe_unix_socket`도 같은 세 갈래 규칙을 사용합니다.

### 3.2 새 경로로 대체하지 않고 거부

조용히 다른 경로를 고르면 충돌이 가려지고, 넘긴 경로로 접속하는 호출자가 깨집니다. 경로를 메시지에 담아 오류를 내면 사용자가 다른 서버를 멈추거나, 다른 경로를 고르거나, 모델 없이 `socket=`만 넘겨 실행 중인 서버에 접속할 수 있습니다.

### 3.3 리뷰 후속 작업: 시작 중 끊긴 탐침

macOS에서 테스트를 실행하면서 `_probe_once`의 별도 결함이 드러났습니다. 준비 확인 요청이 큐에 있는 동안 자식이 종료하면 httpx는 macOS에서 `RemoteProtocolError`를(Linux는 `ReadError`) 냅니다. 이를 잡지 않아 `start()`가 자식의 stderr를 담은 `MlxcelServerError` 대신 httpx 예외를 그대로 내보냈습니다. 이제 "아직 시작 중"으로 취급하고 다음 생존 확인이 종료를 보고합니다. 또한 살아 있는 listener 픽스처의 backlog를 1에서 8로 바꿨습니다. 탐침의 대기 연결이 backlog 1을 채워 macOS가 테스트 자신의 접속 확인을 거부했기 때문입니다.

## 5. 학습 포인트

- Unix 소켓 동작은 이 코드가 의존하는 바로 그 지점에서 Linux와 macOS가 다릅니다. 가득 찬 accept 큐는 Linux에서 `EAGAIN`, macOS에서 `ECONNREFUSED`이므로 macOS에서는 포화된 listener와 stale 소켓을 구별할 수 없습니다.
- accept되지 않은 탐침 연결도 backlog 한 칸을 차지합니다. 탐침 후 다시 접속하는 테스트는 backlog에 여유가 필요합니다.
- 헬스 체크 루프는 "응답 없이 연결이 끝남"의 모든 변형을 일시적인 것으로 보고, 오류는 프로세스 생존 확인이 만들게 해야 합니다. httpx는 같은 사건을 플랫폼마다 다른 예외 클래스로 매핑합니다.
- 검증되지 않은 부분: 확인과 삭제는 원자적이지 않고, 바인드했지만 아직 listen하지 않은 소켓은 stale로 읽힙니다. 둘 다 README에 문서화되어 있습니다.
