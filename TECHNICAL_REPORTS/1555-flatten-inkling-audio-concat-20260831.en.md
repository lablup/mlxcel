**Date**: 2026-08-31
**Author**: mlxcel maintainers
**Status**: In review; implementation and validation complete
**Languages**: Rust, Python, JSON
**Risk Level**: Medium

## Executive Summary

PR #1555 removes a left-deep concatenation graph from the Inkling audio tower. Evaluated chunks are now retained and joined through one many-input MLX operation, while the one-chunk path still returns its existing array without adding a graph node. A 6,000-chunk contract test covers the admitted request ceiling, and a real 256-array MLX test verifies cardinality and order across the FFI boundary.

The PR also replaces a self-referential dMel test oracle with a committed NumPy 2.3.2 fixture. The fixture's waveform and complete 4 x 80 expected output are generated without importing mlxcel or mlx-vlm and without calling the production Rust FFT or Slaney helpers. The generator records the exact NumPy version, RNG recipe, tolerance, and mlx-vlm PR #1767 revisions, making numerical drift detectable and reproducible.

## 1. Problem Statement

### 1.1 Left-deep tower concatenation

The Inkling audio tower processes at most 256 frames per compute chunk so each chunk can be evaluated independently. The previous implementation appended every result to the full prefix with a binary concatenate. For `n` chunks this produced `n - 1` concatenate nodes and repeatedly involved a growing prefix, increasing graph depth and the risk of repeated data movement on long requests.

The model admits at most 6,000 valid audio-frame transforms per request. Because `max_frames_per_chunk` may be configured as 1, the supported edge case is 6,000 chunks, not 256 chunks. The construction therefore needs constant graph depth at the join point and must preserve chunk order for the entire admitted range.

### 1.2 Self-referential numerical oracle

The earlier reference test rebuilt framing and the Slaney filterbank locally but called `crate::audio::fft::real_fft_magnitude` from production. A defect in that FFT path could therefore affect both the implementation and expected-value calculation and remain undetected. The test also reused production-private Slaney conversion helpers, weakening its ability to detect coordinated numerical drift.

The replacement oracle must be static during Rust test execution and generated by a separate numerical stack. It must compare the entire expected tensor, pin a strict tolerance, and preserve provenance so future maintainers can regenerate it exactly.

## 3. Technical Decisions

### 3.1 Use the existing many-input MLX operation

The C++ bridge already accepts a slice of `MlxArray` pointers and forwards it to one `mlx::core::concatenate` call. Extending the bridge or constructing a balanced Rust tree would add code without improving the final graph. The selected Rust wrapper accepts live references, converts them to raw pointers only for the duration of the FFI call, and documents the safety invariant next to the unsafe block.

The tower keeps `eval(normalized)` for each chunk before collection. This preserves the original bounded per-chunk evaluation behavior while removing only the growing concatenate chain. Zero chunks remain an error, one chunk is moved through unchanged, and two or more chunks use the single final operation.

### 3.2 Verify graph shape through an objective seam

Wall-clock benchmarks would be noisy and would not prove graph depth. The generic `join_chunks` helper instead injects the concatenate operation. Its maximum-range regression records invocation count and arity, proving that a 6,000-chunk request creates one final join rather than a left-deep chain.

That pure contract test cannot prove the native bridge accepts a large pointer slice or preserves ordering, so a second test calls the real MLX operation with 256 arrays. Together the tests cover construction shape and FFI behavior without allocating a full 6,000-frame tower model.

### 3.3 Commit a full static NumPy oracle

The generator follows the public mlx-vlm regression recipe: `numpy.random.default_rng(5)`, 2,401 float32 samples, NumPy `rfft`, a periodic Hann window, and an independently implemented Slaney filterbank. It does not import production Rust code or mlx-vlm. The Rust test only deserializes the committed JSON and never executes Python.

The test checks the NumPy version, upstream revisions, shape, waveform length, full expected tensor length, and exact `2e-6` tolerance before comparing all 320 values. Fixing the tolerance in Rust prevents a fixture edit from weakening the oracle by increasing its own allowed error.

## 4. Learning Points

### 4.1 Chunk size and chunk count are different limits

`max_frames_per_chunk = 256` bounds work inside one tower evaluation. It does not bound the number of chunks. With a request ceiling of 6,000 frames and a valid chunk size of 1, the maximum supported chunk count is 6,000. Tests for batching code should derive both boundaries from admission and configuration rules instead of treating a chunk-size constant as request cardinality.

### 4.2 Independent fixtures need independent computations

A reference function is not independent when it calls the production primitive under test. A useful numerical oracle is produced by a different implementation, committed as static data, and protected by exact provenance, shape, length, and tolerance checks. Keeping the generator beside the fixture provides auditability without adding Python or NumPy as a Rust test dependency.

## 7. Validation Limits and Follow-up

This PR validates graph construction, FFI ordering, and host dMel numerics with synthetic MLX arrays and a NumPy oracle. It does not validate a published 153-171 GB Inkling checkpoint, Apple GPU memory use, real transcription quality, or end-to-end throughput. Those hardware-dependent checks remain tracked by issue #1549.

After deployment on a suitable Apple Silicon host, compare long-audio peak memory and prefill latency before and after this change, and run the fixture waveform through the public mlx-vlm implementation as an additional provenance check. No further code change is required for issue #1550.
