# 기술 보고서: PR #3282 - LiquidAI d1-3B 결정 모델 (`lfm2_vl` D1Model)

**날짜**: 2026-11-23
**상태**: 열림 (병합 전에 작성한 드래프트 PR)
**위험도**: 낮음 (새 결정 스코어러 추가. 공유 코드 변경은 LFM2 백본의 새 함수와 로더 재노출뿐)

## 요약

LiquidAI d1-3B는 텍스트나 이미지 상태에 대한 유형별 질문에, 답 위치의 다음 토큰 로그 확률을 읽어 답한다. 체크포인트가 `model_type: lfm2_vl`을 선언하므로 mlxcel은 이를 일반 채팅 모델로 불러왔고, 결정을 얻을 방법이 없었다 (#2367). 이 PR은 #2343 결정 API 뒤에 첫 모델군을 추가한다. `auto_map.AutoModel`이 `D1Model`로 끝나는 것으로 감지하는 `DecisionKind::D1` 로더 분기와, mlx-vlm `models/d1`(d998a620)에서 포팅한 스코어러다. `LiquidAI/d1-3B-MLX-8bit`에서 텍스트 답은 mlx-vlm과 반올림한 네 자리까지 같고, 이미지 답의 차이는 최대 1e-4다.

## 1. 문제

결정 API(`mlxcel decide`, `POST /v1/decisions`, `--decision-model`)는 있었지만 뒤에 테스트용 스텁만 있어서 모든 체크포인트가 거부되었다. d1-3B는 LFM2.5-VL-3B 파인튜닝 모델로, 가중치와 프로세서와 채팅 템플릿은 LFM2-VL 그대로이고 읽어 내는 방식만 다르다. 생성 경로의 모델 감지는 계속 LFM2-VL로 읽어야 하므로(업스트림도 같다), 라우팅은 결정 로더에만 둘 수 있었다.

이슈 작성 이후의 업스트림 변경도 따라야 했다. `d1.py`는 이제 긴 트렁크를 2048 토큰 단위로 나눠 미리 채우고, 질문 행을 절반 길이 규칙으로 묶는다. `prompt.py`는 `true`와 `false` 외의 bool 기준 키를 거부한다.

## 2. 변경 사항

- `src/decision/d1_prompt.rs` (신규): System One 프롬프트(상태 블록, `QUESTION:`, choice, bool, score 질문 문구, 이미지마다 `<image>` 하나), 업스트림 메시지를 그대로 쓰는 `as_question`, 1028개 항목의 단일 토큰 대체 풀을 갖춘 선택지 코드, 읽기 토큰 id, 소프트맥스 읽기, 1024 x 1024 면적 상한의 바이큐빅 축소, 업스트림 `_chunks`에 해당하는 `branch_chunks`.
- `src/decision/d1.rs` (신규): `Lfm2VlModel` 위의 `D1DecisionModel`. 질문이 하나면 한 번의 패스로 끝난다. 여러 개면 상태와 이미지를 트렁크로 `Lfm2LayerCache`에 한 번 읽고, 각 질문은 배치 크기만큼 복제한 캐시에 이어서 오른쪽 패딩 행으로 예산 안에서 묶여 실행된다. 로짓은 묶인 임베딩 헤드에서 f32 로그 소프트맥스로 구하고, 답은 업스트림 `_answer`처럼 네 자리로 반올림한다.
- `src/decision/loader.rs`: `D1` 변형, 감지 분기, 생성 분기. 워커, 라우트, CLI는 바뀌지 않았다.
- `src/models/lfm2.rs`: `Lfm2LayerCache::tile`, `forward_hidden_with_caches`, `project_logits`. 모두 새 함수이고 기존 생성 경로는 수정하지 않았으므로 로짓 트레이스는 필요하지 않았다.
- `tests/fixtures/d1/`: `generate_reference.py`는 체크포인트에서 mlx-vlm `D1Model`을 실행하고, `reference.json`은 아홉 가지 경우의 답, 사용량, 트렁크와 분기와 읽기 토큰 id를 기록한다.
- 문서: `docs/decisions.md`(지원 모델 표, d1-3B 절, 소스 맵), `docs/supported-models.md`, `README.md`, `CHANGELOG.md`.

## 3. 기술적 결정

**라우팅은 결정 로더에만.** `detect_decision_kind`는 `lfm2_vl` / `lfm2-vl`과 `D1Model` `auto_map`을 함께 확인한다. `get_model_type`은 그대로이므로 `mlxcel generate -m d1-3B`는 여전히 채팅하고, 일반 LFM2-VL 체크포인트는 여전히 "결정 체크포인트가 아님"으로 거부된다.

**LFM2-VL 스택을 재사용하고 명시적 캐시 진입점만 추가.** 스코어러는 `load_lfm2_vl`로 불러와 `get_input_embeddings`를 호출하므로, d1 자체의 사전 축소 뒤에 체크포인트가 지정한 프로세서 리사이즈 필터(#2388/#2459)가 적용된다. 생성은 모델 소유 시퀀스 상태를 그대로 쓰고 스코어러는 자기 캐시를 만들기 때문에, 기존 forward를 바꾸지 않고 LFM2 백본에 `forward_hidden_with_caches`를 추가했다. 이미지별 비전 특징 캐시(#2453)는 쓰지 않는다. 결정은 이미지를 한 번만 읽기 때문이다.

**트렁크는 다시 계산하지 않고 복제.** `Lfm2LayerCache::tile`은 보이는 FP16 KV 구간(`visible_state`와 `restore_fp16_live_window`)과 conv 꼬리를 배치 축으로 브로드캐스트한다. 업스트림 `_tile`과 같다.

**1e-4 동등성을 어디서 검증하는가.** 이슈는 함께 묻는 경우와 따로 묻는 경우가 f32에서 1e-4 안에 일치하기를 요구한다. 체크포인트 경로는 f16 활성값으로 돌고, 업스트림 자체도 그 두 경우 사이에 urgency 점수가 3.2e-3 움직인다. 그래서 1e-4 검증은 임베딩 테스트가 이미 쓰는 합성 LFM2 백본 위에서 float32로, 배치 경계와 분할 미리 채우기를 강제한 채 실행하고, 체크포인트 경로는 mlx-vlm 자신의 함께/따로 출력과 2e-3으로 비교한다.

**패리티용 이미지 입력을 정확히 맞춤.** COCO 이미지는 `tests/fixtures/sam3/cats.png`(PIL에서 JPEG와 픽셀 단위로 동일)를 써서 패리티가 JPEG 디코더에 좌우되지 않게 했다. 상한을 넘는 경우는 픽셀 복제로 2배 키운 사본으로, 양쪽이 똑같이 다시 만든다.

## 4. 리뷰 결과

- 구현 리뷰: CRITICAL이나 HIGH 지적 없음. MEDIUM 커버리지 공백(이미지와 여러 질문)은 `cats_multi` 픽스처 경우로 메웠다.
- 보안 및 성능 리뷰에서 HIGH 세 건을 고쳤다. 별칭 대체 탐색이 선택지마다 풀을 처음부터 다시 훑던 문제(이제 이어서 탐색하므로 별칭 계산 한 번에 풀 항목마다 최대 한 번만 인코딩), 프롬프트 길이 상한이 없던 문제(트렁크와 모든 질문의 합이 `text_config.max_position_embeddings`, d1-3B에서 32768을 넘으면 400으로 거부), 넓은 행 하나가 한 번의 forward로 돌던 문제(2048 토큰보다 넓은 행은 조각으로 나눠 읽음). MEDIUM 한 건도 고쳤다. 이미지 요청의 상태에 `<image>`가 문자 그대로 들어가면 500이던 것이 이제 400이다.
- 남은 항목(LOW): `serde_json`은 지수를 `1e20`으로 쓰고 Python은 `1e+20`으로 쓰므로, 그런 JSON 상태는 업스트림과 다르게 토큰화된다. 상태에 적힌 특수 토큰은 제어 토큰으로 해석되는데, 업스트림도 같다.

- d1-3B는 오디오를 읽지 않으므로, #2343의 300초 결정 오디오 상한(전체 디코딩 후 검사)은 오디오를 읽는 첫 결정 모델 포팅으로 넘긴다.
