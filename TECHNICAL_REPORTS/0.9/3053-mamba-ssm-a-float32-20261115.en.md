# Technical Report: PR #3053 - keep Mamba's SSM A in float32 so f16 loads stay finite

**Date**: 2026-11-15
**Status**: PR open (draft, closes #3046)
**Reviewer**: -
**Languages**: Rust
**Risk Level**: Low

---

## Executive Summary

`mlx-community/mamba-130m-hf-bf16` loaded on Apple Silicon and then generated 0 tokens. Apple Silicon casts a bf16 checkpoint to f16 at load, and `MambaBlock::forward` evaluated `A = -exp(A_log)` in that f16 dtype. f16 cannot hold `exp` of anything above 11.09, and this checkpoint has 1530 `A_log` entries above that, so `A` contained `-inf`. Wherever the f16 `softplus` step had rounded to zero, the decay became `exp(0 * -inf) = NaN`, every logit went NaN on the first token, and greedy sampling returned token 0, which is the model's EOS.

The PR computes `A` once at load from a float32 copy of `A_log`, as transformers does. bf16 and float32 models still read `A` in their activation dtype and produce bit-identical output to before. f16 models read it as float32: the fused Metal kernel takes it directly, and the graph scan computes `delta * A` and its `exp` in float32, then rounds only the decay back to f16. On the real checkpoint the bf16 model now produces 24 tokens that match transformers on the same weights, on the fused kernel, the graph scan, and CPU.

## 1. Problem Statement

### 1.1 Background

Mamba's selective scan stores the state transition as `A_log` and uses `A = -exp(A_log)`. For each timestep the scan computes a per-channel decay `exp(delta * A)`, where `delta = softplus(dt_proj(...))`, and multiplies the previous state by it. Because `A` is negative and `delta` is positive, the decay lies in (0, 1].

On Apple Silicon, mlxcel converts bf16 checkpoints to f16 at load (`bf16_to_f16_at_load`, `convert_bf16_weights`) unless `MLXCEL_KEEP_BF16` is set. Every tensor in `mamba-130m` fits f16 as stored (the largest `A_log` is 26.0, well under 65504). The overflow happens only after `exp`.

### 1.2 Existing Issues

The failure chain, on the bf16 checkpoint after the f16 cast:

1. `A = -exp(A_log)` runs in f16. f16's largest finite value is 65504 = `exp(11.09)`. `A_log` reaches 19.5, and 1530 of 589824 entries, spread over 23 of 24 layers, exceed 11.09, so those `A` entries are `-inf`.
2. `dt_proj.bias` goes down to -20.6. For those channels `softplus` returns roughly `exp(-20.6)`, about 1e-9, which is below f16's smallest subnormal (about 6e-8) and rounds to exactly 0.
3. Where a zero `delta` meets a `-inf` `A`, the decay is `exp(0 * -inf) = exp(NaN) = NaN`.
4. The NaN enters the state, then `y`, then every logit on the first token.
5. Greedy argmax over all-NaN logits returns index 0. Token 0 is `eos_token_id` for this model, so generation stops with no output and no error.

The float32 checkpoint and `MLXCEL_KEEP_BF16` never showed the bug because both float32 and bf16 can represent `exp(19.5)` (about 2.9e8).

### 1.3 Risk Assessment

| Risk | Before | After |
|------|--------|-------|
| bf16 Mamba checkpoint on Apple Silicon | Silent 0-token output | Correct output |
| bf16 / float32 numerics | Reference | Bit-identical (A rounded to activation dtype) |
| f16 graph scan numerics | NaN | float32 decay, rounded once to f16 |
| Other SSM models with the same pattern | Exposed | Still exposed (see section 8) |

## 2. Technical Review

### 2.1 Security

Not applicable. No input handling, parsing, or unsafe code changes.

### 2.2 Performance

- `A` is computed once per layer at load instead of `exp` plus `negative` on every forward call. Per call, a bf16 or float32 model now does one `astype`, and an f16 model one `copy`, in place of two elementwise ops.
- Memory: `A` is stored as float32 instead of `A_log` in the loaded dtype. For `mamba-130m` that is 589824 entries times 4 bytes, about 2.4 MB in total, against about 1.2 MB before. Negligible.
- The f16 graph scan adds one `astype` of the decay per step. The fused kernel path is unchanged apart from reading a float32 `A`.

No benchmark was run; the change does not touch any hot loop in a way that would be measurable against the rest of the scan.

### 2.3 Compatibility & Dependencies

- No new dependencies, no config or CLI changes.
- The fused selective scan already keeps its state in float32 registers and accepts `A` through `mamba1_scan_kernel_accepts`; validation shows it takes the float32 `A` with f16 activations.
- The struct field changes from `a_log` to `a`. Two test fixtures in `mamba_tests.rs` (`tiny_mamba_block`, `varied_mamba_block`) are updated to call `ssm_a_from_log`.

### 2.4 Code Quality

- The dtype decision lives in one place (`MambaBlock::scan_a`), so both scans agree on what `A` they read.
- The f16 decay cast in `ssm_step` is conditional on a dtype mismatch, so it is a no-op for bf16 and float32 and touches nothing else on those paths.
- Nothing is clamped or masked. The fix removes the overflow at its source rather than hiding NaN after the fact.

## 3. Technical Decisions

### 3.1 Compute A in float32 at load, not clamp in f16

**Options considered:**

| Option | Outcome |
|--------|---------|
| Clamp `A_log` (or `A`) to the f16 range | Changes the model: a clamped `A` decays more slowly than trained |
| Replace NaN in the decay with 0 | Hides the symptom, and still uses a wrong `A` for the 1530 overflowing entries whenever `delta` is non-zero |
| Keep `A_log` in bf16 or float32 by excluding it from the f16 cast | Fixes the representation but still evaluates `exp` per call, and depends on the load-time policy staying in sync |
| Compute `A = -exp(float32(A_log))` once at load | Matches transformers (`-torch.exp(self.A_log.float())`), independent of the load dtype policy |

The PR takes the last option. `ssm_a_from_log` casts `A_log` to float32, computes `-exp`, and evaluates the result so it is materialized with the other weights.

### 3.2 Keep bf16 and float32 bit-identical

`scan_a` rounds the float32 `A` to the activation dtype for every dtype except f16. For bf16 this gives exactly the value the old code produced, because MLX's bf16 `exp` computes in float32 internally and rounds once, the same as rounding a float32 `-exp(A_log)`. This keeps the change confined to the broken case and means existing bf16 and float32 outputs need no revalidation.

### 3.3 In f16, only the decay goes back to f16

In the f16 graph scan, `delta * A` mixes an f16 `delta` with a float32 `A`, so MLX promotes the product and its `exp` to float32. The decay is then cast back to f16. Since the decay is in (0, 1], the cast cannot overflow, and the state, `y`, and everything downstream stay in f16 as before. A channel with `delta = 0` and a very negative `A` now gets `exp(0 * -2.9e8) = exp(-0) = 1` in float32, which is the mathematically correct decay.

## 4. Implementation Details

### 4.1 Architecture Changes

```
Load:     A_log (any dtype) --astype f32--> -exp --> A (f32, evaluated) stored in MambaBlock
Forward:  scan_a(x_conv): f16 -> copy(A) as f32; otherwise -> astype(A, x dtype)
          fused kernel: reads A as given
          graph scan:   decay = exp(delta * A); cast to x dtype if they differ
```

### 4.2 Key Code Changes

**File: `src/models/mamba.rs`**
```rust
pub(crate) fn ssm_a_from_log(a_log: &MlxArray) -> UniquePtr<MlxArray> {
    let a_log = mlxcel_core::astype(a_log, mlxcel_core::dtype::FLOAT32);
    let a = mlxcel_core::negative(&mlxcel_core::exp(&a_log));
    mlxcel_core::eval(&a);
    a
}
```
**Reason for change:** the only place `A` is computed, in a dtype that holds every trained value.

```rust
fn scan_a(&self, x: &MlxArray) -> UniquePtr<MlxArray> {
    let dtype = mlxcel_core::array_dtype(x);
    if dtype == mlxcel_core::dtype::FLOAT16 {
        mlxcel_core::copy(&self.a)
    } else {
        mlxcel_core::astype(&self.a, dtype)
    }
}
```
**Reason for change:** keeps bf16 and float32 bit-identical and gives f16 a float32 `A`.

In `ssm_step`, the decay is cast to the activation dtype when the two differ, which happens only for f16.

**File: `src/models/mamba_tests.rs`**

- `mamba_f16_converted_bf16_checkpoint_produces_finite_logits`: builds a two-layer model whose `A_log` is 19.5 on four channels and whose `dt_proj.bias` is -30 on two, stores every tensor as bf16, and runs the real `convert_bf16_weights` so the model is built from the same f16 tensors `MambaModel::load` would produce. It prefills four tokens, decodes one, and requires finite logits on the default device (fused kernel on GPU) and on CPU (graph scan), with the two agreeing within 5e-2.
- `mamba_ssm_a_is_float32_and_finite_for_an_f16_a_log`: `ssm_a_from_log` of an f16 `[0, 11, 19.5]` returns float32 `[-1, -exp(11), -exp(19.5)]` within 1e-6 relative error.

### 4.3 Data Model Changes

`MambaBlock.a_log` is replaced by `MambaBlock.a` (float32). No persisted state or file format changes.

## 5. Learning Points

### 5.1 A tensor that fits a dtype can still overflow after one op

**Concept:** checking that every weight fits the target dtype is not enough when the model applies `exp` (or another expanding op) to a weight. f16's range ends at `exp(11.09)`; bf16 and float32 go far beyond it. A cast that is safe for every stored tensor can still make a derived tensor infinite.

**Application in this PR:** `A_log` peaks at 26.0 and fits f16 easily; `exp(A_log)` does not. The fix moves the expanding op ahead of the narrowing cast, which is the order transformers uses.

### 5.2 NaN can look like a clean stop

All-NaN logits under greedy sampling return index 0. When token 0 is the EOS, the model appears to finish normally with empty output, and no error is raised. For "0 tokens" reports, checking whether the first logits are finite is a fast first step.

### 5.3 Matching a reference means matching it on the same weights

The issue asked for bf16 output to match the f32 checkpoint. That cannot hold: the bf16 checkpoint is exactly the bf16 rounding of the f32 one (242 of 242 tensors), and transformers running those rounded weights diverges from f32 at token 6 (`,` against `.`). The correct criterion is agreement with the reference implementation on identical weights, which the PR meets token for token.

**Example Code:**
```python
# transformers' reference for the same computation
A = -torch.exp(self.A_log.float())
```
