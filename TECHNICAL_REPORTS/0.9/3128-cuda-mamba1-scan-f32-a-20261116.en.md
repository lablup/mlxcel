# Technical Report: PR #3128 - let the graph-exact Mamba1 scan take float32 A with f16 x

**Date**: 2026-11-16
**Status**: Completed (verified on GB10; closes #3125)
**Languages**: Rust, C++ (CUDA JIT source)
**Risk Level**: Medium

---

## Executive Summary

Since #3122, f16 Mamba and Jamba keep the SSM `A` in float32 because f16 cannot hold `-exp(A_log)`. CUDA's graph-exact Mamba1 scan kernel accepted only uniform input dtypes, so f16 Jamba on CUDA fell back to the per-timestep graph scan. This PR lets the CUDA kernel accept f16 `x` with float32 `A` and reproduce the graph scan's rounding for that pair, so f16 Jamba prefill on CUDA takes the kernel again. On GB10 (sm_121) the kernel matches the graph scan bit for bit, and f16 Jamba prefill runs about 2.0x faster than on the graph scan.

---

## 1. Problem Statement

`mamba1_scan_kernel_accepts` required every input to share one dtype. After #3122 an f16 model passes `A` as float32, the predicate declined, and Jamba's prefill ran one graph step per token on CUDA. That path is correct but slow on long prompts. Metal and ROCm use a float-state port whose `A` is already float32, so they were unaffected.

---

## 2. Technical Decisions

### 2.1 Admit exactly one extra dtype mix

`mamba1_graph_exact_dtypes_ok` admits uniform floating inputs, plus f16 `x` (with `delta`, `B`, `C`, `D` also f16) and float32 `A`. Wider rules (any float32 `A`, bf16 `x`) were rejected: each extra pair needs its own rounding proof against the graph. A test pins the rule and fails under both mutations tried (rule widened to any float32 `A`; rule reverted to uniform only). The launcher computes `a_t` with the same rule, so an admitted pair is never re-cast.

### 2.2 Mirror the graph's three rounding steps

For the mixed pair the graph scan computes `astype(exp(multiply(delta, A)), f16)`. MLX promotes `delta` to float32 exactly, multiplies once in float32, runs `exp` on float32, then casts round-to-nearest-even. The new `mamba1_decay<T, TA>` does `static_cast<T>(Exp{}(__fmul_rn(float(dt), a)))`. `__fmul_rn` prevents FMA contraction, and no fast-math or ftz flag is set on either the JIT build or the precompiled ops, so the two paths should agree bit for bit. Uniform inputs take the old `Exp{}(mamba1_mul(dt, a))` path.

### 2.3 `TA` only for the CUDA port

MLX's `cuda_kernel` emits template args as `using` declarations at the top of the kernel body, and the generated source is cached by a name derived from the template args. `TA` is therefore added to the template args only on CUDA. The Metal and ROCm sources and cache keys are unchanged. The uniform CUDA instantiation gets a new name (`..._float16`) and one fresh PTX compile.

### 2.4 Mamba stays on the graph scan

`MambaBlock::forward` on CUDA reads the float-state port and keeps the graph scan on purpose, since switching would change CUDA output. The gain here is Jamba-only. The predicate now admits Mamba's f16 inputs too, and a test pins that, but the Mamba forward path is unchanged.

### 2.5 Shared `A` helpers moved

`ssm_a_f32` and `ssm_a_from_log` move from `mamba.rs` into `models::ssm_a`, since Mamba, Jamba, Mamba2 and the SSD scan all use them. The functions are byte-identical.

### Validation

- Metal (M3 Ultra): `mamba1_scan_parity` 7/7, `models::mamba`, `models::jamba`, `models::ssd_scan` pass; clippy, fmt and contract checks pass. The CUDA tests return early here.
- Independent desk check of the CUDA source against MLX's `cuda_kernel` at the pinned commit: no defects found in template-arg emission, `static_assert` placement, intrinsics, cache keys, or the predicate.
- GB10 (sm_121), `--features cuda`: `mamba1_scan` 7 passed (including the f16 `x` + float32 `A` bit-identity test), and `models::jamba models::mamba models::ssd_scan` 56 passed, 3 ignored (including `jamba_f16_cuda_kernel_matches_the_graph_scan_bit_for_bit`). NVRTC compiles the JIT source.
- GB10 prefill A/B, `ai21-jamba-reasoning-3b-4bit` with `MLXCEL_CUDA_F16_NORMALIZE=1`, 2151-token prompt, 3 runs each:

| Scan path | Prefill (tok/s) | Decode (tok/s) |
|---|---|---|
| Kernel | 2071.8 / 2091.5 / 2115.9 | 99.4 / 101.1 / 101.2 |
| Graph scan (`MLXCEL_MAMBA1_SCAN_KERNEL=0`) | 1003.3 / 1012.1 / 1058.1 | 92.3 / 95.1 / 95.8 |

Greedy output (32 tokens) is byte-identical across all six runs and finite.

- The GB10 run also found that `jamba_f16_model_with_an_overflowing_a_log_keeps_finite_logits` (from #3122) aborted a CPU-only lib test run: its MoE fixture reaches MLX's CPU `GatherMM`, which only takes float32. The test now returns early without a GPU backend.
