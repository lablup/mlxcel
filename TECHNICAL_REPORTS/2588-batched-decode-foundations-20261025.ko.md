# 기술 보고서: PR #2588 — 배치 디코드 공통 기반

**날짜:** 2026-10-25 · **상태:** 구현 리뷰 완료; 통합 Metal 인수 검증은 #2587에서 추적 · **관련 이슈:** #2555, #2566, #2587

## 요약

Llama3, Qwen3, Qwen3-MoE의 split attention 처리를 공통화하고, 실제 디코드 경로 표시와 에픽 #2566의 후속 계열 구현에 사용할 회귀 검증 도구를 추가한다. 새로운 계열의 처리량 측정 결과를 제공하는 변경은 아니다.

## 문제 정의

`forward_batched` 메서드가 있다는 사실만으로 디코드 행 사이에서 가중치 읽기를 공유한다고 판단할 수 없다. 일부 구현은 요청을 분리해 단일 요청 forward를 반복하지만 서버는 이를 구분하지 않았다. attention 구현과 계열별 테스트 준비 코드의 중복도 후속 구현을 일관되게 검증하기 어렵게 했다.

## 변경 요약

- `mlxcel_core::batched_decode::SplitAttention`이 projection reshape, 선택적 Q/K 정규화, RoPE, 공통 캐시 attention과 계열별 행 attention 확장 지점을 제공한다.
- 라우팅 헬퍼는 빈 배치 결과와 정확한 단일 요청 경로를 유지하고, 여러 행을 전달받은 배치 구현으로 보낸다.
- trait 경로 표시가 loaded-model 및 vision 래퍼를 통해 서버 시작 로그까지 전달된다. Qwen3.5, Qwen4Exp, Muse Glimmer와 파이프라인 서버는 실제 디코드에서 행별 전체 forward를 반복하므로 fallback으로 남는다.
- 소스 커버리지 목록은 native·위임·fallback 구현을 고정하고, 배치 override 없는 native 또는 위임 표시를 거부한다. Windows에서도 경로가 동일하도록 정규화한다.
- 공유 하네스는 서로 다른 길이의 요청을 독립 디코드 결과와 비교하고 캐시 증가량, 단일 행 일치와 빈 배치를 확인한다.
- `MLXCEL_TRACE_BATCH_ROWS`는 teacher forcing 방식으로 폭 1 디코드를 추적한다. B=1과 B=4의 첫 행은 동일한 입력과 문맥을 사용하고, 나머지 행은 서로 다른 스트림 위치와 문맥 길이를 사용한다. 매 단계 평가 후 첫 행을 원래 위치 번호와 함께 즉시 출력해 전체 배치 로그잇 버퍼의 장기 보관을 피한다.

## 기술적 선택과 이유

경로 분류는 메서드의 존재나 prefill 최적화 여부가 아니라 sequence ID를 사용하는 실제 서버 경로를 기준으로 한다. 리뷰에서 Muse Glimmer와 Qwen4Exp의 낙관적인 분류를 바로잡았으며, 파이프라인 스케줄러도 fallback으로 유지했다. 성능 향상은 별도의 Metal 실측으로 확인하며 CPU 테스트를 그 증거로 간주하지 않는다.

## 검증

CPU 집중 테스트 14개가 통과했다. 커버리지 4개, Llama3/Qwen3 하네스 2개, Qwen3-MoE 하네스 3개, 파이프라인 분류 1개, 추적 계획과 단계별 출력 4개다. Qwen3-MoE의 native override와 Qwen3.5-VL의 위임 override를 각각 임시 제거했을 때 해당 타입을 명시하는 실패가 발생했고, 복원 후 다시 통과했다. 포맷, workspace 전체 타깃 clippy, 소스 계약, Python 도구 테스트 139개, 라이선스 헤더, 의존성 정책, 바이너리 자산 및 Windows 경로 검사도 통과했다.

사용자는 로컬 CI와 리뷰를 병합 기준으로 정하고, 실제 체크포인트 생성 결과, 시작 로그, B=1/B=4 추적 및 Metal 동시 요청 성능 측정을 #2587로 이관했다. 구현을 병합해도 이 측정은 완료되지 않은 상태로 남는다.

## 학습 포인트

배치 지원 여부, 배치 형태의 입력, 실제 배치 디코드는 서로 다른 속성이다. 소스 검사는 경로 표시와 override의 변경 누락을 감지하지만 실제 스케줄러 경로 확인은 여전히 필요하다. 추적 도구 역시 그래프 누적과 결과 결합 비용을 제한해야 자체 오버헤드를 측정하는 오류를 피할 수 있다.
