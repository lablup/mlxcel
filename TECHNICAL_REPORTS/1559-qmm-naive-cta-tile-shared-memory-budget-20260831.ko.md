# 기술 보고서: PR #1559 - qmm_naive CTA 타일을 공유 메모리 예산으로 결정하기

**작성일**: 2026-08-31

**작성자**: mlxcel maintainers

**상태**: 완료. 이슈가 세운 성능 가설은 측정으로 반증됐고 타일 폭은 그대로 둔다. 대신 기존 술어가 가리고 있던 잠재 결함 세 개를 고쳤고, 에픽 #1536이 GB10 하드웨어로 미뤄둔 수용 기준 하나를 여기서 닫았다. sm_80 이상 런타임 검증은 GB10 호스트로 이월.

## 요약

프리앰페어 파트의 모든 프리필을 담당하는 CUDA 양자화 행렬곱 `qmm_naive`는 CTA N 타일을 `enough_smem = sm80 && itemsize <= 2 && group_size <= 64`으로 골랐다. 이름 하나에 성격이 다른 두 판단이 섞여 있었다. 모양 항 둘은 진짜 공유 메모리 규칙이고, 이제 그렇게 적혀 있다. 실행 중인 디바이스에서 조회한 `cudaDevAttrMaxSharedMemoryPerBlockOptin`과의 비교다. `sm80` 항은 공유 메모리와 아무 상관이 없고, Tesla V100이 그걸 반증한다. 옵트인으로 블록당 96 KB, 옵트인 없이 48 KB인데 가장 넓은 후보 타일이 필요로 하는 건 24 KB다.

이슈 #1541은 그 여유분으로 넓은 타일을 열면 프리필이 빨라진다고 봤다. **가정하지 않고 스윕했고, 결과는 손해였다.** 128폭 인스턴스화는 아키텍처 상한인 레지스터 255개를 쓰고 스레드당 128바이트를 스필한다. 64폭은 224개에 스필이 없다. 둘 다 SM당 블록 2개로 같으니 넓은 타일이 사는 점유율은 없다. 결정하는 건 CTA 개수다. 128폭 CTA는 두 배의 출력 일을 대략 두 배의 시간에 하고, 애초에 채워지지도 않는 그리드를 반으로 줄이는 건 그냥 손해다. `qmm_naive`는 106토큰 프롬프트에서 1.50배, 516에서 1.06배, 1,906에서 1.02배, 4,106에서 1.02배 느리다. 실행 횟수는 양쪽이 같다.

그래서 타일 폭은 모든 아키텍처에서 그대로 나간다. 이 변경이 가져오는 건 모양 규칙이 가리고 있던 나머지다. f32 활성화에 group_size 128이 늘 필요했지만 한 번도 없었던 공유 메모리 옵트인, 맞는 타일이 없을 때 드라이버 실패 대신 거부, 모듈 캐시와 PTX 캐시가 키로 쓰는 JIT 모듈 이름에 tile_n 포함, 그리고 앰페어 파트 없이 sm_80 이상 무회귀 주장을 끝내는 호스트 측 전수 검사다.

## 1. 문제 정의

핀 `9a795735`의 `mlx/backend/cuda/quantized/qmm/qmm_naive.cu:17-23`:

```cpp
inline auto make_cta_tiler(int itemsize, int m, int group_size, bool sm80) {
  bool enough_smem = sm80 && itemsize <= 2 && group_size <= 64;
  int tile_m = std::max(16, std::min(64, next_power_of_2(m)));
  int tile_n = enough_smem ? 128 : 64;
  int tile_k = std::max(64, group_size);
  return cute::make_shape(tile_m, tile_n, tile_k);
}
```

문제는 셋인데 이슈가 짚은 건 하나다.

**술어 이름이 사실과 다르다.** `enough_smem`은 공유 메모리 예산 검사처럼 읽히지만 아니다. 안에 `compute_capability_major() >= 8`이라는 아키텍처 비교가 들어 있고, 이건 공유 메모리와 무관하다. 옵트인 없는 블록당 상한은 볼타 이후 모든 아키텍처에서 48 KB고, 옵트인 상한은 sm_70에서 96 KB로 튜링의 64 KB보다 크고 앰페어보다 작다. 그 비교의 양쪽을 공유 메모리로 가르는 건 아무것도 없다.

**더 큰 상한으로 옵트인하는 코드가 없다.** f32 활성화에 group_size 128이면 타일이 `4 * 128 * (64 + 64) = 65,536`바이트의 동적 공유 메모리를 요구한다. `cuFuncSetAttribute(CU_FUNC_ATTRIBUTE_MAX_DYNAMIC_SHARED_SIZE_BYTES)` 없이 런치가 받는 건 48 KB인데, 형제 파일 `qmm_sm80.cu`, `qmm_sm90.cu`와 달리 업스트림 `qmm_naive.cu`는 그 호출을 하지 않는다. 볼타 이후 모든 아키텍처에서 이 모양은 드라이버 안에서 실패한다.

**선택한 타일이 들어가는지 확인하지 않는다.** 튜링의 옵트인 예산은 64 KB라 옵트인을 해도 같은 모양이 안 들어가고, 실패는 타일도 예산도 이름하지 않는 CUDA 런치 오류로 나타난다.

## 3. 기술적 선택과 이유

### 3.1 폭은 스윕이 결정했고, 이슈의 가설과 반대로 나왔다

이슈의 공유 메모리 산술은 맞고 거기서 끌어낸 결론은 틀렸다. 이 호스트에서 측정한 값:

| | tile_n = 64 | tile_n = 128 |
|---|---|---|
| 스레드당 레지스터 | 224 | 255 (상한) |
| 로컬 메모리 스필 | 0 B | 스레드당 128 B |
| 동적 공유 메모리 | 16,384 B | 24,576 B |
| SM당 블록 | 2 | 2 |
| SM당 워프 | 64개 중 8개 | 64개 중 8개 |

어느 폭에서도 공유 메모리는 제약이 아니다. 넓은 타일 블록 두 개가 SM의 98,304바이트 중 49,152를 쓰고, 여섯 개라도 들어간다. 제약은 레지스터다. 224 x 128 = 28,672, 255 x 128 = 32,640이 SM당 65,536과 만나 둘 다 블록 2개로 눌린다.

두 폭이 같은 점유율에 도달한다는 사실이 결과를 깔끔하게 만든다. 넓은 타일은 점유율을 팔아 연산 밀도를 사는 게 아니라, 80 SM을 채우지도 못하는 그리드에서 CTA당 일만 두 배로 늘리는 것이고, CTA 개수가 반으로 줄어드는 손해가 A 타일 트래픽이 반으로 주는 이득보다 크다. 106토큰 프롬프트에서 `qmm_naive`는 19.9928초 대 29.8846초, 실행 횟수는 양쪽 다 497이다.

기다릴 교차점도 없고 그건 구조적이다. `DEFAULT_PREFILL_CHUNK`가 2,048이라 더 긴 프롬프트는 2,048토큰 조각으로 들어가고 `m`이 거기서 막힌다. 그리드의 M 방향은 `2048 / 64 = 32` 블록이 상한이다. 1,906토큰 단은 이 워크로드가 제시할 수 있는 최선에 가깝고 거기서도 넓은 타일이 1.7% 진다. 4,106토큰에서는 마지막 조각이 10토큰이라 넓은 타일에 최악이고, 격차가 2.2%로 다시 벌어진다.

즉 앰페어 미만에서 넓은 타일을 배제한 업스트림의 판단 자체는 옳았다. `enough_smem`이라는 이름이 제시한 이유가 틀렸을 뿐이다. 이제 그 항은 실제로 선택하는 대상의 이름인 `tensor_core_mma`로 들어가 있고, 옆에 측정 근거가 붙어 있다.

### 3.2 선택기가 순수 호스트 함수이므로 무회귀 주장은 GPU가 아니라 단위 테스트다

에픽 #1536의 GB10 인수인계 표는 "모든 `(itemsize, group_size, m)` 조합에 대해 타일러의 sm_80+ 선택이 동일함을 증명"을 앰페어 이상 하드웨어로 미뤄뒀다. 하드웨어 문제가 아니다. 선택기는 호스트 코드이고 정수 다섯 개의 순수 함수라 전수로 끝난다.

CuTe도 CUDA도 MLX도 없이 `qmm_naive_tile.h`로 뽑아낸 게 그걸 가능하게 한다. `mlxcel-core/cpp/`의 C 심이 CMake가 MLX 트리로 복사하는 바로 그 파일을 include하고, `qmm_naive_tile_tests.rs`가 스윕한다. 정의는 하나이고 테스트는 그것을 재진술한 사본이 아니라 그것 자체를 돌린다. 심을 `cuda` 피처 뒤가 아니라 무조건 컴파일하는 이유가 여기 있다. NVIDIA 하드웨어가 없는 호스트에서도 확인 가능해야 한다는 게 요점이다.

테스트는 기준이 요구한 것보다 넓게 단언한다. 모든 `(itemsize, group_size, m)` 조합을 **모든** 실제 블록당 예산과 두 MMA 경로에 대해 돌리므로, sm_80 이상만이 아니라 모든 아키텍처에서 선택된 타일이 업스트림과 같음을 고정한다.

### 3.3 N 타일은 JIT 모듈 이름에 들어가야 했다

`get_jit_module`은 모듈 이름으로 캐시하고, `read_cached_ptx`는 같은 문자열로 영구 PTX 디스크 캐시를 키잉한다. 타일 모양은 커널 이름을 통해서만 컴파일러에 전달된다. 업스트림이 안전한 건 tile_n이 이미 모듈 이름에 있는 항들의 결정적 함수이기 때문인데, 선택이 움직일 수 있게 되는 순간 tile_n을 고정하지 않은 이름으로 캐시된 모듈이 돌아오고 요청한 인스턴스화에 맞는 커널이 없어 `There is no kernel named ...`로 터진다.

`n{}` 추가는 이 변경 이전 빌드가 캐시한 PTX도 무효화한다. #910이 `qmm_sm80.cu`의 모듈 이름을 `qmm_sm80_r2`로 올려 고친 것과 같은 위험이다.

### 3.4 `MLXCEL_QMM_NAIVE_TILE_N`을 디스패치마다 읽는 이유는 패리티를 비트 단위로 만들기 위해서다

타일 폭은 블로킹 결정이다. 어느 CTA가 어느 출력 열을 갖는지, CTA가 몇 개인지를 바꾸지만, `tile_k`와 K 루프는 그대로이므로 개별 출력 원소의 누적 순서는 바꾸지 않는다. 따라서 출력은 근사가 아니라 비트 단위로 같아야 한다.

두 프로세스로 비교하면 타일 폭 효과와 다른 프로세스 간 비결정성을 구분할 수 없고, `cuda_qmm_determinism`은 sm_70의 양자화 프리필이 프로세스 간 재현되지 않는다고 기록해 뒀다. 오버라이드를 캐시하지 않고 디스패치마다 읽으면 한 프로세스가 동일한 피연산자로 두 폭을 돌려 원시 바이트를 비교할 수 있다. 3.3 덕분에 안전하다. 폭마다 자기 모듈과 커널을 갖는다. 비용은 이미 그 경로에 있는 `fmt::format` 두 번과 맵 조회 옆의 `getenv` 하나다.

### 3.5 선택기의 공유 메모리 모델은 런타임에 CuTe와 대조한다

선택기는 타일 크기만으로 `itemsize * tile_k * (tile_m + tile_n)`을 예측한다. 런치 지점은 업스트림처럼 확정된 레이아웃의 `cute::cosize`로 실제 값을 구하고, 둘이 어긋나면 예외를 던진다. 현재 핀에서는 두 타일 크기가 모두 스위즐 기본 타일의 배수라 각 레이아웃의 cosize가 정확히 곱과 같아 일치한다. 레이아웃을 바꾸는 MLX 핀 범프가 있으면 위의 모든 적합성·옵트인 판단이 조용히 틀리게 되는데, 이제는 두 값을 다 밝히는 명시적 오류가 된다.

## 4. 검증

모든 수치는 `volta-sm70-baseline-2026-08-31.md`의 방법론 여섯 규칙을 따른다. 프리필은 `-n 1`에서 프롬프트 길이 차분으로 직접 측정, 두 폭 모두 PTX 캐시 웜, `--cuda-graph-trace=node`, 모든 프로파일을 비프로파일 실행과 대조, 절대 커널 시간은 인스턴스 수가 같은 실행끼리만 비교. 두 arm은 같은 빌드에서 나온다.

**프리필**, `qwen3.8-27B-4bit`, 각 단 안에서 arm을 교차 실행:

| 프롬프트 토큰 | tile_n = 64 | tile_n = 128 | 128 대 64 |
|---|---|---|---|
| 106 | 29,317.5 / 29,697.8 ms | 37,268.4 / 37,383.1 ms | 1.265배 느림 |
| 516 | 87,153.1 / 87,275.0 ms | 92,266.1 / 93,275.9 ms | 1.064배 느림 |
| 1,906 | 253,614.6 / 252,408.5 ms | 257,390.0 / 257,127.6 ms | 1.017배 느림 |
| 4,106 | 550,956.5 ms | 563,107.5 ms | 1.022배 느림 |

**커널 귀속**, 106토큰 프롬프트 `-n 4`, 프리필 대조 98.3%와 99.4%: `qmm_naive_kernel`이 동일한 497 인스턴스에서 19.9928초 대 29.8846초로, 전체 GPU 시간 차 9.873초 중 9.892초를 설명한다. 대조군인 `qmv_kernel`은 1,491 인스턴스에서 0.3386초 대 0.3379초로 움직이지 않는다. `cuModuleLoadDataEx`는 13회에 0.1452초 대 0.1492초라, 비용은 JIT도 모듈 로드도 그래프 구성도 아닌 커널이다.

**커밋된 베이스라인 재현**: 단일 패스 단들에 대한 적합은 프롬프트 토큰당 122.92 ms (베이스라인 125.07), 절편 19.66초 (베이스라인 18.41초)로 둘 다 베이스라인이 정한 10% 밴드 안이다. dense 쌍에서 `qmv` 대조군은 39,151 인스턴스에 6.5626초로 #1539의 6.5654초를 0.04%로 재현한다.

**테스트**: `cargo test --release --features cuda -p mlxcel-core --lib qmm_naive`가 9개 통과, 0개 실패. 호스트 측 타일러 8개와 GPU 패리티 1개. `qmm_naive.cu`는 프로덕션 플래그로 `compute_70`, `compute_80`, `compute_121`에서 깨끗이 컴파일된다. `cargo clippy -p mlxcel-core --lib --all-features -- -D warnings`와 `cargo fmt --check` 통과. `cuobjdump --list-elf libmlx.a`는 큐빈 96개 전부 sm_70.

**출하 선택 하드웨어 확인**: 기본 빌드에서 `MLXCEL_TRACE_QMM_TILE=1`이 `tile 64x64x64 ... regs 224 spill 0 B blocks/SM 2`를 출력하고, 566토큰 프롬프트 프리필이 85,535.8 ms 대 `MLXCEL_QMM_NAIVE_TILE_N=64`의 85,672.5 ms로 같다.

## 5. 검증 한계와 후속

### 5.1 이 호스트에서 이 체크포인트로 8,192 프롬프트 토큰은 측정 불가

이슈는 대략 600, 2,048, 8,192 프롬프트 토큰의 프리필을 요구한다. 8,192 단은 32 GB 카드에 16 GB 체크포인트가 올라간 상태에서 세 번째 청크 안에서 `cudaMallocAsync failed: out of memory`로 실패한다. 이슈 #672가 기술하는 청크 프리필 메모리 프로파일이며, 타일 폭이 아니라 체크포인트와 카드의 성질이다.

4,106토큰 단이 대신 같은 질문에 답한다. 프리필 청킹이 `m`을 2,048에서 막고 따라서 그리드가 커질 수 있는 한계도 막기 때문이다. 더 작은 모델로 바꿔 8,192 수치를 만들었다면 이슈가 물은 질문에는 답하지 못했을 것이다.

### 5.2 `qmm_naive` 수치가 베이스라인 기록과 재현되지 않으며, 그대로 보고한다

dense 쌍에서 `qmm_naive`는 동일한 329 인스턴스, 동일한 대조율에서 베이스라인 기록의 10.0733초 대비 10.867초로 7.9% 느리다. 이 세션 내 반복 산포는 0.24%다. 타일 탓은 아니다. 모든 프로파일에서 두 arm이 0.05% 안에서 일치하고, 이 빌드가 컴파일한 큐빈은 이 변경 이전 옛 모듈 이름으로 캐시된 것과 자원 사용량(`REG:224 STACK:0`)이 같다. 같은 프로파일의 `qmv` 대조군은 #1539를 0.04%로 재현하므로 하네스와 호스트는 일관적이다. 연산 바운드 프리필 커널의 세션 간 차이이고 설명되지 않으며, 베이스라인의 `qmm_naive` 수치를 얼마나 정밀하게 읽어도 되는지의 한계를 정한다.

### 5.3 #1539의 SASS diff 기법은 여기에 적용되지 않는다

#1539는 볼타 호스트에서 `qmv.cu`를 sm_80과 sm_121로 컴파일해 `cuobjdump --dump-sass`를 diff하는 방법으로 sm_80+ 무회귀 기준을 회수했다. 여기서는 안 되고, 되는 것처럼 보고하면 오해를 부른다.

`qmm_naive.cu`는 호스트 디스패치뿐이다. 커널은 `device/qmm_naive.cuh`에 있고 MLX 빌드가 그것을 `cuda_jit_sources.h`의 NVRTC 소스 문자열로 쓸어 담으므로, 오브젝트에는 **디바이스 함수가 하나도 없고** SASS 덤프는 어느 아키텍처에서든 비어 있다. 그래도 `compute_80`과 `compute_121`로 컴파일해 봤고 덤프는 동일한데, 그건 아무것도 말해주지 않는다.

대신 성립하는 논증은 이렇다. `device/qmm_naive.cuh`와 `device/gemm_sm70.cuh`는 손대지 않았으므로 JIT 소스 문자열이 바이트 단위로 같고, 커널 이름은 타일 모양의 순수 함수이며, 호스트 측 전수 검사가 그 모양이 모든 아키텍처에서 업스트림과 같음을 고정한다. 같은 소스, 같은 인스턴스화, 같은 커널이다. 빈 오브젝트의 SASS diff보다 강한 논증이고, 이 변경이 실제로 기대는 논증이다.

### 5.4 `gather_gemm.cu`는 확인했고 포함하지 않았다

이슈는 `mlx/backend/cuda/gemms/gather_gemm.cu`가 같은 결함을 갖는지 묻는다. 아니다. 현재 핀에서 그 파일의 `make_cta_tiler(int m)`는 `sm80` 인자를 받지 않고 모든 아키텍처에서 `tile_n = 128`을 무조건 쓰므로, 아키텍처로 막힌 폭 자체가 없다. mlxcel 빌드에서는 도달조차 하지 않는다. 이미 mlxcel 오버레이인 `matmul.cpp`가 일반 `M > 1, N > 1` `GatherMM` 경로를 `cutlass_gather_mm`으로 보내고, `gemms/gather_gemm.h`를 include하는 곳이 없으며, 빌드된 `libmlx.a`의 어떤 오브젝트도 `mlx::core::gather_mm(bool, bool, ...)`에 대한 미정의 참조를 갖지 않는 반면 `matmul.cpp.o`는 `cutlass_gather_mm`을 참조한다.

다만 그 파일에 진짜 빈틈이 하나 있다. `smem_bytes`를 계산해 놓고 `cuFuncSetAttribute`를 부르지 않아, f32에 `tile_m >= 128`이면 64 KB 또는 96 KB의 동적 공유 메모리를 요구하고 모든 아키텍처에서 런치 실패한다. 아키텍처 독립적이고, 이 이슈의 볼타 범위 밖이며, 이 빌드가 실행하지 않는 파일이다. sm_70의 그룹 GEMM 경로를 담당하는 #1544에 속한다.

### 5.5 GB10으로 이월, 그리고 회수한 기준 하나

구현 호스트에 앰페어 이상 디바이스가 없다. 에픽 #1536의 `## GB10 (sm_121) continuation` 기준:

- **GB10 처리량 불변**: 이월. 선택된 타일은 sm_80+에서 증명 가능하게 불변이고 그 경로에 추가된 작업은 이전에 런치 실패하던 경우의 `cuFuncSetAttribute` 한 번뿐이지만, 처리량은 측정이고 이건 논증이다.
- **sm_121에서 `cargo test --features cuda` 통과**: 이월. 이 변경이 건드리는 대상 스위트는 sm_70에서 통과한다. 워크스페이스 전체 CUDA 실행은 #1048에 따라 `--test-threads=1`이 필요한데 이 호스트의 실행 예산에 맞지 않았다.
- **모든 `(itemsize, group_size, m)` 조합에 대해 타일러의 sm_80+ 선택이 동일함**: **여기서 닫았다**. 하드웨어가 아니라 전수 검사로. 3.2 참조.

### 5.6 #1543 이후 재측정

이 결과를 결정한 레지스터 압박은 앰페어 미만에서 `make_tiled_mma`가 고르는 `UniversalFMA<float, Element, Element>` 아톰의 성질이다. #1543은 볼타에 양자화 GEMM용 텐서 코어 MMA를 주는데, 그러면 누산기 프래그먼트 레이아웃이 바뀌고 넓은 타일을 255개 레지스터와 스필로 몰아넣은 레지스터 수도 바뀐다. 그 재측정이 명령 하나가 되도록 `MLXCEL_QMM_NAIVE_TILE_N`과 `MLXCEL_TRACE_QMM_TILE`이 있고, 벤치마크 기록의 재현 블록이 그 명령이다.
