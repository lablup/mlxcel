# PR #2835: cuda-oxide 타당성 검토와 초기 실험 계획 문서화

**작성일**: 2026-11-03
**상태**: 리뷰 중 (문서 전용, #2831, #2832, #2833, #2834 참조)
**언어**: Markdown
**위험도**: 낮음 (런타임 코드, 빌드, 설정 변경 없음)

## 요약

PR #2835는 NVIDIA의 cuda-oxide Rust CUDA 컴파일러를 mlxcelverse에 도입할 가치가 있는지 검토한 결과와, 근거 게이트가 붙은 실험 순서를 기록한다. 결론은 선택된 Rust 커널만 별도로 컴파일해 PTX/cubin을 기존 MLX precompiled 모듈 경로로 적재하고, 할당, 지연 평가, 스트림, CUDA Graph 스케줄링은 MLX가 계속 소유하는 것이다. 첫 커널은 fused residual-add와 RMSNorm으로 정하고 작업을 네 이슈(#2831~#2834)로 나눈다. GB10에서 툴체인과 아티팩트를 검증하고, 수치 오라클이 있는 독립 커널을 만들고, 기본 비활성 MLX 어댑터를 붙이고, 동일 조건 벤치마크로 확대, 조사, 해결, 중단 중 하나를 결정한다. 프로덕션 활성화, 백엔드 교체, 독립 추론 엔진은 명시적으로 범위 밖이며, 엔진은 MLX 실행 제약이 측정으로 입증될 때만 검토하는 조건부 후속 작업이다.

## 1. 문제 정의

cuda-oxide는 Rust MIR을 Pliron과 LLVM을 거쳐 디바이스 코드로 내리는 alpha 단계 SIMT 컴파일러다. 설치 안내는 Linux, Ampere 이상 GPU, CUDA Toolkit 13.0 이상, 드라이버 580 이상, LLVM/Clang 21 이상, Rust 1.99.1 툴체인을 요구하지만 mlxcel은 Rust 1.97.1을 고정한다. 이전에는 두 방향의 비용을 분리하지 않은 채 논의됐다. 하나는 mlxcelverse 안에서 선택된 커널에 컴파일러를 쓰는 것이고, 다른 하나는 MLX와 나란히 네이티브 CUDA 추론 경로를 만드는 것이다. 두 번째 방향은 생성된 커널이 대상 GPU에서 올바르고 빠른지에 대한 근거가 나오기 전에 모델 실행, 가중치와 KV 저장, 샘플링, 서빙 작업을 먼저 요구한다.

일반 SIMT 컴파일과 아키텍처별 행렬 지원도 분리해야 했다. 검토한 CuTe 프리뷰는 `sm_100a`와 `sm_120a`를 지원하고 `sm_121a`를 거부하므로, 그 공개 검증 결과는 GB10 Tensor Core 가속의 근거가 아니다. 방출 대상이 검증된 기본 SIMT 커널만이 첫 게이트로 성립한다.

이 문서가 지금 필요한 이유는 네 구현 이슈가 문서가 정의하는 아티팩트와 ABI 계약에 의존하기 때문이다. 문서가 없으면 각 이슈가 서로 다른 통합 경계를 전제하고, 첫 이슈가 커널 탐침 대신 엔진을 범위로 잡을 수 있다.

## 2. 기술적 선택과 이유

### 2.1 독립 엔진보다 커널 통합을 먼저

가장 큰 불확실성은 cuda-oxide가 실제 대상 GPU에서 올바르고 유용한 커널을 만드는지이지, Rust로 작성된 엔진이 존재할 수 있는지가 아니다. 엔진을 먼저 만들면 그 질문에 답하기 전에 가중치 적재, 디바이스 메모리 관리, KV 저장, 스케줄링이 추가되고, 성능 비교에서 커널 효과와 실행기 효과를 분리할 수 없게 된다. 선택한 순서는 독립 커널 패키지, MLX 통합과 비교, 그리고 제한된 어댑터 개선으로도 해소되지 않는 실행 제약이 재현될 때만 엔진 검토다.

### 2.2 아티팩트 분리와 얇은 어댑터

권장 경로는 Rust 커널을 별도 패키지에서 컴파일하고 C++ MLX 어댑터가 불변 PTX/cubin 아티팩트를 소비하는 것이다. 할당, 지연 평가, 스트림, 그래프 스케줄링은 MLX가 유지하고, oxide 컴파일러는 일반 mlxcel 빌드에 들어가지 않는다. 문서는 `jit_module.cpp`의 precompiled 분기가 유력한 저수준 재사용 지점이지만 완전한 커스텀 커널 어댑터는 아니라고 기록한다. 새 커널에는 출력을 할당하고, 입력과 출력을 encoder에 등록하고, 인자를 패킹하고, 평가 중 실행을 스케줄하는 MLX primitive가 여전히 필요하다.

### 2.3 아티팩트와 ABI의 정직성

`.oxart` 컨테이너는 PTX, cubin, IR 페이로드를 담을 수 있으며 그 자체가 실행 가능한 PTX는 아니다. 현재 엔트리 메타데이터는 완전한 C++ 인자 스키마가 아니므로, 계획은 digest, 엔트리 심볼, 스칼라 폭, 포인터와 길이 순서, 정렬, dtype, 레이아웃, 앨리어싱, 실행 제약, ABI 리비전을 담은 검증된 manifest를 요구한다. manifest, 대상, dtype, 아티팩트가 맞지 않으면 어댑터는 enqueue 전에 기존 CUDA 경로를 선택해야 하고, 실행 시점 CUDA 오류는 재시도가 아니라 오류로 표면화해야 한다.

### 2.4 게이트와 중단 조건

각 이슈는 자체 수용 게이트를 갖고 배치는 정해진 지점에서 멈춘다. #2831은 대상이나 툴체인이 상당한 업스트림 작업 없이 올바르게 실행되지 않으면 중단한다. #2832는 실제 GB10 실행과 수치 패리티를 요구하며, 컴파일만 하거나 건너뛴 테스트는 충족하지 않는다. #2833은 올바른 스케줄링에 백엔드 교체가 필요하면 중단한다. #2834는 측정 전에 합의한 제안 기준을 적용한다. 모든 정확성 게이트 통과, 잡음 밖의 설명되지 않는 종단 간 2% 초과 회귀 없음, 그리고 반복 가능한 10% 이상 커널 이득과 유용한 종단 간 영향, 문서화된 콜드 스타트 감소, 실질적 유지보수 이득 중 하나다. 측정된 부정 결과도 유효한 최종 결과이며, 하드웨어 근거가 없는 상태로는 조사를 닫을 수 없다.

## 3. 검증

변경은 서술을 그대로 받아들이지 않고 현재 트리와 대조했다.

| 주장 | 검증 |
|---|---|
| 로컬 소스 링크 11개가 모두 해석됨 | `src/backend/mod.rs`, `src/backend/session.rs`, `src/lib/mlxcelverse/kernels/kernel_port.h`, `src/lib/mlxcelverse/kernels/fused_norm.cpp`, CUDA `jit_module.cpp`와 `device.cpp` 오버레이, `src/lib/mlxcel-core/src/fused_norm_parity_tests.rs` 포함 모든 대상 존재 |
| CUDA JIT 로더에 precompiled 분기가 존재 | `jit_module.cpp`가 `builder()` 결과의 precompiled blob을 받아 소스 컴파일 대신 게시 |
| 커널 포트가 백엔드별로 선택됨 | `kernel_port.h`가 백엔드별 `CustomKernelFunction`을 해석하고 null 항목을 정식 부재 상태로 처리 |
| CUDA Graph 순서를 백엔드가 소유 | `device.cpp`가 캡처된 자식 그래프 배리어를 유지 (#2462) |
| 근거 리비전이 실재 | mlxcel `d771735d`는 `main`의 조상이고, MLX pin `7ca40033`은 `src/lib/mlxcelverse/CMakeLists.txt`의 `GIT_TAG` |
| 외부 링크가 해석됨 | GitHub와 문서 URL 12개가 검토 시점에 모두 HTTP 200 |
| 형식 | em dash, 줄 끝 공백, 탭 없음, `git diff --check` 통과 |

검증되지 않은 부분은 문서 자체가 밝힌다. 컴파일러를 설치하지 않았고, oxide 커널을 컴파일하지 않았고, GPU 작업을 실행하지 않았고, 특정 드라이버와 GPU 조합을 검증하지 않았다. 문서는 성능, 프로덕션 준비, GB10 Tensor Core 가속, 백엔드 교체 타당성을 주장하지 않는다.

## 5. 후속 조치

- #2831이 첫 준비 게이트다. 격리 패키지, 재현 가능한 빌드, 아티팩트 manifest, `gpu-lock` 아래 실제 GB10 실행을 다룬다.
- #2832, #2833, #2834는 선행 이슈와 그에 요구되는 GPU 근거에 막혀 있다.
- 계획의 노력 범위(결정 품질의 커널 증명에 2~5 엔지니어-주)는 업스트림 컴파일러 수정, 하드웨어 대기, 프로덕션 하드닝, 독립 엔진을 포함하지 않는다.
- 프로덕션 패키징, 기본 활성화, 다른 연산자 계열, 네이티브 엔진은 이 배치 범위 밖이다.
