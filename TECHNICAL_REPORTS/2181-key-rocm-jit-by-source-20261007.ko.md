# 기술 보고서: PR #2181 - ROCm 커스텀 커널 JIT 모듈을 생성된 소스로 키잉

**날짜**: 2026-10-07

**상태**: gfx1151 호스트에서 구현 및 검증 완료. 헤드 `b11b4cc5`(검증 시점 origin/main `b7116d1d` 기준 최신), PR 열림, 머지 대기. #2149를 닫음(#1801의 일부).

**언어**: C++(ROCm 오버레이의 `custom_kernel.cpp`, cxx 브리지, `turbo/paged_attention*.cpp`의 주석), Rust(mlxcel-core FFI 래퍼, `tests/rocm_custom_kernel_jit_key.rs`), Python(`scripts/ci/check_kernel_dtype_keys.py`의 docstring과 주석), Markdown(`LOCAL_FIXES.md`, `docs/code-guidelines.md`)

**위험도**: 낮음. 프로덕션 변경은 ROCm 오버레이의 모듈 이름 식 하나이며 업스트림 CUDA에서 그대로 가져왔습니다. 소스가 한 번도 달라지지 않던 호출은 더 긴 키 아래에서 이전과 같은 모듈을 받고, 소스가 달라지던 호출은 잘못된 모듈을 재사용하는 대신 자기 모듈을 컴파일합니다.

## 요약

ROCm 오버레이의 `fast::hip_kernel`은 컴파일된 모듈을 장치 인덱스와 커널 이름으로 캐시했고, 그 이름은 `template_args`만 반영합니다. 그런데 생성된 소스는 각 입력과 출력의 dtype, 그리고 각 입력이 0차원인지에도 의존합니다. 이 속성만 다른 이후 호출은 첫 호출의 모듈을 재사용했습니다. f16 입력을 `const float*`로 읽거나, f16 출력을 `float*`로 쓰거나, 모듈이 선언하지 않은 인자 목록으로 0차원 입력을 실행했습니다. 예외는 발생하지 않았습니다.

PR #2181은 모듈을 `name_ + "_" + hex(std::hash<std::string>{}(source_))`로 키잉합니다. 업스트림 CUDA가 9f5f7931(ml-explore/mlx#4273)부터 쓰는 키와 같으며, MLX 핀 `81ba1c6a`에 포함되어 있습니다. 모듈 안의 커널 심볼과 장치 인덱스 접두사는 바뀌지 않으므로 프로파일러 트레이스는 `custom_kernel_*` 이름을 유지합니다. 이 수정은 LOCAL_FIXES 항목 33으로 기록되었고, 2026-10-06 포크 정책에 따라 mlxcelverse에서 유지됩니다.

테스트 전용 브리지 프로브는 템플릿 인자 없이 하나의 커널 이름으로 실행하므로, 생성된 소스만이 호출을 구분할 수 있습니다. 세 테스트가 입력 dtype, 출력 dtype(리뷰에서 추가), 그리고 1차원 입력 뒤의 0차원 입력(자식 프로세스에서 실행)을 다룹니다. 이름 전용 키를 되돌리면 세 테스트 모두 실패합니다. f16 입력 값이 틀리고, f16 출력 값이 틀리고, 0차원 자식 프로세스는 SIGSEGV로 죽습니다. mlxcel 자체 런처의 명시적 dtype 키와 이를 강제하는 CI 검사기는 심층 방어로 유지됩니다. CUDA를 여전히 이름만으로 키잉한다고 설명하던 문서와 주석은 수정되었습니다. 리뷰에서는 ROCm JIT 모듈 캐시에 잠금이 없다는 점도 발견되었고, 이는 이제 이슈 #2183입니다.

## 1. 문제 정의

### 1.1 키가 놓친 것

`src/lib/mlx-cpp/patches-rocm/mlx/backend/rocm/custom_kernel.cpp`에서 `hip_kernel`은 `name_`을 `"custom_kernel_" + name + template_arguments_hash(template_args)`로 만듭니다. 이어서 `build_kernel`이 생성하는 소스는 다음도 담습니다.

- 각 입력의 원소 타입(`dtype_to_hip_type(arr.dtype())`)이 버퍼 매개변수에 들어갑니다.
- 각 출력의 원소 타입이 버퍼 매개변수에 들어갑니다.
- 각 입력의 `ndim() > 0` 여부가 `<input>_shape`, `<input>_strides`, `<input>_ndim` 선언 여부를 결정합니다(LOCAL_FIXES 항목 30이 shape를 값으로 전달되는 고정 폭 `KernelShape`로 바꿨으므로 ndim 값 자체는 더 이상 중요하지 않고, 0인지 아닌지만 중요합니다).

`CustomKernel::eval_gpu`는 `name_`을 `rocm::get_jit_module`에 넘겼고, 이 함수는 프로세스 전역 맵에서 `device.index + ":" + name`으로 메모이즈하며 캐시 미스일 때만 소스 빌더를 호출합니다. 한 이름 아래 처음 컴파일된 소스가 프로세스가 끝날 때까지 쓰였습니다.

### 1.2 불일치가 낳은 결과

- **입력 dtype.** f16이나 bf16 입력이 f32 모듈을 재사용해 `const float*`로 읽혔습니다. 4바이트 읽기 하나가 2바이트 원소 둘을 합쳤고, 커널은 버퍼 크기의 두 배를 읽었습니다. 결과 값은 입력과 무관했습니다.
- **출력 dtype.** f16 출력이 f32 모듈을 재사용해 `float*`로 쓰였고, 쓴 바이트 수도 같은 방식으로 두 배가 되었습니다.
- **0차원 입력.** 항목 30 이후 `eval_gpu`는 `build_kernel`과 맞추어 ndim이 0보다 클 때만 입력의 shape, strides, ndim을 덧붙입니다. 같은 이름으로 1차원 입력 뒤에 0차원 입력이 오면, 캐시된 모듈이 선언한 것보다 적은 인자로 실행되었고 출력 포인터를 포함한 이후 매개변수가 모두 잘못된 슬롯에서 읽혔습니다.

### 1.3 mlxcel이 이를 보지 못한 이유

mlxcel 자체 런처는 #1053과 #1054 이후 `template_args`에 입력 dtype을 명시하며, 이는 `scripts/ci/check_kernel_dtype_keys.py`(`make verify-kernel-dtype-keys`)가 강제합니다. 그래서 `name_`이 입력 dtype마다 달라졌고, 흔한 경우에는 결함이 가려졌습니다. 이 검사는 키에 들어간 입력과 독립적으로 dtype이 바뀌는 입력, 한 입력 dtype에서 바뀌는 출력 dtype, 0차원 대 비0차원 입력은 다룰 수 없습니다. 이 이슈는 모델 출력 오류가 아니라 #2100의 보안 리뷰에서 발견되었습니다.

## 3. 설계

### 3.1 업스트림 CUDA처럼 소스로 키잉

생성된 소스는 hiprtc 컴파일의 입력 전체이므로, 이를 해시하면 모듈을 바꾸는 모든 속성을 나열하지 않고도 덮습니다. 1.1의 세 가지와 앞으로 소스에 영향을 줄 입력까지 포함됩니다. 이 식은 업스트림 CUDA가 `mlx/backend/cuda/custom_kernel.cpp`(핀 기준 313행 부근)에서 쓰는 것으로, 9f5f7931(ml-explore/mlx#4273)에서 추가되었습니다. 그대로 가져오면 ROCm 포크가 추적하는 백엔드와 맞춰지므로, 이후 업스트림의 ROCm 키잉을 포함한 재벤더링도 같은 동작에 도달할 것입니다.

이슈는 모든 입력 dtype을 이름에 덧붙이는 Metal 방식을 기각했습니다. 입력 dtype은 고치지만 출력 dtype이나 0차원 케이스는 고치지 못하고, CUDA와도 갈라집니다.

변경은 의도적으로 좁습니다.

- **심볼 이름 유지.** `kernel_name`은 여전히 `"mlx::core::rocm::" + name_`(사전 컴파일 커널은 `name_`)입니다. 캐시 키에만 해시가 붙으므로 `rocprofv3` 트레이스는 여전히 `custom_kernel_*`을 보여주고 기존 프로파일 도구도 그대로 작동합니다.
- **장치 인덱스 접두사 유지.** `get_jit_module`은 여전히 `device.index + ":"`를 앞에 붙이므로 모듈은 장치별로 유지됩니다.
- **디스크 캐시 문제 없음.** 커스텀 커널은 `use_disk_cache = false`로 `get_jit_module`을 호출하므로 키가 파일 이름이 되지 않습니다. `std::hash` 값은 빌드 간에 안정적이지 않지만, 한 프로세스 안에서만 쓰이는 키에는 상관없습니다.
- **비용.** `eval_gpu`마다 문자열 해시 한 번으로 CUDA와 같습니다. 소스가 바뀌지 않던 런치는 이전과 정확히 같은 횟수로 컴파일됩니다. 소스가 바뀌던 런치는 이제 변형마다 모듈 하나를 컴파일하며, 이는 올바른 결과를 위해 원래 필요했던 것입니다.
- **충돌.** 같은 이름 아래 `std::hash`가 같은 서로 다른 두 소스는 여전히 모듈을 공유합니다. CUDA도 이를 받아들이며 이 수정도 같습니다.

### 3.2 프로브

`rocm_jit_key_probe(input, f16_output)`는 매 호출 `template_args = {}`로 `fast::hip_kernel("mlxcel_jit_key_probe", {"inp"}, {"out"}, ...)`를 실행합니다. 이름과 템플릿 인자가 바뀌지 않으므로 `name_`이 호출 간에 같고, 이것이 이름 전용 키를 드러내는 조건입니다. 커널은 `out[1 + i] = (float)inp[i]`를 쓰고, 스레드 0에서 `out[0] = (float)inp_shape[0]`를 씁니다. 출력은 원소 `n + 1`개의 f32 또는 f16입니다. 입력은 f32, f16, bf16 중 하나여야 하며 0차원 또는 원소 1개에서 1024개의 1차원이어야 하고, `n` 스레드 블록 하나가 이를 덮습니다.

0차원 케이스에는 `inp_shape` 매개변수가 있든 없든 컴파일되는 하나의 소스 텍스트가 필요합니다. 프로브의 헤더는 `mlx::core::rocm` 네임스페이스 범위에 다음을 선언합니다.

```cpp
__constant__ KernelShape inp_shape = {{-1, 0, 0, 0, 0, 0, 0, 0}};
```

1차원 입력에서는 `build_kernel`이 `inp_shape` 매개변수를 선언해 센티널을 가리고, `out[0]`은 길이가 됩니다. 0차원 입력에서는 그런 매개변수가 없으므로 한정되지 않은 이름 조회가 센티널로 내려가 `out[0]`은 `-1`이 됩니다. 생성된 소스가 다르므로(하나는 매개변수가 있고 하나는 없음) 올바른 키는 둘을 구분하며, `out[0]`은 실제로 어느 모듈이 실행되었는지 테스트에 알려줍니다. 프로브가 `template_args`로 `{}`를 넘기므로 CI 검사기는 이를 범위 안에 있지만 검사할 것이 없는 런치로 취급하며, 검사기의 한계 주석이 이를 명시해 의도된 것임을 드러냅니다.

### 3.3 세 테스트

모두 `VALUES = [0.5, -1.25, 3.0, 8.0, -0.75, 96.0, 0.0, 2.5]`를 쓰며, f16과 bf16이 정확히 표현하는 값이므로 f32 변환 후 기대 출력이 비트 단위로 정확합니다. 각 프로브는 변환 전에 단독으로 평가되므로, 검사 대상인 모듈 조회가 더 큰 그래프에 퓨즈되지 않습니다.

- **`input_dtype_selects_its_own_module`**: f32 출력으로 f32, f16, bf16 입력을 차례로 실행합니다. f32를 먼저 실행해, 좁은 dtype이 올 때 이름 기반 캐시에 `const float*` 모듈이 들어 있게 합니다.
- **`output_dtype_selects_its_own_module`**: f32 입력 하나로 f32 출력, 이어서 f16 출력을 실행합니다. 이 케이스는 리뷰에서 추가되었습니다. 입력 dtype 테스트만으로는 입력 dtype은 덮지만 출력 dtype은 덮지 않는 키(Metal 방식이나 템플릿 인자 검사)를 잡을 수 없고, 이슈의 원래 인수 조건은 입력만 다뤘습니다.
- **`scalar_input_after_vector_input_selects_its_own_module`**: 원소 4개의 1차원 입력, 이어서 0차원 입력을 실행합니다. 이름 기반 빌드에서는 두 번째 런치가 잘못된 슬롯에서 매개변수를 읽어 큐를 폴트시킬 수 있고, ROCm에서는 이것이 프로세스 전체의 장치를 망가뜨립니다. 그래서 테스트는 자기 바이너리를 무시된 자식 테스트(`child_scalar_after_vector`, `MLXCEL_ROCM_JIT_KEY_CHILD`로 게이트)로 다시 실행하고, HIP 큐 덤프가 가득 찬 파이프에 막히지 않도록 stdout과 stderr를 별도 스레드에서 비우며, 120초 예산을 적용하고, 프로브마다 `JIT_KEY_PROBE <label> ok=...|err=...` 한 줄을 파싱합니다. 자식은 stdout을 플러시한 뒤 `libc::_exit(0)`로 종료해 폴트된 큐에서 HIP 정리가 멈추지 않게 합니다. 이는 `tests/rocm_gpu_faults.rs`를 따릅니다. 부모는 자식이 성공적으로 종료했는지, 1차원 프로브가 `[4, values...]`를, 0차원 프로브가 `[-1, value]`를 반환했는지 확인합니다.

### 3.4 모든 명시적 dtype 키와 검사기 유지

소스가 키에 들어갔으므로 mlxcel `template_args`의 dtype 항목은 더 이상 ROCm이나 CUDA를 올바르게 만드는 요소가 아닙니다. PR은 이들을 모두 유지하고, `verify-kernel-dtype-keys`도 규칙, 범위, 고정된 범위 내 파일 수(9)를 그대로 둡니다. 이유는 세 가지입니다.

- **비용이 없습니다.** 소스가 이미 dtype마다 다르므로 소스 해시가 이미 그 모듈들을 나눕니다. 명시적 키는 컴파일을 늘리지 않습니다.
- **일부는 쓰입니다.** 여러 런치가 dtype 인자를 커널 본문에서 타입 별칭으로 참조합니다. 이를 지우는 것은 죽은 코드 정리가 아니라 코드 변경입니다.
- **나머지는 보험입니다.** ROCm 포크 재벤더링, MLX 핀 업데이트, 새 백엔드가 이름 전용 키를 되살릴 수 있고, 모델이 틀린 숫자를 낼 때까지 다른 무엇도 이를 알아채지 못합니다. 검사기가 그 회귀를 막는 장치이므로, docstring과 `docs/code-guidelines.md`는 이제 이를 수정 자체가 아니라 심층 방어라고 부릅니다.

### 3.5 오래된 CUDA 설명 수정

검사기 docstring, `docs/code-guidelines.md`, 그리고 `turbo/paged_attention.cpp`와 `paged_attention_v2.cpp`의 키잉 주석은 CUDA가 이름만으로 모듈을 키잉한다고 현재 시제로 말하고 있었습니다. #1053을 발견했을 때는 사실이었지만 현재 핀에서는 아닙니다. 이제 이들은 CUDA가 ml-explore/mlx#4273 이후 소스 해시로 키잉하고, ROCm은 #2149 이후 그렇게 하며, 이름 전용 동작이 명시적 키가 존재하는 이유라고 설명합니다. `paged_attention` 변경은 주석만 바꿉니다.

## 4. 검증

### 4.1 되돌림 증거

gfx1151에서 오버레이에 이름 전용 키를 되돌리면 세 테스트 모두 실패합니다.

- **f16 입력**: 입력 `[0.5, -1.25, 3, 8, -0.75, ...]`에 대해 프로브가 `[8, -0.0313, 131336, 3.5e13, 8, 0, ...]`을 반환했습니다. 원소 0은 올바른 길이이고, 나머지는 f16 값 두 개를 f32 하나로 읽은 것입니다. 테스트가 f16 단언에서 멈추므로 bf16 케이스는 되돌림 상태에서 따로 관찰되지 않았습니다.
- **f16 출력**: 프로브가 `[0, 2.5, 0, 1.75, ...]`를 반환했습니다. `float*`로 쓴 f32 비트 패턴을 f16 절반씩 다시 읽은 값입니다.
- **1차원 뒤 0차원**: 자식 프로세스가 1차원 호출 후 SIGSEGV로 죽었습니다.

수정을 적용하면 세 테스트 모두 통과합니다. 되돌림 결과는 각 테스트가 겨냥한 결함을 검출함을 보여줍니다.

### 4.2 게이트

PR에서, gfx1151 기준:

- `cargo test --profile test-fast --features rocm --test rocm_custom_kernel_jit_key -- --test-threads=1`: 3개 통과.
- `cargo clippy --features rocm --test rocm_custom_kernel_jit_key -- -D warnings`와 `cargo clippy -p mlxcel-core --features rocm --lib -- -D warnings`: 경고 없음.
- `b7116d1d`로 리베이스한 뒤 `make verify-versions verify-kernel-dtype-keys verify-kernel-port-dispatch verify-llama-compat verify-fmt verify-rocm-overlay`: 검사기의 부정 케이스 묶음을 포함해 통과.

오케스트레이터에서, 헤드 `b11b4cc5`(origin/main `b7116d1d` 기준 최신): `make verify-rocm`이 모든 단계를 통과했고, 테스트 11,972개 통과, 0개 실패, 382개 무시, 스모크 단계 OK였습니다. 새 파일은 3개 통과와 1개 무시(자식 테스트)를 더합니다.

검증하지 않은 것: 호스트에 Metal과 CUDA가 없었습니다. 변경은 ROCm 오버레이, ROCm 외에서는 예외를 던지는 스텁으로 컴파일되는 브리지 함수, ROCm 전용 테스트 파일, 주석과 문서만 건드리므로 Metal이나 CUDA 코드 경로는 바뀌지 않습니다.

## 5. 기술적 선택과 그 이유

- **dtype 목록 대신 소스 해시.** 소스를 해시하면 입력 dtype, 출력 dtype, 0차원 여부, 그리고 이후 `build_kernel` 변경이 더할 무엇이든 덮습니다. 목록은 누군가 기억해서 적은 것만 덮으며, Metal 방식이 0차원 케이스를 놓치는 것이 그 예입니다.
- **업스트림 CUDA를 그대로 복사.** 오버레이는 CUDA를 추적합니다. 같은 식을 쓰면 두 백엔드를 같은 방식으로 이해할 수 있고 이후 재벤더링도 단순해집니다.
- **심볼이 아니라 캐시 키를 변경.** 프로파일링과 `custom_kernel_*` 이름을 매칭하는 도구가 계속 작동합니다.
- **템플릿 인자 없는 프로브.** `{}`를 쓰면 mlxcel 자체 런처가 가진 보호막이 사라지므로, 테스트는 백엔드 키 자체를 측정하고, mlxcel의 모든 런처가 dtype 키를 유지하더라도 그 회귀를 잡습니다.
- **폴트 케이스를 자식 프로세스로 격리.** ROCm에서 큐 폴트는 프로세스의 장치를 오염시킵니다. 0차원 케이스를 프로세스 안에서 돌리면 회귀가 무관한 테스트의 실패나 멈춤으로 번집니다.
- **dtype 키와 검사기 유지.** 비용이 없고, 일부는 커널 본문에서 실제로 쓰이며, 오버레이 밖에서는 이 PR이 막을 수 없는 회귀를 지킵니다.
- **mlxcelverse에 수정 유지.** 2026-10-06 포크 정책에 따라 오버레이 항목은 ROCm 포크에 제안하지 않고 여기서 유지합니다.

## 6. 잔여 위험과 후속 작업

- **잠금 없는 JIT 모듈 캐시(#2183).** 리뷰에서 `rocm/jit_module.cpp`의 `get_jit_module`이 함수 정적 `unordered_map`에 잠금 없이 `find`와 `try_emplace`를 수행하고, `try_emplace`가 hiprtc 컴파일을 그 자리에서 실행한다는 점이 발견되었습니다. JIT 커널을 동시에 실행하는 두 스레드(예: 한 서버 안의 채팅 스케줄러와 임베딩 워커)는 같은 키를 둘 다 컴파일하거나, 동시에 진행 중인 `find` 아래에서 테이블을 재해시할 수 있습니다. 업스트림 CUDA와 CUDA 오버레이는 이를 `shared_mutex`로 잠급니다. 이 경쟁은 관찰된 적이 없습니다. 이 PR 이전부터 있던 문제이며 키잉 범위 밖이므로 #2183으로 추적합니다. 다만 이 PR은 프로세스 수명 동안 키를 더 만들기 때문에(소스 변형마다 하나) 새 삽입이 일어나는 구간을 약간 넓힙니다.
- **해시 충돌.** 같은 이름 아래 두 소스의 `std::hash`가 충돌하면 CUDA와 마찬가지로 모듈이 재사용됩니다. 완화책은 추가하지 않았습니다.
- **검사기의 한계는 그대로입니다.** `verify-kernel-dtype-keys`는 여전히 독립적인 입력 dtype, 출력 dtype, 0차원 입력을 다룰 수 없고, 이름 붙은 `template_args` 초기화만 읽습니다. 소스 기반 키잉 백엔드에서는 이 빈틈이 틀린 결과를 낳지 않지만, 이름 전용 키로 회귀하면 낳습니다. LOCAL_FIXES 항목 33이 이를 나열합니다.
- **업스트림에 반영되지 않음.** ROCm 포크는 여전히 이름 전용 키를 갖고 있으며, 수정은 mlxcel 오버레이에만 있습니다. 재벤더링 시 항목 33을 유지해야 하며, `verify-rocm-overlay`와 해당 항목이 이를 드러냅니다.
- **회귀 시 범위 밖 접근.** 입력 dtype과 출력 dtype 실패는 이 호스트에서 버퍼 크기의 두 배를 읽거나 쓰면서도 폴트가 나지 않았습니다. 다른 할당기 배치에서는 같은 회귀가 틀린 값 대신 폴트를 낼 수 있으므로, 이 두 테스트는 그렇지 않다는 가정 아래 프로세스 안에서 실행됩니다.

## 7. 학습 포인트

- **캐시 키는 캐시된 값이 의존하는 모든 것을 덮어야 합니다.** 여기서 빌더의 입력은 템플릿 인자, dtype, 0차원 여부였지만 키는 첫 번째만 덮었습니다. 빌더의 출력(소스)으로 키잉하는 것이 키를 구조적으로 완전하게 만드는 가장 단순한 방법입니다.
- **호출자 쪽 완화책은 백엔드 결함을 가립니다.** mlxcel 런처의 dtype 키가 흔한 경우를 동작하게 만들어 백엔드 키가 올바른 것처럼 보이게 했습니다. 백엔드 속성을 검사하는 테스트는 그런 완화책을 걷어내야 하며, 프로브는 템플릿 인자를 넘기지 않음으로써 그렇게 합니다.
- **보고된 축만이 아니라 버그가 가진 모든 축을 테스트하십시오.** 이슈는 입력 dtype과 0차원 케이스를 명시했고, 리뷰가 원래 테스트로는 놓쳤을 출력 dtype을 추가했습니다.
- **어느 컴파일 변형이 실행되었는지 관찰 가능한 센티널로 확인하십시오.** `__constant__` `inp_shape` 센티널은 하나의 소스가 매개변수 유무와 관계없이 컴파일되게 하고, 결과 자체가 어느 모듈이 실행되었는지 알려주게 합니다.
- **수정 없이 테스트가 실패함을 증명하십시오.** 이전 키를 되돌리고 실패를 기록하면 각 테스트가 결함을 측정한다는 것이 드러나고, 버그가 실제로 어떻게 보였는지 구체적인 숫자를 남깁니다.
