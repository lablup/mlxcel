# Technical Report: PR #1396 - Raise the Development Test Thread Stack

**Date**: 2026-08-24

**Author**: Jeongkyu Shin

**Status**: Completed

**Languages**: Make, Python, Markdown

**Risk Level**: Low

## Executive Summary

PR #1396 prevents mlxcel's documented Make-based development test commands from aborting when Minijinja renders the large Qwen3.8 reasoning-effort fixture on libtest's default 2 MiB thread stack. The three default-profile targets now export a 16 MiB `RUST_MIN_STACK`, while the CI-faithful `verify-test` target and all Cargo profile definitions remain unchanged.

## 1. Problem Statement

`server::reasoning_effort_tests` repeatedly renders an 8,952-byte Qwen3.8 chat template. Under Cargo's unoptimized development profile, Minijinja's native call frames can exceed libtest's default per-test thread stack and terminate the whole test binary with SIGABRT. The optimized `test-fast` and release profiles do not exhibit the same failure, so the defect affected the local `make test`, `make test-verbose`, and `make test-lib` entry points rather than the shipping binary or the documented verification profile.

## 2. Change Summary

| Area | Change |
|---|---|
| `Makefile` | Define an overridable 16 MiB development-test stack and export it only for `test`, `test-verbose`, and `test-lib` |
| `CONTRIBUTING.md` | Explain the development-profile limitation, the Make-managed behavior, and the direct Cargo equivalent |
| Contract tests | Pin the default stack value, all three affected recipes and their dry-run expansions, and the exact unchanged `verify-test` command |

## 3. Technical Decisions

### 3.1 Keep the workaround at the supported entry points

The issue allowed either wrapping individual Rust tests or documenting the development-profile constraint and making the existing Make targets safe. The latter keeps test code and the pinned fixture untouched, covers every test reached through those targets, and leaves direct Cargo users with an explicit documented prefix.

### 3.2 Preserve the verification and release profiles

The change does not modify `[profile.dev]`, `[profile.test-fast]`, or `[profile.release]`. It also leaves `verify-test` on exactly `cargo test --workspace --profile test-fast --features metal,accelerate --no-fail-fast -- --test-threads=1`, so the CI-faithful gate retains its previous performance and numeric behavior.

### 3.3 Verify evaluated Make behavior

The regression test checks both source recipes and the commands emitted by `make -n`. This catches changes to the default stack variable or Make expansion that a source-only string assertion could miss. The subprocess invocation uses an argument vector without a shell and only fixed target names.

## 4. Verification

- `python3 -m unittest tests.test_makefile_dev_test_stack -v`: 4 passed.
- `make -n test`, `make -n test-verbose`, and `make -n test-lib`: each emitted `RUST_MIN_STACK=16777216` before the original Cargo command.
- `make -n verify-test`: emitted the exact existing `test-fast` workspace command with no stack override.
- `RUST_MIN_STACK=16777216 cargo test --lib server::reasoning_effort_tests -- --test-threads=1`: completed three development-profile runs; each reported 19 passed and no SIGABRT.
- `cargo fmt --all -- --check`: passed.
- Hosted CI at the final reviewed code head: change detection, crate versions, kernel dtype keys, cross-repository references, and CLA passed. Rust-path jobs were skipped by the repository's path filters because this PR changes no Rust source or dependency metadata.
- Implementation, correctness, security/performance, and finalization reviews found no unresolved issue after the dry-run contract coverage was added.

## 5. Remaining Validation Boundary

The focused development-profile runs were performed on Linux without the Metal feature. This host has no Apple Metal backend, so the requested Apple Silicon runtime repetition could not be performed locally and is not presented as passed. The accepted documentation-plus-Makefile branch of issue #1384 does not require changing the Metal-dependent Rust execution path.
