# 기술 보고서: PR #2315 - Gemma 4 12B long-context MTP parity

**작성일**: 2026-10-15
**상태**: 완료; 최종 source `1eda64ef`를 release build 및 smoke 검증했으며 CI는 대기 중
**언어**: Rust, Markdown, JSON
**위험도**: 중간

## 요약

PR #2315는 현재 Metal에서 Gemma 4 12B long-buffered MTP divergence를 재현하고 기존 exact row-wise verification 경로를 측정한 12B geometry로 확장합니다. Physical rotating-cache reduction order, maskless single-query full attention, classic prefill chunking을 일치시켜 M1 Ultra에서 측정한 teacher-forced 및 free-generation disagreement를 모두 제거했습니다.

Release 측정은 더 넓은 default 사용을 뒷받침하지 않습니다. 강제로 활성화한 MTP throughput은 세 prompt에서 classic의 0.837, 0.903, 0.815배였고, 강화한 startup probe는 median scheduler-setup-to-probe 구간에 5.80초를 추가했습니다. 따라서 이 PR은 측정한 exactness 경로를 수정하되 default를 넓히지 않습니다. Performance 근거는 commit `bd6d33f2`에 해당하며, review에서 요구된 backend 제한은 `1eda64ef`에 반영되어 별도의 최종 release build와 smoke를 통과했습니다.

## 1. 문제 정의

기존 startup draw 세 개는 rotating cache가 wrap되기 전에 통과했지만 실제적인 1,056-token buffered verification은 classic decode와 달랐습니다. Current-main diagnostic baseline의 `8,8,8,1056` 혼합 sequence는 sliding attention에서 처음 달라졌고, 독립 `1056` draw는 full attention에서 처음 달라졌습니다. 실제 cache snapshot은 speculative verification과 classic decode가 같은 visible key를 서로 다른 physical reduction order로 처리함을 보여줬고, batched verify block은 classic의 maskless single-query full-attention dispatch도 재현하지 못했습니다.

Serving에서는 attention 수정만으로 부족했습니다. Candidate MTP의 whole-prompt prefill 결과는 classic whole-prompt control과 일치했지만 classic의 일반 512-token chunking과는 일치하지 않았습니다. 따라서 verification 전에 target adapter도 classic prefill chunking을 따라야 합니다.

## 2. 기술적 선택과 그 이유

### 측정한 geometry의 exact row-wise verification

변경은 기존 exact-geometry predicate와 31B row-wise 구현을 Gemma 4 12B의 `16/8/1` query/sliding-KV/full-KV geometry 및 256/512 head dimension에 재사용합니다. Verification은 linear singleton으로 제한되고 physical sliding-ring order를 재현하며 maskless single-query full attention을 사용합니다. 지원하지 않는 batched 또는 nonlinear layout은 거부하고 chronological speculative cache가 classic automatic prompt reuse로 전달되는 것을 막습니다. CUDA의 row-wise RoPE 수정은 CUDA 전용으로 유지합니다.

Review에서는 commit `bd6d33f2`가 backend 경계 없이 이 geometry를 활성화하여 측정하지 않은 ROCm과 CPU 동작까지 확장한 점을 발견했습니다. Commit `1eda64ef`는 31B의 기존 backend-independent policy와 정확한 기존 CUDA 조건을 유지하고, Metal이 사용 가능하며 default GPU device로 선택된 경우에만 12B를 추가하며, CPU-selected Metal과 ROCm 및 다른 GPU backend는 이전 policy를 유지합니다. Backend policy 6개와 geometry 7개의 helper matrix 및 live 12B predicate/long-probe assertion이 통과했습니다. 이전 반복 performance 측정은 `bd6d33f2`에 귀속하며, 최종 source에는 별도의 build 및 correctness-smoke 근거가 있습니다.

### 측정한 비용을 포함한 강화된 startup guard

Startup exactness probe는 측정한 row-wise geometry에 대해 `sliding_window + 32` token draw를 추가하고 최대 1,536으로 제한합니다. 이는 8-token draw 세 개가 도달할 수 없는 첫 cache-wrap 구간을 검사합니다. Release 3회 측정에서 median setup-to-probe 구간은 1.245초에서 7.041초로 늘어 5.795초의 startup cost가 발생했고, median health time은 4.796초에서 10.408초로 증가했습니다.

### Correctness는 default 활성화를 의미하지 않음

Release 측정은 수정 경로를 분리하기 위해 MTP를 강제로 활성화하고 adaptive sizing과 slice grant를 비활성화했습니다. Paired MTP/classic throughput ratio는 science 0.837, software 0.903, history 0.815로 각각 16.3%, 9.7%, 18.5%의 regression을 보였습니다. 따라서 기존 default policy는 변경하지 않습니다.

## 3. 근거와 검증

### Diagnostic 및 exactness 근거

- Baseline: main `a2698835`, MLX `243bdf09`, test-fast diagnostic server SHA-256 `b60e1cba62156c6dfa04c9875ce3f3601502370c60c8524bb6fe42af8bc9edc9`.
- Failure localization: 혼합 long draw는 layer 8 sliding attention position 2에서 처음 달랐고, 독립 long draw는 layer 5 full attention position 0에서 처음 달랐으며 동일하게 재현됐습니다.
- Teacher forcing: 일반 block verification은 top-1 18/256개와 decided 2/155개에서 달랐고, 수정된 verification은 0/256과 0/155였으며 reference-choice logit delta도 0이었습니다.
- Serving parity: 1,238-1,638 input token의 prompt 세 개에서 수정된 MTP와 안정적인 classic reference 2회의 256-token output이 byte 단위로 일치했고, MTP proposal, acceptance, round counter는 모두 0보다 컸습니다.
- Regression target: 31B와 bf16 assistant, Qwen3.8 27B와 4-bit MTP는 세 prompt 모두에서 before/after output byte와 draft counter가 동일했습니다.
- `bd6d33f2`의 집중 검증: `gemma4::` 테스트 82개가 통과했고 관련 없는 ffmpeg 테스트 1개는 ignored였습니다. 일반 `gemma4_tests::` 테스트 12개와 명시적으로 선택한 serial 테스트 13개가 통과했습니다.
- `1eda64ef`의 backend 제한: backend policy 6개와 geometry 7개의 집중 helper matrix 및 live predicate/long-probe assertion이 통과했고 formatting도 통과했습니다.
- `16063a00`의 근거 기록: 독립 security review가 throughput, startup, 27개 output-hash guard 및 draft-counter attribution을 다시 계산했고 불일치를 발견하지 않았습니다.
- `e637f970`의 최종 근거: `1eda64ef` release executable의 SHA-256은 `98fb89c5d81daa8d47e0c575ccf68ad93f1439087cd241994de6c3426902237d`입니다. 여섯 completion에서 세 final-head classic/MTP 256-token pair가 각각 서로 일치하고 이전에 기록한 hash와도 일치합니다. MTP proposed/accepted/round counter는 317/150/106, 295/157/99, 322/148/108입니다.
- True-default startup control: 모든 `MLXCEL_*` 및 `LLAMA_ARG_*` 변수를 unset하고 CLI model 인자를 명시한 상태에서 final-head exactness와 health가 10.375초에 통과했습니다. 이는 단일 correctness control이며 startup performance distribution이 아닙니다.

### Release 성능 근거

Immutable baseline server는 `c0ae26b2`에서 build했고 SHA-256은 `4fdb66333c5862fbf7d6b14129c11fde6f017d4a27aae8090035a0346e7c27ba`입니다. 이전 diagnostic baseline과 사이에 관련 없는 model-prefill 수정 네 개가 있으므로 benchmark record는 source identity를 주장하지 않습니다. Candidate release server는 `bd6d33f2`에서 build했고 SHA-256은 `de772cee794bd5680fdbd0e354e25800d3c000e5af2c5ba8d195a7889bcceada`입니다.

Baseline, candidate classic, candidate 강제 MTP arm을 각각 Apple M1 Ultra 128 GiB의 fresh process에서 3회 실행하여 세 scenario에서 27개 output을 얻었습니다. 같은 scenario의 모든 output hash가 일치했습니다. 1분 host load는 4.51-5.94였습니다. Candidate MTP decode median은 각각 29.748 대 35.615 classic tokens/s, 32.160 대 35.615 tokens/s, 29.066 대 35.649 tokens/s였습니다. Dispersion은 benchmark JSON에 min/max 및 median absolute deviation으로 보존했습니다.

## 4. 변경 요약

- Long exactness probe를 측정한 Gemma 4 12B geometry로 확장합니다.
- Long buffered MTP verification에 row-wise singleton attention과 classic-compatible prefill 동작을 재사용합니다.
- 실제적인 window 테스트를 32에서 1,024 token으로 강화하고 fail-closed layout 제한을 유지합니다.
- 명령, cache layout, localization, output hash, counter, startup 측정, throughput 반복, dispersion, host load를 benchmark Markdown과 JSON에 보존합니다.
- 이 host에서 강제 MTP 경로가 더 느리므로 default MTP policy를 변경하지 않습니다.

## 5. 남은 한계

- M5 Max, CUDA, ROCm, CPU는 이번 조사에서 측정하지 않았습니다. M1 Ultra 결과는 해당 backend의 동작이나 profitability를 입증하지 않습니다.
- Untouched-default throughput은 측정하지 않았습니다. 단일 true-default startup control은 exactness와 health만 입증하며 performance distribution이 아닙니다. 반복 release 비교는 validation switch를 고정하고 M1 B=1 eligibility를 강제로 활성화했습니다.
- 31B 및 Qwen 검사는 test-fast correctness regression이며 반복 release performance 측정이 아닙니다. 31B QAT와 Qwen bf16-drafter variant는 측정하지 않았습니다.
- GB10 대기 job을 포함한 repository CI는 이 보고서에서 green이라고 주장하지 않습니다.
