# 기술 보고서: PR #2194 - ADR 0007, CLI/서버 패리티 하네스, B=1 decode 기준선

**작성일**: 2026-10-07

**상태**: GB10에서 구현하고 측정했으며 머지 대기 중이다.

**언어**: Rust(진단용 바이너리, 프로세스 내 서버 드라이버), Python(라운드 드라이버), Markdown(ADR, 결과)

**위험도**: 낮음. decode 경로는 바뀌지 않는다. 운영 코드에서 바뀐 곳은 prompt-cache 저장소 설정을 `resolve_prompt_cache_store`로 옮긴 것 하나뿐이고, 코드를 그대로 옮겼다는 것을 보안 검토에서 확인했다.

## 요약

epic #2166은 llama.cpp의 설계를 따라 CLI decode 경로(`CxxGenerator`)와 서버 decode 경로(`BatchScheduler`)를 배치 기반 엔진 하나로 합친다. 이 PR은 그 epic의 Phase 0(#2167)이다. 목표 구조를 ADR 0007로 남기고, 두 경로가 어디서 갈라지는지 보여 주는 하네스와, 서버 경로를 B=1로 CLI와 나란히 재는 벤치마크를 추가했다. 기준선 측정으로 속도 관련 기본값을 정했다. prefill 청크 2048, 단일 시퀀스 저장소 dense, 회귀 허용치 1.0%다. 측정 결과 현재 서버의 단일 스트림 decode는 CLI보다 8~23% 느리고, 그 대부분은 paged 저장소 때문이다.

## 1. 문제 정의

CLI와 서버는 서로 다른 루프로 decode한다. 모델 forward와 토큰 단위 샘플러는 공유하지만, 종료 처리, 샘플러 상태 수명, prefill 청크 분할, KV 저장소, 기본값, attention 커널은 각각 두 벌로 구현되어 있다. 그래서 한쪽에만 생긴 버그가 여러 번 있었다(#2090, #1205, #2140, #2128). 코드를 옮기기 전에 갖춰야 할 세 가지가 없었다.
- 합의된 목표 설계
- 지금 두 경로가 얼마나 갈라지는지에 대한 측정
- 서버 경로의 단일 스트림 처리량. `bench_decode`는 `CxxGenerator`만 쟀다.

## 2. 변경 요약

- **ADR 0007**
  - 엔진 API 이름을 정했다. `Engine`, dense와 paged 저장소를 묶는 `KvStore`, `PrefillPlan`, `RowSampler`, `FinishStep`이다.
  - epic 하위 이슈 #2168~#2176을 이 구성 요소에 대응시켰다.
  - ADR 0004가 KV와 스케줄러 추상화를 뒤로 미뤘던 결정을 대체한다.
  - CLI와 서버의 기본값이 다른 항목을 모두 결정표에 담았다.
- **`mlxcel-engine-parity`(`make engine-parity`)**
  - 같은 프롬프트와 `SamplingConfig`를 세 경로로 돌린다. `CxxGenerator`, 프로세스 안의 서버(B=1, dense 저장소), 같은 서버(B=1, paged 저장소)다.
  - prompt-cache 미적중과 적중도 비교한다.
  - 결과로 `identical`을 출력하거나, 처음 갈라진 위치와 양쪽 토큰 id를 출력한다. `--expect-identical`을 주면 갈라졌을 때 종료 코드 1로 끝난다.
- **`mlxcel-bench-engine`(`make bench-engine`)과 `scripts/engine_bench_rounds.py`**: 두 경로의 단일 스트림 TTFT와 decode 속도를 256토큰과 8192토큰 프롬프트에서 잰다. 청크 크기와 저장소를 인자로 받고, 측정은 라운드마다 순서를 바꾸며 번갈아 돌리고 null arm을 둔다.
- **`src/server/engine_probe`**: `start_server`와 같은 방식으로 실제 서버 구성을 HTTP만 빼고 띄운다.
- **기준선 결과**: `docs/benchmark_results/unified-engine-baseline-gb10-2026-10-07.md`와 원시 기록.

## 3. 기술적 선택과 그 이유

**복사본이 아니라 실제 경로를 잰다.**
- CLI 쪽은 `mlxcel generate`와 같은 `select_backend().create_session` 호출을 쓰고, 벤치마크는 `bench_decode`의 `generate_with_stats`를 쓴다.
- 서버 쪽은 `build_server_config`, 공유된 prompt-cache 설정, `ModelProvider`, 서버 warmup을 그대로 쓰고, 미리 토큰화한 요청을 provider 채널로 보낸다.
- 복사본 위에 하네스를 만들면 복사본을 재게 될 뿐이다.

**속도 관련 기본값은 측정으로, 출력 의미를 바꾸는 기본값은 근거로 정한다.** 메인테이너는 결정표 확인을 위해 멈추지 않기로 했고, 성능에 관련된 선택은 더 빠른 쪽으로 하라고 정했다.
- 그래서 속도 관련 항목은 번갈아 돌린 A/B 측정과 null arm으로 정했다.
- 의미 관련 항목은 Phase 5에서 CLI가 서버의 클라이언트가 되므로 서버의 llama-server 호환값을 우선했다. 예외는 CLI 클라이언트의 기본값을 greedy로 두는 것 하나이며, 모델 테스트와 벤치마크의 재현성을 지키기 위해서다.

**실제로 무엇이 돌았는지 기록한다.** 리뷰에서 자체 KV 상태를 쓰는 모델 계열은 B=1에서 dense로 decode하면서도 "paged"로 표시된다는 점이 드러났다. 이제 요청마다 paged 커널 호출 횟수를 세므로, 저장소 A/B가 모르는 사이에 dense끼리 비교하는 일은 생기지 않는다.

## 4. 결과

- **prefill 청크: 2048**
  - 512로 바꾸면 8192토큰에서 TTFT가 늘었다. Qwen3 CLI 8.4%, Qwen3 서버 22.9%, Llama CLI 29.4%, Llama 서버 14.6%다.
  - null 범위는 모두 ±1.9% 안이었고, decode 속도는 변하지 않았다.
- **단일 시퀀스 저장소: dense**
  - B=1에서 paged decode는 Qwen3에서 23.0%와 6.5%(256토큰, 8192토큰), Llama에서 8.2%와 8.1% 느렸다.
  - null 범위는 모두 ±1.1% 안이었고, paged 행에서는 paged 커널이 각각 3612회와 2064회 호출되었다.
  - paged는 계속 배치 서빙용 백엔드로 쓴다.
- **회귀 허용치: 1.0%**: CLI null arm의 라운드별 decode 편차 가운데 가장 큰 값이 0.92%였고, 이를 올림했다.
- **현재 서버와 CLI 비교**
  - decode 속도 비율은 Qwen3에서 0.77과 0.92(256토큰, 8192토큰), Llama에서 0.90과 0.90이다.
  - 서버도 dense 저장소로 돌리면 CLI와 1.5% 이내로 맞는다.
  - 8192토큰 TTFT 차이는 청크 크기 차이에서 온다.
- **패리티**: `MLXCEL_SDPA_DETERMINISTIC=1`에서 CLI, 서버 dense, 서버 paged의 출력이 두 모델 모두 400토큰까지 같았다(greedy와 seeded 모두). prompt-cache를 적중시킨 경우만 갈라졌고(Qwen3 greedy는 0번째 토큰부터), 이것은 #2170의 목표다.

## 5. 남은 위험과 검증하지 못한 것

- **청크 결정은 단일 스트림 기준이다.** 서버의 512 기본값은 배치 서빙에서 prefill과 실행 중인 decode를 잘게 번갈아 돌리려는 것인데, 이번 측정은 그 상황을 재지 않았다. 청크 정책은 #2170이 맡으며, 배치 측정 결과가 뒷받침하면 섞인 tick용으로 더 작은 청크를 남길 수 있다.
- **범위가 좁다.** GPU 하나에서 dense 4-bit 모델 두 계열만 쟀다. Llama 8192토큰에서는 paged의 TTFT가 dense보다 8% 낮았지만 Qwen3에서는 차이가 없어서, 저장소의 영향이 모델 계열마다 같지 않다.
- **패리티는 기본 프롬프트, 400토큰까지만 확인했다.** 더 긴 생성이나 다른 모델 계열에서는 갈라질 수 있다.
- **종료 코드 1의 의미가 둘이다.** `--expect-identical`은 출력이 갈라진 경우와 오류가 난 경우 모두 1을 돌려준다.

## 6. 학습 포인트

- **기준선 측정이 계획의 무게중심을 바꿨다.** 서버 단일 스트림이 느린 이유는 대부분 스케줄러가 아니라 저장소 선택(B=1에서도 paged)이었다. 그래서 엔진 통합의 첫 이득은 시퀀스가 하나일 때 dense를 고르는 데서 나온다.
- **자기 설정을 스스로 표시하는 도구에는 실제 동작을 세는 카운터가 필요하다.** 커널 호출 횟수를 기록하기 전까지 "paged"는 요청한 설정일 뿐 사실이 아니었다.
- **경로마다 따로 정한 기본값은 같은 측정 하나로 맞춰야 한다.** CLI의 2048과 서버의 512는 각자의 맥락에서는 그럴듯했지만, 같은 프롬프트로 번갈아 돌린 A/B 한 번으로 결론이 났다.
