# 기술 보고서: PR #2129 - 어텐션 캐시 계열의 모델 인식 스냅샷 크기 산정 (이슈 #1761)

**날짜**: 2026-10-06

**상태**: GB10에서 구현 및 검증 완료, 머지 대기 중.

**언어**: Rust (테스트만), Markdown

**위험도**: 낮음 (런타임 코드 변경 없음, 테스트와 문서만 변경)

## 요약

이슈 #1761은 Gemma 3, Llama 4, AFMoE가 고정 512 MiB 스냅샷 저장소로 대체되며(이 어텐션 캐시 계열의 항목 크기는 컨텍스트에 비례), `model_type()`이 `_text` 표기를 놓친다고 보고했다. PR #1978(`d7279c52`)이 `snapshot_sizing.rs`에서 두 문제를 이미 고쳤다. 남아 있던 것은 실제 체크포인트의 형상으로 작성한 테스트와 기본 메모리 정책 변화의 측정이었고, 이 PR은 둘을 추가하고 정책을 문서화한다.

## 정책

`capacity = max(512 MiB, min(6 * entry, left / 4))`이며, `entry`가 `left / 2` 안에 들어가면 최소 `entry` 하나를 보장한다. `entry`는 `min(ctx, 8192)` 토큰에서 슬라이딩 윈도를 적용하지 않은 스냅샷 크기이고, `left`는 모델 자체의 추정 사용량을 뺀 남은 메모리다. 이 값은 저장소 상한이며, 메모리는 스냅샷이 실제로 삽입될 때만 사용된다.

## 테스트

모듈 테스트를 `snapshot_sizing_tests.rs`로 옮겼다. 새 테스트는 gemma-3-4b(`gemma3_text`, 헤드 필드가 없어 Gemma 3 기본값 사용), llama-4-scout(`llama4_text`), gemma-4-12b(`gemma4_unified_text`), muse-glimmer-30b(`muse_glimmer_text`)의 실제 config와 AFMoE config를 사용한다. 각각 모델 인식 경로를 타고 8192 토큰 비윈도 항목으로 산정되어야 하며, 밀집 KV 저장소 상향은 받지 않아야 한다. 토큰당 추정치는 GB10에서 측정한 첫 턴 경계 스냅샷과 2% 이내(세 모델 모두 1.2% 이내), Scout는 #1752 측정값과 1% 이내로 검증한다.

## 측정

GB10에서 기본 실행한 `mlxcel-server`로 다중 턴 대화를 수행했다. "이전"은 같은 바이너리에 `MLXCEL_PROMPT_CACHE_SNAPSHOT_CAPACITY_BYTES=536870912`를 준 경우다.

| 체크포인트 | 용량 | 크기 초과 거부 | 적중 | 마지막 턴 |
|---|---|---|---|---|
| gemma-3-4b, 31.8k 토큰 | 512 MiB -> 6.375 GiB | 13 -> 0 | 19.9k에서 재사용 정체 -> 계속 재사용 | 15.5 s -> 2.07 s |
| gemma-4-12b, 15.8k 토큰 | 512 MiB -> 15.75 GiB | 8 -> 0 | 0/12 -> 11/12 | 37.7 s -> 4.3 s |
| muse-glimmer-30b, 17.4k 토큰 | 512 MiB -> 2.44 GiB | 0 -> 0 | 양쪽 5/6 | 양쪽 7.4 s |

변경 후 최대 저장 바이트는 각각 2.02 GB, 4.39 GB, 739 MB였다.

## 미검증 항목

Llama 4 Scout(57 GB, 호스트 한도 40 GB 초과)와 AFMoE(로컬 체크포인트 없음)는 단위 테스트로만 확인했다. Metal 환경은 실행하지 않았다.
