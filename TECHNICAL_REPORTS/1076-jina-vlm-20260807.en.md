# Technical Report: PR #1076 - feat(models): add Jina VLM (jvlm) vision-language support

**Date**: 2026-08-07
**Author**: mlxcel maintainers
**Reviewer**: implementation and security review cycle
**Status**: Completed
**Languages**: Rust, Markdown
**Risk Level**: Medium (new model family; four HIGH-severity findings fixed pre-merge; no numeric oracle parity)

---

## Executive Summary

PR #1076 adds Jina AI's small multilingual VLM: a SigLIP-so400m-class ViT (hidden 1152, 27 layers, patch 14, 378x378 input, no CLS token) feeding a Molmo-style connector into a Qwen2-class decoder (hidden 2048, 28 layers, head_dim 128, 16 query / 8 KV heads, per-head Q/K RMSNorm, rope_theta 1e6, no biases). Issue #849 named the config key `jina_vlm`; no released checkpoint carries that value, only `jvlm`, and detection routes accordingly with `jina_vlm` kept as an alias. Three points where the local mlx-vlm reference disagrees with the checkpoint's own vendor code were resolved in the vendor code's favor and pinned by tests. A chat-template defect discovered during validation, not anticipated by the issue, turned out to have a second layer: the server's typed multi-part `content` broke the first version of the fix silently, and the PR's own "824 prompt tokens on the server, same as the CLI" evidence did not actually establish that the two front ends rendered the same prompt. A known trap from the immediately preceding VLM port (Falcon-OCR, PR #1075) was avoided by explicit design. Four HIGH-severity issues were found and fixed before merge: a 622 MB per-decode-step embedding concatenation shared with three other Molmo-family models, an image-processor memory blowup unbounded in source resolution, a quadratic one-hot scatter, and a silent-garbage config hazard from an untied HF/OLMo key alias gap. The full CUDA test gate passed at parity with `main` (7655 passed, 5 pre-existing failures). 27 files, +5204/-13, merged as `6026fe8f`.

## 1. Problem Statement

### 1.1 Background

Issue #849 asked for `jina_vlm` support, citing the upstream `mlx-vlm` port (`Blaizzy/mlx-vlm/mlx_vlm/models/jina_vlm/`) as the implementation reference and `jinaai/jina-vlm` / `jinaai/jina-vlm-mlx` as the checkpoints. The architecture: a 27-layer SigLIP-so400m-class ViT supplies features from two intermediate layers, concatenated on the channel axis, spatially pooled 2x2 through a latent cross-attention block whose single query is the per-window mean, and projected by a SwiGLU projector into a Qwen2-class text decoder with an OLMo-style tensor layout (fused `attn.qkv`, fused `ffn.gate_up`, per-head Q/K RMSNorm, untied `lm_head`).

### 1.2 Existing Issues

- **The issue's `model_type` does not match any checkpoint.** The issue body says `jina_vlm`; `jinaai/jina-vlm-mlx`'s `config.json` says `jvlm`, at the top level and in both `text_config.model_type` and `vision_config.model_type`. `architectures` is `["JinaVLMForConditionalGeneration"]` and `auto_map` points at `modeling_jvlm.JinaVLM`. `jina_vlm` is only the module name mlx-vlm happens to use.
- **The mlx-vlm port is a reimplementation, not the reference.** It disagrees with the checkpoint's own vendor code (`modeling_jvlm.py`, `blocks_jvlm.py`, `image_processing_jvlm.py`) on ViT layer selection, the token-grid arithmetic, and the coverage-mask padding, all silently: each divergence degrades output rather than raising an error.
- **The MLX conversion drops the chat template.** `jinaai/jina-vlm` ships `chat_template.jinja`; `jinaai/jina-vlm-mlx` and its `tokenizer_config.json` carry neither, so the server falls back to a generic template shaped for a different prompt convention.
- **A known cache-layout trap.** PR #1075 (Falcon-OCR) shipped a server-side CRITICAL where the `sequence_state_layout()` trait default inferred an empty external cache from `supports_batching() == false`, and the server silently ran zero decoder layers. Any new `LanguageModel` wrapper is a candidate to repeat this.
- **Shared code carrying a per-step cost.** `Molmo2Embedding`, reused by `molmo.rs`, `molmo_point.rs`, and now `jina_vlm.rs`, concatenated its base and extension tables inside `forward`, which runs every decode step.

### 1.3 Risk Assessment

| Risk | Impact | Likelihood |
|------|--------|------------|
| Config-based mis-routing sends the checkpoint to no loader or the wrong one | High | Certain if detection only matched the issue's spelling |
| A silently wrong ViT-layer or token-grid choice produces fluent but ungrounded output | High | Certain without cross-checking the vendor source |
| The dropped chat template degrades every non-CLI request | High | Certain without a fallback |
| Repeating the Falcon-OCR `sequence_state_layout()` trap | Critical | Low, given the precedent was fresh |
| A shared-code perf regression on the Molmo family from a naive embedding path | High | Certain once measured |
| Unbounded image-processor memory or a quadratic scatter under attacker-influenced image count/size | High | Certain at scale, absent a bound |

## 2. Technical Review

### 2.1 Routing: `jvlm`, not `jina_vlm`

`src/models/detection.rs:328-331` routes on `"jvlm" | "jina_vlm"`, matching what every released checkpoint actually declares while keeping the issue's spelling as an accepted alias for a hand-edited config. A unit test writes a temporary `config.json` for each spelling and asserts both reach `ModelType::JinaVLM`. This is worth stating plainly: mis-routing on `model_type` is the single most common way ports in this tree have failed, and it fails as "the model never loads" rather than as a subtle numeric error, which is why the check exists as a pinned test rather than a one-off manual verification.

### 2.2 Checkpoint anatomy

`jinaai/jina-vlm-mlx` is 4-bit quantized (`bits: 4`, `group_size: 64`) with bf16 tensors mixed in. It splits into 956 tensors: `vision_model` 491, `language_model` 446, `vl_connector` 19. Facts that shaped the loader:

- `language_model.embedding.embedding` is `[151936, 2048]`, and a *separate* `language_model.embedding.new_embedding` is `[128, 2048]`: the split base-plus-extension table `Molmo2Embedding` already models.
- `language_model.lm_head` is quantized and untied from the embedding.
- `vision_model.patch_embed.proj.weight` is `[1152, 588]`, where `588 = 14*14*3`: a linear projection over already-patchified pixels, not a Conv2d.
- `vision_model.pos_embed` is `[729, 1152]`, where `729 = 27*27`: the patch grid at `378/14`.
- `vl_connector.pooling.q` takes a 2304-wide input, independently confirming the two concatenated ViT layers (`2 * 1152 = 2304`).
- `pooling.kv` and `projector.gate_up` are fused tensors.
- `<|image|>` is token id 151940, and the 128-entry extension table starts at 151936 (`<im_start>` 151936, `<im_end>` 151937, `<im_patch>` 151938, `<im_col>` 151939).

The arithmetic closes end to end on a real image: a 640x480 photo becomes 644x476 under `smart_resize`, tiles 2x2, and produces 602 crop tokens plus 212 thumbnail tokens (814 image tokens, 824 total with the text prompt). 5 crops of 729 patches pool to 980 features, 772 of them valid, which is exactly the `<im_patch>` count the processor emitted.

### 2.3 Three divergences from the mlx-vlm reference

All three are silent-failure-prone (they degrade the description rather than error), and all three were independently checked against `modeling_jvlm.py` / `blocks_jvlm.py` / `image_processing_jvlm.py` re-downloaded from `jinaai/jina-vlm`.

1. **ViT layer selection.** `get_visual_features` appends the `post_lnorm` output to `hidden_states` unconditionally, so the list is 28 entries long for a 27-layer tower. `vit_layers: [-4, -10]` therefore selects layers 24 and 18, not the 23 and 17 a naive negative-index read against a 27-long list would give. Layers 25, 26, and `post_norm` are consequently never loaded.
2. **Token-grid rounding.** The token grid uses `_molmo_get_patches_from_tiling`, which rounds `crop_window + margin` up to a multiple of the pooling size *per crop*, then sums. Molmo's shortcut (`tiles * window + margins`, rounded once) only agrees when the crop window is already even. Molmo's crop window is 16 patches (even); Jina VLM's is 19 (odd). For a 2x2 tiling the per-crop rounding gives `ceil(23/2)*2 * 2 = 48`, not the 46 the shortcut produces.
3. **Coverage-mask padding direction.** `image_processing_jvlm.py:805` is `np.pad(img_mask, [[0, 1], [0, 0]], constant_values=-1)`, appending a sentinel row at the end, while the thumbnail crop was prepended to the pixel values at line 782. The mask therefore takes a trailing `-1` row rather than a leading `1.0` row, so the *last* crop reads as partially padded, not the thumbnail. This is an upstream off-by-one, reproduced deliberately here (as mlxcel's own Molmo v1 processor does for the same construction) and pinned by a test rather than corrected, because the checkpoint was trained against the buggy version.

### 2.4 The chat-template defect

The MLX conversion of `jinaai/jina-vlm` drops the vendor's `chat_template.jinja`, and `tokenizer_config.json` carries no template either. Without a fallback, the server rendered the generic `User:\n\nAssistant: ` template and answered `17` to "What is the capital of France?"; a built-in template keyed on `model_type` and consulted only after `tokenizer_config.json`, `chat_template.jinja`, and `chat_template.json` all come up empty (`src/server/chat_template.rs`) fixed that, and the same prompt answers `Paris.`.

The first version of that template was not the end of it. It concatenated `message['content']` as a string, but the server routes any request that carries a media part through `apply_raw_with_kwargs`, where `content` is a typed JSON array of parts, not a string. Every server image request logged `invalid operation: tried to use + operator on unsupported types string and sequence` and silently fell through to `render_simple_fallback`. The original parity evidence for the PR, that the server reported 824 prompt tokens for an image request, the same count the CLI reports, did not actually hold up: the counts agreed by coincidence while the underlying prompts differed, and so did the generated text (the CLI's "lying on its side" against the server's "lying down on its side" for the same image and question). The fix mirrors upstream's `content['type']` loop and emits the literal `<|image|>` marker per image part instead of concatenating; after the fix the fallback-warning count went from 1 to 0 on the same request and the two front ends became byte-identical.

The lesson is worth stating on its own: a matching token count is not evidence that two front ends rendered the same prompt. It can hold by coincidence while the actual rendered text, and therefore the model's output, differs underneath it.

### 2.5 The `sequence_state_layout()` trap, avoided

The `LanguageModel` trait's default `sequence_state_layout()` infers a model-owned (external-cache-free) placeholder from `supports_batching() == false`. PR #1075 (Falcon-OCR), the VLM port immediately before this one, shipped exactly that gap: the server allocated an empty external cache and `forward` ran zero decoder layers with no panic and no log line, a CRITICAL that was only caught by real-checkpoint validation rather than by any test. `src/vision/jina_vlm.rs:214` avoids repeating it by delegating explicitly:

```rust
fn sequence_state_layout(&self) -> SequenceStateLayout {
    LanguageModel::sequence_state_layout(&self.text_model)
}
```

so `DenseKvCache` with 28 layers is declared regardless of what `supports_batching()` reports on the wrapper. A regression test asserts both the backend and the layer count, and the path was confirmed live on the server rather than assumed correct from the test alone.

### 2.6 Security and performance fixes

Four HIGH-severity issues were found during review and fixed before merge:

- **Shared Molmo embedding regression.** `Molmo2Embedding::forward` (`src/models/molmo2.rs`) concatenated a BF16 `[151936, 2048]` table, 622 MB, on every decode token just to gather one row. Because `Molmo2Embedding` is shared by `molmo.rs`, `molmo_point.rs`, and now `jina_vlm.rs`, this was a live regression on three model families, not a new-code issue. The concatenation was hoisted into `from_weights` and evaluated once at load time, giving 83 to 148 tok/s, a 1.79x improvement, with byte-identical output; byte-identity was confirmed independently by control-running `molmo-7b` on `main` and on the branch and comparing output.
- **Image-processor memory.** `src/vision/processors/jina_vlm.rs:158` originally widened the full decoded source image to `Vec<f32>` before any resize bound applied, 12 bytes per source pixel. A roughly 300 KB, 16384x16384 grayscale PNG reached about 4.3 GB peak RSS from that alone. The fix samples the 8-bit source directly inside the bilinear resize (`resize_bilinear_u8`) and only widens the already-bounded, `max_pixels`-capped destination to `f32`; peak RSS at a 12000x12000 source went from 3.11 GB to 1.69 GB and is now flat in source resolution.
- **Quadratic scatter.** The image-feature merge in `src/vision/jina_vlm.rs` originally built a dense `one_hot(target_positions) @ active` matrix to splice pooled features into the prompt embeddings, quadratic in image count because both the sequence length and the target-row count grow with it. A 16-image request built a multi-gigabyte one-hot matrix and ran a teraflop-scale matmul on the single serialized model thread just to move a few tens of thousands of rows. It was replaced with `scatter_add`, which is the same operation: the merge is additive, every non-selected one-hot term was an exact `0.0 * x`, so `scatter_add` reproduces it at the cost of only the rows actually written.
- **Silent-garbage config hazard.** Head geometry (`num_attention_heads`, `num_key_value_heads`, `head_dim`) was originally read only from the OLMo-nested `block_config.attn_config`, with no HF-flat alias. A checkpoint variant shipping a flat HF `text_config` would silently fall back to the released 3B defaults while every slice stayed in-bounds, producing fluent output with the attention heads sliced against the wrong offsets and no error anywhere. `src/models/jina_vlm.rs` now accepts both the OLMo and the HF spelling (OLMo wins when both are present, so the released checkpoint is unaffected), and `validate_fused_qkv_geometry` cross-checks `(num_attention_heads + 2 * num_key_value_heads) * head_dim` against the actual row count of the loaded `attn.qkv` tensor, for both the dense and the quantized case, at load time rather than at the first wrong forward pass.

Beyond those four, several unbounded-input paths were closed defensively: `patch_size`, `pooling_h`, and `pooling_w` each reach a divide site (`crop_patches`, `token_length`, the pooled-grid pad width), so `src/loading/vlm_jina_vlm.rs` rejects (rather than clamps, following the `vlm_locateanything` precedent) values outside `1..=1024`, since a zero is a divide-by-zero panic that a release-profile fail-fast worker turns into a process kill, and a negative reaches `mlxcel_core::pad` as an uncatchable abort across the cxx bridge rather than a `Result`. `pos_embed` and `pad_embed` tensor ranks are checked before use. Margins that would leave zero patches for the crop window are rejected outright, because the alternative, a saturating subtraction that only prevents a panic, would still leave the pooled-grid loop with nothing to tile against and hang the worker; a config that lets that subtraction wrap in a release build was independently identified as capable of driving the same loop into an effectively infinite spin.

### 2.7 Security verdict

Attacker-controlled chat content cannot destabilize the server through this path. The built-in template is a `const &'static str`, never sourced from request data; user content reaches minijinja only as a `Value::from_serialize` data binding, never as template source; the typed `content` shape is an internally-tagged serde enum, so a malformed part shape is rejected with a 400 before the template runs at all; minijinja's fuel bound caps runaway renders; and a render failure degrades to the existing fallback with a warning rather than propagating an error to the client.

## 3. Technical Decisions

### 3.1 Built-in chat template as a last resort, never an override

**Context:** The MLX conversion drops the vendor `chat_template.jinja`, and the server needs a usable default for this checkpoint.

**Alternatives Considered:**

| Option | Pros | Cons |
|--------|------|------|
| Always prefer the built-in template for `model_type: jvlm` | Guarantees the checkpoint's own prompt shape | Silently shadows a template a future re-conversion might actually ship, which would then be invisible |
| Leave the generic fallback as-is | No new code surface | The model answers factual questions wrong (`17` instead of `Paris`); this is the status quo the issue exists to fix |
| **Chosen: consult the built-in only after `tokenizer_config.json`, `chat_template.jinja`, and `chat_template.json` all come up empty** | A checkpoint that does ship its own template is never shadowed; a template-less one still gets the right prompt shape | The resolution order has to be documented so a future template source is not added in the wrong place |

**Rationale:** the fallback exists to compensate for a conversion artifact, not to assert authority over what a checkpoint declares. Ordering it strictly after every declared source keeps that boundary and is enforced by a dedicated test (`a_declared_template_is_never_shadowed_by_the_built_in`).

### 3.2 Reject invalid vision-config divisors instead of clamping

**Context:** `patch_size`, `pooling_h`, and `pooling_w` are each consumed as a divisor at four separate sites in the vision loader and the connector.

**Alternatives Considered:**

| Option | Pros | Cons |
|--------|------|------|
| Clamp to a minimum of 1 | Never fails to load | The image processor reads the same three fields from `preprocessor_config.json` independently; clamping only the vision-config copy desynchronizes the pooled feature count from the `<im_patch>` count the processor emits, trading a loud failure for a quiet mis-computation |
| Leave unchecked | Simplest | A zero panics on the first image request under a release-profile fail-fast worker (killing the whole process, not just the request); a negative reaches `mlxcel_core::pad` as an uncatchable abort across the cxx bridge |
| **Chosen: reject values outside `1..=1024` at load time, matching the `vlm_locateanything` precedent** | Fails once, at load, with a message naming the field and the checkpoint's own numbers; never reaches the divide or the pad call | A config that would have "worked" by accident under a permissive read now refuses to load |

**Rationale:** the two independent copies of these fields (vision config and processor config) is the deciding factor: any silent repair of one copy alone breaks agreement with the other in a way that is far harder to diagnose than a load-time refusal.

## 4. Validation

CLI, GB10 (CUDA, sm_121), release build, `models/mlx/jina-vlm-mlx` (4-bit, group 64), a real 640x480 photo of two cats on a pink couch with two remotes:

```
$ ./target/release/mlxcel generate -m models/mlx/jina-vlm-mlx --image coco_cats.jpg \
    -p "Describe the image." -n 60 --temp 0.0
Jina VLM: inserted 1 image block(s) (814 image tokens, 824 total tokens)
In the image, two cats are comfortably resting on a pink couch. One cat is lying on its side, while the
other cat is lying on its back. Both cats are surrounded by two remote controls, one positioned closer
to the left cat and the other closer to the right cat.
```

Every grounded detail (cat count, couch color, remote count) is correct, and a second, more pointed question on the same image ruled out a generic caption by naming the same details back correctly.

Server, verified separately and after the content-type-loop fix in 2.4: an image request returns `prompt_tokens 824`, matching the CLI count, and produces the same text; a text-only request returns `prompt_tokens 16` and `Paris.` for the capital-of-France prompt; two concurrent image requests through the batch scheduler both answered correctly. Per 2.4, the token-count match alone is not treated as sufficient evidence here, since it was demonstrably insufficient once before on this same PR; the text-output comparison is the actual check.

Full CUDA merge gate on the merge candidate: 7655 passed, 5 failed. All 5 failures reproduce identically on `main` and were control-run there: 4 are TF32 accuracy artifacts that pass with `MLX_ENABLE_TF32=0`, and 1 is a pre-existing integer underflow in `resolve_paged_block_budget` unrelated to this change.

## 5. What Was Not Verified

- **No numeric parity against a PyTorch or mlx-vlm oracle.** Neither runs on this box. The evidence is grounded generation on a real photo plus the token-count arithmetic in 2.2 closing exactly, not a logit diff against a reference implementation.
- **Multi-image prompts are implemented but exercised with only one image.** Crops and blocks concatenate and `image_input_idx` offsets accumulate correctly by construction, but no multi-image request was run against the real checkpoint.
- **`forward_batched` falls back to the serial default.** `supports_batching()` reports `true`, but there is no batched-specific fast path yet; requests are still correct, just not batch-accelerated.
- **No prompt-length check against the context window before KV sizing.** This is a pre-existing, repo-wide gap, not specific to this model.
- **A literal `<|image|>` in user-supplied text steals a splice position.** The runtime does not currently distinguish a user-typed occurrence of the marker from one the template inserted.
- **Greedy image-path generation showed run-to-run nondeterminism on this checkpoint**, predating this change, isolated to the vision tower rather than to `scatter_add` or any matmul touched here. This is why the merge gate leans on bitwise unit tests (39 tests in `jina_vlm` alone, covering negative `vit_layers` resolution, fully padded crops, the pad-embedding mask, the pooled-patch-to-token bijection, and incremental-versus-full-sequence decode parity) rather than single-run byte-identical generation as the reliable check.

## 6. Lessons

- **Mis-routing on `model_type` is the most common way a port in this tree has failed, and it fails silently as "never loads" rather than as a wrong number.** The issue's own spelling did not match any checkpoint; treating the issue text as ground truth instead of the checkpoint would have shipped a model nothing could route to.
- **An upstream reimplementation is a starting point, not the reference; the checkpoint's own code is.** All three divergences in 2.3 were places where a well-maintained port (mlx-vlm) and the vendor code trained into the checkpoint disagreed, and all three fail silently in the direction of plausible-looking, wrong output.
- **A matching token count is not evidence that two front ends rendered the same prompt.** The PR's first parity claim held by coincidence while the underlying text differed; only comparing the actual generated output caught it.
- **A trait default that infers cache layout from an unrelated capability flag is a standing landmine.** The Falcon-OCR CRITICAL was one wrapper away from repeating here; the fix is to state the layout explicitly every time, not to trust the default and add a test after the fact.
- **When the reference model itself is nondeterministic on the code path under test, bitwise unit tests on the deterministic sub-pieces are the reliable gate, not single-run output comparison.** The image-path nondeterminism observed here predates the change and would have made a byte-identity check unreliable regardless of code correctness.
