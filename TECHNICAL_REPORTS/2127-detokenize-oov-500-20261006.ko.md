# 기술 보고서: 이슈 #2127 - POST /detokenize의 어휘 밖 id에 500 응답

**작성일**: 2026-10-06

**상태**: GB10에서 구현 및 검증 완료, 병합 대기.

**언어**: Rust (tokenizer, detokenize 라우트, 라우트 테스트), Markdown

**위험도**: 낮음 (클라이언트에 보이는 변화: 조용히 버려지거나 SentencePiece에서 400이던 id가 이제 500 `server_error`로 응답하며, 유효한 id는 변하지 않음)

## 요약

`POST /detokenize`는 어휘에 없는 id를 HuggingFace와 tiktoken 토크나이저에서는 버리고 200으로, SentencePiece에서는 400으로 응답했고, `-1`은 `as u32` 캐스트로 `4294967295`가 되었습니다. llama.cpp는 모두 500 `server_error`로 응답합니다. 호출자는 잘린 응답과 정상 응답을 구분할 수 없었습니다.

## 1. 변경

- `MlxcelTokenizer::contains_id`는 백엔드별 멤버십 검사입니다. HuggingFace는 `id_to_token(id).is_some()`(`decode`가 쓰는 조회와 같으므로 added 및 special 토큰도 포함), SentencePiece는 special 또는 added contents 또는 `id < processor.len()`, tiktoken은 `special_decoder` 또는 `decoder`입니다. 의도적으로 `id < vocab_size()`가 아닙니다. HuggingFace의 `vocab_size()`는 최대 id + 1이 아니라 항목 수이기 때문입니다.
- `DetokenizeRequest.tokens`는 `Option<Vec<i64>>`가 되어 `i32::MAX`를 넘는 id도 axum의 평문 422 대신 검사에 도달합니다.
- 핸들러는 디코딩 전에 모든 id를 검사합니다. 음수 id, `u32`에 맞지 않는 id, `contains_id`를 통과하지 못하는 id는 요청 순서상 첫 번째 잘못된 id를 클라이언트가 보낸 그대로 담아 `ErrorResponse::internal_server_error("token id {id} is out of vocabulary range (vocab_size {n})")`로 응답합니다. 부분 텍스트는 반환하지 않습니다. `decode`는 바뀌지 않았습니다.

## 2. 검증

- gpu-lock 아래에서 `cargo test --lib --features cuda server::routes::tokenize tokenizer:: -- --test-threads=1`이 신규 라우트 테스트 6개와 `tokenizer::contains_id_tests`를 포함해 모두 통과했습니다.
- 어휘 공백 테스트(id 0..=2의 항목과 id 10의 added 토큰이 있어 `vocab_size()`는 4)는 id 3을 거부하고 id 10을 수용하므로, `contains_id`가 `< vocab_size()`로 바뀌면 실패합니다.
- `cargo clippy --lib --tests --features cuda -- -D warnings`와 `cargo fmt --check`가 깨끗합니다.
- `qwen3-0.6b`로 release `mlxcel-server`를 띄운 실제 확인: `[999999999]`, `[9707,999999999,1879]`, `[-1]`, `[3000000000]`은 id와 `vocab_size 151669`를 명시한 500 `server_error`로 응답했고, `[9707,1879]`는 200 `Hello world`, `[]`는 200 `""`로 응답했습니다.

## 3. 비고

기존 `tower_http` trace 레이어가 모든 500에 대해 로그 한 줄을 남기므로 핸들러 수준의 로그는 추가하지 않았습니다. Continuum Router의 고정된 200 fixture는 이 변경이 반영된 뒤 다시 캡처해야 합니다.
