# PR #3448: Jamba hybrid (Mamba1 + attention + softmax MoE) on OpenXLA/IREE

**Date**: 2026-11-26

**Status**: CPU/CUDA acceptance passed; ROCm replay pending externally

## Executive Summary

Jamba now executes original Hugging Face weights through OpenXLA/IREE. Mamba1 and attention blocks interleave by `attn_layer_period` / `attn_layer_offset`, and dense and MoE feed-forwards alternate by `expert_layer_period` / `expert_layer_offset`. The Mamba1 mixer from #3348 gained learned dt/B/C RMSNorm weights, and the MoE block from the dense families is reused unchanged. Acceptance also exposed a shared IREE compile failure for every softmax-routed MoE ragged decode, fixed by compiling those decodes without aggressive dispatch fusion.

## Problem Statement

`from_json_str` rejected `jamba`. The existing Mamba1 `bcdt_norm` modelled Falcon-Mamba's weightless norms, while Jamba scales each normalized dt, B and C branch by a learned vector. Unlike pure SSM models, every Jamba block has a feed-forward after the mixer, so Mamba1 blocks need the full two-residual layer. The only public checkpoint, `ai21labs/AI21-Jamba-Reasoning-3B`, has `num_experts = 1`, so the real model cannot exercise MoE at all.

## Change Summary and Technical Decisions

`SsmKind::Mamba1` carries `BcdtNorm::{None, Weightless, Weighted}`. Falcon-Mamba keeps `Weightless` and its golden stays byte-identical. Jamba's config derives `layer_mixers` and per-layer FFN kind from the periods and offsets. Mamba1 blocks with an FFN take the general layer path (`input_layernorm`, mixer, `pre_ff_layernorm`, FFN), while FFN-free SSM layers in other families keep their short layout. Attention uses no RoPE. The KV cache spans the attention blocks only and the recurrent state the Mamba1 blocks only. The checkpoint cross-check validates every `mamba.*` tensor, the norm vectors and the expert weights.

Routing follows Hugging Face (softmax over all experts, top-k, no renormalization). The MLX eager path renormalizes over the top-k and is left unchanged. Only the stacked `switch_mlp` expert layout loads; a raw per-expert HF MoE checkpoint is refused at load.

With `--iree-dispatch-creation-enable-aggressive-fusion`, IREE fuses the router softmax into the top-k argmax and cannot lower the fused dispatch on llvm-cpu or CUDA. The existing Qwen2-MoE and OLMoE ragged decode goldens fail the same way on current main and compile without the flag, so this was a latent failure in every softmax-routed MoE family rather than a Jamba regression. `decode_compile_flags` omits the flag when `Config::has_softmax_moe()` is true. Sigmoid routing keeps it, and no emitted graph changes.

## Validation and Evidence Boundaries

The integrated runtime source is `b9b5545a`, rebased onto main `01e6516b` after Falcon-H1 plain RoPE (#3452) and Plamo2 (#3449); later commits add only evidence and documentation. The rebase keeps Plamo2's behaviour: its blocks still take the post-mixer norm and the SSM mixer weights through `layer_has_post_mixer_norm` and `MixerKind::is_recurrent()`, and `plamo2::offset_layer_norms` still wraps every layer's weights. On that source, every registered golden including PLAMO2, FALCON_H1 and JAMBA is byte-exact (584 lib tests), and `clippy -p mlxcel-xla --all-targets -D warnings` is clean. On GB10 CUDA, the Jamba 3B `validate_arch.sh` gate, the 40-token engine test, the CLI 40/40 oracle and the 8/8 concurrent server check all passed again, as did the Jamba synthetic MoE parity on both devices. The Plamo2 (synthetic, window probe, 40-token oracle), Falcon-H1 (synthetic, long positions to 3584, 40-token oracle), Mamba1/Mamba2 SSM single-sequence and state-carry, and Nemotron-H suites also passed on CUDA. The `integrated-*` files in `spike/openxla/jamba_reference/` record these runs.

The first acceptance ran on runtime source `76a3dc4c` on base `c5afefbd`. On GB10 CUDA, `validate_arch.sh --batch 4 --requests 8 --maxcap 24` with the native HF fp32 oracle exited 0: registered goldens, 40/40 token-exact, and 170 batched tokens reference-exact. The CLI matched the 40-token oracle, and four concurrent non-streaming and four SSE server completions matched the CLI's displayed text and token counts.

A seeded four-block, four-expert, top-2 synthetic Jamba is the only MoE evidence. Its router and dt/B/C norm weights are randomized, and the generator asserts that every expert pair is selected and that dropping the norm weights or renormalizing the top-k moves the logits far beyond the 3e-4 tolerance. It passed single-sequence, ragged and slot-recycle parity on local-task (max abs 2.0e-6) and CUDA (3.6e-6), plus CLI, `xla_oracle_check` and `xla_batch_bench` B=4 N=8 on both devices.

The `mlxcel-xla` lib tests passed with every previous golden byte-identical, and fmt, clippy, the prompt-cache/APC guard (Jamba gets neither), the env-var documentation check and the Used by check passed. Evidence and commands are in `spike/openxla/jamba_reference/`.

Not verified: ROCm `hip`, any real MoE Jamba checkpoint, raw per-expert HF MoE layouts, quantized Jamba, and real Qwen2-MoE / OLMoE checkpoints after the decode flag change.

## Learning Points and Follow-up

A real checkpoint that disables a feature (`num_experts = 1`) gives no evidence for it; a synthetic fixture must be built so that each omitted operation measurably fails. A compile flag applied to a whole graph family can hide a latent lowering failure until a new architecture reaches the affected path. Revisit the softmax-MoE exemption on the next IREE upgrade. Request an external ROCm replay on the final head before closing #3349.
