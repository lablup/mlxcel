**Date**: 2026-08-16
**Author**: AI Code Reviewer
**Status**: Completed
**Languages**: Rust, C++ (Metal kernel source)
**Risk Level**: Low (the pairing is gated off by default on every hardware generation measured so far; every dispatch site declines to classic decode rather than silently violating the exactness contract on an unsupported pairing)

---

## Executive Summary

PR #1182 (issue #1165) adds the split-out `qwen3_5_mtp` drafter (e.g. `mlx-community/Qwen3.8-27B-MTP-bf16`) as a first-class MTP drafter and implements mlxcel's `MtpTarget` trait for the Qwen 3.5 family (dense and MoE, text and VLM), so the existing `MtpGenerator` round loop, the tick-cooperative slice path, and the run-to-completion burst all drive this pairing exactly as they already drive Gemma 4. The result only ships correctly because of one specific numerical fix: the temperature-0 exactness gate initially failed with a near-tie argmax flip roughly once every 100-250 generated tokens, traced to the shared gated-delta Metal kernel carrying its recurrent state in float32 across a `T = K` verify block and quantizing to the storage dtype only at the final store, while the classic single-token decode chain quantizes after every token. A `T = K` block was therefore not bit-identical to `K` consecutive `T = 1` decode steps, and a last-ulp state difference flips near-tie logits. The fix is a chain-parity kernel variant (`gated_delta_step_seqpar`) that rounds the state through the storage dtype at the end of every in-block step, making the two shapes provably bit-identical (pinned in `parity_kernel_block_is_bitwise_equal_to_single_token_chain` and confirmed over full 240-token decode chains); it is used only by the speculative verify capture path and the rollback replay, so classic prefill and decode are untouched and DFlash inherits the same numerics for free through the shared `forward_speculative` path.

The measured hardware verdict is negative on the machine available for this PR: MTP decode measures **0.70x** classic at the drafter's own configured block size (3) and 0.59x at the historical block-4 default, on an Apple M1 Ultra. The cause is not a defect in the implementation, every diagnostic in the round loop is healthy, but a hardware ceiling: `verify_forward_cost_scaling` shows the target's own plain multi-token forward gains almost no amortization at this GPU generation's block sizes (about 29 ms per extra block position, roughly two-thirds of a full decode step, on both the verify path and the plain batched-prefill path equally). This is the same pre-M5 regression already encoded for Gemma 4 MTP in `mtp_b1_default` (issue #165: M1 Ultra 0.75-0.96x, M5 Max 1.2-1.4x), and the adaptive MTP policy (issue #333) gates Qwen 3.5 MTP through the identical static-default-plus-profiling mechanism, so a deployment on this hardware class declines to classic decode by default rather than silently regressing. The M5 cell (and M3/M4) for this specific pairing is open; the PR includes a reproduction guide in the issue thread for anyone with different hardware to fill it in.

The third load-bearing fact is a premise correction made before implementation started. The issue body originally scoped "the hard part" as inventing partial-acceptance rollback for a target that mixes 16 full-attention layers with 48 gated-delta linear layers, on the theory that a recurrent state cannot be trimmed and must be snapshotted and restored. That machinery already existed: `Qwen35Model::rollback_speculative_cache` implements exactly this for the DFlash path, trimming attention KV by the unaccepted tail and replaying gated-delta snapshots over the accepted prefix, and the verify pass already returns the hidden states an MTP drafter needs. The genuinely new work was therefore wiring, not cache surgery: a new drafter model, the `MtpTarget` trait implementation wrapping the existing verify/rollback surface, and lifting roughly a dozen Gemma-4-only gates across the server and offline CLI dispatch paths.

Review and security passes on the initial PR fixed two HIGH findings (commit `60ef14b2`) and one HIGH finding (commit `ef3aa95e`) before this finalization pass. This pass closed ten additional findings the review flagged: an unattributed benchmark that could report self-comparison noise as a result, a capability gate that checked Metal availability but not the chain-parity kernel's actual shape contract, a shipped default block size that the PR's own measurement showed was the slower of the two configurations, a C++ dispatch path that silently drops the chain-parity request on an unreachable-today shape, an unmeasured acceptance-under-concurrent-load cell reported as if it were the measured single-request number, a missing environment-variable doc entry, roughly ten stale Gemma-4-only doc claims, three now-false claims that the Qwen drafter's `reset` is a no-op, a 335 MB seed hidden state held a round longer than necessary, and dead `if (true)` scaffolding copied into the new Metal kernel source.

## 1. Problem Statement

### 1.1 Background

Issue #1165 established that Qwen3.8-27B's MTP head is not part of the target checkpoint in any MLX conversion: the upstream `Qwen/Qwen3.8-27B` base ships 15 `mtp.*` tensors alongside `model.*`, but every `mlx-community/Qwen3.8-27B-*` conversion drops them, and mlx-community republishes them as a standalone drafter (`mlx-community/Qwen3.8-27B-MTP-bf16`, `model_type: "qwen3_5_mtp"`, `block_size: 3`). Before this PR, `mlxcel generate --draft-model <that checkpoint>` failed with `Unsupported model type: qwen3_5_mtp` regardless of `--draft-kind`, both messages accurate and fail-closed, so this was a missing capability rather than a latent bug.

### 1.2 Existing Issues (from the review/security pass, addressed in finalization)

- **F1** (High, process/measurement integrity): `parity_kernel_cost_vs_standard` had no arm-attribution guard. With `MLXCEL_GDN_CHAIN_PARITY=0` in the environment, `gated_delta_update_chain_parity` silently falls back to the standard kernel (`chain_parity_enabled()` reads the env var), so both arms of the benchmark resolve to the same code path and the test would compare it against itself. The recorded ratios (1.089 / 1.117 / 0.834 / 1.008) were indistinguishable from that failure mode, precisely the pattern CLAUDE.md's "prove the two arms differ before reporting any number" rule targets (epic #909 named three prior benchmarks with this exact defect).
- **F2** (High, correctness): `mtp_capable_target` gated the Qwen 3.5 family on `metal_is_available()` alone. Byte-identity additionally requires `supports_metal_gated_delta_kernel(hk, hv, dk, dv)` (`dk >= 32 && dk % 32 == 0 && hv % hk == 0`); a Metal host whose checkpoint has an incompatible `linear_key_head_dim` would silently take the ops-based fallback and forfeit the temperature-0 exactness contract with no signal. The tree's own test fixtures already use `linear_key_head_dim: 4` (not a hypothetical shape).
- **F3** (Medium, performance/correctness of defaults): `prefer_requested_block_size() = true` for the Qwen drafter means the drafter's own `configured_block_size()` (3) was never consulted; the per-kind CLI default (4, a Gemma-4-derived constant) always won. The PR's own measurement shows block 3 at 16.48 tok/s / 0.591 acceptance versus block 4 at 13.81 / 0.465, so the shipped default was the slower measured configuration.
- **F4** (Medium, defense in depth): the C++ dispatch in `metal_gated_delta_forward_impl` silently takes the standard kernel branch whenever the gate is vectorized or a mask is present, even when the caller requested `chain_parity = true`. Not reachable from the Qwen 3.5 verify path today (`mask = None`, `g` is always 3-dim there), but nothing enforced that, so a future caller could forfeit byte-identity with no signal.
- **F5** (Medium, documentation honesty): the benchmark record's 0.591 acceptance figure is single-request only; it did not state that `Qwen35MtpDraftModel::reset` destroys the drafter's accumulated KV history (unlike Gemma 4's no-op reset) and fires on every park during concurrent slice-grant rotation, so acceptance under load is structurally worse and was not characterized.
- **F6-F10** (Low, documentation and cleanup): `MLXCEL_GDN_CHAIN_PARITY` was undocumented in `docs/environment-variables.md`; roughly ten module/API doc comments across `speculative_slice.rs`, `speculative_burst.rs`, `scheduler.rs`, `drafter/mod.rs`, and `speculative/mtp/{mod,generator}.rs` still asserted MTP was Gemma-4-only; three of those also claimed the MTP `Drafter::reset` is universally the trait-default no-op, which is false for the Qwen drafter; the seed-round `verify_hidden_full` (`[1, P, H]`, about 335 MB at P=32k/H=5120 in f16) was held alive through an entire round after its one-shot consumer instead of being cleared immediately; and the new chain-parity Metal kernel source carried a dead `if (true) { ... }` wrapper copied from the masked kernel variant.

### 2.2 Performance

The measured verdict (see Executive Summary and `docs/benchmark_results/qwen38-mtp-m1ultra-2026-08-16.md`) is negative on the one hardware generation available for this PR, and F3's fix changes which negative number ships by default (0.70x at block 3, versus 0.59x at the pre-fix block-4 default). Both remain below the 1.0x break-even the adaptive MTP policy uses to decide engagement, so the practical effect of F3 is a better-informed default for the case where the policy is bypassed (`MLXCEL_ENABLE_MTP_B1` pinned on, or profiling disabled), not a change in whether the pairing engages by default.

F1's re-measurement after adding the arm-attribution guard produced five fresh runs, medians 0.979 / 1.007 / 0.994 / 1.022 at T=1/3/4/64 (min-max 0.877-1.043 across runs), still inside the dispatch-noise band the original (unattributed) numbers claimed, but now provably attributable: the guard dispatches both kernels once at `T=3`, asserts their final GDN state differs (which the two kernels are defined to do whenever `T > 1`), and panics before printing anything if that assertion fails. The corrected numbers differ from the originally recorded ones at the individual-ratio level (this is expected: the original numbers were not attributable to begin with, and dispatch-level noise on a loaded box does not reproduce ratio-for-ratio across runs), but the qualitative conclusion, that the kernel's added per-step register round costs nothing measurable outside noise, is unchanged.

### 2.3 Compatibility & Dependencies

- **Breaking Changes**: none. `resolve_draft_block_size`'s signature gained a `model_path: &Path` parameter (F3's fix); both of its call sites (`src/server/speculative_dispatch.rs`, `src/commands/generate.rs`) already have the drafter path in scope at that point. `supports_metal_gated_delta_kernel` changed from private to `pub(crate)` (F2) with no external surface change.
- **New Dependencies**: none.
- **Behavior change**: an operator who runs `mlxcel generate --draft-model <qwen3_5_mtp checkpoint> --draft-kind mtp` (or the server equivalent) without an explicit `--draft-block-size` now gets block size 3 instead of 4, per F3. An explicit `--draft-block-size` override is unaffected. A Metal host whose target's GDN shape does not satisfy the parity kernel's contract now declines to classic decode (F2) instead of silently running without byte-identity; no published checkpoint is affected by this today.

### 2.4 Code Quality

- **Test Coverage**: this pass added `assert_parity_and_standard_arms_are_distinguishable` (the F1 guard, `tests/qwen38_mtp_chain_parity.rs`), three tests for `Qwen35Model::supports_chain_parity_kernel` / `qwen35_config_supports_chain_parity_kernel` (F2, `src/models/qwen3_5.rs`), five tests for `resolve_draft_block_size` and `peek_qwen35_mtp_configured_block_size` across the `mlxcel` and `mlxcel-core` crates (F3), and `chain_parity_forfeited_by_shape_matches_the_cpp_dispatch_branches` plus the underlying pure predicate (F4, `src/models/gated_delta.rs` / `_tests.rs`).
- **Code Complexity**: each fix is localized. F2 factors the GDN-shape check into `Qwen35Model::supports_chain_parity_kernel`, itself a thin wrapper over a free function (`qwen35_config_supports_chain_parity_kernel`) taking a bare `&Qwen35Config`, kept separate specifically so it is unit-testable without constructing a full model with real weights. F4 similarly factors the C++ shape predicate into a pure `chain_parity_forfeited_by_shape(bool, bool) -> bool` so the warning condition is testable without a Metal device.
- **Technical Debt**: decreased. The benchmark record now states its own attribution mechanism rather than asserting a number; the capability gate and the CLI default both now reflect the checkpoint's own declared shape/config instead of a Gemma-4-derived constant applied uniformly across an unrelated drafter family; and roughly a dozen doc sites that would have misled the next contributor into thinking Qwen 3.5 MTP support does not exist, or that its drafter reset is a no-op, are corrected.

## 3. Technical Decisions

### 3.1 Arm-attribution guard: assert-and-panic before the table, not a printed caveat

**Alternatives Considered:**

| Option | Pros | Cons |
|--------|------|------|
| Print a warning alongside the numbers when attribution cannot be confirmed | Keeps the test running, numbers still visible | Exactly the failure mode CLAUDE.md's rule targets: numbers get quoted regardless of the caveat |
| **Chosen: panic before printing any ratio if the arms are provably identical at `T=3`** | No route to a misleading number reaching a report; failure message names the likely cause (`MLXCEL_GDN_CHAIN_PARITY=0`) | The whole `--ignored --nocapture` invocation aborts on the check failing, rather than degrading gracefully |

**Rationale:** the review explicitly named "make the test refuse to report when attribution fails" as the requirement; a warning-and-continue design still lets a copy-pasted number end up in a document. `T = 1` cannot serve as the discriminator (the two kernels are defined to be byte-identical there), so the check runs once at `T = 3`, matching the shape already pinned bitwise-different by the sibling `parity_kernel_block_is_bitwise_equal_to_single_token_chain` test.

### 3.2 Capability gate: fold the shape predicate into `mtp_capable_target`, not a warning

**Alternatives Considered:**

| Option | Pros | Cons |
|--------|------|------|
| Emit a one-time `tracing::warn!` when parity is requested but the shape is incompatible, keep serving | Minimal code change | The exactness contract is documented as absolute ("temperature-0 output byte-identical to classic decode"); a warning does not stop a wrong answer from reaching a client |
| **Chosen: fold `supports_metal_gated_delta_kernel` into `mtp_capable_target` itself** | A checkpoint that cannot honor the contract declines to classic decode automatically, the same fail-closed posture every other MTP gate in this codebase already uses | Requires exposing the shape predicate from `mlxcel-core` and adding a config-reading accessor on `Qwen35Model` |

**Rationale:** the review offered both options; "better" was explicitly named as folding the predicate into the gate. Given every other MTP capability check in this tree (Metal availability, target/drafter compatibility, hidden-size and vocab match) already declines rather than warns, a warn-only fix here would have been the one exception to an otherwise-consistent fail-closed design.

### 3.3 Block-size default: peek the drafter's own config, don't change the shared per-kind constant

**Alternatives Considered:**

| Option | Pros | Cons |
|--------|------|------|
| Change `DEFAULT_MTP_BLOCK_SIZE` from 4 to 3 | One-line fix | `DrafterKind::Mtp` covers both Gemma 4 and Qwen 3.5; this would change Gemma 4's default too, on evidence measured only for Qwen 3.5 |
| Flip `prefer_requested_block_size()` to `false` for the Qwen drafter | Reuses the existing adaptive `effective_mtp_block_size` machinery | Upstream mlx-vlm sets `prefer_requested_block_size = True` specifically for this drafter; flipping it breaks that parity for a reason unrelated to the actual bug (the bug is what value gets treated as "requested", not whether the requested value should be preferred) |
| **Chosen: peek the drafter checkpoint's own `block_size` and use it as the default "requested" value when the operator passes no explicit override** | Fixes the actual defect (a Gemma-4 constant standing in for "no request" on an unrelated family) without touching Gemma 4's default or upstream parity; scoped narrowly via a `model_type == "qwen3_5_mtp"` check so a same-named field on any other drafter shape is never misread | Touches the shared `resolve_draft_block_size` signature (adds a `model_path` parameter), both of its call sites, and adds a new narrow peek function in `mlxcel-core` |

**Rationale:** the actual defect is upstream of `prefer_requested_block_size` entirely: the "requested" value itself was never actually requested by the operator, it was a flat constant standing in for "unset." Reading the specific checkpoint's own declared value when nothing was explicitly requested addresses the defect at its source and generalizes to any future Qwen 3.5 MTP checkpoint that ships a different `block_size`, rather than hardcoding today's measured value.

### 3.4 C++ dispatch warning: `eprintln!`, not `tracing::warn!`

**Rationale:** matches existing precedent in this tree (`report_fused_rope_bypass_once` in `src/models/llama3.rs`): only `mlxcel-server` installs a tracing subscriber unconditionally, the offline `mlxcel` CLI only does so when `RUST_LOG` is set, and the chain-parity path is reachable from both binaries. A `tracing::warn!` here would be silently swallowed on the CLI in the common case.

### 4.3 F3: drafter-configured block-size default (`src/lib/mlxcel-core/src/drafter/mod.rs`, `src/cli/speculative_args.rs`)

```rust
// drafter/mod.rs
pub fn peek_qwen35_mtp_configured_block_size(model_path: &Path) -> Option<usize> {
    let peek = read_drafter_config_peek(model_path)?;
    if peek.model_type.as_deref() != Some(QWEN35_MTP_MODEL_TYPE) {
        return None;
    }
    peek.block_size
}

// speculative_args.rs
pub fn resolve_draft_block_size(
    override_value: Option<u32>,
    kind: DrafterKind,
    model_path: &std::path::Path,
) -> u32 {
    if let Some(n) = override_value {
        return n;
    }
    if kind == DrafterKind::Mtp
        && let Some(configured) = mlxcel_core::drafter::peek_qwen35_mtp_configured_block_size(model_path)
        && let Ok(n) = u32::try_from(configured)
    {
        return n;
    }
    default_block_size_for_kind(kind)
}
```

## 5. Premise Correction: the recurrent rollback already existed

The issue body's implementation plan stated: "The rollback is the hard part: partial acceptance must trim the KV of the 16 full-attention layers and restore the gated-delta recurrent state of the 48 linear layers to the accepted prefix. A recurrent state cannot be trimmed; it must be snapshotted before the draft block and restored on partial accept, or recomputed." A comment on the issue, filed before implementation began, corrected this: `Qwen35Model::rollback_speculative_cache` already implements exactly this for the DFlash path (attention layers trimmed by `block_size - (max(accepted) + 1)` with per-row tail zeroing for `B > 1`; gated-delta layers replayed from `GdnRollbackSnapshot` over the accepted prefix), and the verify pass already returns the hidden states an MTP drafter needs (`VerifyOutput { logits, hidden_states, gdn_states }`).

The corrected scope, wiring rather than cache surgery, is what actually shipped: `5bb9bd1d` adds the drafter and the `MtpTarget` adapter wrapping the existing verify/rollback surface without adding new recurrent-state machinery; `89bcbae6` lifts the Gemma-4-only gates. Both commits are consistent with the corrected premise, not the original one. Recording this here follows the project's own convention (`docs/code-guidelines.md` / CLAUDE.md performance-issue rules): a corrected premise, caught before implementation, is the deliverable for that half of the issue, not a footnote.

### Future Improvements (recorded as known limitations, not fixed here)

- **M5-class hardware is unmeasured for this pairing.** The Gemma 4 precedent (verify amortization holds, 1.2-1.4x on M5 Max) projects a positive sign, but no M5 machine was available. The issue thread includes a reproduction guide for filling this cell.
- **Acceptance under concurrent slice-grant rotation is uncharacterized.** F5 documents this as an explicit open cell rather than fixing it; filling it requires a multi-client load harness exercising the tick-slice grant-rotation path specifically, which is out of scope for this pass.
- **B > 1 batched MTP remains Gemma-4-only.** Qwen 3.5 MTP is B = 1 only by design (issue #1165's own scope); the batched adapter methods return `DrafterError::DraftFailed` per the trait default for this family, matching the documented limitation.
- Splitting an MTP head out of a raw HF checkpoint (so users are not solely dependent on `mlx-community/Qwen3.8-27B-MTP-bf16` continuing to exist) remains a deliberately deferred follow-up, tracked in the issue thread.
