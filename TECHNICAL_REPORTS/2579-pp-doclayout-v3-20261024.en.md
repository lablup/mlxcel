It accepts both released checkpoint layouts, emits original-image pixel boxes with dense one-based `reading_order`, and preserves RT-DETRv2's existing output contract when no order head exists.

The detector's numerical gates are closed on ROCm/gfx1151. ## Problem

Falcon-OCR's layout-aware mode needs PP-DocLayoutV3 boxes and learned reading order. Before this change, mlxcel could accept externally produced layout JSON but could not run PP-DocLayoutV3 itself. RT-DETRv2 has no learned page-order head, so its geometric fallback reads multi-column pages row by row.

## Implementation

### Shared detector boundary

`src/vision/detection/mod.rs` owns the shared `Detection`, `DetectionResult`, and `Detector` contracts. `load_detector` reads the exact `model_type` from `config.json` and dispatches `rt_detr_v2` or `pp_doclayout_v3`. PP detections carry `reading_order: Some(n)`; RT detections retain `None`.

The `detect` command sorts a fully ordered PP result by model order before serialization. When order is unavailable or mixed, it retains the established geometric fallback. JSON adds `reading_order` only when present, preserving RT-DETRv2's schema.

### Native PP-DocLayoutV3 graph

The new family implements:

- HGNetV2-L with asymmetric stem padding, grouped/light blocks, and four feature stages;
- the AIFI/FPN/PAN hybrid encoder and stride-4 mask-feature branch;
- mask-enhanced top-k query initialization;
- six deformable decoder layers with f32 grid sampling for half inputs;
- the mask-to-box path and GlobalPointer order head;
- strict output contracts for `logits [1,300,25]`, `pred_boxes [1,300,4]`, and `order_logits [1,300,300]`.

Configuration and checkpoint loading validate topology, checked allocation bounds, key sets, shapes, floating dtype, and finite values before inference.

### Two checkpoint layouts

The loader distinguishes provenance before renaming:

- `PaddlePaddle/PP-DocLayoutV3_safetensors` at `e4f489dc536556fc1be02b973ba06756e0d4a2ac`, with `model.*` keys and NCHW convolution tensors;
- `HashNuke/pp-doclayout-v3-mlx` at `cd50996ad0c7e35a7e20c27480f99cec1822cf7b`, with converted names and NHWC tensors.

Only tensors proven to come from the raw Paddle namespace are transposed. Mixed layouts and normalized-name collisions fail instead of depending on map iteration or ambiguous shapes.

### Processor and postprocessing

The processor converts input to RGB, stretches it to 800 x 800 through the pinned Torchvision-style uint8 bicubic path, applies the upstream division/normalization expression order, and retains the original dimensions for inverse box mapping. It performs bounded payload, dimension, and allocation checks before expansion.

Postprocessing validates finite tensors and exact shapes, applies sigmoid, selects a global flat top-300 over query/class pairs, keeps scores at or above the threshold, and reconstructs order across all 300 queries before filtering. It preserves distinct numeric label ids even when class names repeat, keeps multiple labels from one query deterministic, sorts by learned order, and renumbers emitted entries to `1..N`.

### Arithmetic parity

The processor discrepancy came from expression order: the pinned route evaluates the zero-mean/unit-std transform as pixel division by 255, while the first Rust version multiplied by a rounded reciprocal. The corrected processor matches both layouts with maximum absolute error zero.

Independent reviews also covered scoped corrections for host positional encoding, fast SDPA, and deformable grid sampling. The final stage diagnostic compares 91 captures: 90 are byte-identical. The sole non-identical entry is the bypassed `decoder.encoder_coordinates` diagnostic, at maximum absolute error `4.76837158203125e-7`; all executed AIFI, decoder, top-query, GlobalPointer, and public raw-output stages are byte-identical. This stage comparison is supporting localization evidence. The acceptance result is the separate source-bound raw parity test, which passes both layouts with zero maximum and RMS error for every public tensor.

### Inherited Falcon integration corrections

The end-to-end run exposed two pre-existing Falcon-OCR integration defects that #2412 had to correct.

First, Falcon's fused `w13` tensor stores gate and up rows interleaved. Splitting it produced two numerically correct but row-strided views. ROCm's M >= 2 matrix path handled those views, while its one-token M = 1 GEMV path read the layout as dense and returned incorrect projections. Replaying the actual released weights and actual Rust decode input reproduced the bad Rust bytes from the strided views: gate/up maximum errors were `2.90893816947937` and `4.000600755214691`. Materializing the same values contiguously reduced each actual-size projection's maximum error to `9.5367431640625e-7` against the f64 dot reference. The fix materializes only Falcon's two deinterleaved planes once during load. It does not change model values, vendor EPSILON constants, KV-cache semantics, or the shared backend matmul/GEMV implementation.

Second, Falcon preprocessing previously mapped the reference's two Pillow bicubic RGB8 passes to `image` crate Catmull-Rom. The corrected path converts to RGB before both resize stages and uses the shared fixed-point Pillow bicubic implementation. This is separate from the PP detector's pixel-division correction. The authenticated Falcon title probe reports processor maximum error, RMS error, and differing-value count all equal to zero.

The focused correction binary passes the actual-size M = 1 regression and both direct-model and `DirectEngine` title probes. Each emits tokens `[526, 969]`, matching the authenticated Python reference. This closes the isolated root cause and engine boundary; the separately preserved full-page acceptance below closes the page-level contract on the captured source.

### Falcon-OCR handoff

The public flow remains explicit:

```bash
mlxcel detect -m models/PP-DocLayoutV3 -i page.png --format json > regions.json
mlxcel generate -m models/falcon-ocr \
  --image page.png \
  --layout-detections regions.json
```

The Falcon stage preserves file order while mapping labels to OCR prompts, skipping textless classes, collapsing duplicate boxes after category mapping, rejecting unusable crops, and falling back to a whole-page plain region when nothing remains. Automatic in-process detector execution inside `generate` remains outside #2412.

Both authentic detector commands exit 0 and produce the same byte-for-byte JSON: 16 detections with contiguous order `1..16`. The earlier Falcon child also exited 0, but its text was invalid and the enclosing integration test exited 101 because the required Introduction anchor was absent. That failure remains preserved, and the anchor contract was not relaxed.

With the scoped Falcon fixes, the full run drops three nested boxes and sends 13 ordered regions to OCR. It produces 1,109 tokens and contains all three required anchors in order: `Introduction`, `Language model pre-training`, then `There are two existing strategies`. The transcript SHA-256 is `d202733dbaa3157741f1953a1178f685d411073372d4e8f9318bcf30adf8472d`; detector JSON SHA-256 is `877e6a5a7562d89b031414968bc83b6589062110ba9fbae750550cad7241ec69` for both layouts.

## Compatibility and limits

- The user flow is two commands; PP detection is not automatically invoked inside Falcon generation.
- The public detector surface is image/file based and outside the token-generation/server runtime.
- The detector targets the two pinned released layouts above; no broader checkpoint-family claim is made.
- The PR also carries the necessary Falcon-only contiguous W13 materialization and exact Pillow preprocessing corrections exposed by the required integration gate. Shared backend matmul/GEMV, vendor EPSILON constants, and cache semantics remain unchanged.
- Metal and CUDA were not validated in this work.
- No throughput, latency, memory benchmark, or comparative performance result is available.
- Historical numerical and Falcon closure remain bound to their original binaries and manifests. The corrected-native reruns are separately bound to `90dc24a7...` and the 75-entry integration packet. The final report still needs the report-bearing head, CI result, and merge identity.
