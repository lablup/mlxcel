**날짜**: 2026-08-07
**작성**: mlxcel 메인테이너
**검토**: 구현 및 보안 리뷰 사이클
**상태**: 완료

**위험도**: 중간 (새 모델 계열, 병합 전 수정된 HIGH 등급 발견 4건, 수치 오라클 대조 없음)

## 요약

PR #1076은 Jina AI의 소형 다국어 VLM을 추가한다. SigLIP-so400m급 ViT(hidden 1152, 27층, 패치 14, 378x378 입력, CLS 토큰 없음)가 Molmo 스타일 커넥터를 거쳐 Qwen2급 디코더(hidden 2048, 28층, head_dim 128, 쿼리 16 / KV 8 헤드, 헤드별 Q/K RMSNorm, rope_theta 1e6, bias 없음)로 들어간다. 이슈 #849는 설정 키를 `jina_vlm`으로 적었지만, 배포된 체크포인트 중 그 값을 가진 것은 없고 전부 `jvlm`이며, 라우팅은 그에 맞춰지고 `jina_vlm`은 별칭으로만 남았다. mlx-vlm 레퍼런스가 체크포인트 자체의 벤더 코드와 어긋나는 세 지점을 벤더 코드 쪽으로 확정하고 테스트로 고정했다. 검증 도중 발견된, 이슈에는 없던 챗 템플릿 결함은 한 겹 더 있었다. 서버가 넘기는 타입 있는 다중 파트 `content`가 첫 번째 수정을 조용히 깨뜨렸고, PR 자신이 내세운 "서버에서 824 프롬프트 토큰, CLI와 동일"이라는 대조 증거는 실제로 두 프런트엔드가 같은 프롬프트를 렌더링했다는 증거가 되지 못했다. 바로 앞선 VLM 포트(Falcon-OCR, PR #1075)에서 나온 알려진 함정은 설계로 미리 피했다. 병합 전 HIGH 등급 문제 넷을 찾아 고쳤다. 다른 Molmo 계열 세 모델과 공유하는 디코드 스텝당 622MB 임베딩 연결, 원본 해상도에 비례해 커지는 이미지 프로세서 메모리, 이차 시간 원-핫 scatter, HF/OLMo 키 별칭 누락으로 인한 조용한 오작동 위험이다. 전체 CUDA 테스트 게이트는 `main`과 동일한 결과였다(통과 7655, 사전부터 있던 실패 5). 27개 파일, +5204/-13, 병합 커밋 `6026fe8f`.

## 1. 문제 정의

### 1.1 배경

이슈 #849는 `jina_vlm` 지원을 요청하면서 구현 레퍼런스로 상류 `mlx-vlm` 포트(`Blaizzy/mlx-vlm/mlx_vlm/models/jina_vlm/`)를, 체크포인트로 `jinaai/jina-vlm` / `jinaai/jina-vlm-mlx`를 지목했다. 아키텍처는 이렇다. 27층 SigLIP-so400m급 ViT가 두 중간 층의 특징을 채널 축으로 연결해 내놓고, 윈도우별 평균을 단일 쿼리로 쓰는 잠재 크로스 어텐션 블록으로 2x2 공간 풀링한 뒤, SwiGLU 프로젝터가 그 결과를 OLMo식 텐서 배치를 쓰는 Qwen2급 텍스트 디코더(융합 `attn.qkv`, 융합 `ffn.gate_up`, 헤드별 Q/K RMSNorm, 분리된 `lm_head`)로 투영한다.

### 1.2 기존 문제

- **이슈의 `model_type`이 어떤 체크포인트와도 맞지 않는다.** 이슈 본문은 `jina_vlm`이라 적었지만, `jinaai/jina-vlm-mlx`의 `config.json`은 최상위와 `text_config.model_type`, `vision_config.model_type` 양쪽 모두 `jvlm`이다. `architectures`는 `["JinaVLMForConditionalGeneration"]`이고 `auto_map`은 `modeling_jvlm.JinaVLM`을 가리킨다. `jina_vlm`은 mlx-vlm이 쓰는 모듈 이름일 뿐이다.
- **mlx-vlm 포트는 레퍼런스가 아니라 재구현이다.** 체크포인트 자신의 벤더 코드(`modeling_jvlm.py`, `blocks_jvlm.py`, `image_processing_jvlm.py`)와 ViT 층 선택, 토큰 그리드 산술, 커버리지 마스크 패딩에서 어긋나며, 셋 다 조용히 어긋난다. 오류를 내는 대신 출력 품질만 낮아진다.
- **MLX 변환판이 챗 템플릿을 빠뜨렸다.** `jinaai/jina-vlm`은 `chat_template.jinja`를 담고 있지만, `jinaai/jina-vlm-mlx`와 그 `tokenizer_config.json` 둘 다 없다. 그래서 서버는 다른 프롬프트 관례에 맞춰진 범용 템플릿으로 대체된다.
- **알려진 캐시 레이아웃 함정.** 바로 앞의 VLM 포트인 PR #1075(Falcon-OCR)는 `sequence_state_layout()` 트레이트 기본 구현이 `supports_batching() == false`로부터 빈 외부 캐시를 추론해, 서버가 디코더 레이어를 0개 돌리는 CRITICAL을 조용히 출하한 전례가 있다. 새 `LanguageModel` 래퍼는 모두 이걸 되풀이할 후보다.
- **디코드 스텝당 비용을 지는 공유 코드.** `molmo.rs`, `molmo_point.rs`, 이제 `jina_vlm.rs`까지 함께 쓰는 `Molmo2Embedding`이 기본 테이블과 확장 테이블의 연결을 매 디코드 스텝을 도는 `forward` 안에서 수행하고 있었다.

### 1.3 위험 평가

| 위험 | 영향 | 발생 가능성 |

## 2. 기술 검토

### 2.1 라우팅: `jina_vlm`이 아니라 `jvlm`

`src/models/detection.rs:328-331`은 `"jvlm" | "jina_vlm"`으로 라우팅한다. 배포된 모든 체크포인트가 실제로 선언하는 값을 우선 매칭하면서, 손으로 고친 설정을 위해 이슈의 철자도 허용된 별칭으로 남긴다. 유닛 테스트가 각 철자로 임시 `config.json`을 만들어 둘 다 `ModelType::JinaVLM`에 도달하는지 확인한다. 분명히 짚어 둘 만하다. `model_type` 오라우팅은 이 트리에서 포트가 실패하는 가장 흔한 방식이고, 미묘한 수치 오류가 아니라 "모델이 아예 로드되지 않는다"는 형태로 실패한다. 그래서 이 확인이 일회성 수동 검증이 아니라 고정된 테스트로 존재한다.

### 2.2 체크포인트 구조

`jinaai/jina-vlm-mlx`는 4비트로 양자화됐고(`bits: 4`, `group_size: 64`) bf16 텐서가 섞여 있다. 총 956개 텐서로, `vision_model` 491개, `language_model` 446개, `vl_connector` 19개로 나뉜다. 로더 설계에 영향을 준 사실들이다.

- `language_model.embedding.embedding`은 `[151936, 2048]`이고, *별도로* `language_model.embedding.new_embedding`이 `[128, 2048]`이다. `Molmo2Embedding`이 이미 모델링하고 있는 기본+확장 분리 테이블 구조다.
- `language_model.lm_head`는 양자화돼 있고 임베딩과 분리(untied)돼 있다.
- `vision_model.patch_embed.proj.weight`는 `[1152, 588]`이고, `588 = 14*14*3`이다. Conv2d가 아니라 이미 패치화된 픽셀에 대한 선형 투영이다.
- `vision_model.pos_embed`는 `[729, 1152]`이고, `729 = 27*27`이다. `378/14`에서 나오는 패치 그리드다.
- `vl_connector.pooling.q`는 2304폭 입력을 받는데, 이는 두 ViT 층을 연결한다는 사실(`2 * 1152 = 2304`)을 독립적으로 재확인해 준다.
- `pooling.kv`와 `projector.gate_up`은 융합 텐서다.
- `<|image|>`는 토큰 id 151940이고, 128개 확장 테이블은 151936부터 시작한다(`<im_start>` 151936, `<im_end>` 151937, `<im_patch>` 151938, `<im_col>` 151939).

실제 이미지 하나로 산술이 끝까지 맞아떨어진다. 640x480 사진이 `smart_resize`를 거쳐 644x476이 되고, 2x2로 타일링되어 크롭 토큰 602개와 썸네일 토큰 212개(이미지 토큰 814개, 텍스트 프롬프트를 더해 총 824개)를 낸다. 729패치짜리 크롭 5개가 980개 특징으로 풀링되고, 그중 772개가 유효한데, 이는 프로세서가 낸 `<im_patch>` 개수와 정확히 일치한다.

### 2.3 mlx-vlm 레퍼런스와 어긋나는 세 지점

셋 다 조용히 실패하기 쉬운 지점이고(오류 대신 설명 품질만 떨어진다), 셋 다 `jinaai/jina-vlm`에서 다시 내려받은 `modeling_jvlm.py` / `blocks_jvlm.py` / `image_processing_jvlm.py`와 독립적으로 대조했다.

1. **ViT 층 선택.** `get_visual_features`는 `post_lnorm` 출력을 `hidden_states`에 조건 없이 덧붙이므로, 27층 타워인데도 리스트 길이는 28이 된다. 그래서 `vit_layers: [-4, -10]`은 27짜리 리스트를 순진하게 음수 인덱싱했을 때 나오는 23·17이 아니라 층 24와 18을 고른다. 결과적으로 층 25, 26과 `post_norm`은 아예 로드되지 않는다.
2. **토큰 그리드 반올림.** 토큰 그리드는 `_molmo_get_patches_from_tiling`을 쓰는데, 이는 `crop_window + margin`을 풀링 크기의 배수로 *크롭마다* 올림한 뒤 합산한다. Molmo의 지름길(`tiles * window + margins`를 한 번만 올림)은 크롭 윈도우가 이미 짝수일 때만 일치한다. Molmo의 크롭 윈도우는 16패치(짝수)지만 Jina VLM은 19패치(홀수)다. 2x2 타일링에서 크롭별 반올림은 `ceil(23/2)*2 * 2 = 48`을 내는데, 지름길은 46을 낸다.
3. **커버리지 마스크 패딩 방향.** `image_processing_jvlm.py:805`은 `np.pad(img_mask, [[0, 1], [0, 0]], constant_values=-1)`로, 782번째 줄에서 썸네일 크롭을 픽셀 값 앞에 붙였음에도 마스크에는 끝에 sentinel 행을 붙인다. 그 결과 마스크는 앞쪽 `1.0` 행이 아니라 끝에 `-1` 행을 갖게 되어, 썸네일이 아니라 *마지막* 크롭이 부분적으로 패딩된 것처럼 읽힌다. 이건 상류의 off-by-one이고, mlxcel 자신의 Molmo v1 프로세서가 같은 구조에서 하는 것과 마찬가지로 여기서도 고치지 않고 의도적으로 재현했으며 테스트로 고정했다. 체크포인트가 바로 그 버그 있는 버전을 두고 학습됐기 때문이다.

### 2.4 챗 템플릿 결함

`jinaai/jina-vlm`의 MLX 변환판은 벤더의 `chat_template.jinja`를 빠뜨렸고, `tokenizer_config.json`에도 템플릿이 없다. 폴백이 없으면 서버는 범용 `User:\n\nAssistant: ` 템플릿을 렌더링해 "프랑스의 수도는?"에 `17`이라 답했다. `model_type`으로 키를 잡고 `tokenizer_config.json`, `chat_template.jinja`, `chat_template.json`이 모두 비어 있을 때만 참조하는 내장 템플릿(`src/server/chat_template.rs`)을 추가하자 같은 질문에 `Paris.`라 답했다.

이 템플릿의 첫 버전이 끝이 아니었다. 처음엔 `message['content']`를 문자열로 이어 붙였는데, 서버는 미디어 파트를 담은 요청이면 무엇이든 `apply_raw_with_kwargs`로 넘기고, 거기서 `content`는 문자열이 아니라 타입 있는 JSON 배열이다. 그래서 이미지가 포함된 서버 요청마다 `invalid operation: tried to use + operator on unsupported types string and sequence`가 로그에 찍혔고, 조용히 `render_simple_fallback`으로 떨어졌다. 애초에 PR이 내세운 대조 근거, 즉 "서버가 이미지 요청에 824 프롬프트 토큰을 보고했고 이는 CLI가 보고하는 수와 같다"는 실제로는 성립하지 않았다. 프롬프트 자체는 서로 달랐는데 토큰 수만 우연히 일치했던 것이고, 생성된 텍스트도 달랐다(같은 이미지와 질문에 대해 CLI는 "lying on its side", 서버는 "lying down on its side"). 수정은 상류의 `content['type']` 순회를 그대로 흉내 내 문자열 연결 대신 이미지 파트마다 리터럴 `<|image|>` 마커를 내보내는 것이었다. 수정 후 같은 요청에서 폴백 경고 횟수는 1에서 0으로 떨어졌고 두 프런트엔드는 바이트 단위로 동일해졌다.

이 교훈은 따로 짚어 둘 만하다. 토큰 수가 일치한다는 것은 두 프런트엔드가 같은 프롬프트를 렌더링했다는 증거가 되지 않는다. 실제로 렌더링된 텍스트, 그리고 그 아래의 모델 출력이 서로 다르더라도 토큰 수는 우연히 맞아떨어질 수 있다.

### 2.5 미리 피한 `sequence_state_layout()` 함정

`LanguageModel` 트레이트의 기본 `sequence_state_layout()`은 `supports_batching() == false`로부터 모델 자체 소유(외부 캐시 없는) 자리표시자를 추론한다. 바로 앞선 VLM 포트인 PR #1075(Falcon-OCR)가 정확히 이 틈을 출하했다. 서버가 빈 외부 캐시를 할당했고 `forward`는 패닉도 로그도 없이 디코더 레이어를 0개 돌렸다. 이는 어떤 테스트도 아니라 실제 체크포인트 검증에서야 잡힌 CRITICAL이었다. `src/vision/jina_vlm.rs:214`는 명시적으로 위임함으로써 이걸 되풀이하지 않는다.

```rust
fn sequence_state_layout(&self) -> SequenceStateLayout {
    LanguageModel::sequence_state_layout(&self.text_model)
}
```

그래서 래퍼의 `supports_batching()`이 뭐라고 답하든 상관없이 28층짜리 `DenseKvCache`가 선언된다. 회귀 테스트가 백엔드 종류와 층 수를 함께 검증하고, 이 경로는 테스트만으로 옳다고 가정하는 대신 서버에서 실제로 확인했다.

### 2.6 보안·성능 수정

리뷰 중 HIGH 등급 문제 넷을 찾아 병합 전에 고쳤다.

- **Molmo 공유 임베딩 경로 회귀.** `Molmo2Embedding::forward`(`src/models/molmo2.rs`)는 행 하나를 gather하기 위해 BF16 `[151936, 2048]`(622MB) 테이블을 디코드 토큰마다 연결하고 있었다. `Molmo2Embedding`은 `molmo.rs`, `molmo_point.rs`, 이제 `jina_vlm.rs`까지 공유하므로, 이는 새 코드의 문제가 아니라 세 모델 계열에 걸친 실제 회귀였다. 연결을 `from_weights`로 끌어올려 로드 시점에 한 번만 평가하도록 고쳤고, 83에서 148 tok/s로 1.79배 개선됐으며 출력은 바이트 단위로 동일했다. 이 동일성은 `main`과 브랜치 양쪽에서 `molmo-7b`를 대조 실행해 출력을 비교하는 방식으로 독립적으로 확인했다.
- **이미지 프로세서 메모리.** `src/vision/processors/jina_vlm.rs:158`은 원래 리사이즈 상한이 적용되기 전에 디코드된 원본 이미지 전체를 `Vec<f32>`로 확장했는데, 소스 픽셀당 12바이트가 든다. 약 300KB짜리 16384x16384 그레이스케일 PNG 하나만으로 피크 RSS가 약 4.3GB에 달했다. 수정은 bilinear 리사이즈(`resize_bilinear_u8`) 안에서 8비트 소스를 직접 샘플링하고, 이미 `max_pixels`로 상한이 걸린 목적지 크기만 `f32`로 확장하는 것이다. 12000x12000 소스에서 피크 RSS가 3.11GB에서 1.69GB로 줄었고, 이제는 소스 해상도에 비례해 늘지 않는다.
- **이차 시간 scatter.** `src/vision/jina_vlm.rs`의 이미지 특징 병합은 원래 풀링된 특징을 프롬프트 임베딩에 끼워 넣는 데 조밀한 `one_hot(target_positions) @ active` 행렬을 만들었는데, 시퀀스 길이와 타깃 행 수가 둘 다 이미지 개수에 비례해 커지므로 이차 시간이었다. 이미지 16장짜리 요청 하나가 수 기가바이트짜리 원-핫 행렬을 만들고 단일 직렬화된 모델 스레드에서 테라플롭급 행렬곱을 돌려 겨우 수만 개 행을 옮기는 셈이었다. `scatter_add`로 바꿨는데, 이는 같은 연산이다. 병합이 덧셈이고 선택되지 않은 모든 원-핫 항은 정확히 `0.0 * x`였으므로, `scatter_add`는 실제로 쓰인 행의 비용만으로 같은 결과를 낸다.
- **조용한 오작동을 낳는 설정 위험.** 헤드 기하(`num_attention_heads`, `num_key_value_heads`, `head_dim`)는 원래 OLMo 중첩 구조인 `block_config.attn_config`에서만 읽었고 HF 평탄형 별칭이 없었다. 평탄한 HF `text_config`를 담은 체크포인트 변종이 오면 모든 슬라이스가 범위 안에 있는 채로 배포된 3B 기본값으로 조용히 대체되어, 어텐션 헤드가 엉뚱한 오프셋으로 잘리면서도 오류 없이 그럴듯한 출력을 냈을 것이다. `src/models/jina_vlm.rs`는 이제 OLMo와 HF 철자를 둘 다 받아들이고(둘 다 있으면 OLMo가 우선이라 배포된 체크포인트는 영향받지 않는다), `validate_fused_qkv_geometry`가 `(num_attention_heads + 2 * num_key_value_heads) * head_dim`을 실제로 로드된 `attn.qkv` 텐서의 행 수와 대조한다. dense와 양자화 케이스 모두, 첫 잘못된 forward가 아니라 로드 시점에 확인한다.

이 넷 외에도 상한 없는 입력 경로 여럿을 방어적으로 막았다. `patch_size`, `pooling_h`, `pooling_w`는 각각 나눗셈 지점(`crop_patches`, `token_length`, 풀링 그리드 패드 폭)에 도달하므로, `src/loading/vlm_jina_vlm.rs`는 (`vlm_locateanything`의 선례를 따라 클램핑이 아니라) `1..=1024` 밖의 값을 거부한다. 0은 release 프로파일의 fail-fast 워커에서 프로세스 전체를 죽이는 0-나눗셈 패닉이 되고, 음수는 `Result`가 아니라 cxx 브리지를 넘는 잡을 수 없는 abort로 `mlxcel_core::pad`에 도달한다. `pos_embed`와 `pad_embed` 텐서의 랭크는 사용 전에 검사한다. 크롭 윈도우를 0으로 만드는 마진 조합은 통째로 거부하는데, 대안인 saturating subtraction은 패닉만 막을 뿐 풀링 그리드 루프가 타일링할 대상이 없는 채로 계속 돌아 워커를 멈추게 만들기 때문이다. 이 뺄셈이 release 빌드에서 wrap되도록 두는 설정 역시 같은 루프를 사실상 무한 루프로 몰아넣을 수 있음을 별도로 확인했다.

### 2.7 보안 결론

공격자가 통제하는 챗 콘텐츠는 이 경로로 서버를 불안정하게 만들 수 없다. 내장 템플릿은 요청 데이터에서 나오지 않는 `const &'static str`이고, 사용자 콘텐츠는 템플릿 소스가 아니라 `Value::from_serialize` 데이터 바인딩으로만 minijinja에 도달한다. 타입 있는 `content` 구조는 내부 태그를 쓰는 serde enum이라 잘못된 파트 모양은 템플릿이 실행되기도 전에 400으로 거부된다. minijinja의 fuel 상한이 폭주하는 렌더링을 막고, 렌더링 실패는 클라이언트에 오류를 전파하는 대신 경고와 함께 기존 폴백으로 내려간다.

## 3. 기술적 결정

### 3.1 내장 챗 템플릿은 최후 수단으로만, 우선순위로 쓰지 않는다

**맥락:** MLX 변환판이 벤더의 `chat_template.jinja`를 빠뜨렸고, 서버는 이 체크포인트에 쓸 만한 기본값이 필요했다.

**검토한 대안:**

| 선택지 | 장점 | 단점 |
|--------|------|------|
| `model_type: jvlm`이면 항상 내장 템플릿을 우선함 | 체크포인트 고유 프롬프트 모양을 보장 | 나중에 재변환된 버전이 진짜로 자기 템플릿을 담아 와도 조용히 가려버려 눈에 띄지 않게 됨 |
| 범용 폴백을 그대로 둠 | 새 코드 표면이 없음 | 사실 관계 질문에 틀리게 답함(`Paris` 대신 `17`). 바로 이 문제를 고치려고 이슈가 만들어졌다 |
| **선택: `tokenizer_config.json`, `chat_template.jinja`, `chat_template.json`이 모두 비었을 때만 내장 템플릿을 참조** | 자기 템플릿을 실제로 담아 오는 체크포인트는 절대 가려지지 않고, 템플릿 없는 체크포인트도 올바른 프롬프트 모양을 받음 | 참조 순서를 문서화해야 나중에 새 템플릿 소스가 엉뚱한 자리에 추가되는 걸 막을 수 있음 |

**근거:** 이 폴백은 변환 과정에서 빠진 걸 메우려는 것이지, 체크포인트가 선언한 것 위에 군림하려는 게 아니다. 선언된 소스 뒤에 엄격히 두는 순서가 그 경계를 지키고, 전용 테스트(`a_declared_template_is_never_shadowed_by_the_built_in`)로 강제된다.

### 3.2 비전 설정 나눗수는 클램핑하지 않고 거부한다

**맥락:** `patch_size`, `pooling_h`, `pooling_w`는 비전 로더와 커넥터의 서로 다른 네 지점에서 각각 나눗수로 쓰인다.

**검토한 대안:**

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 최소 1로 클램핑 | 로드가 절대 실패하지 않음 | 이미지 프로세서도 `preprocessor_config.json`에서 같은 세 필드를 독립적으로 읽는다. 비전 설정 쪽 사본만 클램핑하면 풀링된 특징 개수와 프로세서가 낸 `<im_patch>` 개수가 어긋나, 시끄러운 실패가 조용한 오계산으로 바뀐다 |
| 검사 없이 둠 | 가장 단순함 | 0은 release 프로파일의 fail-fast 워커에서 첫 이미지 요청에 패닉을 일으켜 요청 하나가 아니라 프로세스 전체를 죽인다. 음수는 cxx 브리지를 넘는 잡을 수 없는 abort로 `mlxcel_core::pad`에 도달한다 |
| **선택: `vlm_locateanything`의 선례를 따라 로드 시점에 `1..=1024` 밖의 값을 거부** | 필드 이름과 체크포인트 자신의 수치를 담은 메시지와 함께 한 번, 로드 시점에 실패한다. 나눗셈이나 pad 호출에는 결코 도달하지 않는다 | 우연히 "동작"했을 법한 설정도 이제는 로드를 거부한다 |

**근거:** 이 세 필드가 두 곳(비전 설정과 프로세서 설정)에 독립적으로 존재한다는 점이 결정을 갈랐다. 한쪽 사본만 조용히 손보면 다른 쪽과의 합치가 깨지는데, 이는 로드 시점 거부보다 진단하기 훨씬 어렵다.

## 4. 검증

CLI, GB10(CUDA, sm_121), release 빌드, `models/mlx/jina-vlm-mlx`(4비트, group 64), 핑크색 소파 위에 리모컨 두 개와 함께 있는 고양이 두 마리를 찍은 실제 640x480 사진.

```
$ ./target/release/mlxcel generate -m models/mlx/jina-vlm-mlx --image coco_cats.jpg \
    -p "Describe the image." -n 60 --temp 0.0
Jina VLM: inserted 1 image block(s) (814 image tokens, 824 total tokens)
In the image, two cats are comfortably resting on a pink couch. One cat is lying on its side, while the
other cat is lying on its back. Both cats are surrounded by two remote controls, one positioned closer
to the left cat and the other closer to the right cat.
```

고양이 수, 소파 색, 리모컨 수 등 근거 있는 세부 사항이 모두 맞다. 같은 이미지에 더 구체적으로 캐물은 두 번째 질문도 같은 세부를 정확히 되짚어, 범용 캡션이 아님을 뒷받침했다.

서버는 별도로, 2.4의 content-type 순회 수정 이후 검증했다. 이미지 요청은 `prompt_tokens 824`를 반환해 CLI 수와 일치하고 같은 텍스트를 생성한다. 텍스트 전용 요청은 `prompt_tokens 16`을 반환하고 프랑스 수도 질문에 `Paris.`라 답한다. 배치 스케줄러를 통과한 동시 이미지 요청 두 건도 모두 정확히 답했다. 2.5절에서 말했듯 토큰 수 일치만으로는 여기서 충분한 근거로 삼지 않는다. 이 PR 안에서 이미 한 번 그것만으로는 부족하다는 게 드러났기 때문이고, 실제 검사 기준은 텍스트 출력 비교다.

병합 후보에 대한 전체 CUDA 게이트 결과는 통과 7655, 실패 5다. 실패한 5건 모두 `main`에서 동일하게 재현되고 거기서도 대조 실행했다. 4건은 `MLX_ENABLE_TF32=0`이면 통과하는 TF32 정확도 아티팩트이고, 나머지 1건은 `resolve_paged_block_budget`의 이 변경과 무관한 기존 정수 언더플로다.

## 5. 검증하지 못한 것

- **PyTorch나 mlx-vlm 오라클과의 수치 대조가 없다.** 이 장비에서는 둘 다 돌릴 수 없다. 증거는 실제 사진에 대한 근거 있는 생성 결과와 2.2절의 토큰 수 산술이 끝까지 맞아떨어진다는 것이지, 레퍼런스 구현과의 로짓 차분이 아니다.
- **다중 이미지 프롬프트는 구현됐지만 이미지 한 장으로만 실행했다.** 크롭과 블록 연결, `image_input_idx` 오프셋 누적은 구조상 올바르게 동작하지만, 실제 체크포인트로 다중 이미지 요청을 돌려보지는 않았다.
- **`forward_batched`는 직렬 기본 경로로 떨어진다.** `supports_batching()`은 `true`를 보고하지만 배치 전용 빠른 경로는 아직 없다. 요청은 여전히 정확하지만 배치로 가속되지는 않는다.
- **KV 크기 산정 전에 컨텍스트 창 대비 프롬프트 길이 검사가 없다.** 이는 이 모델에 국한된 게 아니라 저장소 전반에 걸친 기존 공백이다.
- **사용자 텍스트 안의 리터럴 `<|image|>`가 splice 위치를 가로챈다.** 런타임은 아직 템플릿이 삽입한 마커와 사용자가 직접 입력한 마커를 구분하지 않는다.
- **이 체크포인트의 그리디 이미지 경로 생성에서 실행마다 다른 비결정성이 관찰됐다.** 이번 변경 이전부터 있던 현상이고, 여기서 다룬 `scatter_add`나 행렬곱이 아니라 비전 타워 쪽에 국한된다. 그래서 병합 게이트는 단발성 바이트 동일 생성 대신 비트 단위 유닛 테스트(`jina_vlm`에만 39개, 음수 `vit_layers` 해석, 완전히 패딩된 크롭, 패드 임베딩 마스크, 풀링된 패치와 토큰의 전단사 대응, 증분 디코드와 전체 시퀀스 디코드의 일치를 다룬다)에 의존한다.

## 6. 교훈

- **`model_type` 오라우팅은 이 트리에서 포트가 가장 흔히 실패하는 방식이고, 잘못된 수치가 아니라 "아예 로드되지 않는다"는 형태로 조용히 실패한다.** 이슈 자신의 철자는 어떤 체크포인트와도 맞지 않았다. 이슈 텍스트를 있는 그대로의 진실로 삼았다면 아무 곳으로도 라우팅되지 않는 모델을 출하했을 것이다.
- **상류의 재구현은 출발점일 뿐, 체크포인트 자체의 코드가 레퍼런스다.** 2.3절의 세 지점 모두 잘 관리되는 포트(mlx-vlm)와 체크포인트에 학습된 벤더 코드가 어긋난 자리였고, 셋 다 그럴듯해 보이지만 틀린 출력 쪽으로 조용히 실패한다.
- **토큰 수 일치는 두 프런트엔드가 같은 프롬프트를 렌더링했다는 증거가 아니다.** PR의 첫 대조 주장은 우연히 맞아떨어졌을 뿐 그 아래 텍스트는 달랐다. 실제 생성 출력을 비교하고서야 이를 잡아냈다.
- **무관한 능력 플래그로부터 캐시 레이아웃을 추론하는 트레이트 기본값은 상시적인 지뢰다.** Falcon-OCR의 CRITICAL은 래퍼 하나 차이로 여기서도 되풀이될 뻔했다. 해법은 기본값을 믿고 나중에 테스트를 더하는 게 아니라, 매번 레이아웃을 명시적으로 선언하는 것이다.
- **테스트 대상 코드 경로에서 레퍼런스 모델 자체가 비결정적이라면, 결정적인 하위 조각들에 대한 비트 단위 유닛 테스트가 신뢰할 수 있는 게이트이지 단발성 출력 비교가 아니다.** 여기서 관찰된 이미지 경로의 비결정성은 이번 변경 이전부터 있었고, 코드가 옳은지와 무관하게 바이트 동일성 검사를 신뢰할 수 없게 만들었을 것이다.
