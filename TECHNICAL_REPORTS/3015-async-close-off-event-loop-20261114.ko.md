# 기술 보고서: PR #3015 - fix(python): reap the managed server off the asyncio event loop

**날짜**: 2026-11-14
**상태**: 완료
**언어**: Python
**위험도**: 낮음

---

## 요약

`AsyncLLM.close()`는 관리형 `mlxcel` 서버를 종료할 때 동기 함수인 `ManagedServer.close()`를 이벤트 루프 스레드에서 직접 호출했습니다. 이 호출은 `proc.wait()`에서 종료 유예 시간만큼(자식을 강제 종료해야 하면 두 번) 블록되고 로그 스레드 join에서도 블록되므로, 자식 프로세스가 끝날 때까지 루프의 다른 모든 태스크가 멈췄습니다. 이제 종료 작업은 루프의 기본 executor에서 실행되고 await됩니다. 취소는 자식이 회수될 때까지 보류했다가 다시 발생시킵니다. 종료에 350 ms가 걸리는 자식으로 측정했을 때 10 ms 주기 하트비트 태스크는 `close()` 동안 0회, 최대 간격 375 ms에서 36회, 최대 간격 약 11 ms로 바뀌었고, `close()` 자체의 소요 시간은 그대로입니다.

---

## 1. 문제 정의

### 1.1 배경

Python 클라이언트는 로컬 `mlxcel` 서버를 직접 띄우고 관리할 수 있습니다(`python/src/mlxcel/_server.py`의 `ManagedServer`). 동기 `LLM`과 비동기 `AsyncLLM`이 이를 공유합니다. `ManagedServer.close()`는 SIGTERM을 보내고 기다린 뒤 필요하면 SIGKILL로 올리고, 로그 전달 스레드를 join하고 소켓을 삭제합니다. 모두 블로킹 호출입니다.

### 1.2 기존 문제

- `AsyncLLM.close()`가 `self._server.close()`를 직접 호출해 대기가 이벤트 루프 스레드에서 일어났습니다.
- SIGTERM에 늦게 반응하거나 무시하는 서버는 애플리케이션 전체를 유예 시간의 최대 두 배 동안 멈추게 했습니다.
- 바로 앞에 머지된 #3011은 HTTP close 오류나 취소 뒤에도 `finally`에서 서버 종료가 실행되도록 했습니다. 이 PR은 그 `finally`가 기다리는 방식을 바꿉니다.

### 1.3 위험 평가

| 위험 | 영향 | 가능성 |
|------|------|--------|
| 취소 시 워커를 버려 이미 닫힘으로 표시된 클라이언트 뒤에 자식이 남음 | 프로세스 누수 | 설계로 배제, 테스트로 확인 |
| asyncio 루프가 없음(httpx를 통한 Trio) 또는 executor가 작업을 거부 | close가 예외를 내고 자식 누수 | 동기 폴백으로 처리 |
| 지연된 취소가 호출자를 놀라게 함 | `cancel()`이 최대 유예 시간만큼 걸림 | 낮음, 문서화됨 |

## 2. 기술 검토

### 2.1 보안

새로운 입력 경로가 없습니다. 기존 시그널 순서는 그대로이고 대기가 실행되는 위치만 옮겼습니다.

### 2.2 성능

| | 이전 | 이후 |
|---|---|---|
| `close()` 동안 하트비트 (Python 3.12) | 0회, 최대 간격 375 ms | 36회, 최대 간격 10.6 ms |
| `close()` 소요 시간 | 365 ms | 365 ms |

수치는 기여자가 Linux aarch64에서 측정한 값입니다. 종료하는 동안 기본 executor 스레드 하나를 사용합니다.

### 2.3 호환성 및 의존성

- **호환성 깨짐**: API 변화는 없습니다. 종료 중 취소된 태스크는 `CancelledError`를 즉시가 아니라 자식이 끝난 뒤에 받습니다.
- **새 의존성**: 없음.
- **호환 범위**: Python 3.9부터 3.13. 실행 중인 asyncio 루프가 없거나 `run_in_executor`가 `RuntimeError`를 내면(executor 종료, 인터프리터 종료 중) 이전처럼 동기로 종료합니다.

### 2.4 코드 품질

`python/tests/test_async_shutdown.py`는 실제 자식 프로세스를 쓰는 16개 케이스를 추가합니다. 핵심 케이스는 자식의 SIGTERM 핸들러가 이벤트 루프만 만들 수 있는 파일을 기다리게 해서, 루프를 막는 구현은 정상 종료에 도달할 수 없게 합니다. 직접 close와 컨텍스트 매니저, HTTP close 오류와 취소, 종료 중 한 번과 두 번의 취소, 강제 종료되는 자식, 워커 오류, 취소 중 워커 오류를 다룹니다. 그 밖에 connect 모드(워커 없음), 종료되었거나 거부하는 executor, asyncio 루프 없이 구동되는 코루틴을 검사합니다.

## 3. 기술적 선택과 그 이유

### 3.1 취소를 전파하기 전에 회수를 끝냄

**맥락:** `_closed`가 설정되면 두 번째 `close()`는 아무것도 하지 않으므로, 끝내지 못한 작업은 다시 시도되지 않습니다.

**검토한 대안:**

| 선택지 | 장점 | 단점 |
|--------|------|------|
| 즉시 취소 전파, 워커는 계속 실행 | `cancel()`이 즉시 반영 | 닫혔다고 보고하는 클라이언트 뒤에 워커 스레드와 살아 있는 자식이 남을 수 있음 |
| 워커 취소 | 단순함 | 스레드 작업은 중단할 수 없고 자식이 살아남을 수 있음 |
| 워커를 기다린 뒤 다시 발생 | 반환 전에 자식이 항상 회수됨 | 취소가 최대 유예 시간만큼 늦어짐 |

**결정:** 기다린 뒤 다시 발생시킵니다. 지연은 기존 유예 시간으로 제한됩니다.

### 3.2 `asyncio.shield` 대신 `asyncio.wait`

**맥락:** 첫 리비전은 루프 안에서 `asyncio.shield(cleanup)`를 await했습니다. 태스크가 취소된 뒤 워커가 예외를 내면 마지막 shield await가 워커의 예외를 그대로 올려 보내고 기록해 둔 `CancelledError`가 사라져, 취소된 `close()`가 일반 예외로 끝났습니다.

**결정:** 리뷰 후속 커밋은 `asyncio.wait((cleanup,))`를 await합니다. 이 함수는 워커를 취소하지도 워커의 예외를 올리지도 않으므로, 결과를 한 번만 읽고 보류된 취소를 워커 오류보다 먼저 발생시킵니다. `cancel-worker-error` 모드는 shield 버전에서 실패합니다.

### 3.3 전용 풀이 아닌 기본 executor

전용 스레드 풀은 루프보다 오래 살아남을 수 있습니다. 기본 executor는 `asyncio.run()`이 `shutdown_default_executor()`로 join하므로 정리 스레드가 루프 이후까지 남지 않습니다.

## 5. 학습 포인트

- `async def` 안의 블로킹 정리 코드는 여전히 "동작"하기 때문에 놓치기 쉽고, 루프에서는 다른 곳의 지연으로만 드러납니다. 정상 종료가 루프 실행에 의존하게 만든 테스트는 그 지연을 실패로 바꿉니다.
- `asyncio.shield`는 내부 future를 취소에서 보호하지만 내부 future의 결과는 여전히 await하는 태스크로 올려 보냅니다. "영향받지 않고 기다리기"가 목적이라면 `asyncio.wait`가 더 맞는 도구입니다.
- 검증되지 않은 부분: 최종 리비전에서의 실제 Trio 실행(기여자는 이전 리비전으로 확인)과 기여자의 macOS, Windows 실행. 메인테이너가 macOS에서 Python 3.11과 3.9로 테스트를 다시 실행했습니다.
