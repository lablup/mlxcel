# 기술 리포트: PR #1851 — WebUI 계약 게이트

**작성일**: 2026-09-12
**상태**: 머지 전 계약 검증 완료, 런타임 구현은 후속 의존 이슈에서 진행
**언어**: OpenAPI 3.1 / JSON Schema, TypeScript, Python, 영문/국문 문서
**위험도**: 중간

## 요약

PR #1851은 번들 WebUI 에픽 #1834의 선행 계약 이슈 #1835를 구현한다. 스키마, 생성된 TypeScript 선언, JSON fixture 30개, 상태/UX 명세와 CI 동기화·검증 게이트를 추가하며 서버 라우트, 모델 워커, 브라우저 화면은 구현하지 않는다.

## 1. 문제 정의

백엔드와 프런트엔드를 독립적으로 구현하려면 엔드포인트 이름 이상의 합의가 필요하다. 식별자, 자원 소유권, 이벤트 순서, nullable 값, 동작 의미가 고정되지 않으면 각 구현이 그럴듯해도 모델 준비 상태, 메모리 해제 여부, 측정 불가 값과 0의 의미를 다르게 해석할 수 있다.

계약은 로컬 모델 카탈로그와 기존 다운로드 모델 목록, 추론 요청용 모델 식별자를 구분한다. UI는 기존 런타임의 사실을 표현해야 하며 별도 레지스트리나 수명주기 제어기를 만들면 안 된다.

## 2. 기술적 선택과 그 이유

- OpenAPI 3.1을 JSON 호환 YAML로 저장하고 버전을 고정한 JSON Schema Draft 2020-12 검증기로 읽는다. 엄격한 TypeScript 선언을 결정적으로 생성하며 게이트는 선언 드리프트와 알 수 없는 스키마 키워드를 거부한다.
- 안정 모델 ID는 정규화된 소스/항목 식별자를 해시한다. 콘텐츠 fingerprint와 revision을 분리하여 재검색이나 콘텐츠 변경 때문에 모델 정체성이 달라지지 않도록 한다. 정규화 벡터와 소스 충돌 fixture가 후속 구현을 제한한다.
- `draining`과 `unloading`은 워커 종료가 관찰될 때까지 자원 소유권을 유지한다. drain timeout이 두 번째 워커를 시작할 권한은 아니다. 실제 요청 lease는 핸들러 dispatch뿐 아니라 스트리밍 응답 본문의 수명까지 포함해야 한다.
- 서로 다른 시점에 조회한 자원 스냅샷은 최소 sequence부터 SSE를 재생하고 각 자원의 스냅샷 기준으로 중복을 제거한다. 최대 sequence를 사용하면 오래된 스냅샷과 최신 스냅샷 사이 이벤트가 유실된다. gap이나 프로세스 재시작은 동작 재전송 대신 스냅샷 재조회를 요구한다.
- 다음 로드 프로필은 `ctx_size`, `n_parallel`, `kv_cache_mode`만 노출한다. 요청 sampling, 부분 성공 가능한 live 설정, 명시적 CLI override, 시작 시점 전용 설정은 별도 범위로 유지한다.

## 3. 리뷰와 회귀 검증에서 발견한 사항

Operation의 target/result를 임의 데이터 객체에서 판별 가능한 DTO로 변경하고 SSE envelope에 이벤트 식별자와 시간을 필수화했다. 보안 리뷰는 식별자, 입력 필드, 응답 컬렉션, 동일 출처 API base를 제한하고 인증 오류와 의도적으로 심은 민감 정보의 비노출 fixture를 추가했다.

마무리 검증에서는 여러 잘못된 필드를 함께 넣은 다운로드 테스트가 남은 버그를 가리고 있음을 확인했다. `$`가 마지막 개행 직전에도 일치하여 `o/n` 뒤에 개행을 붙인 저장소 ID를 허용했다. 패턴의 끝을 ECMAScript 호환 assertion `(?![\s\S])`으로 바꾸고 필드별 독립 변이 테스트를 추가했다. 패턴 20개를 Python 검증뿐 아니라 JavaScript에서도 컴파일했다. Rust 생산자는 lookaround를 지원하지 않는 Rust `regex` crate에 그대로 복사하지 말고 동등한 구조적/전체 문자열 검증으로 옮겨야 한다.

격리된 `jsonschema` 환경은 date-time 검증을 자동 활성화하지 않는다. 명시적 checker가 잘못된 시간 문자열, 존재하지 않는 날짜, 누락된 offset과 잘못된 offset 범위를 거부하며, 스키마에 대응 checker가 없는 format이 있으면 게이트가 실패한다. 이는 검증 의존성 문제의 해결이지 향후 런타임이 올바른 시간을 출력한다는 증거는 아니다.

직접 작성한 검증 코드는 CLI, 재사용 검사, negative test로 분리하여 각 모듈을 500줄 미만으로 유지했다. 생성된 선언 파일은 단일 기계 생성 산출물로 유지한다.

## 4. 검증과 한계

- 통과: 계약 fixture 30개, 생성 DTO 드리프트, 식별자 벡터, 허용 상태 전이와 연속성, 필드별 negative case, TypeScript 5.9.3 strict `--noEmit` 검사.
- 통과: JavaScript 패턴 컴파일/마지막 개행 거부, Python byte compilation, 라이선스 헤더, `cargo fmt --check`, 호환성 manifest 사례, workspace 버전 일치, kernel dtype key 검사, diff 공백 검사.
- 외부 저장소 참조 검사는 문서화된 로컬 fallback을 사용했고 추가된 bare 참조가 이 저장소 이슈인지 검토했다.
- 오케스트레이터는 사전 기준 커밋에서 CLI help 27개와 호환성 통합 테스트 4개 통과를 별도로 보고했다. 이는 실행 중인 WebUI 검증이 아니다.
- 이 계약 전용 PR은 WebUI 라우트, Rust 직렬화, 모델 추론, GPU 자원 해제, CUDA, Safari, 접근성, 스크린샷 동작을 구현하거나 검증하지 않는다. 이는 특히 #1848을 포함한 후속 이슈의 관문으로 남는다. 런타임 성능 개선은 주장하지 않는다.

## 5. 변경 요약과 후속 조치

공통 아키텍처/API/상태/UX 문서, 생성 선언, fixture 모음, Python 검증 의존성, Makefile target과 CI job이 변경 범위다. 계약이 바뀌면 생산자, 소비자, fixture와 요구사항 매핑을 함께 갱신한 후 의존 작업을 진행해야 한다.

백엔드 담당자는 실제 Rust 응답을 동일 fixture로 검증하고 수명주기/보안 규칙을 런타임에서 강제해야 한다. 프런트엔드 담당자는 생성 DTO와 공통 문자열/test ID 계약을 사용해야 한다. 통합 담당자는 이 명세 게이트를 제품 완성으로 취급하지 말고 모델 없는 시작과 실제 체크포인트/브라우저 검증을 포함한 전체 시스템을 입증해야 한다.
