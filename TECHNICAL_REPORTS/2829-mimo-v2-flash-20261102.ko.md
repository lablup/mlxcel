# PR #2829: Xiaomi MiMo v2 Flash 지원 추가

**Date**: 2026-11-02
**Status**: Completed (PR open; closes #842)

## 요약

PR #2829는 `mimo_v2_flash` 네이티브 지원을 추가하고 실제 173.8 GB `mlx-community/MiMo-V2-Flash-4bit` 체크포인트로 검증한다. 이슈 작성 당시에는 하드웨어에 막혀 있었지만 512 GB M3 Ultra 호스트에서 가능해졌다. 모델은 161.83 GB 상주로 16.9초에 로드되고 24~31 tok/s로 일관된 텍스트를 생성한다. 포트는 이 패밀리의 특이한 형상 세 가지를 다룬다. 하이브리드 sliding/full attention, Q/K `head_dim` 192 대비 V/O `v_head_dim` 128, 학습된 보정 편향을 쓰는 `noaux_tc` 라우터다. 10개 파일, +2177/-2이며 641줄이 테스트다.

## 1. 문제 정의

`XiaomiMiMo/MiMo-V2-Flash`는 `model_type: mimo_v2_flash`를 선언하며, `src/models/mimo.rs`의 기존 dense MiMo v1과 다른 패밀리다. 약 309B 파라미터로 48층, hidden 4096, 256 라우티드 전문가 top-8, `moe_intermediate_size` 2048이다. 공개 체크포인트가 128 GB 개발 머신에 들어가지 않아 `modelsize:xlarge`와 `status:blocked`가 붙어 있었다. 512 GB 호스트와 공개된 4-bit 변환이 그 블로커를 해소했다.

## 2. 구현된 아키텍처

| 기능 | 구현 |
|---|---|
| 층 스케줄 | `hybrid_layer_pattern`을 모듈러스가 아니라 목록으로 읽는다. 체크포인트에서 0, 5, 11, 17, 23, 29, 35, 41, 47층이 full attention(9층)이고 나머지 39층이 윈도 128의 sliding이다 |
| Attention 형상 | Q/K는 `head_dim` 192, V/O는 `v_head_dim` 128을 쓴다. sliding 층은 64 헤드와 8 KV 헤드, full 층은 64 헤드와 4 KV 헤드다 |
| RoPE | 층별 base를 쓴다. sliding은 `swa_rope_theta` 10000, full은 `rope_theta` 5000000이다. `partial_rotary_factor` 0.334은 float로 파싱해 내림하여 64 회전 차원이 된다 |
| Value scale | sliding 층은 캐시 갱신 전에 V에 `attention_value_scale` 0.707을 곱한다 |
| Attention sink | sliding 층은 헤드별 학습 `attention_sink_bias`를 가진다. 체크포인트에 39개 키가 있고 sliding 집합과 정확히 일치한다 |
| 라우터 | `noaux_tc`: f32 시그모이드 점수, 선택에만 `e_score_correction_bias`를 더하고, 가중치는 편향 없는 시그모이드 점수에서 뽑아 정규화하고 1.0으로 스케일한다 |
| 전문가 | 0층은 dense, 1~47층은 256 전문가 top-8 `SwitchGLU`다. `n_shared_experts`는 null이라 선택적 shared MLP 경로는 있지만 실행되지 않는다 |
| 캐시 | 모델 소유다. sliding 층은 `RotatingKVCache`, full 층은 `KVCache`를 쓴다 |

## 3. 기술적 선택

### 3.1 권위는 목록이지 산문이 아니다

갱신된 이슈 본문은 full attention을 0, 5, 10, ..., 45로 적었다. 실제 체크포인트는 0, 5, 11, 17, ..., 47이다. 0층 이후 반복 블록이 sliding 다섯 층과 full 한 층, 즉 주기가 5가 아니라 6이기 때문이다. 로더는 `hybrid_layer_pattern`을 그대로 읽으므로 코드는 체크포인트를 따른다. 39개 sink 키가 sliding 집합과 일치하는 것이 독립적인 확인이었다.

### 3.2 sanitize는 pass-through이며 인덱스로 확인했다

4-bit 변환은 이미 업스트림의 post-sanitize 레이아웃을 담고 있다. 스택된 `mlp.switch_mlp.*` 평면과 affine scale/bias, 양자화되지 않은 BF16 `mlp.gate.weight`, F32 `e_score_correction_bias`, 39개 sink 키가 있고, 전문가별 키와 fp8, MTP 키는 없다. 업스트림의 fp8 디퀀타이즈와 전문가 스태킹은 bf16 원본에 해당한다. 이슈가 요구한 대로 로더를 쓰기 전에 인덱스를 먼저 확인했다.

### 3.3 스케줄 항목이 없으면 full attention으로 폴백

`is_sliding_layer`는 항목이 없으면 false를 반환한다. 전역 층은 sliding 층이 보는 모든 키와 그 이상을 보므로 짧은 목록은 틀리기보다 느려진다. 설정 검증이 잘못된 항목과 짧은 목록을 거부하므로 이 폴백은 설정 경로가 아니라 안전망이다.

### 3.4 배칭은 의도적으로 끈다

모델이 이종 캐시(rotating과 full)를 소유하므로 디코드는 한 번에 한 시퀀스다. `supports_batching`, `supports_padded_prefill`, `supports_chunked_prefill`이 false를 반환해 스케줄러가 모델 소유 풀에 dense 캐시 가정을 적용하지 않게 한다. 임시 지름길이 아니라 능력의 한계다.

### 3.5 라우터 산술은 벤더를 따른다

전문가 가중치는 float32에서 곱하고 마지막에 한 번 캐스트한다. AFMoE가 문서화한 것과 같은 계약이다. 공용 `moe_weighted_sum` 헬퍼는 전문가 가중치를 먼저 낮은 정밀도로 캐스트하므로 MoE 블록은 명시적 float32 경로를 쓴다.

## 5. 미검증

CUDA와 ROCm 실행, 다중 장치 텐서 병렬 실행은 하지 않았다. 이 호스트는 Apple Silicon이다. TP 아키텍처 문자열은 연결했지만 실행하지 않았다. 선택적 shared expert 경로는 체크포인트에 없어 실행되지 않았다. 이 패밀리의 서버 배칭은 설계상 꺼져 있고 동시 부하로 시험하지 않았다.

## 6. 학습 포인트

층 스케줄의 권위는 이슈 산문이 아니라 체크포인트다. 주기 5라는 모듈러스 가정과 주기 6인 목록은 full attention 층 집합을 다르게 만들고, 39개 sink 키가 가중치가 어느 쪽을 담는지 확인하는 가장 싼 방법이었다. 로더를 쓰기 전에 가중치 인덱스를 본 것이 sanitize 질문도 추측성 재매핑 없이 정리했다.

## 7. 위험

중간. 새 패밀리가 한 파일에 1,504줄로 프로젝트의 1,200줄 지침에 가깝지만, 디코더와 라우터, 캐시 로직은 응집되어 있다. 헤드별 attention sink, 분리된 `v_head_dim`, 이종 캐시를 함께 쓰는 첫 모델이라 서버 경로가 dense 패밀리보다 덜 검증됐다. 실제 체크포인트 실행은 스모크 테스트이고 참조 구현과의 수치 패리티 테스트는 아니다.
