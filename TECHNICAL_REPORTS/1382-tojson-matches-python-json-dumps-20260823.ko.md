# 기술 보고서: PR #1382 - 채팅 템플릿 `tojson` 필터를 Python `json.dumps`에 맞춤

**날짜**: 2026-08-23
**작성자**: Jeongkyu Shin
**상태**: 완료
**언어/기술**: Rust (minijinja, serde_json)
**위험도**: 중간 (`tojson`을 호출하는 모든 템플릿의 렌더 결과가 바뀐다. 도구를 지원하는 템플릿 대부분이 해당된다)

---

## 요약

mlxcel은 채팅 템플릿을 minijinja 빌트인 `tojson`으로 렌더했다. HuggingFace에 공개된 채팅 템플릿은 `transformers`를 기준으로 작성되며, 거기서 Jinja의 `tojson`은 `ensure_ascii=False`가 미리 채워진 CPython `json.dumps`다. 둘은 같은 필터가 아니고, 그 간극이 서로 다른 두 가지 실패를 만들었다. `json.dumps` 키워드 인자를 쓰는 템플릿은 렌더 자체가 중단돼 도구가 없는 제네릭 프롬프트로 떨어졌고, 맨 `tojson`을 쓰는 템플릿은 제공자 자신의 토큰화와 공백이 다른 JSON을 만들었다.

이 PR은 빌트인을 mlxcel이 소유한 필터로 대체해 `json.dumps`를 바이트 단위로 재현한다. 이 변경에서 흥미로운 지점은 필터 자체가 아니라 "바이트 단위 일치"를 검증하는 데 무엇이 필요했고 그 검증이 무엇을 찾아냈는가다. 세 가지를 남겨 둘 만하다. 이슈가 지시한 구현 방법으로는 그 이슈 자신의 수용 기준을 만족할 수 없었고, 올바른 중첩 깊이 상한은 맞추려는 대상보다 오히려 **더 높아야** 하며, 바뀐 테스트 픽스처를 레퍼런스 렌더러로 재구성한 것이 변경의 정당성과 함께 그 픽스처에 처음부터 박혀 있던 별개의 결함까지 드러냈다.

## 1. 문제 정의

### 1.1 배경

`src/server/chat_template.rs`는 minijinja 환경에 `raise_exception`과 `strftime_now`만 등록하고 `tojson`은 빌트인에 맡겼다. minijinja 빌트인은 `indent`만 받고 `Kwargs::assert_all_used`를 호출하므로 다른 키워드 인자는 전부 하드 에러이며, `serde_json::to_string`으로 직렬화해 `,`와 `:` 뒤에 공백이 없는 compact 형태를 낸다.

공개 템플릿은 두 제약을 모두 지키지 않는다.

- `poolside/Laguna-XS-2.1`은 `tojson(ensure_ascii=False)`를 호출한다.
- `thinkingmachines/Inkling-Small`은 `tojson(sort_keys=true, separators=(",", ":"))`를 호출한다.
- Muse Glimmer를 포함한 다수 템플릿이 맨 `tool | tojson`을 쓰며, 레퍼런스 렌더러에서는 `", "` / `": "`가 나온다.

### 1.2 기존 문제

두 실패 모드는 가시성이 매우 다르고, **조용한 쪽이 더 해롭다**.

시끄러운 실패는 키워드 인자 거절이다. 렌더가 중단되고 mlxcel은 요청을 제네릭 `User:/Assistant:` 프롬프트로 격하한다. 이때 도구 선언과 도구 호출 이력이 조용히 사라지므로, 모델은 한 번도 본 적 없는 도구를 쓰라는 요구를 받는다. 격하는 에러가 아니라 폴백이라 호출자에게 아무것도 드러나지 않는다.

조용한 실패는 separator 간격이다. 렌더는 성공하고 출력도 유효한 JSON이지만, 토큰 id가 모델 제공자가 학습·평가한 것과 다르다. 형식이 깨지지도 로그가 남지도 않으며, 증상은 도구 선택이 조금 나빠지는 것뿐이다.

### 1.3 위험 평가

중간이되, 위험은 나가는 쪽보다 들어오는 쪽에 있다. 이 필터는 도구를 렌더하는 모든 채팅 요청 경로에 있으므로, 필터의 오류는 모든 프롬프트의 오류다. 이 변경의 검증 기준을 손으로 쓴 기대값이 아니라 CPython과의 차분 등가성으로 잡은 이유가 그것이다.

## 3. 기술적 선택과 그 이유

### 3.1 이슈가 지시한 구현으로는 그 이슈의 수용 기준을 만족할 수 없었다

이슈의 구현 계획은 `serde_json::to_value`로 변환한 뒤 그 `serde_json::Value`를 순회하라고 했다. 같은 이슈가 비유한(non-finite) float을 CPython처럼 맨 `NaN` / `Infinity` / `-Infinity`로 써야 한다고 요구했다.

두 요구는 양립하지 않는다. `serde_json`의 `impl From<f64> for Value`는 다음과 같다.

```rust
Number::from_f64(f).map_or(Value::Null, Value::Number)
```

`Number::from_f64`는 비유한 입력에 대해 `None`을 돌려주므로, 순회기가 값을 보기도 전에 변환 단계에서 `NaN`이 `null`이 된다. 하류에서 아무리 조심해도 이 구분은 복구되지 않는다.

그래서 필터는 `minijinja::Value`를 직접 순회한다. 이 선택은 `serde_json` 경로였다면 새로 생겼을 두 번째 문제도 함께 해결했다. `2`와 `2.0`을 구분하는 문제다. `minijinja::Value::is_integer()`는 정수 표현에만 매칭하고 `F64`에는 절대 매칭하지 않는 반면, 값에 `i64::try_from`을 쓰면 정수값 float이 잘려서 `2.0`이 `2`로 렌더됐을 것이다.

일반화하면, **이슈의 구현 계획은 수용 기준을 만족하는 방법에 대한 가설**이고 둘은 서로 모순될 수 있다. 그때는 수용 기준이 이긴다.

### 3.2 CPython float `repr`은 Rust `{}`와 세 축에서 독립적으로 어긋난다

이 변경에서 가장 위험한 코드라서 인라인 분기가 아니라 독립 함수 + 전용 테스트로 두었다. Rust의 `Display for f64`와 CPython `repr`은 둘 다 shortest-round-trip이지만 표기에서 세 가지가 다르고, 그 셋이 겹친다.

1. **`.0` 접미사.** CPython은 `1.0`, Rust는 `1`.
2. **지수 전환 임계.** CPython은 십진 지수가 `<= -4`이거나 `> 16`일 때 지수 표기로 넘어간다. 그래서 `0.0001`은 고정 표기지만 `0.00001`은 `1e-05`가 되고, `1e15`는 고정이지만 `1e16`은 `1e+16`이 된다. Rust는 다른 경계를 쓴다.
3. **지수 형식.** CPython은 지수에 항상 부호를 붙이고 최소 두 자리로 채운다(`1e-5`가 아니라 `1e-05`).

구현은 Rust `LowerExp`에서 shortest round-trip 자릿수를 얻고(CPython `_Py_dg_dtoa` mode 0과 같다), 표기 조립은 직접 한다.

### 3.3 HTML 이스케이프 제거는 간격 변경이 아니라 실질적 동작 변경이다

minijinja 빌트인은 출력에서 `<`, `>`, `&`, `'`를 이스케이프한다. `transformers`는 하지 않는다. 등가성을 위해 제거가 필요했지만 이슈가 기술한 것보다 큰 변경이고, 그렇게 기록해 둘 가치가 있다. 비교 연산자로 가득한 JSON Schema `pattern`이 이제 그대로 프롬프트에 도달한다.

보안 영향은 확인했고 이 코드베이스에는 없다. `src/server/` 어디에도 `text/html` 응답이나 `Html(` 생성자가 없어 렌더된 프롬프트에 HTML 싱크가 없다. 출력의 `Value::from_safe_string`도 별개 이유로 무해하다. 템플릿이 `chat`이라는 이름으로 등록되는데, minijinja의 기본 auto-escape 콜백은 `.html`, `.htm`, `.xml` 이름에만 HTML 이스케이프를 켠다.

### 3.4 깊이 상한은 맞춰야 할 것처럼 보이는 값보다 높아야 한다

최초 구현은 중첩을 128로 제한하며 "`serde_json`의 기본 재귀 한계와 일치"라고 적었다. 그럴듯하지만 틀렸다.

`chat_request`는 `function.arguments`를 그 wire 문자열에서 **다시 파싱해** 결과를 메시지 트리의 깊이 4쯤에 끼워 넣는다. 그 내부 파싱은 **새로운** 128 예산을 따로 받는다. 따라서 개별 파싱은 각자 한계 안에 있으면서도 조립된 `messages` 값은 정당하게 132 수준에 이를 수 있다.

상한이 정확히 128이면, 인자 객체만이 아니라 메시지 전체를 직렬화하는 템플릿은 **정상 요청에서 에러를 낸다**. 에러는 렌더를 중단시키고, 렌더는 제네릭 프롬프트로 폴백하고, 폴백은 도구 선언을 버린다. 바로 이 필터가 없애려던 실패다. 즉 그 상한은 수정을 통해 버그를 다시 들여왔을 것이다.

상한은 192가 되었고, 근거는 주석이 아니라 기계적으로 고정했다.

```rust
const _: () = assert!(MAX_DEPTH > 128);
```

여기서 컴파일 타임 단언이 적절한 이유는 **틀린 쪽이 직관적이기 때문**이다. `serde_json` 언급 옆의 `192`를 본 사람은 `128`로 "고치고" 싶어질 텐데, 이 단언은 그것을 조용한 회귀가 아니라 빌드 실패로 만든다. 조용한 회귀였다면 깊게 중첩된 도구 스키마에서만 드러났을 것이다.

### 3.5 경계는 입력을 단속하려는 것이 아니라 증폭을 잡으려는 것이다

리뷰 후 경계 3종을 넣었다. `indent` 64칸 클램프, 출력 64 MiB 상한, 위의 깊이 상한. 셋 다 정상 렌더보다 한참 위에 있고, 이유는 **비용의 비대칭**이다. 한계를 넘으면 렌더가 실패하고, 실패한 렌더는 프롬프트에서 도구 선언을 앗아 간다. 빡빡한 경계는 서비스 거부 위험을 조용한 기능 퇴행과 맞바꾸는 셈인데, 후자가 더 나쁘다.

특히 `indent`는 거절이 아니라 클램프다. 같은 이유로, 넉넉한 들여쓰기를 요청한 템플릿이 원하는 것은 예쁜 출력이고 아예 거절하는 쪽이 64칸으로 들어주는 쪽보다 비싸다.

출력 상한은 처음 보이는 것보다 중요하다. `tojson(indent=4)`는 가정이 아니다. Llama 3.1, Llama 4 Scout, Granite 3.3, Granite Vision 템플릿이 전부 그렇게 호출하고, 그중 둘은 이 프로젝트가 권장 테스트 체크포인트로 지정한 모델이다. 깊게 중첩된 구조의 pretty-print는 입력을 크게 증폭하며, `ensure_ascii`가 비ASCII 텍스트를 약 6배로 늘리는 것이 그 위에 얹힌다.

## 4. 검증

### 4.1 손으로 쓴 기대값이 아니라 차분 퍼징

"`json.dumps`와 바이트 단위 일치"는 큰 입력 공간에 대한 주장이고, 손으로 쓴 테스트 집합은 작성자가 이미 떠올린 경우만 표집한다. 그래서 필터를 Python으로 이식해 실제 `json.dumps`와 비교했다.

- 무작위 f64 비트 패턴 약 40만 개와 모든 임계 구간(십진 지수 -330~+320, 정수값 float, subnormal, `f64::MAX`, `0.1 + 0.2`)을 CPython `repr`과 대조. 불일치 0.
- 무작위 중첩 구조를 `ensure_ascii` x `indent` 4종 x `separators` 4종 x `sort_keys` 양쪽으로 교차한 **384만 건** 비교. 페이로드에 C0 제어문자, U+007F, 비ASCII, astral plane 문자, `<>&'`, 따옴표, 역슬래시 포함. 불일치 0.

### 4.2 델타를 믿는 대신 픽스처를 재구성

고정된 단언 3건이 움직였다. Muse Glimmer 렌더 다이제스트 2건과 `chat_request` 인자 문자열 1건이다. **움직인 핀은 진짜 회귀가 예상된 변경 뒤에 숨기 좋은 자리**라서, 그럴듯해 보인다는 이유로 받아들이지 않았다.

두 렌더를 실제 Jinja2 3.1.6에서 재구성했다. 새 형태에는 `transformers`의 실제 `tojson`을, 옛 형태에는 옛 minijinja 빌트인 에뮬레이션(compact separator + HTML 이스케이프)을 썼다. 재구성은 **옛 다이제스트와 새 다이제스트를 둘 다** 비트 단위로 재현했다. 둘 사이의 문자 수준 diff는 삽입된 공백 13개가 전부이며, 이는 `weather_tool` 스키마의 쉼표 5개와 콜론 8개, 그리고 두 테스트에서 관측된 +13바이트와 일치한다.

이것은 "새 다이제스트가 맞다"보다 강한 결과다. 옛 다이제스트가 정확히 "compact + HTML 이스케이프"였고 새 것이 정확히 `json.dumps`이며, 어느 쪽에도 제3의 차이가 숨어 있지 않음을 확립한다.

### 4.3 게이트

`cargo test --workspace --profile test-fast --features metal,accelerate`: 8294 통과, 0 실패. 루트 lib 5804건과 `mlxcel-core` 1521건 포함. `cargo clippy --workspace --all-targets --features metal,accelerate -- -D warnings`와 `cargo fmt --all -- --check` 깨끗.

`--workspace` 범위는 가정하지 말고 명시할 가치가 있다. 워크스페이스 루트가 곧 `mlxcel` 패키지라서 맨 `cargo test`는 `-p mlxcel`로 해석되고 나머지 세 멤버를 아예 빌드하지 않는다. 집계에 들어 있는 `mlxcel-core` 1521건이 이번엔 그러지 않았다는 증거다.

## 5. 리뷰에서 나온 지적

MEDIUM 이하 5건, 전부 반영했다. `indent` 클램프와 패딩 일괄 예약, 출력 상한, 깊이 여유, 시퀀스를 통째로 모으지 않고 검사하는 `separators` arity 확인, 그리고 CPython과의 유일한 알려진 차이를 기록한 주석(`sort_keys`는 문자열화된 키를 정렬하고 CPython은 원래 키 객체를 정렬하므로 숫자 키의 순서가 다르다).

한 건은 인정하되 고치지 않았다. 시퀀스를 쓰기 전에 `Vec<Value>`로 실체화하므로, 빌트인이 serde로 스트리밍하던 것과 달리 거대한 지연 range를 직렬화하는 템플릿은 출력 전에 할당한다. 클라이언트 JSON으로는 도달할 수 없고 그런 range를 작성한 템플릿에서만 가능하며, 수정하면 `write_array` 시그니처가 바뀌어 새 경계 두 개와 얽힌다. 알려진 한계로 기록만 했다.

## 6. 함께 발견해 별도 발행한 인접 결함

이 변경을 검증하다 기존 결함 2건이 드러났다. 둘 다 이 PR에 넣지 않았다. 이 PR의 가치는 파리티 증거에 기대고 있는데, 무관한 동작 변경을 섞으면 그 증거가 의심스러워지기 때문이다.

**#1383 (`priority:high`)**: `dict.get()` Python 호환 shim이 Python의 `None` 자리에 `Value::UNDEFINED`를 돌려준다. minijinja의 `is none`은 둘을 구분하므로 템플릿의 `{%- if end_turn is none -%}` 폴백이 절대 발동하지 않는다. 구체적 결과는 **모든 Muse Glimmer 프롬프트의 마지막 어시스턴트 턴이 `<|eot|>`가 아니라 `<|eom|>`로 끝난다**는 것이다. 4.2의 픽스처 재구성이 비교 대상 레퍼런스 렌더를 만들어 준 덕에 발견됐다. 이 차이는 PR 양쪽에 동일하게 나타나며 그것이 기존 결함임을 확립한다. 고치면 같은 다이제스트가 다시 움직인다는 점에 주의.

**#1384 (`type:test`, `priority:low`)**: `server::reasoning_effort_tests`가 큰 Qwen3.8 템플릿을 렌더하다 `dev` 프로파일 기본 2 MiB 스레드 스택을 넘긴다. `test-fast`나 `release`에서는 재현되지 않아 CI 게이트와 배포 바이너리는 무관하다. 필터 등록 한 줄만 되돌려 이 브랜치 이전임을 bisect로 확인했다.

## 7. 검증하지 못한 것

이슈의 검증 항목 (b), 즉 `poolside/Laguna-XS-2.1-NVFP4` 실체크포인트에서 렌더된 `<available_tools>` 블록이 체크포인트 자신의 설정으로 돌린 `tokenizer.apply_chat_template`와 바이트 동일한지 확인하는 작업은 하지 못했다. 그 체크포인트는 NVFP4 로더가 필요하고 그것은 별개 작업이다. 대신 Laguna·Inkling 형태의 단위 테스트로 템플릿 렌더를 덮었다.

퍼징 뒤에도 잔여 가정이 하나 남는다. 차분 하네스가 shortest-round-trip 자릿수를 CPython에서 가져왔으므로, 조립 로직(임계, `.0`, 지수 형식)은 검증했지만 Rust `{:e}`가 CPython `_Py_dg_dtoa` mode 0과 같은 자릿수 문자열을 낸다는 것은 가정했다. 둘 다 올바른 반올림의 shortest-round-trip이며, 커밋된 `every_finite_float_round_trips_through_the_repr` 테스트가 Rust 쪽을 지킨다.

## 8. 학습 포인트

- 이슈의 구현 계획은 그 이슈 자신의 수용 기준과 모순될 수 있다. 계획을 따르기 전에 기준과 대조하고, 충돌하면 기준이 요구사항이다.
- "아래 계층이 쓰는 한계에 맞춘다"는 값이 그 계층을 두 번 이상 통과할 때 틀린다. 여기서는 요청 본문이 매번 새 예산으로 두 번 파싱되므로, 조립된 값이 파싱 단위 한계를 정당하게 초과한다.
- 수정의 실패 모드가 버그의 실패 모드와 같을 때는 경계를 넉넉히 잡아야 한다. 렌더를 실패시키는 상한은 그 변경이 없애려던 폴백을 다시 들여온다.
- 움직인 테스트 핀은 회귀가 예상된 변경 뒤에 숨는 자리다. 옛 픽스처와 새 픽스처를 레퍼런스 구현으로 함께 재구성하면 "델타가 그럴듯하다"가 증명으로 바뀌고, 그 픽스처에 처음부터 박혀 있던 무관한 결함까지 드러날 수 있다.
- 틀린 값이 직관적인 불변식은 주석이 아니라 `const` 단언으로 고정한다.
