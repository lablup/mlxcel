# PR #2708: Remote pipeline residuals from #2671, #2680 and #2684

**Date**: 2026-10-28 (written before merge; the PR is open as a draft)
**Status**: Implementation complete; the security and performance review at 00bb4723 found no CRITICAL, HIGH or MEDIUM issues, and two of its four LOW findings were fixed in 7c8d340a; the local gate passed on GB10 (spark-102) at 7c8d340a; hosted CI in progress at the time of writing
**Languages**: Rust, Markdown
**Risk Level**: Medium (the zero-config assignment protocol goes from version 1 to 2, and the remote stage reply format changes while the handshake version stays 4, so builds before and after this PR cannot form one pipeline)

## Executive Summary

PR #2708 (closes #2694) lands seven residuals that #2671, #2680 and #2684 left in the remote pipeline. They are grouped in one PR because they share the `src/distributed/` frame and pipeline code, the Gemma4 stage model, and one verification pass. None is a security fix; they cover observability, per-token cost, bring-up atomicity, and test coverage.

The largest change is on the per-token path. The final stage now sends the logits straight to the coordinator as the `RunResult` of the `RunEntry` exchange, using a `reply_nonce` carried on the forward activation, instead of relaying them back through every stage. A decoded token is 3 frames instead of 4 and the roughly 405 KB logits reply crosses the wire once. Together with sealing frames in place (one fewer payload copy per send), decode throughput on a 2-stage loopback qwen3-0.6b-4bit pipeline went from a median of medians of 136.73 tok/s on main (433560c4) to 156.94 tok/s, about 15%, with identical greedy tokens in every repeat.

The other items: a protected stream interprets the frame kind byte only after the AEAD tag verifies; a `--pp-peer` writes a TOML header that describes its own role; zero-config bring-up gains an `Activate`/`Abort` step so a commit failure on one peer starts no stage on another; a Gemma4 stage without a sliding layer builds no sliding mask; and a new stage test pins parity under a front-trimmed KV cache.

## 1. Problem Statement

Each item was re-checked against main @ 54d63b0a when the issue was written, and against main after #2705 when the PR was reconciled.

### 1.1 A tampered kind byte escaped the rejected-frame log

`ProtectedStream::read_frame` parsed the kind byte with `MessageKind::try_from(header[0])?` before reading and opening the body. The header is AEAD associated data, so a kind byte flipped to another valid value failed `open` and surfaced as `FrameRejected`, which callers log through the rate-limited diagnostic budget. A kind byte flipped to an invalid value (0, or 5 to 255) returned a plain `unknown message kind` error before any authentication, and the connection closed with no log line. The same tampering was visible or invisible depending on which value the attacker chose.

### 1.2 Two avoidable per-token costs in the frame path

`TcpTransport::send` built the payload with `serialize_message`, and `write_frame` then allocated a second buffer and copied header plus payload into it before sealing. For the per-token logits reply that is a 405 KB copy per send.

Separately, with two or more stages the final stage returned logits as a reverse `ActivationMessage` to its upstream, each stage relayed it further upstream, and the entry stage turned it into a `RunResult` for the coordinator using a `PendingEntryReply` map keyed by request and micro-batch. Each decoded token therefore carried the logits twice (about 405 KB of base64 JSON each for qwen3) in 4 frames: `RunEntry`, forward activation, reverse activation, `RunResult`. Every relaying stage paid a JSON decode, an AEAD open, a JSON encode and an AEAD seal of that payload.

### 1.3 The peer TOML header described the coordinator

A `--pp-peer` wrote the cluster it received through `render_deterministic_toml`, whose header says the file was generated by `mlxcel-server --pp-auto` and that rerunning the bring-up command reproduces it byte for byte. That is the coordinator's command and the coordinator's guarantee. Rerunning the peer reproduces nothing; the next committed assignment overwrites the file.

### 1.4 A commit-phase failure left committed peers running

`push_stage_assignments` sends `Commit` to all accepted peers concurrently. A peer that answered `Committed` immediately delivered its `CommittedAssignment`, wrote its TOML and started a stage. If another peer then failed the commit, the coordinator bailed with `AssignmentPushFailed` and exited, and the committed peers kept running a stage for a cluster that would never form, with nothing telling them to stop. The two-phase design guaranteed atomicity only across the offer phase.

### 1.5 An unused Gemma4 sliding mask

`text_prefill_masks` built a sliding-window prefill mask whenever `window < l <= 4096`, even when `sliding_attn` was `None`. `Gemma4StageModel::execute_hidden` passes `None` for a stage whose layers are all `full_attention`, so such a stage allocated an `[l, l]` mask that no layer read.

### 1.6 No stage parity coverage under a trimmed cache

`gemma4_stage_tests.rs` covered prefill, over-window prefill and continuation prefill, but no case where `KVCache::trim_front` had advanced `live_start` (#430, `--max-kv-size`). Under trim, the global layers see `live_len` keys, not `offset` keys, and must stay on the maskless causal path in both the dense and the stage model. The only regression test was dense-only.

## 3. Technical Decisions

### 3.1 Authenticate first, then interpret the kind

The fix defers `MessageKind::try_from` until after `open` on protected streams, which reuses the existing rejected-frame logging at both call sites with no call-site change. The rejected alternative mapped any invalid kind to `FrameRejected` from the header alone. That would log an unauthenticated header as an authentication failure, which the oversize check deliberately does not do (`protected_stream_refuses_oversize_header_before_body`), and it would hide a real version-skew case behind a tamper message. Keeping the authenticated unknown kind as its own error keeps the two causes distinguishable: only a secret holder can produce it.

The oversize check still runs on the header before the body is read, so a tampered length cannot force a large read or any cryptography.

### 3.2 One sealing path, sized once

`MAX_TAG_LEN` is 32, the largest `FrameSuite::tag_len`, and a `const` block asserts every suite in `FrameSuite::ALL` fits under it. Without the assertion a future suite with a longer tag would make `seal` reallocate, silently bringing the copy back. The borrowed-payload `write_frame` is now a thin front (copy into a prepared frame, then `write_prepared_frame`), so stream chunks, RPC and stage assignment frames go through the same `finish_frame` as messages. Its copy count is unchanged; only `send`, which builds its own payload, saves a copy.

`write_prepared_frame` is `pub(crate)` and `finish_frame` returns an error for a buffer shorter than the header instead of panicking on the slice (fixed in 7c8d340a after review).

Out of scope: the JSON-to-`Bytes` copy inside `TransportMessage::Control`, which needs a change to the `Transport` trait.

### 3.3 Logits go once, from the final stage to the coordinator

| Option | Pros | Cons |
|---|---|---|
| Keep the reverse relay | No protocol change | Logits cross the wire `num_stages` times; per-request reply state on the entry stage |
| Raw `TensorData` frame for logits | No base64 | Carries no nonce or request id; needs a second correlation path in `exchange` for about 100 KB per token |
| **Chosen: nonce on the forward activation, `RunResult` from the final stage** | One logits transfer; no per-request reply state on any stage; reuses the existing exchange correlation | Coordinator must accept a reply from a stage other than the one it addressed |

The coordinator side keeps the #2637 correlation rules and adds one: `ExchangeMatch` carries `result_peer`, which is `stage_peers.last()` for `RunEntry` and the addressed peer otherwise. A `RunResult` must come from `result_peer`; `Ack`, `State` and `Error` still come from the addressed peer. A `RunResult` from a middle or entry stage, a stale nonce, or a mismatched request or micro-batch is dropped and the wait continues against the absolute deadline. A single-stage pipeline is unchanged because its first stage is its last.

On the stage side, a reverse activation is now dropped with a warning, and a forward activation without `reply_nonce` reaching the final stage drops its logits with a warning: without the nonce the coordinator could not match the frame, so sending it would only produce a frame the coordinator discards. The in-process `stage_worker` keeps its own reverse path.

### 3.4 Reply to the coordinator's authenticated identity, not its configured address

The first implementation (8deca793) sent `RunResult` to `self.coordinator.configured()`. A coordinator listed with an unspecified IP (`0.0.0.0:19000`, which `--pp-auto` writes when the control address follows `--host 0.0.0.0`, and which a peer reuses when it runs from a copy of that TOML) names no host to dial, so a final stage on another machine dialed its own loopback and every decode timed out. 00bb4723 records the authenticated source of the coordinator's most recent command (`coordinator_identity`) and sends `RunResult` there, as every other reply already did; the configured address is a fallback before any command. Every `RunEntry` is preceded by a `PrepareSequence` broadcast to all stages, so the final stage has seen a command before it produces logits. The test `final_stage_sends_run_result_to_authenticated_coordinator_identity` configures the coordinator as `[::]:port` and failed with `Elapsed(())` before the fix.

### 3.5 Activate after every commit, abort otherwise

The peer now holds its commit on the same connection after writing `Committed`, bounded by its `commit_timeout`, and only `Activate` delivers the assignment. `Abort`, any other frame, a closed connection or the timeout reset `shared.committed` and return the peer to its listening loop, the same as the pre-commit discard paths. The coordinator keeps each stream from the commit phase: when every peer committed it sends `Activate` to all; when any commit failed it sends `Abort { detail }` (the failure summary, cut to 1 KiB at a character boundary) to every committed peer, best effort within the push deadline, and then fails as before.

The rejected alternative activated on `Committed` and watched for `Abort` in the background. By then the stage would already be loading weights and binding its transport, so an abort would have to unwind a partly started stage.

The residual window is documented in the module docs and `docs/distributed.md`: a coordinator that dies between two `Activate` writes leaves the peers it already activated running, the same as a crash right after a successful bring-up. A failed `Activate` write is reported as an `AssignmentPushFailed` entry whose reason starts with `committed but not activated`, and the error message then says that the other peers run a stage and should be stopped (00bb4723), rather than claiming no stage started.

The peer logs a received `Abort` detail bounded to 1 KiB and escaped with `escape_debug`, so an authenticated coordinator cannot push a 64 KiB detail or extra log lines into the peer's log (7c8d340a).

### 3.6 Version bumps

`ASSIGNMENT_PROTOCOL_VERSION` goes from 1 to 2, so a mixed coordinator and peer fail fast with `assignment protocol mismatch` instead of a peer waiting for an `Activate` an old coordinator never sends. The handshake `PROTOCOL_VERSION` stays 4: #2705 bumped it to 4 in the same unreleased cycle, and no tagged release (the latest is v0.8.0-beta.1) carries version 3 or 4. The reply format change (no `pending_entry_replies`, new `reply_nonce`) rides on that unreleased version.

## 5. Remaining Gaps and Risks

- **Mixed builds fail without a version signal.** The handshake version is unchanged, so a build of main between #2705 and this PR completes the handshake with a build of this PR. An old coordinator cannot decode the new `Ack`/`State` (the `pending_entry_replies` field it requires is gone), and a new coordinator drops the `RunResult` an old entry stage relays. Both end in exchange timeouts. No tagged release is affected and mixed versions were already unsupported, but the failure looks like a slow or dead stage, not a version mismatch.
- **Non-entry stage errors still time out.** An execution error on a middle or final stage is still sent upstream with nonce 0 and ends in a coordinator timeout (unchanged, out of scope in #2694). With `reply_nonce` and `coordinator_identity` now available on every stage, the final stage could send an `Error` for the exchange directly; the coordinator would also need to accept `Error` from `result_peer` for `RunEntry`.
- **`coordinator_identity` is last-command-wins (LOW, open).** With a coordinator configured on an unspecified IP, `PeerMatcher` accepts any authenticated identity on that port, so a secret holder listening on that port on another host could redirect later logits to itself by sending any command. It needs the secret and a hand-written config (zero-config peers receive a concrete address from `localize_cluster`). Binding the reply identity per request at `PrepareSequence` would close it.
- **The transport read loop still closes silently on an authenticated unknown kind (LOW, open).** `tcp_transport.rs` logs only `FrameRejected` before closing; the new distinct error reaches the stage assignment listener's log but not the transport's, so a version-skewed member is still invisible there.
- **Activation window.** A coordinator crash between two `Activate` writes leaves earlier peers running, as documented.
- **Two-node link numbers** are still missing for #2656 and this change.

## 6. Learning Points

### 6.1 Treat AEAD associated data as untrusted until `open` succeeds

The header is authenticated but not encrypted, which makes it tempting to parse it eagerly. Any decision taken on it before `open` (here, rejecting an unknown kind) creates an unauthenticated error path that behaves differently from the authenticated one, and the difference is observable. Only checks that bound resource use (the length cap) belong before authentication, and they should be classified as such rather than as tamper detection.

### 6.2 Reserve once, seal in place

```rust
let mut frame = Vec::with_capacity(FRAME_HEADER_LEN + payload_len + MAX_TAG_LEN);
frame.resize(FRAME_HEADER_LEN, 0); // header written later by finish_frame
frame.extend_from_slice(payload);   // or encode the message directly here
finish_frame(sealer, kind, &mut frame)?; // header + in-place encrypt + tag append
```

The `finish_frame_seals_without_reallocating` test records `frame.as_ptr()` before sealing and asserts it is unchanged for every suite, which turns "no copy" into a checked property instead of a comment. The `const` assertion over `FrameSuite::ALL` keeps it true when suites are added.

### 6.3 Correlate by nonce, route by identity

Moving the reply off the stage that received the command required no new trust: the coordinator already matched replies by a fresh per-exchange nonce, request id and micro-batch, so changing which authenticated peer may send a `RunResult` is a one-field change to the matcher. The configured address, by contrast, is a dial target that may not name a host at all (`0.0.0.0`), so replies follow the authenticated source of the coordinator's traffic.

### 6.4 A commit is not an activation

Two-phase commit across processes is atomic only if nothing irreversible happens at "prepared". Starting the stage on `Committed` made the commit phase non-atomic. Adding a third message moves the irreversible step after the point where the coordinator knows the outcome, and leaves a much smaller window (a crash between `Activate` writes) that is documented rather than hidden.
