# PR #2829: Add Xiaomi MiMo v2 Flash support

**Date**: 2026-11-02
**Status**: Completed (PR open; closes #842)

## Executive Summary

PR #2829 adds native `mimo_v2_flash` support and validates it on the real 173.8 GB `mlx-community/MiMo-V2-Flash-4bit` checkpoint, which was blocked on hardware when the issue was filed and is now possible on the 512 GB M3 Ultra host. The model loads in 16.9 s at 161.83 GB resident and generates coherent text at 24 to 31 tok/s. The port covers the family's three unusual shapes: hybrid sliding/full attention, Q/K `head_dim` 192 against V/O `v_head_dim` 128, and a `noaux_tc` router with a learned correction bias. 10 files, +2177/-2, of which 641 lines are tests.

## 1. Problem Statement

`XiaomiMiMo/MiMo-V2-Flash` declares `model_type: mimo_v2_flash`, a family distinct from the existing dense MiMo v1 in `src/models/mimo.rs`. It is roughly 309B parameters: 48 layers, hidden 4096, 256 routed experts with top-8, `moe_intermediate_size` 2048. The issue was labelled `modelsize:xlarge` and `status:blocked` because the only public checkpoint did not fit a 128 GB dev box. The 512 GB host and the published 4-bit conversion lift that blocker.

## 2. Architecture as Implemented

| Feature | Implementation |
|---|---|
| Layer schedule | `hybrid_layer_pattern` is read as a list, not a modulus. The checkpoint makes layers 0, 5, 11, 17, 23, 29, 35, 41 and 47 full attention (9 layers), and the other 39 sliding with window 128 |
| Attention shapes | Q/K use `head_dim` 192; V/O use `v_head_dim` 128. Sliding layers use 64 heads and 8 KV heads, full layers 64 heads and 4 KV heads |
| RoPE | Per-layer base: `swa_rope_theta` 10000 on sliding layers, `rope_theta` 5000000 on full layers. `partial_rotary_factor` 0.334 is parsed as a float and floored, giving 64 rotated dims |
| Value scale | Sliding layers multiply V by `attention_value_scale` 0.707 before the cache update |
| Attention sinks | Sliding layers carry a learned per-head `attention_sink_bias`; the checkpoint has 39 such keys and they match the sliding set exactly |
| Router | `noaux_tc`: sigmoid scores in f32, `e_score_correction_bias` added for selection only, weights taken from the unbiased sigmoid scores, normalized, scaled by 1.0 |
| Experts | Layer 0 is dense; layers 1 through 47 are `SwitchGLU` over 256 experts, top-8. `n_shared_experts` is null, so the optional shared MLP path exists but is not exercised |
| Caches | Model-owned: `RotatingKVCache` on sliding layers, `KVCache` on full layers |

## 3. Technical Decisions

### 3.1 The list is the authority, not the prose

The refreshed issue prose described full attention at 0, 5, 10, ..., 45. The published checkpoint actually places it at 0, 5, 11, 17, ..., 47, because the repeating block after layer 0 is five sliding layers and one full layer (period 6, not 5). The loader reads `hybrid_layer_pattern` directly, so the code follows the checkpoint. The 39 sink keys matching the sliding set is independent confirmation.

### 3.2 Sanitize is a pass-through, confirmed by the index

The 4-bit conversion already ships upstream's post-sanitize layout: stacked `mlp.switch_mlp.*` planes with affine scales and biases, an unquantized BF16 `mlp.gate.weight`, an F32 `e_score_correction_bias`, 39 sink keys, and no per-expert, fp8 or MTP keys. The upstream fp8 dequant and expert stacking apply to the bf16 original, not this conversion. The index was inspected before the loader was written, as the issue required.

### 3.3 Missing schedule entries fall back to full attention

`is_sliding_layer` returns false for a missing entry. A global layer attends to every key a sliding layer would and more, so a short list is slower rather than wrong. The config validation rejects malformed entries and a too-short list, so the fallback is a safety net rather than a configuration path.

### 3.4 Batching is intentionally off

The model owns heterogeneous caches (rotating and full), so decode stays one sequence at a time. `supports_batching`, `supports_padded_prefill` and `supports_chunked_prefill` return false, which keeps the scheduler from applying dense-cache assumptions to a model-owned pool. This is a capability limitation, not a temporary shortcut.

### 3.5 Router arithmetic matches the vendor

Weights are multiplied in float32 and cast once at the end, the same contract AFMoE documents. The shared `moe_weighted_sum` helper would cast the expert weights down first, so the MoE block uses the explicit float32 path.

## 5. Unverified

No CUDA or ROCm run and no multi-device tensor-parallel run were performed. This host is Apple Silicon. The TP arch string is wired but not exercised. The optional shared-expert path is unexercised because the checkpoint declares none. Server batching behavior for this family is disabled by design, not tested under concurrent load.

## 6. Learning Points

The checkpoint, not the issue prose, is the authority for a layer schedule. A modulus assumption (period 5) and a list whose period is 6 produce a different set of full-attention layers, and the 39 sink keys were the cheapest way to confirm which one the weights encode. Inspecting the weight index before writing the loader also settled the sanitize question without a speculative remap.

## 7. Risks

Medium. The new family is 1,504 lines in one file, close to the project's 1,200-line guideline, though the decoder, router and cache logic are cohesive. It is the first model to combine per-head attention sinks, a split `v_head_dim`, and heterogeneous caches, so the server path for it is less exercised than the dense families. The real-checkpoint run is a smoke test, not a numerical parity test against a reference.
